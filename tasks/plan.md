Debian/Ubuntu контрольный хост. Три контура: SSH/inventory, OpenSCAP + выбранная

## Этап А: совместимый кандидат

1. Сохранить main равной GitHub; интегрировать изменения PR #74, #78 и #79
   в локальную RC-ветку без перезаписи исторических доказательств.
2. Закрыть P0-02: сохранить evidenceProjection через валидатор, SQLite и
   штатный запуск. Компактное представление сохраняет все ID и точные
   результаты определений; неизвестный режим отклоняется.
3. Закрыть P0-03: единая объектная platformApplicability в новых отчётах,
   совместимость с прежней строковой bounded-проекцией. Подтверждение требует
   false исходного определения, той же базы, актива и поколения; неизвестность
   и смена области не считаются устранением.
4. Проверить integrity и source drift из #78/#79 вместе с настоящим адаптером.
   Регрессии, типизация, production-сборка и HTTP-проверки на изолированных данных.
5. Добавить отмену устаревших PR CI без отмены main/manual доказательств.
   Сохранить обязательные проверки релизного SHA и явные ручные native workflows.
6. Ввести один текущий паспорт релиза; исторические результаты оставить
   неизменными. Локальные тесты не называть exact-head GitHub CI.

Приёмка А: совместимый фиксированный SHA, нет открытых P0 контрактных дефектов,
локальные проверки и требуемый GitHub CI именно этого SHA. Последний подтверждённый
CI-срез — `a46f045432e7c1127034b551a0caadc58747eef1`, 20/20 workflow,
28/28 checks. Он включает обновление поставки, CI gate и исправление лимита
загрузки OVAL после фактического отказа на медленном источнике.
Зафиксированный RC и работающий образ относятся к этому SHA; уточнения
документации не переносят CI-приёмку на другой кодовый коммит.

## Этап Б: операторский E2E

После А: мастер подключения с независимым SSH fingerprint и asset binding;
инвентарь; 18 правил до/после контролируемого нарушения/после восстановления;
полная выбранная XML OVAL; исходные JSON/ARF; UI/API/архив/PDF; отдельный
firewall-переход с внешним сетевым эффектом и откатом. Только реальный стенд,
никакой подмены настоящих результатов фикстурами. Изменение целевого сервера
требует конкретного согласованного действия и доступной консоли/snapshot.

Приёмка Б: комплект оригиналов, SHA, timestamps, идентичность актива и
результат независимой проверки восстановления. Исходные четыре failed правила
не объявляются устранёнными только по опыту pass → fail → pass.

Актуальный read-only срез операторской Astra уже получен через сайт: facts,
18 правил 14 pass / 4 fail, исходные JSON/ARF/XML, один verified asset binding.
Реальный тайм-аут загрузки OVAL сохранён как incomplete; проверены его UI и
PDF с 19 исходниками. После полного скачивания на 2 ГиБ наблюдались SIGKILL
сканера и отдельно исчерпание RAM/swap; kernel OOM не подтверждён. Создан
страховочный снимок памяти/диска, RAM увеличена до 4 ГиБ; SSH identity и
повторные 18 правил сохранились. Повторный OVAL после TLS-ошибки источника
завершился: 19 527 определений / 4 134 true / 15 393 false / 4 068 CVE;
все ID/состояния и source CVE сверены с оригинальными XML. После холодного
снимка выполнены три свежих аудита: 14/4 → 13/5 → 14/4 при изменении только
owner-execute `/etc/passwd`; bytes/owner/inode и исходные состояния восстановлены.
PDF 113 страниц содержит все CVE. На этом срезе новый мастер подключения и
сетевой firewall rollback оставались открытыми. Позднее оба проверены
практически 10 ноября; детали и ограничение packet filtering — в Release Status.

## Этап В: эксплуатация и восстановление

Операторская приёмка #43: preflight, сеть/HTTPS и ограничение входа, сессии,
HMAC с независимым anchor, backup и восстановление на отдельной Ubuntu,
новый вход/SSH, зависимости и воспроизводимость поставки. Лабораторные
проверки не заменяют подпись оператора. EOL Ansible для Astra 1.7,
доверенность CVE-источников и нагрузка 1/3/5 хостов остаются явными рисками.

Независимая гостевая Ubuntu на том же компьютере уже прошла перенос настоящего
runtime/image, byte/HMAC-проверку, отзыв старого cookie, новый вход/выход,
PDF и полный API-цикл архивов. Это выполненная часть этапа В; доступ к Astra,
контролируемый откат и подпись оператора остаются условиями полной приёмки.

В `e71232e` проверены зависимости готового образа и исправлены доступные
APT/npm/Trivy advisories; рабочая панель обновлена с сохранением данных и сессии.
Фактический loopback проверен отдельно. Main защищена четырьмя существующими
CI-статусами; общий gate включается в её политику после одобренного merge workflow.
Остаточные CVE, EOL и воспроизводимость баз/пакетов требуют дальнейшего решения.

Установленный `eacd302` закрепляет Node/Python bases и все Python-пакеты
трёх tool venv по версиям и SHA-256, обновляет старые pip/setuptools. Отдельная
сборка и проверки пройдены; whole-image сравнение одной базой даёт 696 → 674
строки без новых находок. Тот же состав подтверждён в финальном образе из
зафиксированного коммита; созданы SBOM и Docker archive с SHA-256. Новый SHA
прошёл 20/20 workflow и 28/28 checks. При установке сохранены snapshot,
13 таблиц данных, 46 исходных файлов, 201 событие и 15 активных отчётов;
сессии и вход/выход проверены. Последующий локальный `a46f045` добавляет к
этому immutable образу только два Python-файла; зависимости и 27 прежних слоёв
сохранены. Обновление панели проверено на 208 событиях и 19 отчётах.
Полный DR последнего образа ещё не повторялся.

## Продолжение 10 ноября: подготовка без Astra

Текущая Astra выключена по сообщению оператора. Работа ведётся локально:
1. JSON HCP свернуть в технические подробности; PDF и оригиналы оставить на виду.
2. Проверить сценарии на отдельной SSH-цели Docker: шаблон → сохранение →
   синтаксис → запуск → результат; отдельно рабочий запрет произвольного YAML.
3. Выполнить контроллерные проверки firewall/ошибок/отката. Реальную фильтрацию
   и откат Astra не объявлять проверенными без ВМ.
4. Проверить восстановление текущих данных в отдельном изолированном экземпляре:
   байты, SQLite/HMAC, отзыв скопированных сессий, вход, отчёты/PDF/архив.
5. Выполнить локальные проверки CI, зафиксировать рабочую версию в Git и
   обновить локальный сайт. Публикация на GitHub не входит в этот локальный этап.

Результаты сохраняются приватно; в репозитории — только очищенная сводка.
Существующие отчёты, inventory, секреты и системный firewall не меняются
тестовыми сценариями. Живой SSH/сетевой контроль Astra остаётся открытым.
