# HCP: независимая локальная проверка HMAC-цепочки после восстановления

Это **read-only gate** для **остановленной изолированной восстановленной**
копии SQLite HCP, а не испытание продуктивной установки, SSH или прав доступа
к целевым серверам.

## Зачем

`PRAGMA integrity_check` отвечает только на вопрос о структурной
исправности SQLite. Он **не** обнаруживает корректную с точки зрения SQLite
правку содержимого одной строки аудита или изменение связи между записями.
Штатный HCP подписывает события через HMAC-SHA256 с ключом
`HCP_AUDIT_HMAC_KEY`, хранящимся в защищённой конфигурации. В ходе
восстановления нужно повторить контроль подписи **теми же неизменёнными
секретами**, что применялись к исходной базе.

## Что проверить до запуска

1. Отдельно провести `docs/backup-restore.md`: исходная SHA-связка
   резервного архива и восстановление в другой изолированный control node.
2. **Остановить восстановленный HCP и все его фоновые задания**. Существующая
   `hcp.sqlite-wal/-shm` означает, что нельзя игнорировать WAL через
   immutable режим: скрипт прекращает проверку до отдельной изолированной
   процедуры восстановления WAL.
3. Проверить исходную побайтовую копию критических данных с
   `docs/post-restore-acceptance.md`. При чтении должны сохраниться старые
   `.env`, `HCP_AUDIT_HMAC_KEY`, архивы и HCP runtime. Не присылайте
   их в чат, GitHub и CI.
4. Выполнить **только на изолированной Ubuntu**, из checkout HCP,
   с локальным приватным `.env`:

   ```bash
   python3 deployment/tests/verify_restored_audit_chain.py \
     --restored-runtime /private/mounted-restored-hcp \
     --env /private/restored-settings/.env \
     --acknowledge-stopped \
     --output /separate/private/new-hmac-audit-evidence.json
   ```

   Скрипт читает `.env` с ограничениями `0600`, не печатает секрет
   подписи и не создаёт SQL-таблиц. Результат `hmac-chain-valid-with-stated-legacy-limits`
   означает, что все записи от начала цепочки согласованы по HMAC и
   `previous_hash`; он не удостоверяет независимое происхождение самого
   секретного ключа.

## Версии подписи

Новый HCP использует `hash_version=2`: упорядочивает вложенные
объекты по ключам, сериализует JSON без пробелов и подписывает полезную
нагрузку. Сохранённые старые записи `hash_version=1` использовали
`JSON.stringify(value, Object.keys(value).sort())`; это **ослабленная
подпись**, поскольку вложенные свойства, отсутствующие в replacer-списке,
могли не попасть в HMAC.

Поэтому результат сообщает `legacyEntries` и
`payloadProtectedForAllEntries=false`, если есть хотя бы одна v1-запись.
Если требование вашего контура — полная защита всех полей, добавьте
`--require-payload-protection`: при v1 он возвращает явную ошибку
`legacy_entries_payload_not_fully_protected` вместо ложного PASS.
**Нельзя переподписывать исторические v1-записи**, чтобы замаскировать
слабую защиту.

## Чего проверка не делает

Она не входит в восстановленную панель, не проверяет старые cookie и новые
сессии, не запускает SSH, сканирование Astra или firewall. Возможность
изменения одновременно и `.env`, и всей цепочки злоумышленником,
владеющим ключом, данной локальной проверкой не исключается — для
независимого доказательства нужен сохранённый отдельно trusted pin,
контроль доступа к архивам и протокол оператора.

Для настоящей DR приёмки (#43) после контроля HMAC дополнительно:
`docs/restored-admin-session-revocation.md` — отзыв прошлых сеансов
на *изолированной* копии (отдельное разрешённое изменение БД), далее
HTTP 401/403 для старой cookie, новый login, сверка host keys и реальный
новый аудит/откат disposable цели.

Проверки на фикстурах:
`deployment/tests/test_verify_restored_audit_chain.py`.
Они не создают и не подтверждают эксперимент на Astra 1.7.6.15.
