# Hardening Control Platform — технический статус и план завершения

**Дата среза:** 4 ноября 2026 г.  
**Назначение:** техническое состояние дипломной платформы, проверяемые результаты,
неустранённые ошибки и критерии готовности. Статус PR/CI актуален только на дату
среза; для следующих изменений нужен новый exact-head CI, а не ссылка на
исторический зелёный запуск.

## 1. Что представляет собой платформа

HCP — локальное веб-приложение для **безагентного SSH/Ansible-аудита**,
инвентаризации, CVE-анализа по применимым источникам, проверки конфигурации,
управления планом харденинга и **контролируемых** изменений firewall.
Один выделенный Linux control node хранит inventory, индивидуальные SSH-ключи,
проверенные host fingerprints, отчёты, историю и журнал операций в постоянном
Docker volume. Платформа не является SIEM, IDS, сертифицированным сканером
всех ОС или автоматическим средством устранения любых CVE.

**Не путать пять различных доказательств:**

1. Функция написана и имеет тесты.
2. Функция прошла полный GitHub Actions CI на точном commit SHA.
3. Она прошла нативный тест на конкретной ОС/версии и с конкретной областью.
4. Её проверил оператор на **своей** разрешённой инфраструктуре.
5. Есть независимо доверенное подтверждение происхождения производителя
   и применимости CVE/пакета.

Ни один последующий уровень не следует автоматически из предыдущего.

## 3. Настоящая Astra Linux 1.7.6.15 — что уже проверено и где остановились

**Статус: не принята.** Подробности: [PR #62](https://github.com/Danil-super/hardening-control-platform/pull/62),
[issue #40](https://github.com/Danil-super/hardening-control-platform/issues/40),
[issue #38](https://github.com/Danil-super/hardening-control-platform/issues/38).

Проверено на **настоящем** официальном `alse-1.7.6.uu2-base-cloudinit-mg15.3.1-amd64.qcow2`:
полные 407673856 байт и SHA-256
`654aae66598bb4e5e38efc4fc18e2c9cb53170713a31728ff502f04dabf1838e`,
QEMU запустился, SSH доступен, из гостя действительно наблюдается `ID=astra`,
`/etc/astra_version=1.7.6`.

**Подтверждённое исправление:** исходный gate ошибочно ожидал
`1.7.6.15` в `/etc/astra_version`. Документация Astra/ALD Pro различает
`/etc/astra_version` (point release) и `/etc/astra/build_version`
(full build). [PR #64](https://github.com/Danil-super/hardening-control-platform/pull/64)
уже принят с четырьмя зелёными CI. На **настоящей гостевой Astra 1.7.6.UU2**
в [native run 41889382908](https://github.com/Danil-super/hardening-control-platform/actions/runs/41889382908)
после исправления независимо прочитаны **оба фактических значения**:
`/etc/astra_version=1.7.6` и `/etc/astra/build_version=1.7.6.15`.
Точный build подтверждён **внутри** гостя, а не выведен из имени образа.
Однако следующий gate `cloud-init` остался неуспешным; сканирование не
производилось.

**Второй независимый блокер:** у гостя первоначальный `cloud-init`
возвращал `status: error` на `scripts_per_once` (один сценарий).
Настоящее содержимое этого сценария и его причины **не подтверждены**;
проверяется только приватная метаинформация (тип, исполняемость,
интерпретатор, хеш), без публикации скрипта/машинных идентификаторов.
Отключать модуль ради зелёного CI нельзя. До штатного завершения первичной
инициализации нативный experiment PASS заблокирован.

**Не получены на Astra 1.7**: успешный запуск фактических 18 правил HCP,
оригинальные ARF после всех трёх фаз, полная применимая 1.7 OVAL XML evaluation,
проверка восстановления прав и нового SSH после изменения, защищённый PDF с
подтверждёнными source fields, отдельная приёмка `adv/max`.

### Критерий завершения native 1.7 (PR #62, #40 и #38)

- Фиксированный исходный официальный образ, независимый замер `ID=astra`,
  point release `1.7.6`, **full build `1.7.6.15`**, kernel и архитектура,
  machine-id и pinned SSH key; cloud-init **без ошибки**, уровень безопасности
  указан и фактически наблюдён.
- Настоящие штатные Ansible/OpenSCAP 18-rule проверки в трёх точках, один
  зафиксированный контролируемый переход и восстановление оригинальной
  конфигурации в `finally`, сохранённые original ARF/JSON/datastream и SHA.
- Полный 1.7 OVAL-результат того же актива и конкретной базы, полная
  evaluation без `partial`, достоверные причины unknown и никакого
  неподтверждённого CVE recall.
- Новый SSH после восстановления, подтверждённый host fingerprint и
  идентичность актива; операторский протокол с ограничениями и оригиналами.
- `base`, `adv`, `max` не считать взаимозаменяемыми: результат одного
  режима **не подтверждает** остальные.

## 5. Рекомендуемая последовательность больших этапов

**Этап А — достоверность Astra 1.7:** ввести двухфайловую проверку версии,
исследовать `scripts_per_once` без отключения защиты, добиться настоящих
прогонов OpenSCAP/OVAL для base; зафиксировать результаты и источники.
Затем по возможности повторить adv и max независимо.

**Этап Б — приёмка управляющего узла:** отдельная Ubuntu, реальные
настройки/секреты, мастер подключения и реальные отчёты; полный recovery
по `docs/operator-restore-readiness.md` с новым подключением SSH,
отзывом старых cookie, HMAC-проверкой и контрольным firewall rollback.
**Без передачи секретов в GitHub или чат.**

**Этап В — подтверждение источников CVE:** сверка независимых vendor
advisories, исправленных/backported версий пакетов и area/source SHA;
поле неизвестной применимости не делать ложным «безопасно».

**Этап Г — интерфейс и дипломная защита:** операторская визуальная
проверка источников/частичных результатов, пользовательского пути
`подключение → подготовка БД → аудит → анализ → план → изменение → откат`,
финальный PDF с реальными измерениями, технические ограничения и
протокол воспроизводимости.

## 6. Что нельзя заявлять как готовое

- «Поддерживаются все Astra Linux и все режимы безопасности».
- «Обнаруживаются все CVE» или «нулевой отчёт равен нулю уязвимостей».
- «Хеш файла — цифровая подпись производителя».
- «Совпадение 18 статусов — полный откат ОС, firewall и SSH».
- «Production готов», если пройдена только одноразовая CI-лаборатория.
- «Astra 1.7.6.15 нативно испытана», если исходный guest не подтвердил
  full build, `cloud-init` не завершился и отчётов OpenSCAP/OVAL нет.
