# Повтор загрузки источников в native CI

Прогон Astra 1.8.1 кода `97b4bef` завершился до аудита из-за
`TimeoutError` при чтении официального OVAL. Повтор только этого job прошёл.
Загрузчик тестового стенда `deployment/tests/verify_astra_vm.py` прежде
прерывал весь эксперимент после первого такого отказа. В отличие от него,
рабочий `hcp-oval-audit.py` уже имел три попытки; он этим изменением не затронут.

Общий CI-клиент теперь делает не более трёх попыток при timeout/reset
соединения, включая `URLError` с такой причиной. Каждая начинает с нуля:
частичный файл удаляется, счётчик размера и SHA-256 создаются заново.
Общее значение `max_seconds` не сбрасывается; следующему соединению передаётся
не более оставшегося времени. Время проверяется также после EOF, прежде чем
принимать файл. Ошибка сертификата, HTTP-ошибка, неправильный размер или hash
завершают проверку без повторов. Кэш по-прежнему проверяется по точным байтам.

Сигнатура сохранена. Проверены все вызывающие: Astra 1.8, native QEMU 1.7
и полный vendor OVAL 1.7. Изменены только CI helper и его регрессии;
состав/код установленного образа `97b4bef` / `3a6d15a4` не меняются.

## Проверка

- RED воспроизвёл отсутствие повтора и потерю проверки после EOF.
- Все 18 точечных и 246 deployment-тестов прошли. Полный набор выполнялся
  в отдельном контейнере 512 МиБ без сети и без runtime/секретов панели.
  Минимум MemAvailable — 8 786 599 936 байт, OOM/guard не сработали.
- На настоящем собственном HTTPS-сервере первый ответ обрывается тайм-аутом
  после первого МиБ. Прежняя версия делает один запрос и не публикует файл;
  новая делает два и сохраняет все 1 048 616 байт с правильным SHA-256.
  Проверка сертификата и имени включена; временный ключ удалён.
- Отрицательный контроль инвертировал классификацию ошибки только в частной
  копии исходников. Регрессии обнаружили изменение; рабочий код не подменялся.

Материалы: `~/.local/state/hcp-evidence/ci-download-20261115-51apdnwe/`.
Официальная документация через Context7:
[urlopen](https://docs.python.org/3/library/urllib.request.html#urllib.request.urlopen),
[URLError.reason](https://docs.python.org/3/library/urllib.error.html#urllib.error.URLError),
[SSLContext](https://docs.python.org/3/library/ssl.html#ssl.create_default_context).

Это восстановление после конкретного временного отказа, не гарантия
доступности сервера производителя. Socket timeout ограничивает блокирующую
операцию, а не DNS/весь поток; существующий внешний deadline CI сохраняется.
Поздние байты не принимаются, но жёсткое прерывание любого системного вызова
ровно в `max_seconds` не заявляется. Свежая проверка GitHub нового SHA
фиксируется отдельно после публикации.

## Дополнение: закреплённый публичный кэш

CI `3b9288e` действительно сделал три попытки OVAL 1.8, но все три оборвались
на чтении. Другой, не изменённый этим патчем загрузчик OVA 1.7 дважды получил
тайм-аут. Журналы сохранены; эти прогоны не считаются успешной приёмкой.

Поэтому native-матрица 1.8 подключена к существующему проверяемому файловому
кэшу и для XML: обе версии ОС используют один каталог OVAL под `RUNNER_TEMP`,
имя файла содержит полный SHA-256. Ключ Actions зависит от закреплённого
каталога источников. Кэш сохраняется только после успешного job; нет
`restore-keys` или неподтверждённого fallback. На каждом hit полный размер и
hash проверяются до копирования, затем проверяется полученная приватная копия.
Это не свидетельство свежей сетевой загрузки или актуальности всех CVE.

OVA smoke использует уже имеющийся `exact_pinned_original_ova` и тот же
публичный key/path, что native HCP-проверки. Функция разрешает такой cache
только на одноразовом GitHub-hosted runner, проверяет каталог/права, полный
размер и SHA-256 оригинала и копии. Гостевые диски после загрузки, SSH-ключи,
seed и runtime в кэш не входят. Сам загрузчик OVA не переписывался.

RED/GREEN проверили подключение общего XML-кэша для обеих версий и отсутствие
кэша без CI-настройки. Теперь проходят 19 точечных и 247 deployment-тестов;
оба workflow прошли actionlint с его штатными shellcheck/pyflakes.
Сервер производителя всё ещё нужен при miss или смене pin; кэш не устраняет
внешние сетевые отказы и не ослабляет обязательную приёмку нового источника.
[Документация cache v4](https://github.com/actions/cache/blob/v4/README.md)
прочитана через Context7. Итог GitHub нового SHA проверяется отдельно.

## Итог GitHub на `0b573b8`

Точный SHA `0b573b8c13f152afd252544aef484b57793f1882` прошёл **20/20 workflow
и 28/28 checks**. Повторён только QEMU smoke после трёх timeout чтения
закреплённого образа; затем он прошёл на том же SHA. Отказы сохранены.
Установленный HCP по-прежнему `97b4bef` / `3a6d15a4`.

OVA smoke действительно переиспользовал проверенный оригинал: поле
`cachedPublicSourceByteVerified=true` подтверждено протоколом artifact
`14168215178`, ZIP SHA-256
`73430d3e90cc8633cce5bcd217e15c27d614c5328e437b50159038f22ae7cadc`.
Обе версии 1.8 прошли, общий публичный OVAL-кэш создан. Сам факт наличия
кэша не выдаётся за свежую загрузку с сервера производителя.

Native 1.7 подтвердил 18 правил 14/4 → 13/5 → 14/4 с восстановлением и новым
SSH, все 20 062 определения точного XML (346 true / 19 716 false). Проверен
artifact `14167638965`, ZIP SHA-256
`8ae711ecb6a443b2df0832b78d3cc4a4451c5fafa49e922497fa1db8576dbe7c`.
Это scoped-проверка, не полнота всех CVE или rollback всей ОС.

В более раннем `3b9288e` два native 1.7 прогона также остановились на
`native_vendor_apt_install_timeout` (install, exit 124). Публичный протокол
не устанавливает причину внутри APT; его не выдавали за успешный аудит.
APT-код этим изменением не менялся, его deadline сохранён. Нельзя утверждать,
что кэш устранил все сетевые/пакетные задержки или гарантирует будущий успех.

Полные списки workflow/checks, исходные отказы, принятые ZIP и сверка digest
сохранены в указанном закрытом каталоге. Подпись производителя независимо
не подтверждалась, gates и byte/hash/TLS-проверки не ослаблялись.
