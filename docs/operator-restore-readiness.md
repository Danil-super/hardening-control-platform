# Одна проверка перед запуском восстановленного HCP

## Назначение

Команда `deployment/tests/check_restore_readiness.py` запускает **все три
локальные read-only проверки** на новой изолированной Ubuntu: резервные
архивы, байты восстановленного runtime и SQLite, HMAC-цепочку журнала. Она
не запускает Docker, SSH, сканеры, не удаляет сессии и не изменяет файлы.

Используйте её только на **остановленном** восстановленном HCP **до**
первого входа и любых намеренных изменений `admin_sessions`. Само по себе
заявление `--acknowledge-isolated-stopped` не доказывает, что процессы
действительно остановлены и том не является оригинальной production БД.

## Обязательные исходные данные

Архив `HCP_BACKUP_DIR` подготовлен по `docs/backup-restore.md`.
Заранее в **другом, отдельно защищённом месте**, а не в том же backup,
сохранены два контрольных свидетельства:

1. Полный SHA-256 файла `SHA256SUMS` исходной остановленной копии.
   Он связывает архивы и другие обязательные файлы; сам `SHA256SUMS`
   без независимой фиксации может быть переписан вместе с архивами.
2. `lastEntryHash` и точное `entries` из исходной HMAC-цепочки
   после остановки записи событий, до сохранения архива. Для получения
   используйте отдельную read-only методику
   `docs/restored-hmac-audit-acceptance.md`. Проверка обычной
   целостности цепочки **без этих значений** не обнаруживает удаление
   последних корректно подписанных событий.

Также необходимы восстановленный каталог `/var/lib/hcp`, в
котором находится настоящая `hcp.sqlite` и сохранённые индивидуальные
SSH-ключи и отчёты, и **исходный приватный** `.env` с неизменённым
`HCP_AUDIT_HMAC_KEY`. Ни один из этих файлов не загружается в чат
или GitHub.

## Запуск одной командой на отдельной Ubuntu

```bash
python3 deployment/tests/check_restore_readiness.py \
  --backup-dir /private/source-backup/hcp-20261104T000000Z \
  --restored-runtime /private/new-isolated-controller/runtime \
  --env /private/restored-settings/.env \
  --expected-manifest-sha256 НЕЗАВИСИМО_СОХРАНЁННЫЙ_SHA256_МАНИФЕСТА \
  --expected-head-hmac НЕЗАВИСИМО_СОХРАНЁННЫЙ_64_ЗНАКА_HMAC \
  --expected-entry-count ТОЧНОЕ_ЧИСЛО_СОБЫТИЙ_ДО_BACKUP \
  --acknowledge-isolated-stopped \
  --output /separate/private/new-restore-preflight.json
```

Программа не запрашивает секреты интерактивно и не принимает их через
аргументы командной строки: ключ HMAC читается только из защищённого
локального `.env` (режим 0600). Выход создаётся исключительно новый с
правами 0600 вне исходной копии, `.env` и восстановленного runtime.

## Смысл результата

- `local-preflight-complete-live-recovery-unverified` и exit code **0**:
  все критичные файлы совпали, SQLite `PRAGMA integrity_check=ok`,
  HMAC-цепочка и заранее зафиксированные **число/конец** событий совпали,
  нет legacy v1 с недостаточной защитой payload. **Это не означает,
  что восстановленная панель запущена и её SSH работает.**
- `local-preflight-incomplete-authority`, exit code **2**:
  файлы и локальная HMAC-цепочка проверены, но отсутствует хотя бы один
  внешний pin либо обнаружен старый v1-формат. Результат сохраняет
  `reviewRequired` и не может выдаваться за полностью проверенный.
- `blocked`, exit code **1**:
  обнаружена повреждённая/неполная копия, несовпадение байтов, SQL,
  HMAC или внешнего anchor, небезопасная файловая система или
  не выполнено обязательное условие изоляции.

Тесты требуют наличие как минимум одного **реально сохранённого**
индивидуального ключа HCP и отчёта: пустой демонстрационный runtime
не должен получить эксплуатационный зелёный статус.

Результат содержит только агрегаты и SHA-256, никогда не содержит
значений `.env`, SSH-ключей, SQL payload, cookie и содержимого
отчётов. Длительность каждого локального этапа измеряется фактически.

## Дальнейшая практическая приёмка

После локального preflight, **только на отдельной изолированной
восстановленной машине**, можно намеренно отозвать старые
административные сессии по
`docs/restored-admin-session-revocation.md` (операция **изменяет**
восстановленную DB, требует отдельного подтверждения и SHA пина).
Затем запустить HCP и проверить реальными HTTP-запросами
401 для старой cookie, новый вход, 403 при чужом Origin, список
сохранённых хостов, старые отчёты, SSH fingerprint и новый разрешённый
аудит. Для firewall отдельно проверить безопасное изменение и откат
на disposable цели с независимым доступом через консоль.

GitHub CI `docs/disposable-controller-restore-acceptance.md` проверяет
часть этих действий на настоящих **лабораторных Debian SSH контейнерах**.
Он **не** заменяет эксплуатационную приёмку пользователя (#43), не
подтверждает поставщика OVA и не доказывает Astra SE 1.7.6.15 (#40).
Эксплуатационный protocol с фактическими версиями, timings, run IDs,
ограничениями и подписью оператора остаётся необходимым.
