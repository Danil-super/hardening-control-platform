# Нативные испытания Debian и Ubuntu

Этот стенд проверяет конкретные выпуски **Debian 12/bookworm** и
**Ubuntu 24.04/noble**, архитектуру **x86_64**, systemd и UFW. Его задача —
сопоставить результаты HCP с наблюдаемым состоянием отдельных виртуальных
машин, проверить передачу пакетных данных в настоящий Trivy и восстановление
после изменения firewall. Успех другого выпуска или архитектуры из этих
испытаний не следует.

Для обычного подключения сервера используйте [Linux setup](linux-setup.md).
Поднимать этот CI-стенд на каждом проверяемом сервере не требуется.

## Среда и воспроизводимость

Workflow `.github/workflows/linux-deb-vm-integration.yml` создаёт две независимые
VM на GitHub-hosted runner. Harness `deployment/tests/linux_deb_vm_integration.py`
проверяет принадлежность процесса QEMU, доступность KVM, ОС и архитектуру гостя,
systemd как PID 1 и различие идентификаторов загрузки гостя и контроллера.
Совпадение строк `uname -r` не означает общее ядро и само по себе не запрещается.

Образы закреплены в
[`linux-deb-images.json`](../deployment/tests/fixtures/linux-deb-images.json):

| Гость | Датированная сборка | Формат | Проверка загрузки |
| --- | --- | --- | --- |
| Debian 12 genericcloud amd64 | `20261026-2643` | QCOW2 | Точный размер, SHA256 и опубликованная SHA512 |
| Ubuntu 24.04 server cloudimg amd64 | `20261017` | QCOW2 | Точный размер и опубликованная SHA256 |

Полные файлы этих образов сверены с контрольными суммами издателей при
подготовке manifest. CI повторно проверяет загруженные байты. Это фиксация
содержимого и проверка целостности; независимая цепочка доверия OpenPGP-подписей
на этапе подготовки manifest **не проверялась**. Подмена содержимого по тому же
URL должна завершить загрузку ошибкой. Обновление образа требует отдельной
смены pin и нового нативного прогона.

Гостевые пакеты устанавливаются из репозиториев соответствующего выпуска;
точный получившийся инвентарь сохраняется в evidence. Закреплённый образ не
делает сетевые apt-репозитории неизменяемыми. Поэтому воспроизводится процедура,
а состав установленных обновлений сверяется по артефакту конкретного запуска.
Для CVE фиксируются версия Trivy, хеш базы и её metadata; база должна быть
достаточно свежей при запуске и оставаться неизменной во время сравнения.

## Проверки системного аудита и отчётов

Сначала устанавливается доверенный ключ SSH отдельного гостя и собирается
идентичность актива. Затем выполняются штатные playbook и удалённые сборщики
репозитория. Содержимое `os-release` не подменяется для выбора другого адаптера.

| Контроль | Исходное состояние | Заданное изменение | Восстановление |
| --- | --- | --- | --- |
| Временный каталог | Sticky bit присутствует | Sticky bit снят у принадлежащего стенду каталога | Исходные права возвращены |
| Служба cron | Реально active | Реально inactive | Снова active |
| UFW / INPUT | Ограничивающие правила | Временные помеченные ACCEPT перед правилами INPUT для обоих семейств IP | Удалены только принадлежащие стенду правила |

Для каталога ожидаются `passed → failed → passed`. Для cron сверяются нативное
состояние systemd, `serviceObservations` и evidence правила
`critical_services_review`: само это правило остаётся ручной проверкой
необходимости службы, а остановка cron не объявляется универсальной мерой
харденинга. Для ограниченной модели `firewall_active` ожидаются
`passed → failed → passed`.

У firewall-контроля есть отдельные предварительные условия: известные INPUT
цепочки, отсутствие конкурирующего владельца правил, уникальная метка изменения
и проверка точного различия ruleset. Неподдержанная конфигурация не должна
автоматически превращать этот контроль в успешный. Восстановление сравнивает
настройки и kernel ruleset с исходными снимками, исключая только изменяемые
счётчики и служебные handles. Область самого firewall-оценщика описана в
[Linux firewall audit](linux-firewall-audit.md); такой контроль не доказывает
полноту политики портов или доступность сервера из Интернета.

Шесть исходных системных отчётов проходят через production-функции
`recordAssetObservation`, `publishCapturedAssetReports` и `readAnsibleReport`.
Проверяются:

- идентичность наблюдалась до сканирования, alias и привязка к активу совпадают;
- все исходные наблюдения и причины неполноты сохранены при публикации;
- ни одна находка, её статус, риск или evidence не потеряны при нормализации;
- `partial` не исчезает, неполный результат не приобретает числовую оценку;
- число находок по уровням риска соответствует исходным данным.

Это проверка серверного пути публикации и нормализации. Полный браузерный
мастер подключения в данном стенде не выполняется. Приватный machine-id нужен
для вычисления привязки, но в опубликованные артефакты не включается.

## Пакеты и CVE

Полученный через SSH инвентарь сопоставляется с отдельным нативным запросом
`dpkg-query`: имя, binary version, архитектура, source package, source version,
состояние dpkg, Maintainer и Origin. После этого
`deployment/tests/verify_linux_packages.mjs` вызывает production SBOM и
CVE-маршрут HCP с настоящим Trivy **0.74.0**. Отдельный native replay того же
SBOM на той же базе проверяет сохранение записей и находок.

Размеченные контроли в
[`linux-package-controls.json`](../deployment/tests/fixtures/linux-package-controls.json)
проверяют конкретную границу **CVE-2024-6119**:

| Выпуск | Binary / source | Исправленная версия производителя | Источник |
| --- | --- | --- | --- |
| Debian 12 | `libssl3` / `openssl` | `3.0.14-1~deb12u2` | [Debian tracker, DSA-5764-1](https://security-tracker.debian.org/tracker/CVE-2024-6119) |
| Ubuntu 24.04 | `libssl3t64` / `openssl` | `3.0.13-0ubuntu3.4` | [USN-6986-1](https://ubuntu.com/security/notices/USN-6986-1) |

В уязвимом контроле требуется находка с нужным CVE и источником. В исправленном
контроле требуется отсутствие **этого** CVE; это не утверждение, что версия
свободна от любых других уязвимостей. Контрольные версии являются входными
метаданными и не устанавливаются в гостевую ОС.

Дополнительные синтетические случаи проверяют epoch, различие исходной и
бинарной версии, multiarch и неизвестного/стороннего поставщика. Они проверяют
интерпретацию метаданных; выдуманная комбинация версии и архитектуры не считается
отдельным подтверждённым уязвимым пакетом производителя. Maintainer/Origin
остаются эвристикой, а не доказательством подписи и установленного репозитория.

Сохранение каждой пакетной записи, обработка её детектором и применимость
advisory — отдельные условия. Пропущенная сканером запись или неизвестное
происхождение не равны отрицательному результату CVE. Два контрольных advisory
не позволяют оценить общую precision/recall системы для всех Linux-пакетов.

## Применение и восстановление

Стенд вызывает штатные backup, preview, apply и rollback playbook для UFW.
Отдельно проверяются сохранение SSH, закрытие тестового HTTP-порта с внешней
для гостя стороны, повторное применение, сохранение ограничения после reload
и возвращение доступности после отката.

Аварийный контроль посылает SIGKILL только принадлежащему стенду процессу
rollback в точке после перемещения каталога конфигурации. Затем штатное
восстановление должно продолжиться по durable journal. Итоговый PASS требует
сравнения восстановленных настроек и runtime с исходным состоянием, а не
только нулевого exit code команды. Повтор завершённого rollback также
проверяется.

Этот сценарий не расширяет production-список backend: автоматические изменения
по-прежнему ограничены поддерживаемыми UFW/firewalld на systemd. Новому backend
нужны собственные проверки владения, резервирования, применения и восстановления.

## Запуск и чтение результатов

В GitHub Actions запустите workflow **Native Debian and Ubuntu hardening acceptance**
для нужного commit/ref. Он также запускается на изменениях файлов, перечисленных
в его `paths`. Для запуска через настроенный GitHub CLI:

```sh
gh workflow run linux-deb-vm-integration.yml --ref main
```

Исполняйте harness через предусмотренный workflow на одноразовом runner.
Проверки среды запрещают перенос изменяющих конфигурацию команд на произвольный
контроллер или рабочий сервер. Отдельные read-only регрессии публикации отчётов
можно выполнить локально после `npm ci` в `web`, используя Node 24:

```sh
node --test deployment/tests/verify_deb_vm_normalization.test.mjs
```

Оценивайте завершившийся запуск по его commit SHA. В артефактах должны быть
протокол VM, исходные и опубликованные отчёты, результат нормализации, снимки
firewall и пакетный acceptance protocol. Недоступность образа, базы, KVM или
обязательного инструмента является ошибкой проверки, а не успешным пропуском.
SSH private keys, cloud-init seed, диски VM и приватное наблюдение идентичности
не публикуются. Истёкшее хранение GitHub Actions artifacts не заменяет
необходимость сохранять итоговые краткие протоколы в `docs/evidence`.
