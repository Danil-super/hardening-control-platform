# Проверка критически важных данных после восстановления HCP

Статус: **автоматизированная локальная проверка файлов**, а не подтверждение
эксплуатационной готовности. Для завершения задачи #43 требуются испытания
**на другой разрешённой изолированной Ubuntu**, ручная проверка панели,
подлинности активов, SSH и реального отката.

## Граница безопасности

Эта проверка предназначена только для **остановленного** восстановленного HCP.
Не направляйте её на работающий экземпляр или на исходный сервер. Инструмент
не делает сетевых запросов, не запускает Docker, не перезаписывает SQLite и не
вводит пароль администратора. Архивы должны быть получены через
`docs/backup-restore.md` и пройти проверку
`deployment/tests/verify_backup_bundle.py`.

Права на восстановленный runtime и архивы должны позволять **только
уполномоченному оператору** читать их содержимое. Сохраните исходную
шифрованную/изолированную копию отдельно. Не отправляйте секреты в GitHub/чат.

## Порядок

1. Создайте резервную копию исходного управляющего узла и выполните проверку
   `verify_backup_bundle.py`. Убедитесь, что исходный Git commit и Docker
   image digest совпадают с планом восстановления.
2. На **другой** Ubuntu восстановите те же settings, image и runtime
   в **новый пустой** volume по `docs/backup-restore.md`. Сохраните доступ к
   оригинальной копии. Не обновляйте версию HCP и не меняйте таймеры.
3. **Остановите** восстановленный HCP и все конкурирующие операции.
   Рекомендуется не запускать его до завершения проверки. Для offline
   инструмента сделайте локальный read-only mount восстановленного volume.
4. Пройдите byte-for-byte gate. На новой Ubuntu, из checkout HCP, пример:

   ```bash
   python3 deployment/tests/verify_restored_runtime.py \
     --backup-dir /private/backup/hcp-20261104T000000Z \
     --restored-runtime /private/mounted-restored-runtime \
     --acknowledge-stopped \
     --require-enrolled-host \
     --output /separate/private/new-post-restore-evidence.json
   ```

   Подставьте **свои реальные локальные** абсолютные пути. В восстановленной
   копии должны существовать `hcp.sqlite`, `inventory.ini`,
   `known_hosts` и как минимум одна индивидуальная SSH-пара и один отчёт.
   Эти пути не публикуйте. Флаг `--acknowledge-stopped` является
   **заявлением оператора**, а не автоматическим подтверждением остановки
   процессов. `--require-enrolled-host` обязателен для практической приёмки,
   где действительно подключена тестовая цель.

## Что делает инструмент

- Повторно проверяет состав архива через `verify_backup_bundle.py` и
  сопоставляет bytes/hashes критически важных файлов `hcp.sqlite`,
  `inventory.ini`, `known_hosts`, `reports/**`,
  `ssh-host-keys/**`, `sbom/**` с исходным `runtime.tar.gz`.
- Читает TAR только потоково, **не извлекает архив** на диск и не следует
  небезопасным symlink. Файлы restored открываются относительно каталога
  через `O_NOFOLLOW`, проверяются размер, байты и неизменность fd. Приватные
  файлы должны быть недоступны group/other.
- Отдельно запускает `PRAGMA integrity_check` на **неизменяемой, только
  читаемой** SQLite-копии. Если остались `hcp.sqlite-wal/-shm`, инструмент
  **останавливается**, а не игнорирует непроверенную WAL-часть базы.
  Восстановление WAL/чекпойнт выполняется в отдельной изолированной
  процедуре, не над рабочим HCP.
- Выдаёт только численные итоги, статус проверки SQLite, hashes манифеста и
  обобщённые коды отказов. Не выводит содержимое приватных ключей, инвентаря,
  базы, отчётов или `.env`. Опциональный результат создаётся впервые с
  правами 0600 **вне** архивов и runtime.

Возвращаемый успех имеет ограниченный статус
`critical-runtime-bytes-match-backup`. Значения
`actualLoginVerified=false`, `auditHmacChainVerified=false`,
`sessionsRevokedVerified=false`, `sshReconnectVerified=false`
явно указывают, что эти требования пока не измерены.

## Обязательная оставшаяся реальная эксплуатационная приёмка

После byte-for-byte gate **отдельно**:

- Загрузить восстановленную копию HCP **только на выделенном тестовом адресе**,
  проверить здоровый контейнер и вход администратора; проверить отказ
  неавторизованных запросов и origin-policy.
- Сверить HMAC-цепочку журнала тем же прежним секретом подписи, что сохранялся
  в резервной копии. Проверка файлов SQLite сама по себе не подтверждает HMAC.
- Проверить сохранённый SSH fingerprint, личные host-credentials, старые
  отчёты, отсутствие случайного повторного исполнения незавершённой операции,
  а затем новый разрешённый аудит.
- На отдельной disposable цели провести безопасное изменение UFW/firewalld с
  собственным backup, новым SSH-соединением, подтверждённым откатом и
  проверкой доступа через отдельную консоль. Снять timings и run IDs.
- Оформить реальный протокол с ограничениями и подписью ответственного.
  Ошибка одного этапа — приёмка не пройдена. Задачи #40/#43 **не закрывать**
  по одному локальному успеху.

Регрессионные тесты:
`deployment/tests/test_verify_restored_runtime.py`. Их SQLite, ключи и
отчёты **синтетические** и не доказывают восстановление продукта.
