# Native Astra Linux SE 1.7.6.15 — автоматическая KVM-приёмка

Статус: **CI-сценарий создан; прохождение настоящей нативной приёмки должно
подтверждаться завершившимся GitHub Actions run и исходными артефактами**.
Один только успешный Python unittest не считается настоящим экспериментом.

## Автоматический прогон

Workflow: `.github/workflows/astra17-vm.yml`, имя
`Real native Astra SE 1.7.6.15 acceptance`. При PR, меняющем
сканер/плейбук/источники, запускается одноразовая ВМ **base**. Из GitHub
Actions → Run workflow можно вручную выбрать `base`, `adv` или `max`
по одному. Это не автоматическое подтверждение всех трёх режимов: каждый
должен пройти независимо.

Целью всегда является **собственная временная ВМ GitHub runner**. На
пользовательской Astra не производится удалённых действий. Приватные SSH
ключи и оригинальный `machine-id` находятся только во внутренней папке CI,
не публикуются как артефакты.

Сценарий:

1. Проверяет, что runner — GitHub-hosted и образ действительно qcow2 без
   внешнего backing-файла. Перед использованием проверяет полный SHA-256
   и размер файла. Повторно верифицирует кеш по байтам.
2. Создаёт независимый overlay-диск и cloud-init seed с отдельными
   **одноразовыми** учётными данными. Публикация SSH ключей и source qcow2
   не требуется.
3. Поднимает настоящий QEMU/KVM, фиксирует реальный `ID=astra`,
   `/etc/astra_version=1.7.6` и `/etc/astra/build_version=1.7.6.15`, ядро, package database, SSH host-key и
   безопасную hash-привязку machine-id.
4. Устанавливает OpenSCAP **только в своей тестовой VM**, если его нет в
   образе, и применяет штатные Ansible playbook для facts и package inventory.
   На чужой ОС HCP не ставит пакеты без разрешения.
5. Три раза выполняет тот же встроенный профиль HCP из 18 конфигурационных
   правил. Между первым и вторым прогоном **на собственной одноразовой ВМ**
   временно меняется флаг executable у `/etc/passwd`; исходное состояние
   возвращается в `finally`.
6. Сверяет оригинальные XCCDF/ARF, SHA фактически выполненных datastream,
   переход `passed→failed→passed`, а также вновь устанавливает SSH и
   проверяет, что после восстановления совпали machine-id, kernel и права
   тестового файла.
7. Публикует оригинальные три JSON через штатный
   `publishCapturedAssetReports` с одной идентичностью актива, использует
   `measure_astra_baseline.py --restored`. Запрещены придуманное «100%
   защищено» или отсутствие CVE при недостаточных данных.
8. Загружает **полную неизменённую** Astra OVAL 1.7 XML. Сравнивает число
   определений в реальном XML с числом фактически проверенных результатов
   сканера и их уникальностью. Отсутствующие определения,
   `scanner.partial=true`, неудачный `oscap` либо несовпадение SHA
   не являются успешной нативной приёмкой.
9. Публикует OVAL JSON через штатный production normalizer с проверенным
   assetBinding. Сохраняет только заранее перечисленные артефакты и
   **только при полном успешном** завершении проверки. Ограничение
   `retention-days=14`.

## Подтверждённая диагностическая граница

Первые настоящие запуски на исходном образе версии 1.7.6.UU2 подтвердили
побайтовую целостность исходного файла и SSH-доступность. Причина отказа
двух отдельных проверок: ошибочное ожидание `1.7.6.15` в
`/etc/astra_version` и ошибка модуля `cloud-init scripts_per_once`.
Проверка версии теперь опирается на два системных файла (см. PR #64).

`scripts_per_once` в cloud-init запускает одноразовые скрипты
в `/var/lib/cloud/scripts/per-once`. Если модуль завершился ошибкой,
приёмка **останавливается**. Диагностика на собственной ВМ читает только
файловые метаданные и тип интерпретатора; не публикует содержимое скриптов,
private keys или raw machine-id. Нельзя отключать модуль ради зелёного CI.

Оригинальные образы из разных официальных каталожных сборок (например
MG15.1.0 и MG15.3.1) не взаимозаменяемы: для каждого нужен отдельно
зафиксированный SHA-256 и самостоятельный реальный прогон.

## Что означает PASS

Только то, что для **конкретного выпуска, уровня и образа** доказаны:
нативное выполнение, факты ОС, одна область из 18 правил, контрольное
нарушение, восстановление и точный скан указанного источника OVAL.

Это **не** доказывает: поддержку всех уровней Astra, полноту всех CVE,
функционирование КСЗ в реальной инфраструктуре, безопасность production
харденинга, сертификационное соответствие или полное восстановление всей ОС.
Физический гипервизор заказчика и эксплуатационная приёмка #43 требуют
отдельного протокола. Даже успешная CI Astra 1.7 не закрывает все пункты
#40: необходим независимый разбор нативных артефактов и ограничений.

При расследовании base CI (4 ноября) оригинальная Astra подтвердила
`/etc/astra_version=1.7.6` и `/etc/astra/build_version=1.7.6.15`,
но `cloud-init status --wait` завершился ошибкой `scripts_per_once`.
В госте есть **один исполняемый shell-скрипт per-once**. Причина его
неуспешного завершения ещё не установлена. Диагностика проверяет синтаксис
shell-сценария **без выполнения**; отдельный стандартный Python-пробник анализирует
оба журнала `cloud-init.log` и `cloud-init-output.log` **внутри гостя**
(ограниченный объём, только чтение) и передаёт наружу исключительно
заранее разрешённые категории: сетевые/DNS, пакеты, службы, права,
файловая система, числовые коды возврата и базовые признаки сети/диска.
Сырые строки журналов, скрипты, адреса, user-data и секреты не отправляются.
Такой результат — **диагностическая гипотеза**, а не доказанная первопричина.
Публикует исключительно безопасные агрегаты,
без команд, строк логов и приватных идентификаторов. Штатный модуль не отключается
и не обходится; никакая нативная приёмка не засчитывается до успешной
инициализации. После неё идентичность и обе версии проверяются повторно,
как и после восстановления исходных настроек.

Если pipeline не проходит из-за отсутствия подходящего OpenSCAP/SCE, это
**содержательный результат о границе совместимости**, а не основание
объявлять тест успешным. В CI-логах нужно зафиксировать причину и
область неполноты, не заменять результаты фиктивными.
