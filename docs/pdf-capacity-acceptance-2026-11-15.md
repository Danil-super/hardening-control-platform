# Общий лимит формирования PDF — 15 ноября 2026 года

## Причина и изменение

API PDF отдельной проверки ограничивал свои запросы двумя, но итоговый PDF
вызывал тот же renderer без ограничения. Одновременные запросы к разным API
могли запускать дополнительные Python-процессы.

`runPdfRenderer` теперь допускает два запуска на один Node-процесс, включая
отдельные копии модуля в сборках маршрутов. Третий запрос отклоняется до
сериализации снимка в renderer. Оба API возвращают HTTP 429 с понятным
сообщением. Существующий ранний лимит API отдельной проверки сохранён.
Место освобождается только после `close` дочернего процесса; `error` и
запрос на SIGKILL сами по себе ещё не подтверждают его завершение.

Пределы входа 32 МиБ, выхода 12 МиБ и времени 120 секунд сохранены.
Данные не сокращаются, пароли/вывод renderer не добавлены в ответы,
схема БД и формат сохранённых отчётов не меняются. Итоговая запись PDF
создаётся после успешного формирования, поэтому отказ по занятости не
сохраняет незавершённый итоговый отчёт.

## Проверки

- Четыре регрессии сначала отклонили прежнюю реализацию, затем прошли:
  общий лимит двух копий модуля; ошибки подготовки/размера/запуска;
  timeout и ошибка запуска до `close`; превышение выхода и повтор.
- Восемь точечных проверок renderer и двух API прошли.
- Вся web-серия: **641 pass, 0 fail, 0 skipped**; typecheck прошёл.
- Production build прошёл в отдельном контейнере 2 ГиБ без сети,
  с прежними установленными зависимостями.
- **140 HTTP-проверок** собранного Next, включая прежние 132 и отдельную
  проверку общего лимита. Два настоящих renderer итоговых PDF временно
  приостановлены только внутри собственного fixture-сервера. Оба API
  вернули 429; `/jobs` остался доступен. После возобновления получены два
  итоговых PDF и PDF проверки, все 4000 CVE и последний ID присутствуют
  в каждом. SHA исходного JSON и его неизменность подтверждены.

HTTP-проверка использовала обычные renderer и production-маршруты;
приостановка нужна только для воспроизводимой занятости. Настройки
операторской Astra и данные рабочей панели не использовались.

## Измерение

Одинаковые четыре вызова renderer, по 4000 записей каждый, через две
независимо загруженные копии модуля. Docker: один CPU, 1,5 ГиБ RAM и такой
же предел memory+swap, без сети. Пик — сумма RSS Node и его непосредственных
дочерних процессов, опрос каждые 50 мс; это не полный RSS рабочего компьютера.
Отклонённые новые запросы повторены после завершения первой пары.

| Вариант | Одновременных Python | Пик RSS, два прогона | Успешно завершено |
| --- | --- | --- | --- |
| Прежний renderer | 4 | 462 176 256 / 459 034 624 байт | 4 из 4 |
| Общий лимит | 2 | 319 492 096 / 315 207 680 байт | 4 из 4 после повтора |

Снижение пика в этом сценарии — около 31%. Во всех 16 PDF двух пар
прогонов проверены все 4000 CVE и последний ID; каждая копия — 929 423 байта.
Из этих результатов не выводятся предел памяти любого отчёта или общий SLA.

## Ресурсы, отказы и границы

Первый запуск серии прошёл тесты и typecheck, но production build был
убит cgroup OOM при тестовом пределе 1,5 ГиБ. Рабочий HCP и ВМ не останавливались;
минимум MemAvailable был 3 751 612 416 байт. Сборка повторена с ранее
проверенным пределом 2 ГиБ: build и HTTP прошли, минимум MemAvailable
3 871 182 848 байт, OOM и защитной остановки нет.
Порог остановки собственных тестовых контейнеров — 2,25 ГиБ MemAvailable;
swap рабочего компьютера не изменялся и не объявляется свободным.

Два первых запуска частной HTTP-проверки ошибочно выполняли новый сценарий
после logout существующего fixture-сеанса. Авторизация правильно вернула
401. Сценарий перенесён перед logout, защита продукта не ослаблялась;
неудачные журналы сохранены.

Доказательства находятся в приватном локальном каталоге
`~/.local/state/hcp-evidence/pdf-budget-20261115-r8tt6_lo/`:
исходный архив `fea7861`, baseline/bounded receipt и логи, RED/GREEN,
полная серия, сборка и HTTP-сценарий. Учётные данные и рабочие отчёты в Git
не включались. Code Graph проверен для корня HCP; Graphify обновлён.

Это первый ограниченный шаг общего бюджета ресурсов. Лимит не объединяет
PDF с HTML, OVAL, Trivy, импортом или чтением крупных JSON и не координирует
несколько Node-процессов/контроллеров. Общая защита RAM, три полных OVAL
одновременно и универсальный SLA остаются открыты.

## Отказ подготовки Astra 1.8.6 в CI

У `cb8df37` job `132870439571`, run `43733342213` остановился через 600
секунд на установке OpenSCAP в госте. Образ и полный XML уже прошли byte/SHA
проверку cache, подлинная ОС и ядро подтверждены; до baseline/OVAL-аудита
этого гостя запуск не дошёл. Причина зависания установки пока неизвестна:
внешняя сеть, APT и другие причины не различены по имеющимся данным.
Это не отказ нового PDF renderer.

Архив `14170225867` сверен с SHA-256
`9f5461d23fdc0653aa009f0f326a18a1a8ee73643bba196178686eeaf9998da5`.
В нём только пять файлов (protocol, identity, cloud-init, console и QEMU),
журнал `guest-oscap-install.log` отсутствует: общий CI-helper записывал вывод
только после нормального возврата `subprocess.run`.

Локально исправлен этот пробел: при `TimeoutExpired` helper сохраняет точные
накопленные bytes stdout/stderr, включая неполную кодировку, и вновь
выбрасывает исходное исключение. Лимиты времени, код успеха, проверки и
очистка гостя не ослаблялись. Два RED-кейса воспроизвели отсутствие журнала;
после изменения все **250 deployment-тестов** прошли без сети в 512 МиБ.
Настоящий зависший дочерний процесс остановлен и собран; пустой вывод,
обычный успех и проверка exit code также проверены.

Этот диагностический код не входит в образ `17bb5e9c` и пока не опубликован;
runtime-файлы HCP он не меняет. Повторён только исходный failed job Astra
1.8.6 на том же `cb8df37`, исходный отказ/ZIP сохранены. Успешный итог
повтора не объявляется. Evidence дополнения — подкаталог `ci-diagnostics/`.
