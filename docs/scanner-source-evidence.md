# Происхождение пакетов и целостность источников Trivy

## Что сохраняет новый сбор пакетов

Для DEB сохраняются наблюдаемые поля `Maintainer` и `Origin` вместе с двоичной/исходной версией, epoch, архитектурой и состоянием dpkg. Необязательный пустой `Origin` не считается ошибкой инвентаризации. Эти данные попадают в CycloneDX: `supplier`, `hcp:maintainer`, `hcp:origin` и описание способа оценки происхождения.

Метаданные установленного пакета **не доказывают**, что архив получен из подписанного репозитория. HCP применяет консервативную эвристику:

- `distribution-maintainer`: Maintainer содержит адрес домена дистрибутива, а имеющийся Origin не противоречит ему;
- `third-party`: явный сторонний Origin либо известный сторонний Maintainer;
- `unknown`: сведений недостаточно, в том числе в старом инвентаре без Maintainer.

На Ubuntu допускаются наблюдения Maintainer Ubuntu/Debian; на Debian — Debian. Поддомены проверяются по границе домена: `ubuntu.com.example.org` не относится к Ubuntu. Официальный Debian-пакет может иметь личный адрес сопровождающего и получить `unknown`; такое ограничение остаётся видимым. Результат эвристики не называется проверкой подписи или подтверждением репозитория.

У Trivy 0.74 нативный dpkg-анализатор тоже использует Maintainer-эвристику, но его CycloneDX-путь не воспроизводит эту классификацию автоматически. Поэтому совпадение с advisory ОС для стороннего или неизвестного пакета сохраняется в HCP как `manual` с неподтверждённой применимостью. Находка и исходный CVE не удаляются. Полнота покрытия становится `false`, а пустой результат не превращается в утверждение об отсутствии CVE.

Старые отчёты не переписываются. Новый скан старого инвентаря сохраняет доступные наблюдения, но остаётся неполным до нового сбора данных. Для RPM и неподдерживаемых поставщиков сохраняются прежние ограничения применимости.

Первичные источники: [dpkg-анализатор Trivy 0.74](https://github.com/aquasecurity/trivy/blob/v0.74.0/pkg/fanal/analyzer/pkg/dpkg/dpkg.go), [CycloneDX decoder](https://github.com/aquasecurity/trivy/blob/v0.74.0/pkg/sbom/cyclonedx/unmarshal.go), [ограничения vulnerability scanning](https://trivy.dev/docs/latest/scanner/vulnerability/).

## Какие байты действительно использовал сканер

Controller helper `ansible/scripts/hcp-trivy-source.py` выполняет обновление и сканирование под общей Linux `flock` для выбранного cache. Блокировка согласует процессы HCP, а её дескриптор наследует настоящий процесс Trivy: принудительное завершение контроллера не освобождает ещё используемый источник. Ожидание ограничено; истёкшее ожидание даёт неполный результат.

Перед сканированием и после него потоково вычисляются SHA-256 базы, metadata, исполняемого файла Trivy, SBOM и конфигурации. Сверяются также inode, размер и времена изменения. В отчёте `vulnerabilityScan.sourceEvidence` сохраняются обе группы наблюдений, параметры и версия движка. Дата базы берётся из metadata **того же источника**, даже если другой процесс обновил общий cache сразу после завершения скана. Конфигурация каждого скана хранится отдельно рядом с SBOM.

Результат признаётся завершённым только при совпадении наблюдений. Смена байтов, замена файла с прежними байтами, пропавший файл, неверный тип, таймаут или превышение размера вывода дают `partial`; отрицательное CVE-заключение при этом не создаётся. Обычные символические ссылки и специальные файлы в источниках не принимаются.

После успешной загрузки фиксируется `.hcp-source.json` с хешами базы и metadata. Старый cache без этого файла допускается для совместимости; после первого успешного исполнения Trivy его наблюдаемые байты также фиксируются, без объявления происхождения проверенным. Последующие сканы обнаруживают изменение пары и между запусками.

`flock` — **согласуемая блокировка, а не неизменяемый снимок**. Внешний процесс может не соблюдать её. Проверка хешей и идентичности обнаруживает изменения в проверенных границах; она не изолирует источник от администратора хоста и не сохраняет все прежние гигабайтные базы бессрочно. Для последующего воспроизведения исторического результата нужно отдельно сохранять базу и metadata под записанными хешами. Число CVE и результат относятся к указанному инвентарю и источнику.

## Обновление и локальный импорт

Сетевая загрузка выполняется в отдельном staging-каталоге. Неуспешная попытка registry сохраняет прежнюю пару файлов. После успешной загрузки пара публикуется под блокировкой. Маркер `.hcp-refresh-pending.json` записывается до публикации; остановка между файловыми заменами сохраняет неопределённое состояние, и сканирование не считает такой cache готовым. Успешное повторное обновление восстанавливает источник. Маркер и lock не следует удалять для обхода проверки.

Для первоначального переноса локальной базы используйте проверенный cache целиком. Если нужно заменить файлы в уже зарегистрированном offline cache, сначала завершите операции HCP и перенесите согласованные `trivy.db`/`metadata.json`. Затем зарегистрируйте их с двумя **заранее проверенными контрольными суммами** из протокола передачи. Пример внутри штатного контейнера:

```bash
python3 /app/ansible/scripts/hcp-trivy-source.py \
  --action register-import \
  --cache-dir /var/lib/hcp/trivy-cache \
  --expected-db-sha256 '<64 hex из проверенного протокола>' \
  --expected-metadata-sha256 '<64 hex из проверенного протокола>'
```

Не заменяйте ожидаемые суммы суммами случайно найденных файлов, чтобы просто снять ошибку. Регистрация проверяет именно переданные байты и обновляет локальный манифест; ответ содержит `vulnerabilityAssessment=not_run`. Подпись поставщика, применимость базы к дистрибутиву и результат CVE-аудита этим действием не устанавливаются. После регистрации выполните новый CVE-скан.

## Проверки

`ansible/tests/test_trivy_source.py` выполняет реальные локальные процессы и файловые операции: конкурентный refresh, принудительное завершение helper с живым child, изменение/замену файлов, недопустимые типы, повреждённую или прерванную публикацию, проверку import digest, таймауты и переполнение вывода. `web/tests/trivy-accuracy.test.mjs` проверяет весь производственный адаптер с явно обозначенным CLI-контрактом, включая применение provenance, старые инвентари, архитектуры/epoch, изменение источника и одновременные сканы.

`deployment/tests/verify_trivy_matching.mjs` использует настоящий Trivy и базу для Ubuntu backport-пары CVE-2023-0286, i386, искусственного epoch и неизвестного поставщика. Последние два случая проверяют интерпретацию метаданных, а не существование таких выпусков у поставщика. Нативный положительный и исправленный контроль имеют известные реальные версии из [Ubuntu USN-5844-1](https://ubuntu.com/security/notices/USN-5844-1). Отчёт проверяет хеши источников, состав пакетов, сохранение CVE и причины неполноты; это ограниченный эталонный набор, не измерение общей precision/recall.
