# Завершение проекта у заказчика

Этот порядок подходит для временно развернутого HCP: аудит → согласованные работы → повторная проверка → передача результата → отзыв доступа. Он не удаляет доказательства автоматически.

## 1. Зафиксируйте результат

1. Для каждого хоста проверьте «План работ»: у выполненных пунктов укажите полный свежий повторный аудит и переведите их в «Подтверждено». Для отложенных мер выберите «Принято как риск», укажите владельца, внешний документ и дату пересмотра.
2. Откройте «Итоговые PDF», выберите хост, заполните заказчика, проект, период и специалиста. Скачайте PDF.
3. Сохраните PDF вместе с его SHA-256 из страницы, а также резервную копию HCP по [инструкции резервирования](backup-restore.md). Итоговый PDF создаётся из неизменяемого серверного снимка: манифест связывает его с ID и SHA-256 исходных JSON-отчётов. HMAC-цепочка HCP защищает события, но сама по себе не является подписью каждого исходного JSON.

Не выдавайте отсутствие свежего или полного отчёта за подтверждённое исправление. Итоговый отчёт фиксирует область и ограничения, в том числе что OVAL Astra относится к выбранной базе, а не ко всем возможным CVE.

## 2. Остановите расписание на control node

До отзыва ключей отключите таймеры на Ubuntu control node, чтобы они не пытались выполнять новые задания во время закрытия:

```bash
sudo systemctl disable --now hcp-scheduled-audit.timer hcp-deep-audit.timer
sudo systemctl stop hcp-scheduled-audit.service hcp-deep-audit.service
systemctl list-timers 'hcp-*audit.timer'
```

Последняя команда не должна показывать активных будущих запусков HCP. Если systemd-таймеры не устанавливались, этот шаг не нужен.

## 3. Отзовите доступ по одному хосту

В «Хосты» откройте настройки хоста → «Дополнительные действия с хостом» → «Завершить работы по хосту». Введите точно его alias и подтвердите операцию.

HCP делает это строго в следующем порядке:

1. подключается **только ключом** HCP через ранее закреплённый ключ SSH-сервера из `known_hosts`;
2. удаляет в `~/.ssh/authorized_keys` ровно строку индивидуального ключа данного хоста, не затрагивая остальные ключи;
3. только после ответа цели удаляет локальную пару HCP и строку в inventory;
4. записывает начало, результат или ошибку в HMAC-журнал.

Если ключ сервера изменился, доступ отклонён, нет административных прав или ключ не найден на цели, операция останавливается: локальные ключи и inventory **не удаляются**. Сначала разберите причину по доверенному каналу. Для автоматического отзыва нужна учётная запись `root` либо разрешённый `sudo -n`; при работе от root дополнительная настройка sudo не требуется. Если HCP создавала своё правило `/etc/sudoers.d/zz-hcp-<ID ключа>`, завершение работ предварительно сверяет его точное содержимое и удаляет вместе с уникальным ключом. Чужие правила sudo HCP не изменяет.

`known_hosts` намеренно сохраняется: это история доверия к серверу, а не средство входа. JSON-отчёты, SQLite-журнал, план работ и firewall-бэкапы тоже сохраняются. Старый общий/устаревший ключ без индивидуального `credentialId` HCP автоматически не отзывает — удалите такой ключ вручную на цели и зафиксируйте это в акте.

## 4. Передача и остановка HCP

После отзыва доступа ко всем хостам передайте PDF, хеши, резервную копию и перечень принятых рисков. Затем можно остановить контейнеры, не удаляя данные:

```bash
docker compose down
```

Не добавляйте `-v`, пока заказчик не подтвердил срок хранения материалов. Удаление volume — отдельное необратимое решение владельца данных после передачи и проверки резервной копии.

## 5. Контрольный лист

- [ ] План: все меры подтверждены повторным аудитом либо документированы как принятый риск.
- [ ] Итоговые PDF скачаны, их SHA-256 и манифесты источников сохранены.
- [ ] Плановые HCP-таймеры остановлены.
- [ ] Для каждого хоста показан успешный отзыв индивидуального ключа.
- [ ] Вход старым ключом HCP на тестовом хосте не проходит; доступ других администраторов не изменился.
- [ ] Отчёты, HMAC-журнал и резервная копия сохранены до удаления инфраструктуры.
