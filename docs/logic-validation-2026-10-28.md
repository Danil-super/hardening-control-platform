# Проверка достоверности результатов и жизненного цикла изменений

Дата: 28 октября 2026 года. Это продолжение [первого аудита и исправлений HCP-01–13](audit-remediation-2026-10-28.md). Исходный срез для повторной проверки — [`6076068`](https://github.com/Danil-super/hardening-control-platform/commit/6076068d0170650d2ca4b7458e2fb265cdf754db), объединение PR #3 в `main`.

Проверка охватывает путь от результатов сканеров до корреляции, пунктов плана, итогового PDF, управляемого изменения, резервной копии и отката. Применялись чтение кода, исполнение реальных модулей и SQLite, отдельные процессы, реальные временные архивы, нативные CI-сценарии и контролируемые ошибки. Рабочие хосты пользователя и их firewall не использовались.

## Оценка пригодности

HCP имеет работающие интеграции сканеров и управляемые операции с доказательствами. Нативные испытания подтверждают обнаружение конкретных заранее известных отклонений и восстановление конкретных правил firewall. При повторной проверке найдены ошибки, способные скрыть повторное нарушение, выдать неполный сбор за полную проверку или разрешить откат при ещё работающей предыдущей команде. Поэтому успешная сборка и зелёные обычные сценарии сами по себе не подтверждали достоверность каждого итогового заключения.

Практически платформа пригодна для аудита заданной области и контролируемого харденинга с участием оператора. Полнота обнаружения всех CVE, статистические precision/recall, корректность всех политик на каждом выпуске Astra и автоматическое восстановление после любой аварии этой проверкой не доказаны. Числовую оценку вида «точность 95%» по имеющимся данным обосновать нельзя.

## Почему это проверки логики

Для HCP-14 использовались настоящий `executeAnsiblePlaybook`, orchestration и SQLite. Только внешний CLI был заменён управляемой локальной программой, которая создавала отдельную задачу, переживающую завершение родителя. До исправления наблюдалась последовательность `baseline → restored → late-apply` при финальном `rolled_back`. После исправления повтор и откат блокируются, а состояние остаётся неизвестным до отдельной сверки.

Независимый review дополнительно нашёл и закрыл вариант **настоящего Ansible task timeout**: код `2`, `killed=false`, `signal=null` и полный recap не мешали задаче продолжать изменение. Ответ `FAILED!` без `rc` теперь не считается завершившейся нативной командой. Испытание `ansible-task-timeout.test.mjs` выполняет настоящий Ansible с локальным helper и отдельной управляемой задачей, записывающей только временный файл. Регрессия прошла на Ansible 2.14.18 и 2.19.14.

Для HCP-15 создавался настоящий tar-архив временного дерева с числовыми владельцами и нестандартными правами. Проверялось не только содержимое, но и `stat` после восстановления. Команды системного firewall заменены безопасными ответами; это проверка файловой части отката.

Первый CI-кандидат выявил несовместимость варианта `chmod(..., follow_symlinks=False)` с настоящим Python 3.5.10. Исправление переведено на открытие объекта без перехода по ссылке и операции `fchown`/`fchmod` с проверками через один дескриптор. Добавлены проверки отсутствия зависимости от несовместимого path API, отказа для подставленной ссылки/FIFO и фактического сохранения прав в target acceptance. До прохождения старого целевого интерпретатора этот кандидат не объединяется в `main`.

Для HCP-16–21 применялись настоящие JSON-отчёты, корреляция, план, SQLite и Python PDF renderer. Отдельные проверки извлекают текст сформированного PDF. Гонка удаления воспроизводилась через production DELETE-handler во время ожидания renderer, а не только прямым вызовом функции удаления.

Для HCP-22 выполнен настоящий `dpkg-query` с отдельной временной базой состояний. В этом конкретном PoC Trivy был контрактной программой, поэтому доказан пропуск входных пакетов и ложная полнота, а не конкретный пропущенный реальный CVE. Проверка известного CVE настоящим Trivy описывается отдельно.

Для HCP-23 использовался стандартный XML-контракт GMP с контролируемой ошибкой. Работоспособность настоящего движка Greenbone подтверждена отдельным CI-прогоном, что не заменяет проверку обработки ошибок импорта.

## Прямое сопоставление CVE и backport настоящим Trivy

28 октября отдельно исполнен Trivy **0.74.0** с настоящей базой и production-путём HCP: инвентарь → CycloneDX SBOM → `scanPackageInventory` → общий normalizer отчётов. Инвентари явно синтетические; уязвимые пакеты не устанавливались и не эксплуатировались. Применимость исправленной версии взята из [Ubuntu USN-5844-1](https://ubuntu.com/security/notices/USN-5844-1).

| Ubuntu 22.04 amd64, libssl3 / source openssl | Ожидаемый результат CVE-2023-0286 | Нативный Trivy | HCP и normalizer |
| --- | --- | --- | --- |
| `3.0.2-0ubuntu1.7` | Находка присутствует | Присутствует, `HIGH`, `FixedVersion=3.0.2-0ubuntu1.8`, источник Ubuntu CVE Tracker | Сохранена как `failed`, рекомендация содержит исправленную версию |
| `3.0.2-0ubuntu1.8` | Эта находка отсутствует | Отсутствует | Отсутствует |

В обоих случаях проверен один пакет из одного, инвентарь/результат полные в этой ограниченной области. Одинаковый основной номер `3.0.2` не привёл к ошибочному сохранению данной CVE после vendor backport. Остальные CVE не скрывались: фиксированный контроль не объявлялся полностью безопасным.

Первый успешный прогон: `12:48:18–12:48:31 UTC`. База `UpdatedAt=2026-10-28T07:10:42.861393948Z`, SHA-256 `2c8f4b04f224aded9ecd149b9b5304146736668220dfa403403358fb423a52fd`; хеш до и после сопоставлений совпал. Сохранённый нативный stdout получен отдельным повтором тех же SBOM на том же снимке базы, а production-функция также запускала настоящий бинарник. Это доказательство для одной пары версий и одной CVE, не статистическая оценка всего Trivy или всех пакетов HCP.

Повторены успешные сценарии новой загрузки и использования готового cache (`12:54:19–12:54:35 UTC`); исходники production-модулей во втором случае размещались так же, как в CI-wrapper. Оба прогона подтвердили ту же пару и неизменный хеш базы. Новый [нативный acceptance](../deployment/tests/verify_trivy_matching.mjs) включён в общий lab workflow; он сохраняет протокол, native stdout/stderr, SBOM и отчёты HCP.

Один промежуточный локальный повтор завершился неуспешно: к его началу файл cache имел другой SHA-256 и меньший размер, а сам Trivy аварийно завершился в bbolt. Причина изменения файла не установлена; этот повтор не записан как успешный и не объявлен доказанным дефектом HCP. Платформа вернула `partial=true`, `coverage.complete=false`, 0 проверенных пакетов и сообщение о незавершённом сканировании. После новой загрузки повторные проверки прошли. Это также показывает, почему одной даты metadata недостаточно для воспроизводимости: для строгого протокола нужны хеш и неизменность фактической базы.

## Остающиеся ограничения и следующие работы

### 1. Аварийное восстановление каталога firewall

Дополнительно воспроизведена остановка между двумя `rename` в rollback: предыдущая конфигурация сохраняется в staging, рабочий каталог отсутствует, прямой повтор возвращает `FileNotFoundError`. Данные копии не потеряны, но полностью автоматического восстановления после этой точки нет. Этот случай **не считается исправленным** в данном наборе. Подробная процедура и различие между исходной копией и `previous`: [operations-recovery.md](operations-recovery.md#аварийная-остановка-во-время-замены-каталога).

Следующий шаг — протокол этапов на целевом хосте, устойчивая идентичность staging и проверяемое восстановление после остановки до и после каждой замены/reload. До такой реализации нельзя обещать атомарный rollback при аварийном выключении или `SIGKILL`.

### 2. Полнота резервной копии

Формат сохраняет конфигурацию выбранного UFW/firewalld, UID/GID, mode и `security.PDPL`. Произвольные POSIX ACL и другие xattrs в него не входят. Копия не сохраняет состояние всего ядра, connection tracking, приложения или весь хост. Для систем, где такие метаданные обязательны, нужен либо расширенный проверяемый формат, либо явный отказ от неподдерживаемого состояния до изменения. Снимок ВМ и резервирование `/var/lib/hcp-backups` остаются отдельными механизмами.

### 3. Происхождение пакетов и границы CVE

В inventory/SBOM HCP не сохраняется достаточная информация о происхождении сторонних DEB-пакетов и Maintainer. Нативный dpkg-анализатор Trivy использует такие признаки для классификации third-party. Конкретный ошибочный реальный CVE по этому пути в повторном проходе не доказан; это ограничение данных и приоритет следующей проверки, а не ещё одна подтверждённая CVE-ошибка.

Нужно сохранять provenance и проверять поставщика вместе с OS/release/source version/epoch/architecture. Пакеты сторонних репозиториев, вручную установленные бинарники, библиотеки приложений и образы контейнеров требуют собственных областей оценки. Нельзя переносить полноту Debian/Ubuntu на Astra через `ID_LIKE=debian` или считать source inventory всего dpkg полным покрытием всего программного обеспечения.

### 4. Версионный набор эталонов точности

Для каждого поддерживаемого выпуска ОС нужен набор известных состояний: уязвимый пакет, исправленный пакет, backport с прежним upstream-номером, пакет с epoch, несколько архитектур, неподдерживаемый поставщик, частичная инвентаризация, устаревшая БД. Для каждого сценария фиксируются ожидаемые идентификаторы, выбранные advisory, версии движков, SHA базы/контента, actual findings и причина неполноты.

Для Astra нужны испытания на реальных заявленных выпусках с базой производителя и подтверждённой применимостью. Авторский профиль HCP из 18 правил не является полным CIS/STIG/ФСТЭК-профилем и не доказывает сертификационное соответствие. Для Greenbone следует отдельно проверять аутентификацию локальных проверок, QoD, фильтры экспорта и фактическое число выполненных VTs.

Precision/recall имеет смысл считать только для размеченного набора конкретной области: `TP/(TP+FP)` и `TP/(TP+FN)`. Количество зелёных тестов, ноль находок или среднее значение severity не заменяют такой набор.

### 5. Идентичность машины и управление операциями

История в основном привязана к inventory alias. Изменение IP само по себе не доказывает замену машины, но alias тоже не гарантирует, что это прежняя машина. Следующий архитектурный шаг — отдельный идентификатор актива с machine-id, доверенным SSH fingerprint и журналом смены привязки. Несколько alias одного физического хоста требуют общей блокировки операций по идентичности актива.

Фоновая очередь рассчитана на один контроллер. Исправление живого локального процесса не вводит распределённые leases для нескольких контейнеров/серверов. Неизвестный результат удалённой мутации должен оставаться неизвестным до проверки; автоматическое снятие блокировки только по времени небезопасно.

### 6. Чтение итогового заключения

В каждом заключении нужно различать: команда выполнилась; выбранная область проверена; обнаружено конкретное состояние; исправление применено; его эффект подтверждён новым наблюдением; риск принят до заданной даты. Успешный reload не является доказательством закрытия порта для всех сетевых путей. Повторное сетевое измерение должно выполняться с подходящей точки сети.

Встроенный обратимый автоматический workflow ограничен `closePort` и `blockIp`. Пакетные CVE имеют `remediationAvailable=false`: обновление пакетов не выполняется этим firewall-откатом. Для расширения автоматических исправлений нужен собственный проверяемый цикл каждого действия, включая область копии, проверку эффекта и восстановление.

Нулевой список CVE относится к конкретному инвентарю и снимку базы. `manual`, `unknown`, неполный охват, просроченный источник и непроверенная область должны оставаться видимыми. Старые подписанные PDF не переписываются: исправленный отчёт нужно формировать заново с новой датой и манифестом.

## Где воспроизводить исправления

Локальная совместная проверка после объединения production-исправлений:

| Проверка | Результат |
| --- | --- |
| `cd web && npm test` с настоящим Ansible 2.14.18 в PATH | 290/290, без пропусков |
| `cd web && npm run test:http` на собранном приложении | 62/62 |
| `python3 -m unittest discover -s ansible/tests -v` | 174 теста: 172 прошли, 2 нативных OpenSCAP-теста пропущены из-за отсутствия локального движка |
| `python3 -m unittest discover -s deployment/tests -v` | 9/9 |
| TypeScript и production Webpack build | Успешно |
| Ansible `--syntax-check` | 14/14 playbook |
| Настоящий Ansible task-timeout на 2.19.14 | 1/1 дополнительный независимый прогон |

Это разные уровни проверки; их числа не складываются в процент точности сканирования. Проверки полноты нативных движков, которые отсутствуют локально, подтверждаются только соответствующими CI-сценариями и их ограниченной областью. Первую локальную сборку ограниченная среда остановила на дочернем вызове TypeScript; повтор со штатным доступом к локальным дочерним процессам прошёл. Обычная Turbopack-сборка проверяется в CI.

Целевые регрессии находятся в `web/tests/remediation-execution.test.mjs`, `web/tests/ansible-task-timeout.test.mjs`, `web/tests/audit-jobs.test.mjs`, `web/tests/report-correlation.test.mjs`, `web/tests/project-report-lifecycle.test.mjs`, `web/tests/trivy-accuracy.test.mjs`, `ansible/tests/test_firewall.py`, `ansible/tests/test_package_inventory.py` и `ansible/tests/test_scanner_adapters.py`. Общие наборы выполняются обычными командами из README; subprocess-тестам нужен рабочий Node/Python, PDF renderer и Ansible. Тесты с временными файлами не запускают реальный firewall.

Нативные стенды находятся в `deployment/lab` и `deployment/tests`. Для них нужны отдельные одноразовые цели и заявленные зависимости. Пропуск нативного теста из-за отсутствия движка не считается успешным подтверждением.

## После обновления существующей установки

Новый код не восстанавливает сведения, которые прежний collector или importer уже отбросил. Для пакетного контура соберите **новый инвентарь**, затем повторите CVE-проверку. Для Greenbone повторно импортируйте исходный полный XML либо выполните новый скан; старый нормализованный JSON не содержит потерянных ошибок. Чтобы увидеть исправленную логику текущих наблюдений, сформируйте новый PDF. Исторические PDF, планы и исходники сохраняются.

При прерванной операции сначала выполните [сверку состояния](operations-recovery.md); не снимайте блокировку удалением записи БД. Обычное обновление контейнера выполняется командами из [README](../README.md#если-платформа-уже-была-запущена) с сохранением постоянного тома. Обновление GitHub само по себе не обновляет развёрнутый у пользователя контейнер.
