# Проверка перед первым самостоятельным прогоном

Обновлено 11 сентября 2026 года; даты отдельных испытаний указаны в связанных прогонах. Проверялся код HCP, инструкция установки, обработка результатов сканеров, сохранение состояния и управляемое изменение firewall. Работу разделили на шесть направлений: deployment, адаптеры сканеров, Trivy/SBOM, OpenSCAP/расписание, SSH/remediation, отчёты/журнал/API.

## Что исправлено


Дополнение по совместному тестированию страницы «Хосты», 11 сентября 2026:

- Всплывающие уведомления всех типов автоматически закрываются через 3 секунды; наведение и фокус приостанавливают таймер. Подробные результаты проверки остаются в соответствующем блоке страницы.
- Страница показывает сканирование сети, затем первоначальную подготовку SSH/sudo и открытую форму добавления. Команда выдачи ключа видна сразу и не дублирует одинаковую разрешающую строку. Общий ключ, повторное чтение и порядок замены объяснены отдельно. Подтверждение сервера находится рядом с адресом; кнопки проверки и сохранения вынесены в отдельную строку. Новая форма всегда включает sudo, в том числе после редактирования хоста без повышения прав; настройки существующих записей не меняются автоматически.
- Исправлен контракт GET discovery: успешный ответ содержит `ok: true`, отсутствие подходящей подсети остаётся подсказкой. В Docker добавлены `iproute2` и `iputils-ping`; чтение интерфейсов имеет резервный путь и обработку отказа ОС. Диапазоны по IP цели/сайта помечены как предложения /24, сеть Docker не выбирается автоматически. Выбор подсети не запускает сканирование.
- Локально прошли 98 модульных проверок, TypeScript, чистая production-сборка и 41 HTTP-проверка. Проверены порядок секций и наличие кнопок в HTML, начальное sudo, ответы API подсетей и отказ сканировать неподходящие диапазоны. Проверки включают недоступность обоих способов чтения интерфейсов. Визуальную проверку и поведение интерфейса на Ubuntu пользователя продолжаем совместно; тесты HTML её не заменяют.

## OVAL-аудит Astra: настоящий движок и HTTPS

[Прогон ffd2c72](https://github.com/Danil-super/hardening-control-platform/actions/runs/34578221343) успешно проверил новый отдельный OVAL-адаптер. Проверены реальные HTTPS-загрузка с временным доверенным сертификатом, несовпадение SHA-256, запрет перехода на другой origin. Настоящий Ansible выполнил копирование адаптера, запуск, получение отчёта и очистку на хосте Ubuntu: неподходящая ОС корректно дала неполный результат без достоверного нуля CVE. Для проверки маршрутизации по выпускам в отдельном тесте подставлялась только идентичность Astra; работа пакетного сканера оставалась настоящей.

## Встроенный профиль Astra: настоящий OpenSCAP и проверка нарушения

[Прогон ece7979](https://github.com/Danil-super/hardening-control-platform/actions/runs/34580156875) успешно выполнил оба задания: `real-openscap-engine` и `real-python35`. Исправлена выявленная настоящим движком ошибка: экспортируемые XCCDF-значения теперь явно задают `operator="equals"`, отсутствие которого вызывало аварийное завершение SCE в OpenSCAP 1.3.9.

На одноразовой Ubuntu 24.04 исходный профиль корректно вернул **18 notapplicable**. Отдельная явно изменённая фикстура идентификации выполнила весь профиль: **13 pass, 1 fail, 4 unknown**. Это успешная проверка исполнения, а не утверждение о соответствии системы: неизвестные результаты сохранены и требуют выяснения доступности наблюдений. Использованы 17 SCE-правил, одно нативное OVAL-правило и нативное CPE-условие семейства; валидация исходного XML и собранного datastream включена.

Настоящая смена прав отдельного временного файла дала **pass → fail → pass после восстановления**. Проверены совпадение исходного ARF с отчётом HCP, сохранение вывода SCE, контрольная сумма datastream вместе с кодом проверок, очистка временных каталогов и неизменность идентичности рабочей ОС. Никакого переключателя фиктивной Astra в боевой код не добавлено. Второе задание выполнило неизменённый SCE-модуль на настоящем Python 3.5.10.

## Диагностика Astra перед подключением

Флаг `--include-oval-metadata` у `hcp-host-readiness.py` формирует один JSON с готовностью хоста, сведениями локальной базы пакетов об `oval-db` и SHA-256 доступных файлов-кандидатов. Он не запускает CVE-аудит, не устанавливает пакеты и не проверяет подпись или применимость XML. Обычный режим мастера подключения не изменён. Команда и ограничения описаны в [инструкции Astra](astra-lab.md).

11 сентября команда целиком выполнена в рабочей Ubuntu-среде с Python 3.12: получен корректный JSON, отсутствие `oval-db` отражено как `not_installed`, оценка уязвимостей — `not_run`. ## Реальный UFW: применение и откат

[Прогон bac96cf](https://github.com/Danil-super/hardening-control-platform/actions/runs/34485244626) успешно выполнил настоящие плейбуки `backup-remediation`, `close-port` и `rollback-remediation` на отдельной Ubuntu 24.04 VM с работающим firewall ядра. ## Воспроизводимый прогон

Расширенные проверки полного OpenSCAP, NVD-источника Dependency-Track, firewalld и ограниченного сетевого сценария Greenbone подтверждены успешными прогонами выше. Их области проверки различаются: завершённый тест одной HTTP-цели не заменяет полный Greenbone-аудит своей ВМ. Эти сценарии не подтверждают поддержку Astra; её [инструкция](astra-lab.md) и мастер готовности явно показывают ограничения.

В [инструкции лаборатории](../deployment/lab/README.md) описаны запуск Docker-стенда и полноценный эксперимент на ВМ. `deployment/lab/verify.py --online` выполняет реальные API-вызовы и проверяет SSH/Ansible, Nmap, Lynis, Trivy online/offline и корректную ошибку неподготовленного OpenSCAP. `--check-persistence` проверяет сохранность отчётов и настройки базы после перезапуска. Результат сохраняется в `.lab/verification.json`.

Этот сценарий выполняется в GitHub Actions как job `lab`; OpenSCAP, Dependency-Track и UFW имеют отдельные workflows. Выше приведены ссылки на реально успешные прогоны и границы каждого испытания. Наличие workflow в репозитории само по себе не означает, что он выполнился успешно.

Для окончательного протокола диплома необходимо выполнить на своём стенде:

1. Полный выбранный OpenSCAP-профиль на своей ВМ с подходящим для точного выпуска ОС datastream, реальным нарушением и временным исключением.
2. Реальный Greenbone-аудит ВМ с актуальными feeds и сверку импортированных адресов, OID, CVE и QoD.
3. Актуализацию выбранных источников Dependency-Track и завершение анализа реального SBOM в его интерфейсе. Обратный импорт результатов в HCP пока отсутствует; подтверждённый приём SBOM не заменяет этот этап.
4. Повторение проверенного UFW/firewalld-цикла через интерфейс HCP на своей ВМ: baseline → dry-run → применение → Nmap с control node → откат → повторный Nmap. Подтвердить сохранение новых SSH-подключений и сохранить снимок ВМ. Испытания Ubuntu CI не заменяют этот эксперимент на Astra и не подтверждают сетевой IPv6.
5. Проверку нескольких CVE по advisory поставщика и сравнение времени ручного/автоматизированного выполнения одного набора действий.

## Ограничения и обновление существующей установки

- Основной CVE-сценарий — системные пакеты Debian/Ubuntu. RPM-результаты частичные; приложения и контейнеры требуют отдельного SBOM.
- Базовая SSH-проверка оценивает глобальные настройки. Условия `Match`, наследование настроек nginx/Apache и актуальность пакетного cache требуют отдельного решения администратора.
- Статический inventory использует явные alias, группы, `[group:children]` и `[group:vars]`. Диапазоны вида `node[1:9]` и запись порта в alias не поддерживаются; порт задавайте через `ansible_port`. Установка `unattended-upgrades` сама по себе не подтверждает, что его timer активен.
- Временный Lynis не следует запускать одновременно с независимым Lynis на той же машине: проверка PID-файла не устраняет гонку с внешним процессом.
- Firewalld с различающимися runtime/permanent настройками блокируется до их согласования. Backup старого формата требует ручного восстановления.
- Старые записи журнала сохраняются и помечаются как HMAC v1 с ограниченной защитой вложенных данных; их нельзя задним числом объявить защищёнными по v2.
- Перед обновлением сохраните постоянные тома. Bind-mounted `ansible/inventory.ini` теперь служит начальным образцом; рабочий файл — `/var/lib/hcp/inventory.ini` в томе HCP.
- API удаления отчётов отключён для сохранения исходных свидетельств. Политика архивирования и хранения больших объёмов данных остаётся отдельной задачей.

Подробности источников данных и сетевых требований: [интеграции аудита](audit-integrations.md). Установка: [README](../README.md).
