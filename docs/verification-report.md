# Проверка перед первым самостоятельным прогоном

Дата: 10 сентября 2026 года. Проверялся код HCP, инструкция установки, обработка результатов сканеров, сохранение состояния и управляемое изменение firewall. Работу разделили на шесть направлений: deployment, адаптеры сканеров, Trivy/SBOM, OpenSCAP/расписание, SSH/remediation, отчёты/журнал/API.

## Что исправлено

| Область | Обнаруженная проблема | Результат исправления |
| --- | --- | --- |
| Установка | Недоступный для записи inventory, неявный путь SSH-ключа, потеря доверия лабораторного хоста | Рабочий inventory в постоянном томе; явный Ansible key; проверка ключа и сохранение host key |
| Trivy | `fixed` считался безопасной установленной версией; неполные сведения ОС/source package; пустой JSON давал нулевой риск | Исправлена трактовка статуса, контракт SBOM и проверка покрытия; ограничение поддержки явно отражено |
| История CVE | Повторное сопоставление одного инвентаря перезаписывало отчёт и SBOM | Уникальные файлы каждого запуска, запрет перезаписи, ссылка на исходный инвентарь |
| Базы | Дата копирования файла могла считаться датой актуальности | Проверяются непустой файл базы и `UpdatedAt`; неизвестность/просрочка сохраняется в отчёте |
| SSH/Nmap/Lynis/OpenSCAP | Ошибки и пустые результаты могли выглядеть успешными; находки молча обрезались | Проверка формата/завершения, явная неполнота, сохранение всех результатов |
| Реальный запуск SSH/Lynis | Debian ssh-audit 2.5 не поддерживал необходимый JSON/флаг; временная копия Lynis не имела каталога плагинов | Закреплён ssh-audit 3.3.0 и предварительная проверка CLI; Lynis получает изолированный каталог и ограниченную диагностику запуска |
| Базовый Ansible-аудит | Ошибки системных команд маскировались; privileged Docker определялся неверно | Ошибки становятся неполными проверками; Docker анализируется по JSON |
| Greenbone | Находки чужих адресов приписывались выбранному хосту | Проверка цели, фильтрация чужих результатов, QoD и время исходного сканирования |
| Dependency-Track | HTML с HTTP 200 принимался за успех; не проверялась принадлежность SBOM | Проверяются хост, компоненты и токен очереди; загрузка не считается завершённым анализом |
| OpenSCAP | Группы разбирались неверно; scheduler игнорировал политики; исключения скрывали нарушения | Политика выбирается для каждого хоста; исключения сохраняют исходные результаты и риски |
| Firewall | UFW мог пропустить вставку DENY при существующем ALLOW с кодом успеха; ошибки firewalld/rollback скрывались | Удаление только точных конфликтующих правил, prepend и проверка приоритета IPv4/IPv6; действительный dry-run, проверка backup и повторяемый откат |
| Журнал | Подпись не защищала вложенные значения; параллельные записи могли нарушить цепочку | Рекурсивная HMAC v2, транзакции SQLite, проверка конкурирующих процессов |
| API | Старый запуск обходил основной workflow; discovery обходил мастер; DELETE стирал evidence | Единый маршрут запуска, добавление через мастер, запрет удаления отчётов через API |
| Представление | CVE давались как процент защищённости; совпадение порта считалось подтверждением; находки считались событиями | Убраны искусственные оценки, исправлены корреляция/счётчики, ручная оценка отделена от ошибки сбора |

## Реальный OpenSCAP на отдельной ВМ

[Прогон 36f98c1](https://github.com/Danil-super/hardening-control-platform/actions/runs/34483202494) успешно выполнил `openscap-audit.yml` на одноразовой Ubuntu 24.04 VM с настоящим OpenSCAP и официальным ComplianceAsCode 0.1.79. ZIP проверен по закреплённой SHA-256. В datastream добавлен отдельный приёмочный профиль, выбирающий шесть неизменённых OVAL-проверок SSG: права/владелец/группа `/etc/passwd`, права `/etc/shadow`, GID root и отсутствие других UID 0.

Получены **6 результатов passed**, `partial=false`; проверены точные ID правил, профиль, группа, checksum и время файла content. Системные настройки ВМ не менялись. В артефакте `openscap-six-rule-acceptance` сохранены происхождение content, версии, отчёт и журнал плейбука. Это подтверждает работу сканера и интеграции на шести правилах, **не прохождение полного CIS-профиля**. Прогон также выявил и помог исправить несовместимость строковых `when` с новой Ansible: условия теперь возвращают boolean.

## Полный официальный профиль OpenSCAP

[Прогон ab0f454](https://github.com/Danil-super/hardening-control-platform/actions/runs/34494211741) успешно выполнил исходный `xccdf_org.ssgproject.content_profile_cis_level1_server` из того же SSG 0.1.79 на Ubuntu 24.04. Полный datastream не изменялся, ограничение `--rule` не использовалось. Из 639 правил benchmark выбраны **405**: **221 pass, 121 fail, 63 notapplicable**; остальные 234 имеют `notselected`. Ошибок `error/unknown/notchecked` нет, `partial=false`. Нарушения конфигурации эталонной GitHub-ВМ не считаются ошибкой исполнения теста и не выдаются за успешное соответствие CIS.

Все результаты нормализованного отчёта сверены с исходным ARF, включая ID, статусы, количества, профиль и checksum. Отдельный контрольный профиль из шести неизменённых правил обнаружил добавленный бит выполнения в правах `/etc/passwd`: **1 fail и 5 pass**. После восстановления исходных прав получены **6 pass**. Настоящий обработчик исключений сохраняет исходный `failed`, риск, evidence и итоги; просроченные и чужие исключения не применяются, повторная обработка идемпотентна.

Ранние прогоны выявили отдельную проблему выгрузки root-owned отчёта с mode 0600; исправлена передача владельца только CI-артефактов, права боевых отчётов не ослаблены. **Результат подтверждает выполнение полного указанного профиля на Ubuntu, но не его применимость к Astra и не индивидуальную точность каждого правила.**

## Реальный UFW: применение и откат

[Прогон bac96cf](https://github.com/Danil-super/hardening-control-platform/actions/runs/34485244626) успешно выполнил настоящие плейбуки `backup-remediation`, `close-port` и `rollback-remediation` на отдельной Ubuntu 24.04 VM с работающим firewall ядра. HTTP-сервис слушал тестовый порт 8088 на bridge-адресе ВМ; отдельный Docker-клиент проверял его доступность по IPv4.

Подтверждены все девять наблюдений: исходная доступность, доступность при активном разрешающем UFW, неизменная доступность после preview, неизменная конфигурация после preview, недоступность после DENY, продолжающий работать локальный HTTP-сервис, идемпотентное повторное применение, восстановление доступности после rollback и точное восстановление файлов конфигурации. Cleanup вернул исходный неактивный UFW и удалил временные Docker-ресурсы.

Во время испытаний обнаружена особенность [UFW](https://github.com/jdstrand/ufw/blob/main/src/backend_iptables.py): вставка правила с существующей комбинацией адресов/порта может быть пропущена с `rc=0`, даже если требуется другой action. HCP теперь удаляет только точные конфликтующие входящие правила, ставит DENY через `prepend` и проверяет его первым для IPv4 и включённого в UFW IPv6. Широкие разрешения, другие порты и правила OUT/FWD не удаляются. Поддерживаются оба формата вывода входящего действия: `DENY` и `DENY IN`.

Артефакт `ufw-kernel-acceptance` содержит протокол, контрольные суммы конфигурации и журналы. Этот тест **не подтверждает живой firewalld, сетевую доступность по IPv6, сохранение реальной SSH-сессии или работу интерфейса транзакций на удалённой ВМ**: здесь плейбуки выполнялись с `ansible_connection=local`. Эти границы учитываются при самостоятельном эксперименте ниже.

## Реальный firewalld: сетевой эффект и SSH

[Прогон ab0f454](https://github.com/Danil-super/hardening-control-platform/actions/runs/34494211525) успешно выполнил **17 проверок** на отдельной Ubuntu 24.04 с firewalld 2.1.1. Клиент находился в изолированном network namespace; настоящие плейбуки HCP передавались по SSH на отдельный порт 2228 с проверкой host key и `StrictModes=yes`.

Подтверждены backup, preview без изменения файлов/runtime, блокировка HTTP 8088 при работающем сервере, неизменность повторного применения, сохранение запрета после reload и точный откат файлов/runtime. Новые SSH-подключения проходят после apply, reload и rollback. Четыре попытки закрыть управляющий SSH-порт или заблокировать адреса управления/цели отклонены без изменения firewall. Очистка возвращает исходное состояние служб и удаляет временные ключи.

Живое испытание выявило ошибку HCP: одинаковые зоны runtime/permanent могли выводиться в разном порядке и с разными маркерами активности. Сравнение теперь учитывает содержимое независимых блоков, сохраняя порядок правил и значения. Дополнительно сравниваются политики firewalld на версиях с policy API; различия runtime/permanent остаются причиной отказа от изменения. Новые регрессионные проверки подтверждают отказ при изменении target, interface, правила и порядка rich rules.

Артефакт `firewalld-kernel-acceptance` сохраняет протокол, результаты трафика и журналы. **Область: Ubuntu 24.04 и сетевой IPv4. Astra и доступность по IPv6 этим запуском не проверены.**

## Воспроизводимый прогон

Расширенные проверки полного OpenSCAP, NVD-источника Dependency-Track и firewalld подтверждены успешными прогонами выше. Отдельный `greenbone.yml` выполняет официальный VT на собственной HTTP-цели; до фиксации успешного результата он не считается проверенным. Эти сценарии не подтверждают поддержку Astra; её [инструкция](astra-lab.md) и мастер готовности явно показывают ограничения.

В [инструкции лаборатории](../deployment/lab/README.md) описаны запуск Docker-стенда и полноценный эксперимент на ВМ. `deployment/lab/verify.py --online` выполняет реальные API-вызовы и проверяет SSH/Ansible, Nmap, Lynis, Trivy online/offline и корректную ошибку неподготовленного OpenSCAP. `--check-persistence` проверяет сохранность отчётов и настройки базы после перезапуска. Результат сохраняется в `.lab/verification.json`.

Этот сценарий выполняется в GitHub Actions как job `lab`; OpenSCAP, Dependency-Track и UFW имеют отдельные workflows. Выше приведены ссылки на реально успешные прогоны и границы каждого испытания. Наличие workflow в репозитории само по себе не означает, что он выполнился успешно.

Для окончательного протокола диплома необходимо выполнить на своём стенде:

1. Полный выбранный OpenSCAP-профиль на своей ВМ с подходящим для точного выпуска ОС datastream, реальным нарушением и временным исключением.
2. Реальный Greenbone-аудит ВМ с актуальными feeds и сверку импортированных адресов, OID, CVE и QoD.
3. Актуализацию выбранных источников Dependency-Track и завершение анализа реального SBOM в его интерфейсе. Обратный импорт результатов в HCP пока отсутствует; подтверждённый приём SBOM не заменяет этот этап.
4. Повторение проверенного UFW/firewalld-цикла через интерфейс HCP на своей ВМ: baseline → dry-run → применение → Nmap с control node → откат → повторный Nmap. Подтвердить сохранение новых SSH-подключений и сохранить снимок ВМ. Испытания Ubuntu CI не заменяют этот эксперимент на Astra и не подтверждают сетевой IPv6.
5. Проверку нескольких CVE по advisory поставщика и сравнение времени ручного/автоматизированного выполнения одного набора действий.

## Ограничения и обновление существующей установки

- Основной CVE-сценарий — системные пакеты Debian/Ubuntu. RPM-результаты частичные; приложения и контейнеры требуют отдельного SBOM.
- Базовая SSH-проверка оценивает глобальные настройки. Условия `Match`, наследование настроек nginx/Apache и актуальность пакетного cache требуют отдельного решения администратора.
- Статический inventory использует явные alias, группы, `[group:children]` и `[group:vars]`. Диапазоны вида `node[1:9]` и запись порта в alias не поддерживаются; порт задавайте через `ansible_port`. Установка `unattended-upgrades` сама по себе не подтверждает, что его timer активен.
- Временный Lynis не следует запускать одновременно с независимым Lynis на той же машине: проверка PID-файла не устраняет гонку с внешним процессом.
- Firewalld с различающимися runtime/permanent настройками блокируется до их согласования. Backup старого формата требует ручного восстановления.
- Старые записи журнала сохраняются и помечаются как HMAC v1 с ограниченной защитой вложенных данных; их нельзя задним числом объявить защищёнными по v2.
- Перед обновлением сохраните постоянные тома. Bind-mounted `ansible/inventory.ini` теперь служит начальным образцом; рабочий файл — `/var/lib/hcp/inventory.ini` в томе HCP.
- API удаления отчётов отключён для сохранения исходных свидетельств. Политика архивирования и хранения больших объёмов данных остаётся отдельной задачей.

Подробности источников данных и сетевых требований: [интеграции аудита](audit-integrations.md). Установка: [README](../README.md).
