# Подтверждённые измерения Astra Linux SE 1.8 на нативных ВМ

**Источник:** <https://github.com/Danil-super/hardening-control-platform/actions/runs/40716626983> (28 октября 2026 года). Данные повторно извлечены из **двух настоящих GitHub Actions артефактов** `astra-vm-1.8.1` и `astra-vm-1.8.6`, включая `protocol.json`, исходные JSON профиля и XML ARF. Гости запускались в QEMU/KVM с собственным ядром и пакетной базой Astra; это не подменённый `os-release` Ubuntu.

Распакованные файлы и вычисленные SHA-256 служат доказательствами **конкретных** нативных тестов; никакие чужие серверы и пользовательские ОС не проверялись. Источники не подтверждают Astra 1.7, редакцию max, другие архитектуры, сертификационное соответствие или полное CVE-покрытие.

## Фактическая динамика базового профиля

| Состояние | Astra SE 1.8.1 | Astra SE 1.8.6 |
| --- | --- | --- |
| Исходный запуск | 14 pass / 4 fail | 14 pass / 4 fail |
| Контрольное нарушение прав `/etc/passwd` | 13 pass / 5 fail | 13 pass / 5 fail |
| После восстановления исходных прав | 14 pass / 4 fail | 14 pass / 4 fail |
| Изменившееся правило | `openscap_xccdf_org.hcp_rule_passwd_permissions` | то же |
| Нарушение → восстановление | 1 переход fail → pass | 1 переход fail → pass |
| Регрессии относительно исходного состояния после восстановления | 0 по выбранным 18 правилам | 0 по выбранным 18 правилам |

Значения получены сравнением точных идентификаторов всех 18 нормализованных правил, а не вычитанием счётчиков без сверки. Указанные изменения были **введены намеренно** в одноразовых ВМ, затем восстановлены. Это проверка чувствительности и повторяемости конкретного контроля, а **не** доказательство устранения всех рисков или измерение экономии времени на эксплуатации.

| SHA-256 JSON после восстановления | `5ac82b9379692ef9dd605d85a3fa7d5509c2483e617c29e8ec7f1d73756dc6b8` | `16335cb02f40416f204a84212384eb8681f54cd98c47646e25e6565e716ef7ff` |

Оба выпуска фиксируют один и тот же **хеш исходного пакета правил** `bundle-sha256:d5dcd96987d288da7ca92bfcfced2b1cfc3b51f787821870ed14a49c9b0416b7`. При этом SHA-256 заново скомпилированного datastream различается между запуском и восстановлением, поскольку в `ds:component timestamp` вносятся временные метки. Побайтовая сверка оригинальных XML после исключения именно этих служебных timestamp-полей подтверждает одинаковое содержимое правил во всех фазах. Поэтому методика эксперимента сравнивает `scanner.contentIdentity`, сохраняет исходные SHA-256 обоих исполнявшихся datastream и отдельно проверяет одинаковые ID правил.

## CVE-контроль

- В обоих гостях реально обработано **8 284 из 8 284** определений выбранной OVAL-базы. Исходный SHA-256 базы: `3ba7e4c8126be503fc95bb916f2d9b45306869bd0f58f200abc5b1e1effbbe3d`.
- Контрольное определение `CVE-2024-5535` с нативным сравнением версии пакета действительно сработало на Astra 1.8.1 (`true`), но не сработало на 1.8.6 (`false`). Успех этого контроля не оценивает полноту обнаружения остальных CVE.
- Независимая аутентификация доверенного набора ключей производителя только из этих файлов **не доказана**. Шестнадцатеричная контрольная сумма подтверждает байты, но не издателя. Никакие корректировки пакетов на базе этих результатов автоматически не разрешаются.

## Ограничения использования в дипломе

Результаты применимы как **реальные экспериментальные наблюдения для Astra 1.8.1 и 1.8.6 на тестовых гостях**. Они не могут служить результатами испытаний на Astra 1.7.6.15. Для основной защищаемой конфигурации следует выполнить отдельный опыт по [протоколу Astra](astra-experiment-acceptance.md) и сохранить исходные JSON, ARF и происхождение источников. Нельзя выводить точность сканера, скорость устранения уязвимостей, снижение риска в процентах или полноту всех CVE на основе одного контрольного правила.
