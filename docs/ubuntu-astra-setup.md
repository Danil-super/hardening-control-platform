# Стенд: Ubuntu управляет хостами Astra Linux

Это единая основная инструкция установки и подключения хостов. README и страница «Инструкция» на сайте ссылаются на этот порядок. Для уже добавленного хоста используйте [обновление административного доступа](#existing-host).

Основной маршрут установки для схемы **HCP на Ubuntu → аудит Astra Linux по SSH**. Для первой установки используйте Docker Engine и Compose на Ubuntu. Ansible и инструменты управляющей машины уже входят в образ HCP; системный Python Ubuntu не используется как Python проверяемой Astra.

| Где | Что устанавливается и хранится |
| --- | --- |
| Ubuntu | Git, Docker Engine, Compose; контейнер HCP, интерфейс, отчёты, SQLite, отдельные приватные SSH-ключи хостов |
| Каждая Astra | Работающий SSH-сервер, совместимый Python 3 и административная учётная запись с разрешённым парольным входом для первой настройки |
| Astra для OVAL/OpenSCAP | Дополнительно OpenSCAP; для профиля HCP нужна поддержка SCE, для CVE — подходящий XML OVAL |
| Внешнее хранилище | Копии данных HCP, его секретов и образа; отдельно резервные копии или снимки Astra |

Docker на Astra для этого сценария не нужен. Greenbone и Dependency-Track — отдельные интеграции; сначала проверьте основной маршрут на одном хосте, затем подключайте их по [инструкции интеграций](audit-integrations.md).

## 1. Ubuntu: подготовка

Для первого стенда рекомендуется Ubuntu 24.04 LTS x86-64, 4 vCPU, 8 ГБ RAM и свободное место под образы, отчёты и резервную копию. Ресурсы Greenbone/Dependency-Track в эту оценку не входят. Другую версию Ubuntu сначала сверяйте с [поддержкой Docker](https://docs.docker.com/engine/install/ubuntu/); она не определяет номер выпуска целевой Astra.

На Ubuntu:

```bash
sudo apt update
sudo apt install -y git openssh-client openssl curl ca-certificates
```

Установите Docker Engine и плагин Docker Compose по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/#install-using-the-apt-repository). При существующей установке сначала проверьте её; повторно устанавливать Docker не требуется.

```bash
sudo docker version
sudo docker compose version
sudo docker info >/dev/null
```

Нужен работающий Docker daemon и Compose 2.20 или новее. Здесь команды Docker выполняются через `sudo`, поэтому добавлять пользователя в группу `docker` не требуется.

Первоначальная сборка требует интернета на Ubuntu: GitHub, реестры контейнеров, Debian APT, npm и PyPI. Для изолированной установки подготовьте образ и базы заранее; одно наличие Git-репозитория этого не заменяет. После установки базовые SSH-проверки работают по локальной сети.

## 2. Ubuntu: установка HCP

Команды ниже предназначены для **первой установки**. При обновлении не создавайте повторно ключи и `.env`.

```bash
git clone https://github.com/Danil-super/hardening-control-platform.git
cd hardening-control-platform
cp .env.production.example .env
cp ansible/inventory.example.ini ansible/inventory.ini
mkdir -p secrets
chmod 700 secrets
install -m 600 /dev/null secrets/known_hosts
chmod 600 .env secrets/known_hosts
```

Откройте `.env` в редакторе. Замените `HCP_ADMIN_PASSWORD`, `HCP_AUTH_SECRET`, `HCP_AUDIT_HMAC_KEY`, `HCP_SCHEDULE_API_KEY` отдельными случайными значениями. Каждое можно получить командой `openssl rand -base64 48`. Пароль Dependency-Track понадобится при включении этой интеграции. Сохраните `.env`: эти значения необходимы и для восстановления.

Оставьте `HCP_BIND_ADDRESS=127.0.0.1`, `HCP_PORT=3000`. В `HCP_CONTROL_IPS` укажите IPv4 Ubuntu, через который она обращается к Astra; несколько адресов разделяются запятыми. Это дополнительная защита от их блокировки в интерфейсе.

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build --wait --wait-timeout 180 hcp
sudo docker compose ps
sudo docker compose logs --tail=80 hcp
```

Ожидается статус `healthy`. Откройте <http://127.0.0.1:3000> в браузере **на Ubuntu** и войдите с `HCP_ADMIN_PASSWORD`. Долгая первая сборка допустима; если команда завершилась ошибкой, сначала разберите журнал. Для просмотра потока журнала используйте `sudo docker compose logs -f hcp`; `Ctrl+C` завершает просмотр, а не контейнер.

Если браузер находится на другом компьютере, выполните на нём `ssh -N -L 3000:127.0.0.1:3000 user@IP_UBUNTU` (замените `user` и `IP_UBUNTU` на пользователя и адрес управляющей Ubuntu) и откройте тот же адрес браузера. Привязку панели к loopback менять не требуется.

### Если контейнер healthy, но вход не работает

`healthy` подтверждает, что контейнер отвечает на запрос страницы `/login`. Это не проверка отправки пароля из браузера и сохранения сеанса.

В версии до исправления от 16 сентября 2026 года вызов браузерного `fetch` мог завершаться `TypeError: Illegal invocation` ещё до отправки запроса. Интерфейс показывал «Нет связи с платформой». Обновите проект из его каталога на Ubuntu:

```bash
git pull --ff-only
sudo docker compose up -d --build --wait --wait-timeout 180 hcp
```

После обновления перезагрузите страницу через `Ctrl+Shift+R` и повторите вход с `HCP_ADMIN_PASSWORD`. Если ошибка сохранилась, откройте инструменты разработчика (`F12`), вкладки Console и Network, затем повторите вход. Для диагностики достаточно текста ошибки, адреса страницы, названия браузера и HTTP-статуса запроса `/api/ansible/auth/login` (либо отметки, что запрос отсутствует). Не передавайте пароль, содержимое `.env`, тела запросов и значения cookies.

## 3. Сеть Ubuntu → Astra

Ubuntu и контейнер HCP должны достигать SSH-порта Astra. Если Astra запущена в VirtualBox на этой Ubuntu, для первого стенда подходит **Host-only** адаптер; дополнительный NAT можно использовать для обновлений. **Internal Network** связывает гостевые ВМ между собой и сама по себе не подключает к ним Ubuntu-хост. Для HCP в отдельной Ubuntu-ВМ подключите обе ВМ к одной внутренней сети. Один NAT без маршрута или проброса порта не обеспечивает входящий SSH к Astra.

Различия режимов описаны в [документации VirtualBox](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/networkingdetails.html).

На Astra через её консоль узнайте адрес: `hostname -I`. На Ubuntu проверьте маршрут командой `ip route get IP_ASTRA`, затем из каталога HCP:

```bash
sudo docker compose exec --user node -T hcp nmap -Pn -sT -p 22 IP_ASTRA
```

Замените `IP_ASTRA` и `22` фактическим адресом и SSH-портом. Ожидается `open`. Эта проверка подтверждает доступность порта, но ещё не ключ, Python и sudo.

<a id="host-onboarding"></a>
## 4. Единый порядок подключения Astra

**Сканирование сети → выбор хоста → пользователь и пароль → «Подключить хост».** Вручную входить через терминал и создавать пару не нужно. Платформа сначала входит на Astra по паролю, после этого создаёт и устанавливает ключ, проверяет его и сама сохраняет хост. HCP создаёт для каждого подключения отдельную случайную пару Ed25519 на управляющей Ubuntu. На Astra передаётся только публичный ключ; приватный остаётся в HCP. Копировать команду добавления ключа вручную не нужно.

Для первой настройки нужны доступный SSH-сервер, существующий пользователь Astra и разрешённый вход его паролем. HCP не создаёт учётную запись и не включает парольную аутентификацию на закрытом сервере. Если такого доступа нет, его предоставляет администратор машины по вашей политике. Постоянный агент на Astra не устанавливается.

### 4.1. Найдите хост и заполните параметры

На странице **«Хосты»** сначала расположен блок **«1. Сканирование сети»**. «Подставить подсеть» предлагает диапазон, но не запускает поиск. В Docker HCP не видит все интерфейсы Ubuntu: сеть контейнера не подставляется автоматически. Предложение по IP хоста или сайта ограничено /24 и требует проверки. Можно вручную задать свою подсеть от /24 до /30. Поиск проверяет порт 22; для другого порта или известного адреса сразу используйте форму ниже.

Выберите найденную машину. В блоке **«2. Подключение по паролю»** основные поля — **адрес Astra, администратор Astra и пароль администратора Astra**. Адрес подставляется из результатов поиска; пользователь и пароль относятся к учётной записи на целевой машине.

В **«Дополнительных параметрах»** можно изменить:

| Параметр | Значение по умолчанию |
| --- | --- |
| Имя в списке | Определяется по адресу, например `host-192.168.1.10`; своё имя необязательно |
| Порт SSH | `22` |
| Группа хостов | `linux_hosts`; для общих политик Astra можно выбрать `astra_hosts` |

### 4.2. Подключите хост на сайте

Откройте HCP через **HTTPS** либо `http://127.0.0.1:3000` на Ubuntu. Для браузера на другом компьютере используйте SSH-туннель из раздела 2. При обычном HTTP по сети ввод пароля недоступен.

1. Введите логин и пароль администратора Astra: root с разрешённым SSH-входом **или обычную административную учётную запись, которой разрешено выполнить `sudo` со своим паролем**. Это не пароль входа в саму панель HCP. Если пароль для `sudo` отличается от пароля SSH, раскройте одноимённое дополнительное поле.
2. Нажмите **«Подключить хост»**. Для учётной записи не root HCP один раз использует этот пароль для `sudo`, создаёт проверенное правило `sudoers` для последующей работы по уникальному ключу и затем проверяет права автоматически.

HCP выполняет действия последовательно: **входит по паролю → создаёт отдельную пару на Ubuntu → устанавливает публичный ключ на Astra → для пользователя не root один раз настраивает `sudo` → проверяет новое подключение по ключу, Python и права root → сохраняет хост**. Отдельно нажимать «Создать ключ», «Проверить подключение» или «Добавить хост» не требуется. Индикатор на кнопке показывает текущий этап.

Если сервер ещё не подтверждён, форма раскроет «Проверка Astra перед первым входом» из подраздела 4.3 **до отправки пароля**. Введённый пароль пока останется только в форме браузера. После подтверждения нажмите «Подключить хост» ещё раз; заново вводить пароль не нужно. При фактической отправке пароля поле очищается. Пароль не записывается в inventory, SQLite, журналы или файлы HCP. Правило `sudoers` остаётся на Astra для плановых аудитов и удаляется кнопкой завершения работ вместе с ключом HCP.

Для HTTPS reverse proxy задайте `HCP_TRUSTED_TLS_PROXY=true` только если HCP доступен исключительно через доверенный прокси, который сам устанавливает `X-Forwarded-Proto: https`. Сохраните loopback-привязку контейнера. Для обычного HTTP и локального SSH-туннеля эта настройка не нужна.

### 4.3. Проверка Astra перед первым входом

**Сначала сверяется ключ сервера, затем HCP передаёт пароль администратора.** Получить публичный ключ по сети можно до входа в учётную запись. Если нажать «Подключить хост» раньше подтверждения сервера, форма остановится на этом шаге; пароль ещё не будет передан.

Проверяем один и тот же ключ **целевой Astra**, полученный двумя способами:

| Источник | Что он показывает |
| --- | --- |
| Доверенная консоль целевой Astra или реестр администратора | Отпечаток ключа нужного сервера |
| HCP на управляющей Ubuntu | Отпечаток ключа, полученного с указанного адреса по сети |

Эти значения должны совпасть для одного типа ключа. Отпечаток собственного ключа Ubuntu здесь не используется. Индивидуальная пара, которую HCP создаст после парольного входа для дальнейшего доступа, — другой ключ и другой этап.

1. На сайте раскройте **«Проверка Astra перед первым входом»**. Проверьте адрес и порт целевой Astra.
2. Получите отпечаток из реестра администратора или откройте доверенную консоль **именно этой Astra** — например, окно ВМ в гипервизоре. Выполните:

```bash
for key in /etc/ssh/ssh_host_*_key.pub; do
  [ -f "$key" ] && ssh-keygen -lf "$key" -E sha256
done
```

3. Скопируйте **одно значение `SHA256:…`**, без длины ключа, пробелов, комментария и названия алгоритма. Вставьте его в поле **«Отпечаток из консоли Astra или реестра»**.
4. Нажмите **«Сверить и сохранить»**. HCP сам получит ключ с указанного адреса, вычислит отпечаток и сохранит ключ только при совпадении. Предварительно нажимать «Получить отпечатки по сети» не нужно: эта кнопка осталась для просмотра подробностей.
5. После успешной сверки нажмите **«Подключить хост»**. HCP проверит сохранённый ключ при SSH-соединении, выполнит парольный вход и продолжит установку индивидуальной пары.

Команда только читает существующие публичные ключи. Она не создаёт ключи и не выполняет вход по SSH. Если строк несколько, достаточно одного ключа, используемого SSH-сервером. При ручном сравнении сверяйте одинаковый алгоритм: ED25519 с ED25519, RSA с RSA. Несовпадение разных типов ключей нормально.

Если команда ничего не вывела, администратор проверяет действующие пути `HostKey` через `sudo /usr/sbin/sshd -T` с используемой конфигурацией; при запуске sshd с другим конфигурационным файлом необходимо указать его через `-f`. Публичный файл или его каталог может отличаться от стандартного. Отсутствие `/etc/ssh/ssh_host_ed25519_key.pub` само по себе не доказывает отсутствие рабочего SSH.

Ключ, полученный только сетевым сканированием, не подтверждает подлинность. Не используйте новый, ещё не проверенный SSH-сеанс как независимый источник отпечатка. HCP хранит проверенный ключ в `/var/lib/hcp/known_hosts` и сверяет его автоматически при следующих подключениях; неожиданный изменённый ключ блокирует аутентификацию. [Описание ssh-keyscan](https://man.openbsd.org/ssh-keyscan), [показ отпечатка ssh-keygen](https://man.openbsd.org/ssh-keygen#l).

<a id="host-trust-fleet"></a>
#### Если хостов много

Сверка нужна при первоначальном установлении доверия, а не при каждом аудите. Администратор может собрать ключи после их индивидуальной генерации при развёртывании машин либо через уже доверенную систему управления. В реестре сохраняют **адрес или имя, порт SSH, тип ключа, отпечаток и источник подтверждения**. При добавлении хоста в HCP оператор берёт соответствующий отпечаток из этого реестра; открывать консоль каждой ВМ заново не требуется. Простое сканирование сети реестр доверенных ключей не заменяет.

Для **первого запуска новой установки HCP** уже проверенные публичные ключи всех серверов можно заранее записать в `secrets/known_hosts`. Это файл формата OpenSSH с адресом, типом и полным публичным ключом; таблица из одних отпечатков для него не подходит. Адрес или имя должны совпадать с тем, что вводится в HCP; для нестандартного порта используется `[адрес]:порт`. Содержимое переносится в постоянный том, только пока рабочий `known_hosts` пуст. После этого мастер находит сохранённое доверие автоматически.

На уже работающей установке изменение `secrets/known_hosts` не дополняет непустой рабочий файл автоматически. Сейчас массового импорта через сайт нет: для новых адресов используйте форму и доверенный реестр. Не заменяйте существующий рабочий `known_hosts`, чтобы не потерять ранее установленные связи доверия. SSH-сертификаты от общего центра — возможный дальнейший вариант для большого парка; мастер HCP пока работает с отдельными ключами серверов.

<a id="sudo-access"></a>
### 4.4. Административный доступ

Форма подключения предназначена для полного административного режима. HCP проверяет запуск настоящего модуля Ansible с результатом `id -u = 0`; недостаточные права блокируют сохранение подключения в этом режиме.

| Учётная запись | Требование |
| --- | --- |
| root | Разрешённый вход по SSH; отдельная настройка sudo не нужна |
| Другой администратор | Разрешённый `sudo` с паролем при первом подключении; HCP настроит свой `sudoers` для последующих заданий |

При входе по SSH как root Ansible по умолчанию пропускает повторное повышение до того же пользователя: [BECOME_ALLOW_SAME_USER](https://docs.ansible.com/projects/ansible/latest/reference_appendices/config.html#become-allow-same-user).

Пароль SSH нужен для первой установки индивидуального ключа и не сохраняется. Для пользователя не root HCP использует пароль SSH как пароль `sudo` только в этом запросе (или отдельное значение из раскрытого поля), создаёт файл `/etc/sudoers.d/zz-hcp-<ID ключа>` и проверяет его через `visudo`. Файл содержит правило полного повышения `пользователь ALL=(root) NOPASSWD: ALL` и точечное `Defaults:пользователь !requiretty`: второе нужно для плановых Ansible-заданий на защищённых конфигурациях Astra, где `sudo` требует терминал. Исключение действует только для подключённой учётной записи HCP. Контролируйте доступ к HCP и к этой учётной записи как к привилегированным. При завершении работ HCP удаляет только свой файл с совпадающим ID и точным содержимым; другие правила `sudo` не затрагиваются.

До подключения для диагностики под **тем же пользователем SSH** на Astra выполните `id -u`. Для root результат уже `0`. Для другого администратора убедитесь, что интерактивное повышение разрешено:

```bash
sudo -k id -u
```

Ожидается `0` после ввода пароля. После успешного подключения `sudo -k -n id -u` также должен вернуть `0` без запроса: HCP дополнительно проверяет настоящий модуль Ansible, а не только команду `id`.

Если политика Astra запрещает HCP создавать файл в `/etc/sudoers.d`, администратор может подготовить отдельную техническую учётную запись и правило вручную. Например, для `hcp-audit` (замените на фактическое имя):

```bash
visudo -f /etc/sudoers.d/zz-hcp-audit
```

Содержимое правила полного административного доступа:

```sudoers
Defaults:hcp-audit !requiretty
hcp-audit ALL=(root) NOPASSWD: ALL
```

Затем в том же root-сеансе:

```bash
chown root:root /etc/sudoers.d/zz-hcp-audit
chmod 440 /etc/sudoers.d/zz-hcp-audit
visudo -c
```

Каталог должен подключаться основным sudoers; после проверки синтаксиса проверьте результат под целевым пользователем. Правило только для `id` не обеспечивает запуск временных Python-модулей Ansible. При отказе PAM/PARSEC администратор проверяет политику конкретной Astra; HCP не отключает её защитные механизмы.

### 4.5. Результат подключения

После успешной проверки появится сообщение **«Хост подключён и добавлен в список»**. Для сохранения через форму нужны рабочие SSH, совместимый Python и успешный запуск Ansible с правами root. Отсутствие дополнительных сканеров отображается отдельно и не блокирует регистрацию рабочего подключения.

При ошибке хост не сохраняется, а форма показывает результат проверки. Уже установленный индивидуальный ключ сохраняется для повторной попытки. Исправьте указанную причину и снова нажмите **«Подключить хост»**. Повторное нажатие использует ту же пару. Если ответ потерялся на этапе сохранения, сначала проверьте список хостов: запись могла успеть добавиться.

| Ошибка | Действие |
| --- | --- |
| Сервер ещё не подтверждён / ключ изменился | Проверьте его через доверенный канал, затем подтвердите в HCP |
| Пароль не принят | Проверьте имя пользователя, пароль и разрешение парольной аутентификации на SSH-сервере |
| Ключ установлен, вход по нему не работает | Администратор проверяет разрешение public key auth, домашний каталог, authorized_keys и политику Astra |
| Недостаточно административных прав | Введите пароль администратора повторно: HCP настроит свой sudo-доступ. Если политика запрещает изменение sudoers, подготовьте правило вручную или используйте root по утверждённой политике |
| Python отсутствует или несовместим | Администратор устанавливает поддерживаемый Python из репозиториев целевой ОС; не заменяйте его пакетами Ubuntu |

Если SSH, пользователь или Python ещё не подготовлены, администратор Astra настраивает их через уже доступную консоль. Для типовой установки из репозиториев выпуска: `apt install openssh-server python3`, затем `systemctl enable --now ssh`. Парольная подготовка ключа сама не требует Python на цели; дальнейшие модули Ansible требуют совместимой версии.

<a id="existing-host"></a>
### 4.6. Уже добавленный хост: обновление административного доступа

Откройте **«Хосты» → «Настроить»** у существующей записи. Сохраните её имя, чтобы сохранить историю аудитов. Для перехода со старого общего ключа введите SSH-пароль и нажмите **«Сохранить подключение»**. Проверка и сохранение выполняются автоматически. Переключение конкретной записи на индивидуальный ключ не меняет остальные хосты.

Если отдельный ключ уже настроен для того же пользователя, его можно использовать без повторного ввода SSH-пароля. Для перехода на другого администратора измените пользователя и введите его пароль; HCP установит индивидуальный ключ для этого подключения. Нажмите «Сохранить подключение»: форма повторно проверяет права root, в том числе у ранее добавленных записей без sudo. Для отдельной проверки раскройте «Дополнительные действия с хостом» → «Только проверить доступ». Удалять запись не требуется; до успешного сохранения действуют прежние параметры.

<a id="key-rotation"></a>
### 4.7. Несколько хостов, сохранность и отзыв ключей

Повторяйте настройку для каждой машины: у каждой записи собственная пара, привязанная к адресу, порту и пользователю. Массового ввода паролей в этой версии нет. Ключи сохраняются в постоянном томе HCP: `/var/lib/hcp/ssh-host-keys/<идентификатор>/id_ed25519`. Каталоги имеют права `700`, приватные файлы — `600`. Они не зашифрованы отдельной парольной фразой, чтобы расписание работало без диалога; защищайте управляющий сервер и резервные копии. Весь этот каталог входит в [бэкап runtime](backup-restore.md).

Перезапуск, пересборка и повторная настройка не меняют пару. Для завершения работ используйте кнопку **«Завершить работы»** в карточке хоста: HCP по проверенному SSH-соединению удалит конкретную строку публичного ключа и своё совпадающее правило sudoers, затем удалит локальную пару и inventory. При ошибке локальные данные не удаляются. Полный порядок приведён в [инструкции завершения проекта](project-closeout.md). Автоматической ротации ключа пока нет.

Существующие хосты со старым общим `secrets/hcp-control` продолжают работать до индивидуального перевода. Новая установка этот файл не требует. После перевода старый общий публичный ключ остаётся на Astra: удалите его отдельно после проверки нового доступа, если он больше не нужен другим средствам управления. Не удаляйте общий приватный файл, пока от него зависят другие записи HCP. Смена/отзыв ключа входа не меняет ключ сервера Astra.

## 5. Первый аудит

После регистрации или изменения прав нажмите «Настроить» → «Дополнительные действия с хостом» → «Только проверить доступ». Затем выберите хост и профиль «Базовый Linux», запустите «Запустить аудит» и откройте полученный отчёт. Оцените ошибки сбора и неполноту отдельно от найденных нарушений.

Далее запускайте SSH-проверки, Nmap и Lynis с учётом режима прав. Для CVE Astra назначьте группе источник в **«Источниках» → «CVE пакетов Astra»**, затем выполните **«Проверить CVE Astra по OVAL»**. Общий пункт «Проверить пакеты и CVE» формирует инвентарь/Trivy и не подтверждает CVE-покрытие Astra. Для конфигурационного OpenSCAP назначьте группе в **«Политиках»** профиль **«Astra Linux — базовые проверки HCP»**, затем выполните **«Проверить профиль OpenSCAP»**.

OpenSCAP запускается **на Astra**, поэтому его наличие внутри контейнера Ubuntu недостаточно. На Astra сначала выполните `oscap --version`; для встроенного профиля нужен SCE. Если команды нет, проверьте `apt-cache policy openscap-scanner libopenscap8 oval-db` и установите доступный пакет сканера из своего выпуска. Имена и наличие пакетов различаются; универсальная установка одного набора для всех редакций не предполагается.

Для OVAL можно использовать локальный `/usr/share/oval/db.xml`, если он существует и подходит вашей системе. Путь из установленного пакета показывает `dpkg -L oval-db`. XML разработчику пересылать не нужно. Для разных выпусков назначайте соответствующие источники группам. Полный порядок, включая SHA-256 и свежесть: [OVAL и OpenSCAP](astra-audit.md).

Код не ограничен только Astra 1.7.6. Совместимость проверяется по возможностям: Python целевых программ — 3.5+, а комплектный Ansible 2.14 рассчитан на целевые Python 3.5–3.11. Мастер проверяет эту совместимость. Подтверждение каждой редакции/архитектуры и полноты её CVE-базы требует собственного прогона.

## 6. Изменения, резервные копии и восстановление

Через панель доступны закрытие порта и блокировка IPv4 через **один активный UFW или firewalld**. Системы с иным firewall можно аудировать, но этот механизм применения/отката к ним не подключён. HCP не устанавливает и не включает firewall сам.

1. Получите завершённый базовый аудит. При неполном исходном аудите применение остановится.
2. Выберите действие, укажите причину, выполните предварительную проверку и подтвердите точный alias.
3. При применении HCP сначала создаёт на Astra `/var/lib/hcp-backups/txn-…/firewall-state.tar.gz` и `metadata.json`, затем меняет firewall и запускает повторный аудит. Проверьте отчёт и сетевой эффект с Ubuntu.
4. Для отмены нажмите «Откатить» у транзакции с резервной копией. После успешного отката повторите аудит вручную. Откат также доступен для `failed`/`rollback_failed`, если резервная копия успела сохраниться.

Архив содержит конфигурацию `/etc/ufw` либо `/etc/firewalld`, а не всю Astra. Он остаётся на целевой машине. Между применением и откатом не вносите другие изменения в эту конфигурацию: восстановление вернёт каталог целиком. При нескольких изменениях на одном хосте отменяйте их в обратном порядке. При потере SSH используйте консоль ВМ и сохранённый снимок; автоматического отката по таймеру нет.

**Бэкап самой платформы** выполняется отдельно на Ubuntu. В [инструкции резервирования и восстановления](backup-restore.md) приведены команды для данных HCP, ключей, настроек и образа. Снимки/полные копии Astra создаются средствами гипервизора или вашей системой резервирования.

## 7. Расписание и проверка готовности

Сначала завершите ручной прогон на одном хосте. Затем можно установить systemd units по [инструкции развёртывания](../deployment/README.md#периодический-аудит-через-systemd). Их `WorkingDirectory` должен совпадать с каталогом HCP на Ubuntu; пример `/opt/hardening-control-platform` нужно заменить, если проект находится в другом месте.

В текущем планировщике `packages` означает инвентарь + Trivy. **Отдельный OVAL-аудит Astra в штатное расписание ещё не включён**; запускайте его из «Хостов». Конфигурационный OpenSCAP можно включить задачей `openscap` после назначения профиля.

Стенд готов к собственным испытаниям, когда панель `healthy`, проходит подключение к Astra, получены содержательные отчёты, контролируемое firewall-изменение отменяется, а резервная копия HCP восстановлена на отдельной Ubuntu. Прежние CI-проверки и их границы: [протокол](verification-report.md).
