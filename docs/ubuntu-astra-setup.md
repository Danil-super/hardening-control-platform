# Стенд: Ubuntu управляет хостами Astra Linux

Это единая основная инструкция установки и подключения хостов. README и страница «Инструкция» на сайте ссылаются на этот порядок. Для уже добавленного хоста без sudo начните с [настройки повышения прав](#sudo-access), затем [обновите его карточку](#existing-host).

Основной маршрут установки для схемы **HCP на Ubuntu → аудит Astra Linux по SSH**. Для первой установки используйте Docker Engine и Compose на Ubuntu. Ansible и инструменты управляющей машины уже входят в образ HCP; системный Python Ubuntu не используется как Python проверяемой Astra.

| Где | Что устанавливается и хранится |
| --- | --- |
| Ubuntu | Git, Docker Engine, Compose; контейнер HCP, интерфейс, отчёты, SQLite, отдельный SSH-ключ |
| Каждая Astra | Работающий SSH-сервер, совместимый Python 3 и учётная запись, допускающая ключ HCP; sudo нужен для административного режима |
| Astra для OVAL/OpenSCAP | Дополнительно OpenSCAP; для профиля HCP нужна поддержка SCE, для CVE — подходящий XML OVAL |
| Внешнее хранилище | Копии данных HCP, его секретов и образа; отдельно резервные копии или снимки Astra |

Docker на Astra для этого сценария не нужен. Greenbone и Dependency-Track — отдельные интеграции; сначала проверьте основной маршрут на одном хосте, затем подключайте их по [инструкции интеграций](audit-integrations.md).

## 1. Ubuntu: подготовка

Для первого стенда рекомендуется Ubuntu 24.04 LTS x86-64, 4 vCPU, 8 ГБ RAM и свободное место под образы, отчёты и резервную копию. Ресурсы Greenbone/Dependency-Track в эту оценку не входят. Другую версию Ubuntu сначала сверяйте с [поддержкой Docker](https://docs.docker.com/engine/install/ubuntu/); она не определяет номер выпуска целевой Astra.

На Ubuntu:

```bash
sudo apt update
sudo apt install -y git openssh-client openssl curl ca-certificates
```

Установите Docker Engine и плагин Docker Compose по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/#install-using-the-apt-repository). При существующей установке сначала проверьте её; повторно устанавливать Docker не требуется.

```bash
sudo docker version
sudo docker compose version
sudo docker info >/dev/null
```

Нужен работающий Docker daemon и Compose 2.20 или новее. Здесь команды Docker выполняются через `sudo`, поэтому добавлять пользователя в группу `docker` не требуется.

Первоначальная сборка требует интернета на Ubuntu: GitHub, реестры контейнеров, Debian APT, npm и PyPI. Для изолированной установки подготовьте образ и базы заранее; одно наличие Git-репозитория этого не заменяет. После установки базовые SSH-проверки работают по локальной сети.

## 2. Ubuntu: установка HCP

Команды ниже предназначены для **первой установки**. При обновлении не создавайте повторно ключи и `.env`.

```bash
git clone https://github.com/Danil-super/hardening-control-platform.git
cd hardening-control-platform
cp .env.production.example .env
cp ansible/inventory.example.ini ansible/inventory.ini
mkdir -p secrets
chmod 700 secrets
ssh-keygen -t ed25519 -N '' -f secrets/hcp-control -C hcp-control
install -m 600 /dev/null secrets/known_hosts
chmod 600 .env secrets/hcp-control
```

Откройте `.env` в редакторе. Замените `HCP_ADMIN_PASSWORD`, `HCP_AUTH_SECRET`, `HCP_AUDIT_HMAC_KEY`, `HCP_SCHEDULE_API_KEY` отдельными случайными значениями. Каждое можно получить командой `openssl rand -base64 48`. Пароль Dependency-Track понадобится при включении этой интеграции. Сохраните `.env`: эти значения необходимы и для восстановления.

Оставьте `HCP_BIND_ADDRESS=127.0.0.1`, `HCP_PORT=3000`. В `HCP_CONTROL_IPS` укажите IPv4 Ubuntu, через который она обращается к Astra; несколько адресов разделяются запятыми. Это дополнительная защита от их блокировки в интерфейсе.

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build --wait --wait-timeout 180 hcp
sudo docker compose ps
sudo docker compose logs --tail=80 hcp
```

Ожидается статус `healthy`. Откройте <http://127.0.0.1:3000> в браузере **на Ubuntu** и войдите с `HCP_ADMIN_PASSWORD`. Долгая первая сборка допустима; если команда завершилась ошибкой, сначала разберите журнал. Для просмотра потока журнала используйте `sudo docker compose logs -f hcp`; `Ctrl+C` завершает просмотр, а не контейнер.

Если браузер находится на другом компьютере, выполните на нём `ssh -N -L 3000:127.0.0.1:3000 user@IP_UBUNTU` и откройте тот же адрес браузера. Привязку панели к loopback менять не требуется.

## 3. Сеть Ubuntu → Astra

Ubuntu и контейнер HCP должны достигать SSH-порта Astra. Если Astra запущена в VirtualBox на этой Ubuntu, для первого стенда подходит **Host-only** адаптер; дополнительный NAT можно использовать для обновлений. **Internal Network** связывает гостевые ВМ между собой и сама по себе не подключает к ним Ubuntu-хост. Для HCP в отдельной Ubuntu-ВМ подключите обе ВМ к одной внутренней сети. Один NAT без маршрута или проброса порта не обеспечивает входящий SSH к Astra.

Различия режимов описаны в [документации VirtualBox](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/networkingdetails.html).

На Astra через её консоль узнайте адрес: `hostname -I`. На Ubuntu проверьте маршрут командой `ip route get IP_ASTRA`, затем из каталога HCP:

```bash
sudo docker compose exec --user node -T hcp nmap -Pn -sT -p 22 IP_ASTRA
```

Замените `IP_ASTRA` и `22` фактическим адресом и SSH-портом. Ожидается `open`. Эта проверка подтверждает доступность порта, но ещё не ключ, Python и sudo.

## 4. Единый порядок подключения Astra

Порядок один: **учётная запись и SSH → разрешённый ключ платформы → выбранный режим прав → подтверждённый ключ сервера → проверка подключения → сохранение хоста**. Для уже подготовленной машины проверяйте существующий доступ и переходите к форме; повторная установка пакетов, создание пользователя и добавление того же ключа не требуются.

HCP работает без постоянного агента, но использует заранее выданный SSH-доступ. В текущей форме нельзя ввести SSH/sudo-пароль, загрузить личный ключ или автоматически выдать права на неподготовленной машине. Некоторые проверки временно передают и удаляют файлы на хосте. Для настройки доступа нужен администратор Astra или действующая система управления конфигурацией.

### 4.1. Зафиксируйте параметры одного хоста

| Поле на сайте | Пример | Что означает |
| --- | --- | --- |
| Имя хоста | `astra-01` | Уникальное имя в HCP, не имя пользователя |
| IP-адрес или домен | адрес вашей Astra | Адрес, доступный из контейнера Ubuntu |
| Пользователь SSH | `hcp-audit` | Существующая учётная запись на этой Astra |
| Порт SSH | `22` | Фактический порт SSH-сервера |
| Группа inventory | `astra_hosts` | Группа для назначения OVAL/OpenSCAP; форма включает её в `linux_hosts` |
| Использовать sudo | включено или выключено | Запрашивать уже разрешённое повышение прав до root |

`hcp-audit` далее — **пример**. Если хост уже добавлен под другим пользователем, используйте именно его имя в командах, правиле sudoers и форме. Создавать второго пользователя для включения sudo не нужно.

### 4.2. Только если SSH, Python или пользователь ещё не подготовлены

Этот подраздел выполняет **администратор в консоли целевой Astra**, а не на Ubuntu. Получите разрешённый root-сеанс через `sudo -i` из учётной записи администратора или войдите в консоль под root. Если такого доступа нет, подготовку выполняет администратор машины; панель HCP его не заменяет.

В root-сеансе установите только отсутствующие компоненты из репозиториев своего выпуска Astra:

```bash
apt update
apt install -y openssh-server python3
systemctl enable --now ssh
```

Если выбранной учётной записи ещё нет, создайте её:

```bash
adduser hcp-audit
```

Проверьте `python3 --version`, `/usr/bin/python3 --version` и `cat /etc/astra_version`. Платформа проверяет совместимость целевого Python с Ansible из контейнера; системный Python Astra нельзя заменять пакетами другой ОС. Разрешите фактический SSH-порт в действующем firewall по вашей политике. Не включайте второй менеджер firewall поверх существующего.

### 4.3. Один раз разрешите ключ платформы

В HCP откройте **«Хосты» → «Добавить хост» → «Доступ по SSH» → «Ключ платформы»**. Раскройте «Если доступ этому ключу ещё не выдан» и скопируйте команду.

Выполните её **на целевой Astra от имени выбранного пользователя SSH**. В консоли сначала проверьте `id -un`: имя должно совпасть с полем на сайте. Администратор с root-сеансом может открыть сеанс этого пользователя командой `su - hcp-audit`. Команда из HCP добавляет публичный ключ в домашний `~/.ssh/authorized_keys` и устанавливает права каталога/файла. Существующие чужие ключи сохраняются.

Результат: в `authorized_keys` выбранного пользователя присутствует одна полная строка публичного ключа HCP. Если она уже присутствует и вход работает, повторять команду не нужно. `secrets/hcp-control` — приватный ключ на Ubuntu; на Astra передаётся только публичная часть. Один ключ платформы используется для всех хостов этой установки и не меняется при перезапуске или «Обновить сведения».

Если добавление выполняет администратор напрямую, владельцем `.ssh` и `authorized_keys` должен быть целевой пользователь, права — `700` и `600`. Не запускайте команду из HCP под root, если на сайте указан обычный пользователь: тогда ключ попадёт в другой домашний каталог.

<a id="sudo-access"></a>
### 4.4. Выберите режим прав и при необходимости настройте sudo

**Без sudo от обычного пользователя** хост можно добавить и проверять в пределах выданных прав. **С sudo** HCP запрашивает повышение до root без ввода пароля. Галочка сама не устанавливает sudo, не меняет sudoers и не выдаёт административных прав.

| Задача | Без sudo от обычного пользователя |
| --- | --- |
| Проверка подключения, сведения об ОС/Python, «Проверить связь» | Доступны при рабочем SSH и совместимом Python |
| Nmap и SSH-криптография | Выполняются с управляющей Ubuntu; sudo на Astra им не нужен |
| Сведения и инвентарь пакетов | Обычно доступны; результат зависит от разрешений на чтение |
| Базовый аудит, системные события, Lynis, OpenSCAP/OVAL | Возможны ошибки или неполное покрытие; доступ к защищённым данным зависит от прав и конкретных проверок |
| Изменения firewall, его резервная копия и откат | Нужны права root; для обычной учётной записи используйте настроенное sudo |

Успешное добавление без sudo не означает готовность ко всем аудитам. Отдельно проверяйте «Готовность к аудиту», ограничения и полноту отчёта. Для штатного административного сценария далее используется отдельная техническая учётная запись с беспарольным sudo. HCP не поддерживает ввод sudo-пароля и выбор `su` через форму.

**Диагностика на Astra от имени пользователя SSH:**

```bash
id -un
sudo -k -n id -u
```

Ожидается `0` без запроса пароля. `-k` исключает успех только за счёт ранее введённого пароля, `-n` запрещает интерактивный запрос. Не выполняйте эту проверку под другим администратором или на Ubuntu: она проверит другого пользователя/другую ОС. [Опции sudo](https://manpages.ubuntu.com/manpages/noble/man8/sudo.8.html).

| Результат | Что сделать |
| --- | --- |
| `a password is required` / `Missing sudo password` | Настроить разрешённое NOPASSWD для пользователя SSH; одного членства в группе sudo недостаточно |
| `not in the sudoers file` / `not allowed to execute` | Администратор должен проверить правила для этой учётной записи |
| `sudo: command not found` | Администратор устанавливает sudo из репозиториев Astra |
| Ошибка PAM, PARSEC или отказ несмотря на правило | Проверить журнал и политику конкретной Astra с её администратором; не отключать защитные механизмы |
| `0` локально, но проверка HCP не проходит | Проверить имя пользователя на сайте и выполнение Ansible-модуля; локальный `id` ещё не доказывает право запуска всего workflow |

**Настройка для выделенной лабораторной учётной записи — администратором в root-сеансе на Astra:**

Если sudo отсутствует, установите `apt install -y sudo`. Затем откройте отдельное правило:

```bash
visudo -f /etc/sudoers.d/90-hcp-audit
```

Добавьте строку, заменив `hcp-audit` именем пользователя из карточки хоста:

```sudoers
hcp-audit ALL=(root) NOPASSWD: ALL
```

Это полные административные права root для этой учётной записи, без пароля. Для рабочих защищённых машин такой доступ должен соответствовать вашей политике. Ansible запускает временные Python-модули, поэтому разрешение только `/usr/bin/id` или нескольких системных команд не обеспечивает работу полного набора HCP. [Ограничения become в Ansible](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_privilege_escalation.html#privilege-escalation-must-be-general).

В том же root-сеансе:

```bash
chown root:root /etc/sudoers.d/90-hcp-audit
chmod 440 /etc/sudoers.d/90-hcp-audit
visudo -c
```

Проверка должна закончиться без ошибок. Основной `/etc/sudoers` должен подключать `/etc/sudoers.d`: обычно это `#includedir /etc/sudoers.d` (для старых sudo) или `@includedir /etc/sudoers.d`. Если файл не читается, администратор проверяет подключение каталога через `visudo`; имя файла не должно содержать точку. Не перезаписывайте основной sudoers готовым шаблоном. [Формат sudoers](https://manpages.ubuntu.com/manpages/noble/man5/sudoers.5.html).

Откройте сеанс пользователя SSH и повторите `sudo -k -n id -u`. После `0` продолжите проверку в HCP. Настройка sudo не требует замены SSH-ключа, пересборки контейнера или удаления уже добавленного хоста.

### 4.5. Один раз подтвердите ключ сервера Astra

Ключ сервера удостоверяет саму Astra и отличается по назначению от ключа входа HCP. В доверенной консоли **этой Astra** прочитайте отпечаток:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
```

Команда читает публичный ключ и ничего не меняет. Если ED25519 отсутствует, используйте существующий публичный host key RSA/ECDSA. Отпечаток также может предоставить администратор через доверенный реестр.

В форме HCP проверьте адрес/порт и раскройте **«Доступ по SSH» → «Ключ сервера»**. Нажмите «Получить отпечатки по сети», сравните соответствующий отпечаток с доверенным значением. При совпадении вставьте именно `SHA256:…` в поле «Подтверждённый SHA256-отпечаток» и нажмите **«Сохранить проверенный ключ»**. Дождитесь уведомления об успехе. Не используйте результат сетевого сканирования как единственное основание доверия.

HCP сохраняет доверие в `/var/lib/hcp/known_hosts` постоянного тома Ubuntu. Обычный `ssh` из терминала Ubuntu использует свой `known_hosts`; принятие ключа только в этом терминале не заменяет сохранение в HCP. При неизменном ключе, адресе/порте и сохранённом томе повторять подтверждение не требуется.

### 4.6. Проверьте и сохраните новый хост

1. В форме заполните параметры из шага 4.1. Включите «Использовать sudo», если беспарольное повышение прав уже проверено; иначе осознанно оставьте режим без повышения.
2. Нажмите **«Проверить подключение»**. Для сохранения нужны успешные SSH и Python; при включённом sudo также требуется успешное повышение прав. Пропущенная проверка не является успешной проверкой.
3. Если SSH сообщает `No ED25519 host key is known`, вернитесь к шагу 4.5. Если `Permission denied (publickey)` — проверьте пользователя и ключ из шага 4.3. При ошибке sudo используйте шаг 4.4.
4. После успешной проверки нажмите **«Добавить хост»**. Изменение адреса, пользователя, порта или режима sudo требует повторной проверки.
5. Проверьте хост в таблице. Дополнительные сканеры настраиваются отдельно: их отсутствие не блокирует регистрацию рабочего SSH-подключения.

<a id="existing-host"></a>
### 4.7. Если хост уже добавлен без sudo

Сохраните существующую запись и её историю. После настройки прав из шага 4.4 откройте **«Хосты» → «Настроить»** у нужной машины, включите **«Использовать sudo»**, нажмите **«Проверить подключение»**, затем **«Сохранить изменения»**. Имя SSH-пользователя должно совпадать с пользователем, которому выданы права.

При ошибке не меняйте выбранный режим только ради зелёного результата: либо исправьте права, либо сохраните осознанный режим без sudo и учитывайте его ограничения. Если выбрана другая существующая административная учётная запись, ключ HCP должен быть разрешён и для неё. Без действующего административного доступа самостоятельно выдать себе sudo через HCP невозможно.

### 4.8. Несколько хостов и замена ключа

Повторяйте шаги 4.1–4.6 для каждого хоста. Публичный ключ платформы общий, а разрешённый пользователь, права и подтверждение ключа сервера относятся к каждой конкретной машине. Для массовой подготовки можно использовать существующее средство управления конфигурацией с уже выданным административным доступом; встроенного массового первичного подключения в HCP нет.

При плановой ротации сначала создайте новую пару на Ubuntu в отдельном файле, добавьте новый публичный ключ на все нужные хосты рядом со старым и проверьте доступ новым ключом. Сохраните защищённую резервную копию старой пары, замените `secrets/hcp-control` и `secrets/hcp-control.pub` новой парой (приватный файл — права `600`), затем выполните на Ubuntu `sudo docker compose up -d --force-recreate hcp`. После проверки через HCP удалите старую разрешающую строку со всех хостов. «Обновить сведения» само не выполняет ротацию. Ключи серверов Astra при этой операции не меняются.

## 5. Первый аудит

После регистрации или изменения прав нажмите «Настроить» и проверьте подключение с сохранёнными параметрами. Затем выберите хост и профиль «Базовый Linux», запустите «Запустить аудит» и откройте полученный отчёт. Оцените ошибки сбора и неполноту отдельно от найденных нарушений.

Далее запускайте SSH-проверки, Nmap и Lynis с учётом режима прав. Для CVE Astra назначьте группе источник в **«Источниках» → «CVE пакетов Astra»**, затем выполните **«Проверить CVE Astra по OVAL»**. Общий пункт «Проверить пакеты и CVE» формирует инвентарь/Trivy и не подтверждает CVE-покрытие Astra. Для конфигурационного OpenSCAP назначьте группе в **«Политиках»** профиль **«Astra Linux — базовые проверки HCP»**, затем выполните **«Проверить профиль OpenSCAP»**.

OpenSCAP запускается **на Astra**, поэтому его наличие внутри контейнера Ubuntu недостаточно. На Astra сначала выполните `oscap --version`; для встроенного профиля нужен SCE. Если команды нет, проверьте `apt-cache policy openscap-scanner libopenscap8 oval-db` и установите доступный пакет сканера из своего выпуска. Имена и наличие пакетов различаются; универсальная установка одного набора для всех редакций не предполагается.

Для OVAL можно использовать локальный `/usr/share/oval/db.xml`, если он существует и подходит вашей системе. Путь из установленного пакета показывает `dpkg -L oval-db`. XML разработчику пересылать не нужно. Для разных выпусков назначайте соответствующие источники группам. Полный порядок, включая SHA-256 и свежесть: [OVAL и OpenSCAP](astra-audit.md).

Код не ограничен только Astra 1.7.6. Совместимость проверяется по возможностям: Python целевых программ — 3.5+, а комплектный Ansible 2.14 рассчитан на целевые Python 3.5–3.11. Мастер проверяет эту совместимость. Подтверждение каждой редакции/архитектуры и полноты её CVE-базы требует собственного прогона.

## 6. Изменения, резервные копии и восстановление

Через панель доступны закрытие порта и блокировка IPv4 через **один активный UFW или firewalld**. Системы с иным firewall можно аудировать, но этот механизм применения/отката к ним не подключён. HCP не устанавливает и не включает firewall сам.

1. Получите завершённый базовый аудит. При неполном исходном аудите применение остановится.
2. Выберите действие, укажите причину, выполните предварительную проверку и подтвердите точный alias.
3. При применении HCP сначала создаёт на Astra `/var/lib/hcp-backups/txn-…/firewall-state.tar.gz` и `metadata.json`, затем меняет firewall и запускает повторный аудит. Проверьте отчёт и сетевой эффект с Ubuntu.
4. Для отмены нажмите «Откатить» у транзакции с резервной копией. После успешного отката повторите аудит вручную. Откат также доступен для `failed`/`rollback_failed`, если резервная копия успела сохраниться.

Архив содержит конфигурацию `/etc/ufw` либо `/etc/firewalld`, а не всю Astra. Он остаётся на целевой машине. Между применением и откатом не вносите другие изменения в эту конфигурацию: восстановление вернёт каталог целиком. При нескольких изменениях на одном хосте отменяйте их в обратном порядке. При потере SSH используйте консоль ВМ и сохранённый снимок; автоматического отката по таймеру нет.

**Бэкап самой платформы** выполняется отдельно на Ubuntu. В [инструкции резервирования и восстановления](backup-restore.md) приведены команды для данных HCP, ключей, настроек и образа. Снимки/полные копии Astra создаются средствами гипервизора или вашей системой резервирования.

## 7. Расписание и проверка готовности

Сначала завершите ручной прогон на одном хосте. Затем можно установить systemd units по [инструкции развёртывания](../deployment/README.md#периодический-аудит-через-systemd). Их `WorkingDirectory` должен совпадать с каталогом HCP на Ubuntu; пример `/opt/hardening-control-platform` нужно заменить, если проект находится в другом месте.

В текущем планировщике `packages` означает инвентарь + Trivy. **Отдельный OVAL-аудит Astra в штатное расписание ещё не включён**; запускайте его из «Хостов». Конфигурационный OpenSCAP можно включить задачей `openscap` после назначения профиля.

Стенд готов к собственным испытаниям, когда панель `healthy`, проходит подключение к Astra, получены содержательные отчёты, контролируемое firewall-изменение отменяется, а резервная копия HCP восстановлена на отдельной Ubuntu. Прежние CI-проверки и их границы: [протокол](verification-report.md).
