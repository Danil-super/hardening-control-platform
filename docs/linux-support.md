# Поддержка Linux: возможности, проверка и границы

HCP развивается как общая система аудита и контролируемого харденинга Linux.
Поддержка определяется отдельно для сбора сведений, конфигурационных правил,
пакетных CVE, SCAP, изменения firewall и отката. Успешное SSH-подключение не
подтверждает остальные возможности. Полный охват всех Linux-выпусков, CVE и
средств управления настройками сейчас не заявляется.

Начальная настройка описана в [Linux setup](linux-setup.md), правила привязки
отчётов — в [идентичности активов](asset-identity.md), восстановление операций —
в [operations recovery](operations-recovery.md).

## Как выбирается адаптер

Общий реестр находится в `web/lib/linux-platform.ts`. Он сохраняет точный
`ID`/`VERSION_ID` из `os-release`, отдельные сведения Astra и способ получения
пакетов. `/etc/os-release` имеет приоритет над `/usr/lib/os-release`; содержимое
файла не исполняется как shell. Если первый файл существует, но повреждён,
подменять его другим дистрибутивом нельзя.

`ID_LIKE` разрешает выбрать семейство команд сбора. Он не разрешает считать
базу Ubuntu базой любого производного дистрибутива или базу RHEL базой любого
RPM-сервера. CentOS Stream отделён от обычного CentOS. Наличие маршрута Trivy
означает возможность попытки сопоставления, а не подтверждённую поддержку
каждого выпуска: точный OS family/release, пакетные метаданные, результат
детектора, источник и свежесть базы проверяются при сканировании.

## Матрица реализации

| ОС/семейство | Инвентаризация | Пакетный CVE-маршрут | Системный аудит |
| --- | --- | --- | --- |
| Debian, Ubuntu | dpkg; установленные состояния и source-пакеты | Собственный маршрут Debian/Ubuntu в Trivy | По доступным инструментам и менеджеру служб |
| Astra Linux | dpkg и точный выпуск Astra | Отдельный OVAL производителя; Debian не подставляется | Общий аудит; отдельный встроенный профиль HCP/OpenSCAP |
| AlmaLinux, Rocky Linux | RPM; полная EVR, source RPM, архитектура, vendor/module metadata | Собственный маршрут Alma/Rocky в Trivy; фактические пробелы происхождения сохраняются | systemd либо ограниченный иной адаптер |
| RHEL, Oracle, Amazon Linux, CentOS | RPM | Собственный маршрут производителя, с проверками метаданных и выпуска; RHEL content sets и особые репозитории требуют отдельного подтверждения | По возможностям хоста |
| SLES, openSUSE Leap/Tumbleweed | RPM | Идентификаторы детекторов закреплённой версии Trivy; реальная полнота оценивается отдельно | По возможностям хоста |
| Alpine, Wolfi | APK; установленная БД, полный `-rN`, origin, архитектура | Отдельные маршруты Alpine/Wolfi; смешанные/сторонние ветки репозиториев ограничивают покрытие | OpenRC/systemd при подтверждении; контейнер не считается полноценным сервером |
| ALT, РЕД ОС, ROSA, Fedora, SLED, неизвестные производные | RPM либо установленный подходящий адаптер | Требуется подтверждённый источник именно этого производителя; общей гарантии CVE нет | Доступные общие проверки |
| Arch, Gentoo, NixOS и прочие ОС без dpkg/RPM/APK-адаптера | Специальный адаптер пока отсутствует | Не подтверждено | Только применимые общие проверки; штатные средства управления ОС учитываются отдельно |

RPM сохраняет полную **binary EVR**; исходный epoch не содержится в SOURCERPM и
не выдумывается. Детекторы, сравнивающие binary EVR, от этого не блокируются.
Для SQLite-базы RPM модуль `sqlite3` должен быть доступен в выбранном целевом
Python. Без него согласованность чтения не подтверждается: сбор завершается
неполным результатом с ошибкой и пустым списком пакетов; неподтверждённый запрос
не выполняется. Это требование не относится к dpkg, APK и другим форматам RPM БД.

Путь и backend RPM определяются через его native-настройки и закрепляются в
аргументах запроса. Проверяется именно эта база, включая нестандартный каталог;
старая копия в обычном расположении не заменяет её. Для SQLite отслеживаются
подтверждённые изменения данных, путь и inode, а служебное изменение WAL при
чтении не выдаётся за установку пакета. Неизвестный backend, смешанные файлы
разных backend и неразрешённые макросы в пути дают явный неполный результат.

Maintainer/Vendor используются как явно обозначенная эвристика, а не проверка
подписи. APK repositories описывает настроенную ветку; происхождение уже
установленного пакета этим не удостоверяется. Даже официальный пакет с внешним
адресом сопровождающего может сохранить неопределённую применимость advisory.

SBOM использует пространства имён закреплённого Trivy: в частности,
`almalinux → alma`, `ol → oracle`, `amzn → amazon`, `sles → suse`, варианты
openSUSE → `opensuse`. Проверка фактически обработанных пакетов обязательна:
неподходящее пространство имён может привести к пропуску записей сканером.

RPM-записи `gpg-pubkey` сохраняются в инвентаре, SBOM и списке прочитанных
Trivy записей. Это ключи доверия, а не версии установленного ПО: native Trivy
исключает их из CVE-сопоставления. Отчёт отдельно показывает `inventoryPackages`,
`decodedRecords`, `eligiblePackages`, `scannedPackages` и точный список
`excludedNonSoftware`. Записи ключей не увеличивают число проверенных пакетов
и не превращаются в неизвестных поставщиков ПО. Это не аудит доверия или
срока действия ключей. Инвентарь, состоящий только из ключей, не получает PASS.
Подтверждение устранения CVE сверяет исключения с новым исходным инвентарём;
произвольно исключить обычный пакет из этой проверки нельзя.

Таблица описывает кодовые маршруты. Она не заменяет протокол испытаний конкретного
выпуска и не утверждает поддержку неподдерживаемых upstream выпусков. Одна
уязвимость, найденная контрольным тестом, не измеряет общую полноту обнаружения.

### Службы и журналы

- **systemd:** используются состояния `LoadState` и `ActiveState`. Ошибка D-Bus,
  переходное состояние или нераспознанный ответ остаются неизвестными.
- **OpenRC:** нужен работающий OpenRC, а не просто установленный `rc-service`.
  Адаптер проверяет существование и состояние службы. Поддержаны алиасы
  `ssh`/`sshd`, `cron`/`crond`, `apache2`/`httpd`.
- **SysV:** допускается ограниченный read-only вызов `status` для LSB init-скрипта.
  Он не даёт универсальной гарантии для произвольных init-скриптов.
- **runit, s6 и неизвестные варианты:** неподтверждённые состояния служб не
  превращаются в «служба выключена» или в успешную проверку.
- **Журналы:** доступные auth-файлы, при необходимости messages/syslog и journald, а также
  ограниченная выборка firewall/IDS/kernel событий. Отсутствие источника и
  ошибка чтения отражаются отдельно. Это не полнотекстовый анализ всей истории
  и не доказательство отсутствия инцидента. Выборка из смешанного syslog
  сохраняет найденные строки, но без подтверждённого маршрута auth остаётся
  неполной. Пустой journald без доказательства читаемого журнала не даёт PASS.

### Python и Ansible

Удалённые скрипты сохраняют совместимость с Python 3.5+, но Ansible имеет свой
диапазон совместимости. В Docker-образе предусмотрены системный legacy runtime
и отдельный современный runtime. Для операции выбирается runtime, совместимый
со всеми выбранными целями; версия проверяется до отправки playbook.

| Runtime | Python контроллера | Python целевого хоста |
| --- | --- | --- |
| Legacy ansible-core 2.14, пакет Debian | Системный Python образа | 3.5–3.11 |
| Современный ansible-core 2.21.5 | Отдельный Python 3.13 | 3.9–3.14 |

Если группе одновременно нужен слишком старый и слишком новый Python и общего
runtime нет, запуск прекращается до исполнения; разделите inventory-группы.
Системный Python серверов не заменяется. Legacy runtime оставлен для старых
целевых ОС; это не продление поддержки upstream Ansible/ОС. Его использование
нужно учитывать в плане обновления инфраструктуры.

`ansible_python_interpreter` должен быть явным абсолютным путём. Этот путь
используется в проверке готовности, Ansible-модулях и собственных удалённых
сборщиках HCP. Внешний SCAP/SCE-контент имеет дополнительные собственные
зависимости, которые проверяются отдельно.

## Применение и откат

Транзакционные изменения пока реализованы для активного **UFW или firewalld на
systemd**, при отсутствии конкурирующего менеджера правил. nftables/iptables
могут участвовать в аудите, но самостоятельный nftables/iptables backend не
получает автоматическую поддержку изменений. На Alpine/OpenRC общий аудит и
APK-инвентарь не означают разрешение автоматического firewall-remediation.

Резервная копия конфигурации сохраняет содержимое, владельца, группу, режим,
поддерживаемые метки `security.PDPL` и `security.selinux`. Метки включаются в
проверяемый manifest и хеш конфигурации. Потеря атрибута при восстановлении,
подмена PAX headers, неизвестные xattrs/ACL и несовместимость архива вызывают
отказ. SELinux не переводится в permissive и не отключается.

Старые архивы без исходных SELinux-меток не могут доказать точное восстановление
на SELinux-хосте. Такой откат останавливается до замены рабочей директории.
Создайте новую проверенную резервную копию до новой операции. Архив firewall
не заменяет snapshot ВМ, резервирование HCP или бэкап данных приложений.

## Что считается доказательством

| Уровень проверки | Что проверяется | Чего это не доказывает |
| --- | --- | --- |
| Поведенческие регрессии | Неизвестные состояния, ошибки, метаданные, источники, архивы, аварийное восстановление | Нативную поддержку каждого дистрибутива |
| Python 3.5/3.7 acceptance | Реальное исполнение target-кода на старом интерпретаторе | Службы и средства защиты конкретной ОС |
| Alpine VM workflow | Настоящий OpenRC, APK, native source metadata, положительные/отрицательные контроли | Все Alpine/Wolfi и архитектуры |
| Alma/Rocky VM workflow | systemd, enforcing SELinux, RPM, настоящий firewalld, закрытие/открытие порта и откат | Все RHEL-производные, политики SELinux, контейнерные/облачные сети |
| Existing Astra VM workflow | Реальные образы 1.8.1/1.8.6, OVAL и SCAP-контроли | Все выпуски/режимы обязательного контроля Astra |

Актуальные исходники проверок: `.github/workflows/linux-alpine-vm-integration.yml`,
`.github/workflows/linux-rpm-vm-integration.yml`, `.github/workflows/astra-vm.yml`.
Успех фиксируется только по завершившемуся запуску соответствующего commit SHA.
Артефакты содержат protocol и сырые результаты; приватные SSH-ключи, seed-диски
и диски ВМ в артефакты не загружаются. Недоступный образ, инструмент или база
не превращаются в пропущенный успешный тест.

## Следующие этапы

1. Отдельные нативные стенды Debian/Ubuntu, SLES/openSUSE, ALT/РЕД ОС и архитектуры
   aarch64; новые строки поддержки после проверок, а не по `ID_LIKE`.
2. Поставщики CVE/OVAL для дистрибутивов без пригодного маршрута, с явной областью
   advisory, пакетным происхождением, модулями и политикой свежести.
3. Отдельный транзакционный nftables backend с проверкой синтаксиса,
   восстановлением сети после сбоя и собственными нативными тестами.
4. Адаптеры управления конфигурацией для immutable/декларативных систем; прямое
   редактирование файлов не считается универсальным способом исправления.
5. Набор независимых уязвимых/исправленных контролей для каждого детектора,
   измерение false positive/false negative на размеченном наборе, отдельные
   показатели покрытия и соответствия политике.
