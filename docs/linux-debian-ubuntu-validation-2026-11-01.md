# Debian и Ubuntu: проверка точности и восстановления, 1 ноября 2026 года

Этот этап проверяет **Debian 12/bookworm и Ubuntu 24.04/noble, x86_64,
systemd и UFW**. Проверки запускаются на отдельных KVM-гостях с собственным
ядром. Образы, порядок подготовки, SSH-идентичность и критерии приёмки описаны
в [инструкции нативного стенда](linux-debian-ubuntu-acceptance.md).

Подключение обычного сервера описано в [Linux setup](linux-setup.md).
Стенд CI поднимать на каждом рабочем сервере не требуется.

## Подтверждённые проблемы и исправления

| Область | Что было обнаружено | Что изменилось |
| --- | --- | --- |
| DEB multiarch | Native CycloneDX decoder Trivy объединял записи одинакового имени и версии без отдельного идентификатора архитектуры | SBOM передаёт поддержанный `aquasecurity:trivy:PkgID`, равный PURL с архитектурой; проверяется сохранение пакетов и CVE-находок |
| Происхождение DEB | Штатный адрес `alioth-lists.debian.net` не распознавался эвристикой поставщика | Добавлен только точный домен; сторонний Origin/Maintainer сохраняет приоритет; криптографическое подтверждение не заявляется |
| Пакетные контроли | Acceptance helper применял RPM-правила к DEB source version и неправильно сопоставлял полный выпуск Ubuntu | Форматы разделены, source epoch сохранён, выпуск сравнивается полностью; это исправление проверяющего сценария |
| Native UFW | nft JSON скрывает параметры `xt conntrack`; Ubuntu также использует точное поле IPv4 `ip.protocol` | В исходном nft-графе восстанавливается только строго сопоставленный `--ctstate`; поддержана наблюдаемая форма IPv4 без обобщения на IPv6 `nexthdr` |
| Неизвестные iptables extensions | Неизвестный match мог считаться обычным условием, хотя `hashlimit` способен самостоятельно отбросить пакет; получалось ложное доказательство свободного прохода | Достижимый неподдержанный модуль/опция сохраняет `manual`; поздний verdict или условие не скрывают неопределённость |
| Условия и verdict | Требовалось явно сохранить неизвестное состояние limiter, в том числе при невыведенных defaults, и прекращать обработку после терминального verdict | Добавлены регрессии defaults, затенённых правил, `hotdrop`, `rt` перед DROP и терминального REJECT |
| Нативный стенд | Пустой `ssh_genkeytypes` нарушал schema cloud-init Ubuntu; owned comment ожидался только в nft metadata | Удалён недопустимый ключ; принадлежность временных правил подтверждается одновременно полными native `-S` и nft-снимками |
| Объём ответа Trivy | Candidate 3 на Ubuntu достиг CVE-сканирования, но полный native JSON превышал ограничение stdout 64 MiB | Предел согласованно повышен до 128 МиБ в producer, проверяемом файловом reader и независимом replay. Список находок не сокращается; выход за предел по-прежнему даёт manual/partial и очистку временного файла |

Неопределённый native UFW первоначально давал `manual/partial`, а не ложный
положительный результат. Это было ограничением покрытия. Ошибка с неизвестным
iptables match, напротив, могла дать неверный уверенный `failed`. Эти случаи
имеют разный смысл и не объединяются в одну оценку точности.

Новый `agentless.evaluatorVersion` — **1.3.0**. Подробная модель INPUT,
значения статусов, поддержанные формы и диагностика описаны в
[Linux firewall audit](linux-firewall-audit.md). Повторные наблюдения и GETGEN
проверяют согласованность; они не блокируют весь сетевой стек и не являются
атомарным снимком.

Системные контроли используют принадлежащий стенду временный каталог и службу
cron. Для каталога проверяются `passed → failed → passed`; для cron — реальные
переходы active/inactive/active и соответствующие наблюдения в отчёте. Остановка
cron не объявляется универсальной рекомендацией по харденингу.

Firewall-контроль сохраняет UFW включённым. После исходного снимка стенд
добавляет ровно по одному собственному раннему ACCEPT в IPv4 и IPv6 INPUT,
ожидает `failed`, удаляет только свои правила и ожидает `passed`. Сравниваются
оставшиеся полные правила и состояние. Работающий демон сам по себе не даёт PASS.

### Отчёты и привязка к активу

Шесть исходных системных отчётов на каждый гость проходят production-функции
`recordAssetObservation`, `publishCapturedAssetReports` и `readAnsibleReport`.
Идентичность наблюдается до сканирования. Сверяются исходные metadata,
идентификаторы находок, статусы, риски, evidence, количества и причины неполноты.
Неполный исходный результат не должен приобретать числовую оценку при публикации.

Эта стадия проверяет сохранённый JSON, привязку к активу и production
normalization. Native-сценарий не вызывает HTML/PDF export или браузер.
Отдельная проверка PDF описана ниже; браузерное отображение и скачивание
этими сценариями не проверяются.

При успешном сопоставлении исходные строки iptables/ip6tables сохраняются в
evidence вместе с параметрами bridge. Если bridge недоступен, evidence содержит
причину; native-снимки обеих семей дополнительно сохраняются стендом.
Скрытое условие нельзя восстановить только по имени
цепочки или по названию `conntrack`. Приватный machine-id и SSH private keys
в опубликованные артефакты не включаются.

Во всех двенадцати системных отчётах — **17 находок**. В каждой контрольной
серии оценка меняется **63 → 55 → 63**. Baseline/restored содержат **4 failed,
7 passed и 6 manual**; нарушенное состояние — **5 failed, 6 passed и 6 manual**.
`partial=false` и пустой `incompleteChecks` означают полноту предусмотренного
машинного сбора; шесть правил всё равно требуют ручного решения. Оценка не
является вероятностью безопасности сервера.

В исходном и восстановленном UFW bridge подтверждён для IPv4/IPv6 и
восстанавливает 16 conntrack predicates. В фазе контролируемого ACCEPT bridge
остаётся unavailable для unsupported xt projection; `failed` доказывается
исходным native-графом и поддержанным no-op comment, без подмены всего ruleset.

### Применение, резервирование и откат

Проверяется штатный цикл backup → preview → apply → повторное apply → reload
→ rollback. Preview должен оставить конфигурацию без изменений. После apply
тестовый HTTP-порт должен стать недоступен с контроллера, при работающем HTTP
внутри гостя и сохранённом SSH. После rollback доступность должна восстановиться.

Аварийный контроль посылает SIGKILL принадлежащему стенду процессу rollback
после перемещения конфигурационного каталога. Следующий запуск восстанавливает
состояние по durable journal. Проверяются содержимое, права, владельцы,
поддержанные метки, runtime и повтор завершённого rollback. Итоговое состояние
гостя сравнивается с исходным снимком, включая активную cron.

Инвентарь сравнивается с независимым `dpkg-query` по восьми полям: имя,
бинарная версия, архитектура, source package, source version, состояние dpkg,
Maintainer и Origin. Затем один и тот же SBOM обрабатывается production-путём
HCP и отдельным native Trivy. Сравниваются записи пакетов и полные существенные
поля всех найденных уязвимостей, а не только число результатов.

Сценарий каждой ОС предусматривает девять контрольных случаев. Реальная граница
**CVE-2024-6119** задаётся advisory соответствующего производителя:

| Контроль | Уязвимая версия | Исправленная версия | Источник |
| --- | --- | --- | --- |
| Debian 12, `libssl3` / `openssl` | `3.0.14-1~deb12u1` | `3.0.14-1~deb12u2` | [Debian tracker, DSA-5764-1](https://security-tracker.debian.org/tracker/CVE-2024-6119) |
| Ubuntu 24.04, `libssl3t64` / `openssl` | `3.0.13-0ubuntu3` | `3.0.13-0ubuntu3.4` | [USN-6986-1](https://ubuntu.com/security/notices/USN-6986-1) |

Дополнительные случаи проверяют multiarch, binNMU, source/binary различия,
epoch и неизвестного/стороннего поставщика. Это синтетические метаданные для
проверки интерпретации, а не утверждение, что каждая их комбинация была выпущена
производителем. Контрольные уязвимые версии не устанавливаются в гостевые ОС.
Отсутствие указанного CVE в исправленном контроле не означает отсутствие всех CVE.

Maintainer/Origin остаются эвристикой. Неизвестное происхождение, пропущенная
сканером запись и неприменимый advisory не должны превращаться в отрицательный
результат. PASS самого acceptance-сценария означает, что эти ограничения
сохранены корректно; он не делает каждую находку подтверждённо эксплуатируемой.

### Почему много пакетных находок не равно числу различных CVE

В локальном Ubuntu replay семь бинарных пакетов из `linux 6.8.0-147.147`
получили один и тот же набор из **3176 CVE** с одинаковыми vendor status,
FixedVersion, severity и источником. Получилось **22 232 пакетных наблюдения**;
ещё 124 относятся к другим пакетам. Во всём результате — **3240 различных CVE**.
Source version сохранена правильно; наблюдавшееся ядро — `6.8.0-147-generic`.

Выборочно сопоставлены три записи с официальным tracker Ubuntu для
**noble / linux** по состоянию на 1 ноября 2026 года:

| Advisory | Статус производителя | Что проверено |
| --- | --- | --- |
| [CVE-2013-7445](https://ubuntu.com/security/CVE-2013-7445) | Уязвимо, исправление отложено | Native `affected` согласуется с незакрытым advisory; уточнение deferred в нём отсутствует |
| [CVE-2026-63825](https://ubuntu.com/security/CVE-2026-63825) | Уязвимо; приоритет Critical | Native статус и severity согласуются с tracker; условия GCOV/IPComp не проверялись |
| [CVE-2026-99999](https://ubuntu.com/security/CVE-2026-99999) | Уязвимо; работа над `6.8.0-149.149` продолжается | Отсутствие опубликованного FixedVersion согласуется с work in progress; целевая версия не объявляется доступным исправлением |

Эта выборка не подтверждает все 3176 kernel CVE. Source-level advisory само по
себе не доказывает наличие уязвимого исполняемого кода в headers, libc headers
или tools, нужную конфигурацию ядра, загруженный модуль или достижимость пути.
В отчётах следует различать CVE, затронутые пакетные записи и подтверждённую
применимость к работающей системе. Это отдельное направление развития оценки.

### Третий запуск: обнаружение ограниченного объёма вывода

[41342030119](https://github.com/Danil-super/hardening-control-platform/actions/runs/41342030119)
проверял source `3d18731453d6fd747464f11fc066137ec0cb17e1`, tree
`b2c0b6585180042073ee0fe1da945b7df6026410`. Дерево PR checkout
`9860538737818526408a36c35460d64c5d13a2c9` совпало с ним.
Debian прошёл 11 из 11 стадий. Ubuntu прошёл первые 9, включая шесть отчётов,
их публикацию и аварийный rollback, затем остановился на CVE-проверке.
Общий workflow завершился с ошибкой; финальный checkpoint Ubuntu не выполнялся.

Причина подтверждена read-only replay сохранённого инвентаря из 664 пакетов:
Trivy 0.74.0 на той же базе вернул валидный JSON объёмом **90 119 014 байт**,
что больше прежних **64 МиБ = 67 108 864 байт**. Выход был нулевым, stderr пустым,
источники до/после не изменились. SBOM пересоздан с теми же пакетными метаданными
и новым serial/timestamp; побайтовое совпадение с исходным SBOM не заявляется.
Ошибка транспорта правильно сохранила `manual/partial`, а не результат
«уязвимостей нет».

После повышения предела до **128 МиБ** отдельный полный production replay
прошёл native inventory и девять controls. Сохранены 664 пакета и 22 356
записей CVE/пакет, относящихся к 3240 различным CVE. Полный HCP JSON составил
26 609 727 байт, нормализованный JSON — 53 804 283 байта. Неизвестный supplier
одного пакета оставил coverage частичным. Эти локальные результаты отделены
от последующего полного native запуска в итоговой таблице выше.

Peak RSS этого acceptance helper — **1 360 076 КиБ, около 1,30 ГиБ**.
Helper включает нормализацию и отдельный native replay; это не замер
standalone web scan. Предел stdout не является общим пределом памяти:
JSON parser, массивы находок и экспорт требуют собственных ресурсов.

## Границы результата

- Подтверждены конкретные выпуски, образы и архитектура x86_64. Новые выпуски,
  SUSE, aarch64 и другие Linux-системы требуют собственных нативных протоколов.
- Ограниченная модель firewall не подтверждает весь внешний сетевой путь,
  все роли сервера, FORWARD, ICMP, DNAT, контейнерные сети и существующие соединения.
  Отдельный внешний IPv6-трафик этим стендом не проверяется.
- Девять контролей на ОС и одна CVE-граница на производителя не измеряют общую
  precision/recall всех Linux CVE. Полноту нужно измерять на расширенном размеченном наборе.
- Browser onboarding и полнота политик AppArmor/SELinux здесь не аттестуются.
  Ранее проверенный enforcing SELinux на Alma/Rocky остаётся отдельным протоколом.
- Автоматическое изменение firewall ограничено поддержанными UFW/firewalld
  на systemd. Новый audit-декодер не включает самостоятельный nftables remediation.
- Проверены байты закреплённых образов по контрольным суммам издателей;
  независимая OpenPGP-цепочка при подготовке image pins не проверялась.
  Сетевые apt-репозитории и CVE-база изменяемы; протокол фиксирует полученное состояние.
- GitHub Actions хранит полные артефакты этого workflow 14 дней. Краткий протокол,
  хеши и контрольные fixtures сохранены в репозитории; это не архив всей CVE-базы.

Следующие направления: [roadmap](future-roadmap.md), прежде всего проверка
firewall относительно роли, расширение размеченных CVE-контролей и отдельные
нативные матрицы новых дистрибутивов и архитектур.
