# Инструменты аудита и источники данных

HCP запускает установленные сканеры и объединяет их результаты. Ansible доставляет команды и собирает данные по SSH. Для аудитов сохраняются отдельные JSON-отчёты с источником, временем и техническими доказательствами. Dependency-Track сохраняет отдельно подтверждение передачи SBOM и полученный позднее результат анализа. CVSS одинаковых CVE из разных источников не суммируются.

| Контур | Что подтверждает | Где выполняется | Результат в HCP |
| --- | --- | --- | --- |
| Ansible + проверки HCP | Настройки SSH, службы, права и другие выбранные параметры Linux | Команды на хосте через SSH, управление с control node | Факты и результаты конкретных проверок |
| ssh-audit | Криптографические алгоритмы и рекомендации для SSH-сервера | На control node, подключение к SSH-порту | Алгоритмы, рекомендации, ограничения проверки |
| Nmap | Наблюдаемые из control node открытые TCP-порты | На control node | Порты и явно зафиксированный охват; открытый порт сам по себе не считается CVE |
| Lynis | Системные настройки и рекомендации по харденингу | Во временном каталоге целевого хоста | Предупреждения, рекомендации и отдельный индекс Lynis |
| OpenSCAP + SSG | Соответствие конкретному базовому профилю | На подготовленной целевой ВМ | Правила profile: pass/fail/manual |
| Trivy | Известные CVE пакетов поддерживаемого дистрибутива | В контейнере control node | CVE, установленная версия, версия с исправлением и статус поставщика |
| Greenbone / OpenVAS | Сетевая поверхность и уязвимости сервисов | На отдельном сетевом scanner | Импорт XML-отчёта по одному хосту |
| OWASP Dependency-Track | Анализ компонентов, SBOM и VEX | В отдельном Docker profile | Передача SBOM и отдельный импорт находок; полнота vulnerability intelligence требует проверки |

| Инструмент | Сеть во время аудита | Откуда берутся правила/база |
| --- | --- | --- |
| Ansible, ssh-audit, Nmap | Доступ control node к хосту; интернет для проверки не нужен | Проверки HCP и данные установленной версии инструмента |
| Lynis | SSH для передачи и сбора; необязательная проверка обновления Lynis отключена | Локальные тесты и профиль из установленного пакета |
| OpenSCAP | Интернет при выполнении локального SSG не нужен, если все зависимости content подготовлены | Заранее установленный datastream для точной ОС |
| Trivy | В сетевом режиме — доступ к registry базы; в локальном режиме — сохранённый cache | Trivy DB с advisory поставщиков; дата базы проверяется |
| Greenbone | Scanner должен видеть цель; для обновлений — сервер feeds или подготовленный перенос | Локальные Greenbone feeds; импорт XML в HCP работает без интернета |
| Dependency-Track | HCP должен видеть API сервиса; сам сервис обращается к включённым источникам intelligence | Его собственные источники и cache, независимо от переключателя Trivy |

Первичная установка пакетов, контейнеров и обновлений требует доступа к их источникам либо заранее подготовленных локальных зеркал. Переключатель «Сетевая/Локальная база» на сайте управляет **только Trivy**.

## Nmap: глубина проверки портов

В «Дополнительных проверках» выберите **«Открытые TCP-порты — Nmap»** и одну глубину. Это один инструмент с разным охватом, а не три отдельные кнопки.

| Режим | Охват | Когда выбирать |
| --- | --- | --- |
| Быстрая | 100 наиболее распространённых TCP-портов | Оперативная первичная проверка |
| Стандартная | 1 000 наиболее распространённых TCP-портов | Обычный ручной аудит сервера |
| Полная TCP | Все порты 1–65 535 | Приёмка, расследование или проверка нестандартных сервисов |

Полная TCP-проверка может занять до 30 минут, если firewall отбрасывает пакеты без ответа. Все режимы выполняют облегчённое определение сервиса только на открытых портах. **UDP не входит ни в один из них**: UDP-сканирование существенно медленнее и выполняется отдельно по согласованному объёму. В отчёте HCP всегда отображается выбранный охват; успешный быстрый или стандартный режим не означает, что все TCP-порты закрыты.

## 1. Trivy: основной CVE-контур

Контейнер HCP содержит закреплённый Trivy. После выбора «Пакеты и CVE — Trivy» в «Дополнительных проверках» платформа создаёт CycloneDX 1.5 SBOM из фактического инвентаря пакетов, запускает `trivy sbom` и сохраняет CVE-отчёт и SBOM в persistent volume.

В сетевом режиме HCP сам поддерживает общий cache Trivy: перед CVE-аудитом он проверяет `trivy.db` и `metadata.json`, а если базы нет, она устарела или дату нельзя подтвердить — один раз запускает `trivy image --download-db-only`. Это один общий cache для поддерживаемых ОС, а не отдельная база на хост или выпуск. В панели «Источники» отображается свежесть и есть кнопка «Обновить сейчас», но вручную готовить базу перед обычным аудитом не нужно.

**Локальная база** выбирается только в «Расширенной настройке для изолированной сети». В этом режиме обновление баз и сетевой поиск зависимостей Trivy отключены; используется существующий cache в persistent volume HCP. Этот выбор относится к Trivy, а не к сетевым настройкам остальных сервисов. Сохранённый в интерфейсе выбор имеет приоритет над начальным значением `HCP_TRIVY_MODE` из `.env`.

Для сети с разрешённым доступом к публичным источникам оставьте сетевой режим и стандартную настройку:

```env
HCP_TRIVY_MODE=online
```

Если public Internet запрещён, но есть внутреннее OCI-зеркало, укажите его и оставьте **сетевой режим** для обновления CVE-базы:

```env
HCP_TRIVY_DB_REPOSITORY=registry.security.intra/trivy-db
```

При пустой `HCP_TRIVY_DB_REPOSITORY` HCP последовательно указывает Trivy официальные источники: Google mirror, GHCR, AWS ECR и Docker Hub. Несколько внутренних адресов можно указать через запятую в порядке приоритета. После автоматической подготовки пакетный аудит использует проверенный cache с `--skip-db-update`; кратковременная недоступность registry не меняет уже начатую проверку.

Для изолированной сети сначала загрузите и проверьте cache совместимой версии Trivy на узле с доступом к источнику, затем перенесите каталог `db` целиком, включая `trivy.db` и `metadata.json`, в `HCP_TRIVY_CACHE_DIR` control node. Обеспечьте чтение файлов пользователем `node`. В панели выберите **Локальная база**. Требование полной сетевой изоляции обеспечивается также правилами сети стенда.

Отсутствующая база, неизвестная дата публикации, неполный инвентарь или нераспознанная ОС не дают заключения «уязвимостей нет». HCP проверяет наличие файла базы и дату `UpdatedAt` в metadata, сравнивает возраст с `HCP_TRIVY_MAX_DB_AGE_HOURS` (по умолчанию 168 часов). Дата копирования/скачивания файла не подтверждает свежесть CVE-данных. Ограничения сохраняются в отчёте и видны в панели.

Для каждой находки HCP сохраняет статус поставщика и источник Trivy. **`fixed` означает, что поставщик выпустил исправление: найденная установленная версия всё ещё уязвима.** `FixedVersion` показывает, до какой версии нужно обновиться. `will_not_fix` не означает безопасность. CVE не переводятся в произвольный процент защищённости. Эти значения определены в [официальной документации статусов Trivy](https://trivy.dev/docs/latest/configuration/filtering/#by-status).

При сопоставлении важны точный дистрибутив, его версия, источник пакета и версия source package. Совпадение upstream-номера само по себе недостаточно: поставщики выпускают backport-исправления. Покрытие пакетного инвентаря и ограничения конкретного выпуска ОС проверяйте в отчёте; приложения, установленные вручную вне поддерживаемого пакетного менеджера, этим аудитом не покрываются. См. [источники CVE и правила выбора advisory Trivy](https://trivy.dev/docs/latest/scanner/vulnerability/).

Основной поддерживаемый сценарий этого сборщика — пакеты ОС Debian/Ubuntu из dpkg. Результаты RPM помечаются частичными: сбор не подтверждает все сведения о source epoch, modularity и репозиториях. Библиотеки приложений и контейнерные образы требуют отдельного сбора SBOM и этим инвентарём не покрываются.

Для Astra Linux сохраняется также точный выпуск из `/etc/astra_version` в инвентаре и свойстве SBOM `hcp:astra-version`. `ID_LIKE=debian` не подменяет экосистему Astra экосистемой Debian. Для Astra предусмотрен отдельный [OVAL-аудит и встроенный конфигурационный профиль](astra-audit.md). Полнота охвата CVE остаётся свойством выбранной базы и не переносится с Debian; условия OVAL оценивает OpenSCAP. Подготовка описана в [инструкции Astra](astra-lab.md).

## 2. OpenSCAP и SCAP Security Guide

OpenSCAP даёт сильное доказательство только при точном соответствии ОС, datastream и профиля. Поэтому HCP не выбирает «похожий» файл автоматически и не устанавливает scanner на рабочую ВМ.

На каждом хосте администратор отдельно подготавливает OpenSCAP и подходящий контент SSG. Для Debian сначала проверьте доступные файлы установленного пакета:

```bash
sudo apt update
sudo apt install openscap-scanner ssg-debian
dpkg -L ssg-debian | grep -- '-ds.xml$'
```

Наличие `ssg-debian` не гарантирует datastream для вашего выпуска Debian. Если подходящего файла нет, подготовьте проверенный выпуск ComplianceAsCode, поддерживающий точную ОС. Не подставляйте профиль другого дистрибутива. Через `oscap info /путь/к/проверенному-ds.xml` получите реальный ID профиля, затем назначьте его группе в разделе «Политики». Для Ubuntu и других ОС требуется свой content.

Согласованное исключение содержит ID правила, причину и дату окончания. Оно добавляет пояснение к находке, сохраняя исходные `status`, `risk` и счётчики нарушений. Если группы хоста задают конфликтующие политики, запуск блокируется до устранения конфликта.

Переменные ниже используются для хостов без назначенной политики. Это пример формы значения; путь и ID необходимо заменить на существующие на вашей ВМ:

```env
HCP_OPENSCAP_DATASTREAM=/usr/share/xml/scap/ssg/content/ssg-debian12-ds.xml
HCP_OPENSCAP_PROFILE=xccdf_org.ssgproject.content_profile_cis_server_l1
```

Перезапустите HCP и в «Дополнительных проверках» выберите `Проверить профиль OpenSCAP`. На ВМ создаётся временный каталог с ARF-результатом; он удаляется в блоке `always`. Для встроенного профиля Astra туда также передаётся содержимое проверок. HCP сохраняет нормализованный отчёт с ID правила, исходной severity и результатом. Если `oscap`, datastream или переменные не готовы, результат отмечается `manual`, а не `passed`.

Не применяйте один CIS/STIG-профиль ко всем ролям без исключений и протокола утверждения. Результат OpenSCAP — доказательство состояния, а не разрешение автоматически менять систему.

## 3. Greenbone / OpenVAS

### Где выполнять действия

Основной вариант для стенда: Greenbone Community Containers работают **на управляющей Ubuntu, где уже запущен HCP**, но отдельным Docker-проектом. На целевую Astra сканер не устанавливается.

| Место | Что здесь делать |
| --- | --- |
| Обычный терминал управляющей Ubuntu, вне контейнера HCP | Установить и запустить контейнеры Greenbone, смотреть их логи. |
| Целевая Astra | Включить ВМ и узнать её IP. Команды установки Greenbone здесь не выполнять. |
| Браузер на управляющей Ubuntu: `https://localhost` | Интерфейс Greenbone: создать цель, запустить задачу, скачать XML. |
| Тот же браузер: `http://localhost:3000` | Интерфейс HCP: выбрать ту же Astra и импортировать скачанный XML. |

`localhost` всегда означает компьютер, где открыт браузер. Это адрес локального интерфейса сканера, **не адрес цели**. В поле цели Greenbone указывается IP Astra из HCP, то есть адрес именно той машины, которую вы хотите проверить. Сканер должен иметь сетевой доступ к Astra из своих контейнеров; работающее SSH-подключение HCP само по себе этого не подтверждает.

### 1. Терминал Ubuntu: запустите сканер

Проверьте `docker version` и `docker compose version`: текущему пользователю нужен доступ к Docker. Также нужны `curl`, интернет и дополнительные ресурсы сверх HCP: минимум 2 CPU, 4 ГБ RAM и 20 ГБ диска; рекомендуется 4 CPU, 8 ГБ RAM и 60 ГБ диска. Установка Docker описана в [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/).

Если Greenbone уже установлен, переходите к шагу 2. Иначе выполните строки по порядку в одном обычном терминале Ubuntu:

```bash
GREENBONE_DIR="$HOME/greenbone-community-edition"
mkdir -p "$GREENBONE_DIR"
curl -fL https://greenbone.github.io/docs/latest/_static/compose.yaml -o "$GREENBONE_DIR/compose.yaml"
docker compose -p greenbone-community-edition -f "$GREENBONE_DIR/compose.yaml" pull
docker compose -p greenbone-community-edition -f "$GREENBONE_DIR/compose.yaml" up -d
```

Файл Greenbone находится в домашнем каталоге Ubuntu. Не добавляйте эти службы в Compose-файл HCP. Открытие инструкции не выполняет команды автоматически.

### 2. Браузер и терминал Ubuntu: дождитесь баз

Сначала в терминале Ubuntu проверьте готовность менеджера:

```bash
GREENBONE_DIR="$HOME/greenbone-community-edition"
docker compose -p greenbone-community-edition -f "$GREENBONE_DIR/compose.yaml" ps gvmd
```

Дождитесь `healthy` у `gvmd`. Страница входа может быть доступна раньше менеджера; в это время появляется `GMP error during authentication`. После готовности обновите страницу и повторите вход. Если статус стал `unhealthy` или ошибка сохраняется при `healthy`, проверьте логи `gvmd` и `gsad`: это требует отдельной диагностики, а не сброса пароля наугад.

В браузере **на той же Ubuntu** откройте `https://localhost`. Для новой установки из официального Compose первый вход — `admin` / `admin`; сразу смените пароль в интерфейсе. Локальная установка использует самоподписанный сертификат.

Первая загрузка и индексация баз проверок (feeds) может занимать от нескольких минут до нескольких часов. Контейнеры могут уже работать, пока сканер ещё загружает данные. Логи смотрите в терминале Ubuntu:

```bash
GREENBONE_DIR="$HOME/greenbone-community-edition"
docker compose -p greenbone-community-edition -f "$GREENBONE_DIR/compose.yaml" logs -f ospd-openvas gvmd
```

`Ctrl+C` закрывает просмотр логов, контейнеры продолжают работать. Дождитесь загрузки баз, доступности сканера и конфигурации `Full and fast` в интерфейсе. При обновлении повторите `pull` и `up -d` из шага 1 и снова дождитесь загрузки данных службами. Одного скачивания образов недостаточно.

### 3. Сайт Greenbone: задайте цель Astra

Откройте **Configuration → Targets → New Target**. Задайте имя «Astra» и укажите в **Hosts** один IP Astra из HCP. Для каждого проверяемого хоста указывайте его собственный адрес. Здесь не нужны адрес управляющей Ubuntu или `localhost`. При импорте в HCP выбирайте тот же хост, который проверяли; если XML содержит несколько машин, импортируйте его для нужных хостов поочерёдно — результаты других машин HCP исключит.

Первую сетевую проверку проводите без учётных данных Astra. SSH-ключи HCP не используются и сканеру не передаются.

### 4. Сайт Greenbone: запустите задачу

В **Scans → Tasks → New Task** выберите цель «Astra», сканер по умолчанию и конфигурацию **Full and fast**. Сохраните задачу, запустите и дождитесь **Done**. Если конфигурации нет, вернитесь к шагу 2.

Объём проверки зависит от конфигурации и списка портов. Этот запуск не гарантирует обнаружение всех уязвимостей ОС.

### 5. Сайт Greenbone: скачайте отчёт

В **Scans → Reports** откройте отчёт завершённой задачи и выберите экспорт и формат с точным названием **XML**. **Anonymous XML не подходит:** в нём адреса хостов заменены, и HCP не сможет сопоставить результаты с выбранной машиной. Если этот формат уже скачан, повторять сканирование не нужно — заново экспортируйте тот же готовый отчёт. Нужен отчёт, а не экспорт настроек задачи. PDF, CSV и архив не подходят.

Перед экспортом откройте **Edit Filter** (карандаш): задайте **QoD = 0**, включите **Critical, High, Medium, Low, Log, False Pos.** и нажмите **Update**. Сверьте счётчик Results: показанное число должно совпадать с общим количеством записей. Затем нажмите **Download filtered Report**, выберите **Report Format → XML** и **OK**. Иначе часть находок и диагностических записей не попадёт в файл; HCP отметит такой импорт как неполный. Низкий QoD сохраняется как требующий проверки, а не как подтверждённая уязвимость.

Файл `.xml` сохранится на компьютере, где открыт браузер, обычно в папке «Загрузки» Ubuntu. На Astra его переносить не нужно.

### 6. Сайт HCP: импортируйте XML

Откройте HCP → **Хосты → Настроить** у той же Astra → **«Сетевой сканер Greenbone / OpenVAS — импорт XML»**. Выберите скачанный распакованный `.xml` до 20 МБ и нажмите **«Импортировать XML»**. После импорта откройте отчёт HCP.

В веб-отчёте Greenbone названия, описания и рекомендации переводятся на русский локально, по мере появления записей на экране. Рядом доступен английский оригинал. CPE, CVE, адреса, порты, версии с буквенными суффиксами и названия SSH-алгоритмов сохраняются как технические данные. Исходный JSON не переписывается. CVSS и QoD сохраняют значения инструмента; перевод не участвует в определении риска или статуса находки.

HCP проверяет адрес выбранного хоста и исключает чужие результаты. Он не запускает задачи Greenbone через API. Исходный XML обрабатывается во временном каталоге и удаляется; сохраняется нормализованный отчёт: OID, CVE, адрес, порт, threat, CVSS severity, QoD, описание и рекомендация Greenbone. Состояние завершения и ограничения экспорта влияют на полноту результата; дата импорта не заменяет дату аудита. Низкий QoD и открытый порт сами по себе не подтверждают эксплуатацию уязвимости.

### Если сканер на отдельной Ubuntu-ВМ

Все команды шагов 1–2 выполняйте **на ВМ сканера**. Astra остаётся целью. Чтобы открыть Greenbone в браузере управляющей Ubuntu, запустите **на управляющей Ubuntu** туннель:

```bash
ssh -N -L 9443:localhost:443 SCANNER_USER@SCANNER_HOST
```

Замените `SCANNER_USER` на имя пользователя ВМ сканера, а `SCANNER_HOST` — на адрес этой ВМ. Оставьте терминал открытым. Greenbone будет доступен на управляющей Ubuntu по `https://localhost:9443`; шаги 3–5 выполняйте там. HCP остаётся по прежнему адресу. Выбирайте XML из загрузок этого браузера.

Официальные источники: [Greenbone Community Containers](https://greenbone.github.io/docs/latest/22.4/container/index.html), [загрузка и обновление feeds](https://greenbone.github.io/docs/latest/22.4/container/workflows.html), [создание цели и задачи](https://docs.greenbone.net/GSM-Manual/gos-24.10/en/scanning.html), [экспорт отчётов](https://docs.greenbone.net/GSM-Manual/gos-24.10/en/reports.html).

## 4. OWASP Dependency-Track

Dependency-Track включён в отдельный Compose profile. Заполните секреты в `.env`, затем запустите его вместе с HCP:

```bash
docker compose --profile dependency-track up -d --build
```

Интерфейс D-Track по умолчанию слушает только `127.0.0.1:8080`; API — `127.0.0.1:8081`. После первоначальной безопасной настройки в его UI создайте API key и поместите его только в `.env` HCP:

```env
HCP_DEPENDENCY_TRACK_URL=http://dependency-track-api:8080
HCP_DEPENDENCY_TRACK_API_KEY=replace-with-scoped-api-key
```

После следующей проверки пакетов Trivy HCP автоматически отправит созданный SBOM в проект с именем inventory alias. Версия проекта `hcp-sbom:<SHA-256>` фиксирует конкретный SBOM; другая инвентаризация получает другую версию и не перезаписывает компоненты предыдущей. Повторная отправка того же исходного отчёта при неизменном SBOM и endpoint использует сохранённое подтверждение передачи.

В отчёте Dependency-Track нажмите **«Получить результат анализа»**. HCP проверяет состояние обработки и до трёх минут повторяет запросы; ожидание можно остановить и продолжить позже. Завершённый импорт открывается отдельным отчётом `dependency-track-analysis`. Его находки входят в единую сводку и итоговый PDF, а исходное подтверждение передачи остаётся исторической записью. Новая проверка результата создаёт новый снимок только при изменении анализа; старые отчёты не переписываются.

API key должен иметь `BOM_UPLOAD`, а при автоматическом создании проектов — `PROJECT_CREATION_UPLOAD`. Для получения результата нужны также `VIEW_PORTFOLIO` и `VIEW_VULNERABILITY` с доступом к нужным проектам. Отсутствие прав чтения не мешает самой передаче, но получение результата явно завершится ошибкой доступа. После изменения `.env` пересоздайте HCP через `docker compose up -d hcp`: обычный `restart` не перечитывает environment. Точный порядок первоначального запуска, версии образов и постоянные тома описаны в [README](../README.md).

Для Dependency-Track **4.14.3** `/api/v1/event/token/{uuid}` возвращает только `processing`: значение `false` возможно и для неизвестного токена. Поэтому HCP дополнительно проверяет серверные времена импорта и анализа, имя/версию/UUID проекта, полный манифест компонентов и неизменность проекта во время чтения. Пагинация и `X-Total-Count` проверяются, находки других компонентов отклоняются. SHA-256 исходного CVE-отчёта и SBOM сверяется повторно перед публикацией. Ранее переданные отчёты без такой привязки требуют новой передачи исходного CVE-отчёта.

`analysisStatus=complete` означает, что HCP получил согласованный результат анализа этого SBOM. Он **не доказывает** полноту зеркал NVD/GHSA/OSV или успешность каждого настроенного анализатора: API 4.14.3 не предоставляет такого доказательства. Поэтому импорт сохраняет `partial=true`, не создаёт `PASS` при нуле находок и не подтверждает устранение пункта плана. Нативная severity, CVE/идентификатор поставщика, установленная версия, PURL/CPE и решение D-Track сохраняются; suppressed/false-positive/not-affected/resolved остаются явно обозначенными наблюдениями для ручной оценки.

Программный клиент использует `POST /api/ansible/dependency-track/refresh` с `{ "hostAlias": "host", "reportId": "идентификатор-передачи-или-результата" }`. Ответ содержит `status: processing | complete | error`; при `complete` — `reportId` нового или повторно используемого снимка. Один запрос ограничен 45 секундами, каждый полный список — 30 000 элементами / 32 МиБ; превышение прекращает импорт целиком. API key и адрес сервера не записываются в отчёт: для связи с конфигурацией сохраняется fingerprint endpoint.

Контракт проверен по исходникам версии 4.14.3: [EventResource](https://github.com/DependencyTrack/dependency-track/blob/4.14.3/src/main/java/org/dependencytrack/resources/v1/EventResource.java), [BomUploadProcessingTask](https://github.com/DependencyTrack/dependency-track/blob/4.14.3/src/main/java/org/dependencytrack/tasks/BomUploadProcessingTask.java), [VulnerabilityAnalysisTask](https://github.com/DependencyTrack/dependency-track/blob/4.14.3/src/main/java/org/dependencytrack/tasks/VulnerabilityAnalysisTask.java), [FindingResource](https://github.com/DependencyTrack/dependency-track/blob/4.14.3/src/main/java/org/dependencytrack/resources/v1/FindingResource.java).

### Проверка CVE-источников Dependency-Track

Приём SBOM и окончание BOM-processing не доказывают завершение CVE-анализа. В настройках DTrack проверьте источники: NVD REST API и внутренний анализатор; GHSA включайте при наличии отдельного токена. OSV должен оставаться отключённым. Для NVD API-ключ необязателен, но без него первичная синхронизация ограничивается скоростью запросов. Интернет нужен серверу DTrack при обновлении источников; его локально сохранённые данные используются внутренним анализатором без интернета. Онлайн-анализаторы имеют собственные сетевые требования. [NVD](https://docs.dependencytrack.org/datasources/nvd/), [GHSA](https://docs.dependencytrack.org/datasources/github-advisories/).

Для чтения состояния своего сервера создайте отдельный ключ с `SYSTEM_CONFIGURATION` и передайте его через переменную окружения, не через аргумент команды. Обычный upload-only ключ HCP для этого не подходит. Команды ниже выполняются из корня репозитория в Bash; скрытый ввод не попадает в историю:

```bash
read -r -s -p 'Dependency-Track inspection API key: ' HCP_DEPENDENCY_TRACK_API_KEY
export HCP_DEPENDENCY_TRACK_API_KEY
python3 deployment/tests/verify_dependency_track_sources.py \
  --inspect-url http://127.0.0.1:8081 --allow-http \
  --output .lab/dtrack-source-inspection
unset HCP_DEPENDENCY_TRACK_API_KEY
```

Скрипт выполняет только GET-запросы и сохраняет `existing-source-inspection.json`: готовность API/БД, включённые источники и безопасный набор настроек, даты и обнаруженные проблемы. Даже код выхода 0 здесь означает только `inspection-only`, а `fullMirrorVerified` остаётся `false`: свежий курсор не доказывает успешную первичную загрузку всей базы. Дополнительно проверьте завершение `NistApiMirrorTask` в логах, обработку общего числа записей без download/persistence errors, а затем находку на контрольной уязвимой версии и отсутствие этой же CVE на исправленной.

Для отдельного воспроизводимого испытания есть `python3 deployment/tests/verify_dependency_track_sources.py`: он создаёт собственный временный DTrack 4.14.3 и загружает настоящую CVE-2021-44228 штатным NVD mirror. Затем через адаптер HCP проверяет `log4j-core` 2.14.1 и 2.17.1. Требуются Linux, Docker Compose, Node 24, `npm ci` в `web` и доступ к NVD. Существующий DTrack не меняется. Это ограниченная проверка источника и сопоставления версий; она не подтверждает весь NVD, GHSA или пакеты Astra. Фактический результат CI указан в [протоколе](verification-report.md).

## Как принимать итоговый отчёт

1. Проверьте дату, доступность scanner и полноту каждого отчёта. Разберите записи `manual`: они требуют решения администратора и не равны успешной проверке.
2. Для CVE сверяйте пакет, установленную версию, fixed version и vendor security tracker: дистрибутивы могут backport-ить исправления без смены upstream-версии.
3. Подтверждайте сетевые находки Greenbone с владельцем сервиса и Nmap/фактической конфигурацией firewall.
4. По OpenSCAP фиксируйте профиль, версию SSG и допустимые исключения.
5. Приоритет исправления давайте по подтверждённой комбинации: эксплуатируемость, доступность из сети, роль сервера и наличие исправления, а не только по CVSS.

## Регулярный запуск и корреляция

`hcp-scheduled-audit.timer` выполняет лёгкий Ansible-аудит каждые 15 минут. `hcp-deep-audit.timer` ежедневно запускает инвентаризацию пакетов и Trivy; для этого в `.env` нужен отдельный `HCP_SCHEDULE_API_KEY`. OpenSCAP включается в глубокий запуск только через systemd override после подготовки SSG и отдельной inventory-группы.

В «Сводке» HCP сопоставляет последние отчёты одного inventory-хоста по CVE, сетевым портам, OpenSCAP rules и Greenbone OID. Устаревшие, неполные и недоступные источники отмечаются отдельно. Совпадение CVE или порта не доказывает уязвимость: два инструмента могут использовать одну и ту же первичную базу или наблюдать разные компоненты. CVSS не суммируются. Срок свежести задаёт `HCP_CORRELATION_MAX_AGE_HOURS` (по умолчанию 168).

Практический порядок проверки всех интеграций и ожидаемые результаты приведены в [инструкции тестового стенда](../deployment/lab/README.md).

Исходные спецификации: [Trivy air-gap](https://trivy.dev/docs/latest/advanced/air-gap/), [SCAP Security Guide](https://www.open-scap.org/security-policies/scap-security-guide/), [Greenbone Community Containers](https://greenbone.github.io/docs/latest/22.4/container/index.html), [Dependency-Track](https://docs.dependencytrack.org/).
