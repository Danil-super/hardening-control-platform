# Debian: наблюдение за APT-репозиториями и границы происхождения пакетов

## Почему отдельная проверка

В инвентаре Debian `dpkg-query` показывает бинарный/исходный пакет, версию, архитектуру, Maintainer и Origin. Эти поля необходимы для сопоставления с Debian Security Tracker, но **не удостоверяют**, что конкретный установленный `.deb` был получен из официального архива, проверен ключом Debian или не был подменён. Даже адрес электронной почты из домена Debian может быть записан сторонним пакетом.

В HCP теперь выполняется **дополнительное пассивное наблюдение локальных APT-индексов**, но оно не изменяет статус пакета или заключение по CVE:

- Только для точного `ID=debian` и известного `VERSION_CODENAME`. Astra Linux и Ubuntu не наследуют этот контроль.
- Выполняется `env LC_ALL=C apt-cache -o Dir::Cache::pkgcache= -o Dir::Cache::srcpkgcache= policy`, **без** `apt-get update`, установки, удаления пакетов, обращения к сети или генерации файлов кэша.
- Для `release`-записей сохраняются число индексов, количество записей с меткой Debian и другими метками, названия веток, их согласованность с кодовым названием ОС и SHA-256 полного локально наблюдённого ответа. Псевдоисточник `/var/lib/dpkg/status` (`release a=now`) исключается.
- Не сохраняются URL репозиториев, логины, токены, пути к индексам и сырые построчные ответы. Неизвестные имена поставщиков представлены как `other-label-observed`, а не передаются в публичные отчёты.
- При невозможности однозначного разбора статус `ambiguous` либо `unavailable`, а не `verified`. При отсутствии старого поля инвентаря — `not_collected`.

Результат включается в исходный JSON пакетов (`packageInventory.aptRepositories`), CVE-отчёт (`vulnerabilityScan.aptRepositoryEvidence`), страницу отчёта и итоговые JSON/PDF, привязанные к SHA-256 исходного отчёта. В итоговом отчёте сохраняется контрольная сумма проекции `debianAptIndexEvidenceSha256`.

**Три поля всегда равны `false`:** `publisherAuthenticated`, `repositorySignatureVerified`, `installedPackageOriginVerified`. Это намеренно. Совпадение метки Debian или имени ветки не подтверждает подпись `InRelease`, цепочку `Packages → .deb`, криптографическую подлинность ранее установленных пакетов, происхождение пакета или доверенный CVE-вердикт. Сверка остаётся предварительной, исходный Trivy-результат сохраняется, автоматические исправления не разрешаются.

## Приёмочные испытания

`ansible/tests/test_package_inventory.py` проверяет разбор, отсутствие утечек URL/учётных данных, ошибочные, сторонние и пустые источники, выключение для Astra/Ubuntu и совместимость Python 3.5. `web/tests/debian-apt-provenance.test.mjs` проверяет, что контроллер не принимает неподтверждённые утверждения о подписи или происхождении как достоверные. `web/tests/trivy-accuracy.test.mjs` подтверждает независимость вывода Trivy от APT-метаданных.

В нативном CI Debian 12 основной `hcp-package-inventory.py` и **независимый** `apt-cache policy` на одноразовом KVM-госте должны получить идентичный SHA-256, без изменения пакетов. Затем результат присутствует в протоколе CVE-проверки, а итоговые JSON/PDF должны сохранять источник и контрольные суммы. Это проверка целостности наблюдения, **не** проверка подписи репозитория.

## Что необходимо для более сильной аттестации

Для криптографического происхождения нужны отдельные подтверждённые ключи/пинованные отпечатки Debian, проверенная цепочка `InRelease/Release → Packages → .deb`, содержимое бинарного пакета и доказательство соответствия **именно установленным байтам**. Данные текущего APT cache и сведения dpkg сами по себе эту цепочку не обеспечивают. Такой шаг должен иметь отдельную безопасную политику получения доверенных ключей и не может просто переключить булево поле на `true`.
