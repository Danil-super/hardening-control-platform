# Astra Linux SE 1.7.6.15 — контроль подлинности области эксперимента

**Статус: инструмент проверки доказательств, не протокол фактически проведённого испытания.**
Дипломный эксперимент на Astra 1.7.6.15 можно объявить выполненным только после
нативного запуска на разрешённом стенде. Исторические результаты Astra 1.8
не являются измерениями для 1.7, даже если набор правил одинаковый.

## Подготовка стенда

Приоритетный выпуск: **Astra Linux Special Edition 1.7.6.15 (UU2)**, x86_64.
Фактическую редакцию (Орёл / Воронеж / Смоленск), состояние СЗИ, ядро,
точные уровни безопасности, наличие SCE и реальную версию установленного
OpenSCAP фиксируют непосредственно на разрешённой ВМ. Публичный каталог UBI
предлагает виртуальные образы 1.7.6.UU2:
https://registry.astralinux.ru/download/ и
https://registry.astralinux.ru/descriptions/local/qemu/ .
Для Astra 1.7.6.UU2 на настоящей гостевой ВМ нужно увидеть **две различные строки**: `RELEASE=1.7.6` из `/etc/astra_version` и `BUILD_VERSION=1.7.6.15` из `/etc/astra/build_version`. Одна лишь версия 1.7.6 не подтверждает установленное UU2. Оба файла читаются только после проверки SSH host key;
сходство названия образа с выпуском само по себе не достаточно.

До подключения и изменений зафиксировать исходный хеш скачанного официального
образа, URL конкретного файла, размер и дату публикации. Побайтовый SHA-256,
полученный с того же хранилища, **не доказывает независимую подпись изготовителя**.
Сделать снапшот ВМ и проверить гипервизорную консоль. Не отключать PARSEC,
МРД, МКЦ, ЗПС и иные защитные механизмы для прохождения проверки.

## Какие оригинальные файлы нужны

Все файлы остаются **на управляющем узле**, не помещаются в публичный репозиторий.
Запрещено отправлять `guest-identity.txt` в чаты и CI: он содержит сырой machine-id.

- `facts.json` — оригинальный HCP-отчёт после действия «Сведения о хосте —
  Ansible»: точный alias, ОС ветки 1.7, архитектура x86_64, ядро, дата.
- `before.json`, `changed.json`, `restored.json` — **три подлинных**
  отчёта OpenSCAP HCP, опубликованных после проверки SSH-идентичности;
  все с `assetBinding.status=verified`. Отчёты должны содержать одну и ту
  же фактическую проверку встроенного профиля Astra (18 правил), общую
  исходную `bundle-sha256` и строго возрастающие временные метки.
- `guest-identity.txt` — оригинальное чтение системной идентичности
  **по уже независимо проверенному SSH fingerprint**:
  `/etc/os-release`, `/etc/astra_version`, `/etc/astra/build_version`, `uname -r`,
  `/etc/machine-id`. Формат показан ниже; машинный идентификатор
  обрабатывается исключительно локально и не включается в результат.
- `SSH_FINGERPRINT` — ранее независимо подтверждённый SHA256
  fingerprint SSH host key из мастер-подключения HCP. Получить fingerprint
  только через отдельное проверенное средство/консоль; один
  `ssh-keyscan` по непроверенной сети недостаточен.

На **управляющей Ubuntu**, в отдельном каталоге со строгими правами, можно
сохранить read-only native observation после проверки SSH fingerprint.
Пример для уже настроенного key-only доступа (подставить свои разрешённые
адрес, ключ, host alias и порт; не вводить sudo-пароль в командной строке):

```bash
umask 077
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes \
    -o UserKnownHostsFile="$HOME/.ssh/known_hosts" \
    -i /path/to/hcp-approved-private-key -p 22 approved-admin@approved-host \
    'set -eu; cat /etc/os-release; printf "\nRELEASE="; cat /etc/astra_version; printf "\nBUILD_VERSION="; cat /etc/astra/build_version; printf "\nKERNEL="; uname -r; printf "MACHINE_ID="; cat /etc/machine-id' \
    > /private/path/guest-identity.txt
chmod 600 /private/path/guest-identity.txt
```

Это **read-only SSH-вызов с контроллера**, а не команда, которую нужно вручную
вводить в терминале Astra. Проверка не требует постоянного агента.
Для некоторых защищённых конфигураций /etc/machine-id может быть недоступен;
тогда сверка останавливается с ограничением, а не подменяет идентичность.

## Выполнение строгой проверки после трёх прогонов

```bash
python3 deployment/tests/verify_astra_17_experiment.py \
  --before /private/path/before.json \
  --changed /private/path/changed.json \
  --restored /private/path/restored.json \
  --facts /private/path/facts.json \
  --native-identity /private/path/guest-identity.txt \
  --ssh-fingerprint 'SHA256:ACTUAL_INDEPENDENTLY_VERIFIED_FINGERPRINT' \
  --output /private/path/new-astra-17-experiment.json
```

Значение fingerprint в примере — **местозаполнитель**, а не реальная
контрольная сумма. Указать точный полученный отпечаток.
Скрипт ничего не выполняет по сети, не запускает SSH/сканеры,
не изменяет ОС и не переписывает исходные файлы.
`--output` создаёт новый JSON только один раз с правами `0600`.

## Проверяемые утверждения

1. Реально наблюдённые поля `ID=astra`, `RELEASE=1.7.6` и `BUILD_VERSION=1.7.6.15`
   и ядро согласуются с оригинальным HCP `facts.json` ветки 1.7.
2. Сырой machine-id локально преобразуется тем же алгоритмом
   HCP `HMAC-SHA256`, а проверенный SSH fingerprint совместно с ним
   образует ровно тот `assetId`, который есть в опубликованных отчётах.
3. Один alias, asset ID/generation, SSH fingerprint, connection ID,
   18 правил, стабильный пакет исходных правил, полный результат и
   строгая хронология сохраняются во всех трёх наблюдениях.
4. Переходы `passed → failed` и `failed → passed` по каждому правилу
   хранятся без выдуманной оценки «защищённости».
5. Несовпадение статусов после отката сохраняется в JSON
   для разбора с кодом возврата **2**. Неполнота или недостоверная
   идентичность — отказ с кодом **1** без заявления об эффективности.

Даже успешный результат **не** доказывает подпись производителя, честность
самой гостевой ОС, идентичность всех настроек после rollback, сохранение
сетевого доступа, полноту CVE или работу КСЗ на других уровнях защиты.
Эти выводы требуют отдельных независимых проверок и протокола.
Синтетические тесты `deployment/tests/test_verify_astra_17_experiment.py`
проверяют только отказ на подмену данных, но не заменяют настоящий стенд.
