Рабочая ветка: `rc/audit-2026-11-06`, опубликован черновой PR №80.
Последний подтверждённый CI-срез:
`1306a2ac81cc6f5faebe31855ceef83476638cec`, **20/20 workflow**, включая Greenbone.
Этот же код установлен на локальной панели. Проверенный продуктовый RC остаётся
зафиксирован на этом SHA; последующие локальные уточнения документации
не являются новой CI-приёмкой другого коммита.
План исполнения: [план](../tasks/plan.md) и [задачи](../tasks/todo.md).

**Статус: CI кандидата пройден; восстановление сервиса на отдельной Ubuntu-ВМ

## Контракты кандидата

- Сохранённая OVAL-политика передаёт `evidenceProjection` в штатный запуск.
  При отсутствии поля используется bounded; explicit detailed остаётся допустимым.
  Bounded сокращает повторное вложение XML, но сохраняет каждый ID и точный статус.
- Новые bounded/detailed определения используют объект `platformApplicability`.
  Чтение старой строковой формы сохраняется; unknown/foreign не становятся proof.
- Подтверждение устранения требует того же источника, исходного определения,
  актива и поколения подключения. Смена базы не означает исправления CVE.
- Неполный, дублированный или неизвестный результат не получает статус complete.
  Проверка согласованности JSON не удостоверяет подлинность производителя.

## Локальная проверка кандидата, 6 ноября

На отдельной копии исходников прошли типизация, Next production build,
**560 веб-регрессий**, **350 Ansible/Python-регрессий**, **233 deployment-регрессии**
и **75 HTTP-проверок**. HTTP проверяет сохранение OVAL-политики через перезапуск,
подтверждение администратора, передачу bounded исполнителю и публикацию JSON
с verified asset binding. Реальные сканеры в этом HTTP-прогоне заменены
явными фикстурами; новый сетевой аудит или firewall-изменение не выполнялись.
Команды, окружение, причины повторов и ещё открытые критерии: [задачи](../tasks/todo.md).
Эти проверки не являются GitHub CI единого RC SHA или операторским E2E.

### Сохранение оригиналов сканеров

Установленный локальный кандидат сохраняет при штатных OpenSCAP/OVAL-запусках
исходный ARF либо OVAL results XML и фактически оценённый XML-источник в
`reports/.raw-evidence/<report-id>/` внутри runtime volume. Каталог закрыт
правами 0700, файлы — 0600. Поле `rawEvidence` исходного HCP JSON фиксирует
относительные пути, размеры и SHA-256; оно связано с asset binding этого JSON.
Оригиналы публикуются до JSON, а рабочий временный каталог затем удаляется.
Обычная CLI-проверка сохраняет прежний режим; сохранение запрашивает штатный
исполнитель HCP или явный флаг `hcp_preserve_raw_evidence`.

Отсутствие оригиналов делает новый отчёт partial с явной причиной. Символьная
ссылка, неподдержанный тип, превышение бюджета либо расхождение checksum
останавливают публикацию. XML копируется блоками без полного чтения в JS heap.
Наличие этих файлов не подтверждает подпись производителя или успешность аудита.
Оригиналы могут содержать сведения о конфигурации хоста: не публикуйте runtime
архив или каталог оригиналов в GitHub. Они входят в резервную копию volume и
сверку восстановленных файлов как часть `reports/`.

Локально прошли **563 веб-теста**, прежние **583 Python-проверки**, сборка и
**75 HTTP-проверок** с новыми assertions оригиналов. Настоящий OpenSCAP
проверил сохранение source/results на синтетической пакетной базе; идентичность
Astra в этом контрольном тесте подставлена и не является новым native опытом.
Проверка этого изменения на разрешённой Astra через UI ещё требуется.

Опубликован [черновой PR №80](https://github.com/Danil-super/hardening-control-platform/pull/80).
Приёмка требует зелёной матрицы именно последнего SHA этого PR; результат
предыдущего кандидата не переносится на новый коммит автоматически.

### Локальный стенд и контроль доступа

Панель доступна на `http://127.0.0.1:3000`; runtime volume сохранён.
Обновление до `7f3439b` проверило миграцию SQLite, вход и logout, семь основных
страниц, неизменность исходных отчётов и SSH-ключей. Слабый служебный ключ
плановых проверок заменён; preflight после обновления: 0 blockers / 0 warnings.
Приватные backup, settings, ключи и исходные отчёты не включены в GitHub.

Проверка P1-03 воспроизвела несоответствие доверия forwarded-заголовкам:
при выключенном `HCP_TRUSTED_TLS_PROXY` посторонний Origin вместе с подставленным
`X-Forwarded-Host` доходил до валидации тела. Контрольное тело было пустым,
настройки не менялись. Исправление использует forwarded-адрес только при
явном доверии прокси и отклоняет неоднозначные authority/protocol; регрессия
проверяется на production HTTP-сервере. Учтена и подмена схемы в nextUrl,
которую Next.js уже построил по `X-Forwarded-Proto`: штатный HTTP listener
HCP не становится HTTPS без явно доверенного прокси. Это не доказательство браузерной
эксплуатации или завершённого review публичного ingress/rate limiting.

После исправления прошли **568/568 веб-тестов**, типизация, production build и
**79 HTTP-проверок**, включая штатный HTTPS Origin за доверенным прокси.
Новая production HTTP-регрессия до исправления получала
400 вместо ожидаемого 403; после исправления отклоняется до обработчика.

Ранее подключённая Astra сейчас отвечает `No route to host`; ожидается доступная
ВМ и подтверждение снимка. Оператор подтвердил, что ВМ сейчас недоступна.
Сеть, VPN и правила firewall Astra не менялись.

### Фактическое восстановление в отдельную Ubuntu

На другой гостевой ОС Ubuntu 24.04.5 с 2 vCPU / 4 ГиБ памяти восстановлены
настоящие runtime, настройки и образ `1306a2a`. Образ Ubuntu проверен по GPG
ключом Ubuntu из системного keyring и по SHA-256. Перед передачей секретов
гостю закрыт выход в рабочую сеть; административный SSH доступен только через
loopback forwarding. Это самостоятельная ОС на том же физическом компьютере.

До копирования штатный checkpoint SQLite сохранил данные всех 14 таблиц;
исходные DB/WAL отдельно сохранены. Остановка основной панели заняла 54 секунды.
Внешние pins manifest и исходного HMAC-head/count удержаны вне переносимой копии.
После восстановления проверены исходные байты и цепочка из 201 события;
старый контрольный cookie присутствовал в копии и не был просрочен, а после
отзыва сессий получил 401. Новый вход, выход и запрет повторного cookie прошли.

На исторических данных прошли 22 HTTP-проверки: семь страниц, список хостов,
отчёты, исходный JSON одного отчёта, Origin-защита и PDF. PDF содержит три
страницы с корректной кириллицей; два скачивания совпали по SHA-256, manifest
проверен по 15 исходникам. Устаревшие проверки и ограниченный охват Nmap
сохранены как ограничения. Нового сканирования Astra и проверки нового ARF нет.

Дополнительно 31 HTTP-проверка охватила очистку и возврат отчётов/PDF и журнала.
Полное восстановление архива вернуло 27 отчётов, включая 12 ранее скрытых;
связанный PDF доступен даже из архива, а удаление его исходника отклонено с 409.
Возвращено 114 записей видимого журнала. После PDF и четырёх архивных операций
проверена цепочка из 206 событий, включая прежний внешний anchor на первых 201.
Все 46 исходных файлов доказательств сохранили байты. Эти операции выполнялись
только на восстановленной копии. Приватные копии,
PDF, snapshot и протоколы остаются вне Git и GitHub.

Первый пробный запуск с 2 ГиБ закончился V8 heap OOM: это ниже указанного в
README минимума 4 ГБ. Успешный прогон использовал 4 ГиБ; создание PDF заняло
4,911 с, peak memory cgroup контейнера — около 2,14 ГиБ. Это измерение одного
набора данных, не приёмка одновременной нагрузки 1/3/5 хостов.

Выявленные особенности процедуры: шесть исторических отчётов имели слишком
широкие права; права закрыты в копии и исходной установке без изменения байтов.
Docker с containerd image store показывает manifest digest вместо прежнего
config ID: проверены SHA обоих metadata blobs, связь manifest → config,
конфигурация исполнения и все 26 RootFS layers. Восстановленный образ из сети
не скачивался. Подробности практических шагов: [резервирование](backup-restore.md).

Новый SSH/контролируемый rollback на Astra, проверка публичного HTTPS/rate limit,
desktop/mobile браузер и человеческая подпись остаются открытыми. Полная
операторская DR-приёмка и production-ready этим прогоном не объявляются.

На 6 ноября GitHub API сообщает `main.protected: false` и отсутствие
обязательных status checks. Перед выпуском нужны защита ветки и правило
фиксации релизного образа; текущий зелёный CI эти настройки не заменяет.

## Последовательность приёмки

1. Локальные регрессии, типизация, production build и изолированный HTTP.
2. Зафиксированный RC SHA и необходимая GitHub CI-матрица именно этого SHA.
3. Обновление выделенного стенда и настоящий операторский E2E.
4. Независимое восстановление, desktop/mobile и итоговый пакет диплома.

Автоотмена CI относится только к устаревшим прогонам одного PR и workflow.
Push main и ручные прогоны имеют собственный run ID и не отменяют друг друга.
Состав проверок и их триггеры сохранены. Дополнительное разделение быстрых и
дорогих проверок требует отдельной проверки required checks перед публикацией.

## Ограничения, которые сохраняются

Legacy Ansible для Python Astra 1.7 находится вне поддержки upstream.
Совместимость исполнения не равна поддерживаемости или production-безопасности.
Доверие к CVE-источникам, backports, сетевой perimeter/rate-limit, зависимости,
image digests и нагрузка 1/3/5 хостов требуют отдельных проверок.
Автоматический rollback ограничен поддержанными UFW/firewalld; он не является
универсальным восстановлением ОС. Все уязвимости обнаруженными не объявляются.
