## Обновление существующей установки

- Перед обновлением сохраните резервную копию persistent volume по [инструкции](backup-restore.md).
- SQLite получает дополнительные таблицы/поля без удаления истории. Исходные JSON и ранее созданные PDF не переписываются.
- Старые постоянные cookie перестают приниматься: после обновления войдите заново. Новые действующие сессии сохраняются после обычного перезапуска и отзываются при выходе.
- Для старых пунктов плана оценка восстанавливается только из исходных отчётов с совпадающим SHA-256. При отсутствии такого доказательства отображается неизвестная историческая оценка.
- Старые OpenSCAP-отчёты без устанавливаемого профиля/идентичности контента получают ограничение охвата. Они сохраняются в истории, но не подтверждают исправление другой области.
- Старые прерванные операции без надёжной идентичности владельца требуют ручной сверки. См. [восстановление операций](operations-recovery.md). Не удаляйте строки SQLite и lock-файлы, чтобы просто разрешить новое изменение.

## Что означает подтверждение и PASS

Пункт плана подтверждается по проверяемому результату того же контроля. Для Astra OVAL используется явный `false` исходного vulnerability definition в той же базе. Для Trivy отсутствие CVE принимается только при доказанном покрытии новой полной инвентаризации после выполненной меры и актуальной базе. Исчезновения строки Greenbone/Lynis/Nmap без явного результата исходного контроля недостаточно: пункт остаётся выполненным до получения подходящего доказательства. Подробнее — [завершение проекта](project-closeout.md).

Firewall PASS означает обнаруженное ограничение на проверенном INPUT-пути. Он не доказывает внешнюю недоступность каждого порта или защиту трафика Docker/NAT. Неподдерживаемые неоднозначные правила остаются manual/partial. Для подтверждения сетевого эффекта изменения нужна проверка с подходящей точки сети.

В локальной среде использован Webpack: запуск Turbopack ограничен доступом среды к созданию процессов/сокетов. Обычный `npm run build` остаётся отдельной проверкой GitHub Actions. HTTP-прогон проверяет реальный локальный сервер, logout/replay, серверное истечение сессии и сохранение состояния после перезапуска, используя изолированные данные.

Для веб-тестов требуются Node 24, установленный Ansible и PDF-зависимости из workflow `Verify hardening platform`.

```bash
cd web
npm ci
npm run typecheck
npm test
npm run build
npm run test:http
python3 -m unittest discover -s ../ansible/tests -v
```

Отдельные проверки развёртывания запускаются из корня репозитория:

```bash
python3 -m unittest discover -s deployment/tests -v
```

Проверка передачи буквальных строк выполняет настоящий Ansible только на localhost. Она проверена на ansible-core 2.14.18 и 2.19.14; рабочие SSH-хосты и их firewall при этом не изменяются. Тесты аварийных состояний используют временную SQLite, отдельные процессы и контролируемые ответы внешних команд. Две native OpenSCAP-проверки требуют установленного `oscap` и без него явно пропускаются.

Эти исправления не заменяют приёмку на поддерживаемых выпусках настоящей Astra, проверку реальных firewall/backend вариантов и исправление отдельного Greenbone live-стенда. Общие precision/recall всей платформы этим набором тестов не измеряются. Лицензия, политика сообщений об уязвимостях, роли/MFA, ограничение попыток входа и независимое хранение контрольных точек журнала остаются отдельными задачами сопровождения и усиления.
