# Безопасный отзыв старых сессий после восстановления HCP

**Назначение:** после восстановления runtime SQLite на **новой изолированной**
управляющей Ubuntu не допустить сохранения старых административных cookie.
В HCP таблица `admin_sessions` содержит SHA-256 хеши bearer-токенов.
Если восстановить ту же SQLite и те же `HCP_ADMIN_PASSWORD` и
`HCP_AUTH_SECRET`, срок ещё действующих токенов **может не истечь** и
старые cookie могут остаться действительными.

Этот инструмент является отдельным, **явно подтверждаемым изменением
восстановленной копии**, не read-only аудитом. На исходной работающей
установке его запускать нельзя.

## Правильная последовательность

1. Получить согласованную исходную копию по `docs/backup-restore.md`.
2. Проверить исходный архив `verify_backup_bundle.py`, **не извлекая
   секреты**, а затем восстановить в **новый пустой том** на отдельной Ubuntu.
3. **При остановленном HCP**, до первого входа, выполнить
   `verify_restored_runtime.py` на этой копии и сохранить его
   `critical-runtime-bytes-match-backup`. Это фиксирует исходную
   побайтовую идентичность SQLite, отчётов и host-credentials.
4. На той же **остановленной** восстановленной копии посмотреть только число
   записанных хешей сессий и точный хеш SQLite:

   ```bash
   python3 deployment/tests/revoke_restored_admin_sessions.py \
     --restored-runtime /isolated/private/hcp-restored-runtime
   ```

   Статус `preview-only` не изменяет SQLite. Скрипт не показывает сами
   токены, их хеши, секреты или данные других таблиц.

5. Оператор независимо сверяет, что путь ведёт к новому изолированному
   экземпляру, что исходный контейнер не смонтирован и восстановленный
   HCP **остановлен**. При необходимости дополнительно проверяется SHA файла:

   ```bash
   sha256sum /isolated/private/hcp-restored-runtime/hcp.sqlite
   ```

6. Только после явного решения применить отзыв с **точной контрольной
   суммой, полученной на предыдущем шаге**:

   ```bash
   python3 deployment/tests/revoke_restored_admin_sessions.py \
     --restored-runtime /isolated/private/hcp-restored-runtime \
     --apply --confirm-isolated-stopped \
     --confirm-text INVALIDATE_ONLY_ISOLATED_RESTORED_HCP_SESSIONS \
     --expected-db-sha256 ВАШ_РЕАЛЬНЫЙ_SHA256_ВОССТАНОВЛЕННОЙ_БД \
     --output /отдельный/закрытый/каталог/new-session-revocation.json
   ```

   Команда не принимает произвольное имя DB: изменяется **только**
   `hcp.sqlite` в выбранном каталоге. По заранее совпавшему хешу,
   безопасному обычному файлу с режимом 0600, без symlink и без старых
   `-wal/-shm`, выполняется одно транзакционное
   `DELETE FROM admin_sessions`. Все остальные таблицы и старые записи
   аудита оставляются без SQL-изменений. При ошибке согласования,
   несовпадении SHA, неожиданной схеме или отсутствии явного подтверждения
   изменение запрещено.

7. **Повторить preview**: число `storedSessionHashes` должно быть 0.
   Новый файл протокола содержит числа и SHA SQLite до/после, но не секреты.
   Теперь SQLite закономерно **отличается от исходной копии** — это
   намеренное, отдельно задокументированное post-restore изменение.
8. Запустить HCP только на изолированном адресе и **независимо**
   проверить: прежняя browser cookie получает 401/403, новый сеанс
   администратора успешно создаётся, HMAC-цепочка audit событий продолжает
   проходить целостность, оригинальные host-credentials и отчёты доступны.
   Проверить реальный SSH и безопасный откат на disposable тестовом хосте.
   Эти тесты не выполняются данным скриптом.

## Граница ответственности

- `preview-only` — чтение SQLite без записей.
- `--apply` — **разрушительное действие только над таблицей сохранённых
  административных сессий восстановленной копии**. Для реального HCP это
  означает принудительный выход всех ранее входивших администраторов в
  данной восстановленной БД. Не запускать на производственном runtime.
- Старые `-wal/-shm` требуют отдельной контролируемой SQLite-процедуры:
  нельзя использовать режим `immutable` и молча игнорировать незавершённые
  транзакции WAL.
- Отзыв токенов по таблице не доказывает отказ существующей cookie
  со стороны настоящего сервера; эту проверку проводить по HTTP отдельно.
- Ничего не запускается на целевой Astra, нет SSH, Docker, прямого доступа
  к сети и автоматического применения firewall.
- Протокол не содержит приватных ключей, паролей, токенов и хешей отдельных
  токенов. Его хранить с ограниченным доступом.
- Исходные архивы должны сохраняться неизменяемыми; результаты до и после
  revocation хранятся **отдельно**.
- Проверка на синтетической SQLite:
  `deployment/tests/test_revoke_restored_admin_sessions.py`.
  **Не закрывать задачу #43** без успешного полного DR drill на
  разрешённом изолированном стенде.
