# Подготовка оригинального образа Astra Linux SE 1.7.6.UU2 для дипломного стенда

## Что подтверждено производителем

Astra Linux 1.7.6 с обновлением **UU2** соответствует версии **1.7.6.15**
(см. таблицу версий ALSE 1.7 на https://wiki.astralinux.ru/spaces/flyingpdf/pdfpageexport.action?pageId=323668672
и рекомендации https://www.aldpro.ru/professional/ALD_Pro_Module_02/ALD_Pro_deployment.html).

В публичном JFrog-каталоге Astra Linux UBI:
https://registry.astralinux.ru/ui/native/mg-generic/alse/virtualbox/
указаны точные **VirtualBox OVA** для 1.7.6.UU2, MG 15.3.1, amd64:

| Уровень защиты, заявленный в имени образа | Имя OVA |
| --- | --- |
| Базовый (Орел) | `alse-1.7.6.uu2-base-virtualbox-mg15.3.1-amd64.ova` |
| Усиленный (Воронеж) | `alse-1.7.6.uu2-adv-virtualbox-mg15.3.1-amd64.ova` |
| Максимальный (Смоленск) | `alse-1.7.6.uu2-max-virtualbox-mg15.3.1-amd64.ova` |

В каталоге есть отдельные `.sha256` для каждого OVA. **Они не являются
независимой цифровой подписью изготовителя**, поскольку находятся в том же
хранилище. Версия и режим, указанные в имени файла, не заменяют проверку
настоящей загруженной машины.

## Автоматическое получение образа через официальное хранилище

Для начального знакомства с источником **не нужно вручную искать URL**.
В HCP зафиксированы точные публичные имена base/adv/max 1.7.6.UU2.
Команда выполняется **только на управляющем Ubuntu**, не внутри Astra.

Посмотреть только опубликованный Artifactory SHA-256 без скачивания образа:

```bash
python3 deployment/tests/download_astra17_ova.py --level base --inspect-only
```

Скачать OVA с контролем прогресса и SHA-256 в новый приватный каталог:

```bash
mkdir -m 700 -p "$HOME/hcp-astra-images"
python3 deployment/tests/download_astra17_ova.py \
  --level base \
  --output-dir "$HOME/hcp-astra-images"
```

При наличии **независимо записанного** оператором точного SHA-256 и размера
передайте дополнительно `--expected-sha256` и `--expected-bytes`. Это
предотвратит использование файла, чей хеш изменился относительно независимой
записи. Без этих параметров сверка производится только с `.sha256` **из того
же официального хранилища**. Она подтверждает совпадение байтов с опубликованной
в том же источнике суммой, но не подпись издателя.

Для уровней `adv` или `max` замените только значение `--level`. Загрузчик
принимает исключительно три заранее определённых файла. Он не следует HTTP
переадресациям, использует HTTPS с системной проверкой TLS, ограничивает размер
8 ГиБ и длительность скачивания, выводит фактически полученные МиБ и не
подменяет существующий файл. При ошибке частичный файл удаляется, а результат
не объявляется успешным. Создаются два локальных файла с mode 0600: OVA и
`*.ova.source.json` — запись происхождения. В обоих режимах
`publisherSignatureVerified=false`, `nativeGuestVerified=false`.
Если сервер официального каталога недоступен или использует неподдерживаемое
перенаправление, операция завершается с ошибкой; пользователь может
прибегнуть к контролируемой ручной загрузке и следующей локальной проверке,
**без обхода хеширования**.

## Практические действия на управляющей Ubuntu (не на целевой Astra)

1. Из оригинального каталога Astra скачайте выбранный **точный** OVA (без
   `latest`); по возможности сохраните неизменяемый оригинал и отдельно
   зафиксируйте его происхождение, URL, момент скачивания и размер.
2. Запишите ожидаемые SHA-256 и размер в **свой независимый локальный журнал**
   после сверки с доступными сведениями изготовителя и источниками, которым
   доверяете. Не приписывайте им статус криптографической подписи. Не публикуйте
   внутренние ключи и данные доступа.
3. Проверьте локальный OVA без сети, установки, распаковки или запуска:

   ```bash
   python3 deployment/tests/pin_astra17_vm_image.py \
     --file /path/to/alse-1.7.6.uu2-base-virtualbox-mg15.3.1-amd64.ova \
     --expected-sha256 ВАШ_ПРЕДВАРИТЕЛЬНО_ПРОВЕРЕННЫЙ_SHA256 \
     --expected-bytes ТОЧНОЕ_ЧИСЛО_БАЙТ \
     --reference INTERNAL-REVIEW-RECORD-001 \
     --output /path/to/new-astra17-image-evidence.json
   ```

   Команда только читает локальный обычный файл, проверяет TAR/OVA-заголовок,
   точный размер и полный SHA-256 и создаёт **новый** JSON с правами 0600.
   Символьные ссылки, неизвестные версии, изменяемые при чтении файлы,
   несовпадающие хеши и попытка перезаписать исходник отклоняются.

4. Через VirtualBox импортируйте OVA как **новую изолированную гостевую ВМ**,
   сделайте её snapshot, настройте разрешённую сеть и сохраните доступ к
   гипервизорной консоли. Приоритетная приёмка — *base*; усиленный и
   максимальный режимы проверяются отдельно и не считаются подтверждёнными
   только по успешному base.
5. Подключите ВМ через HCP по SSH со сверкой server fingerprint. На
   управляющем узле используйте штатный preflight, проверку идентичности и
   инструмент `deployment/tests/verify_astra_17_experiment.py` (если
   соответствующий PR уже объединён). Он читает сведения с гостя через
   разрешённый SSH, ручные команды внутри Astra не нужны.
6. Нативно подтвердите `/etc/os-release`, `/etc/astra_version` (ожидаем
   **1.7.6.15**), ядро, архитектуру, `machine-id`, реальное содержимое dpkg,
   уровень защищённости и версии OpenSCAP/SCE. Любое несоответствие —
   блокирующая причина, а не автоматическое изменение `/etc/astra_version`.
7. Запустите один и тот же профиль 18 правил до изменения, после
   согласованного безопасного изменения и после отката. Сохраните исходные
   JSON, ARF и SHA-256, результаты OVAL для точного выпуска. На управляющей
   Ubuntu выполните `measure_astra_baseline.py --restored` только для
   оригинальных source-bound отчётов с одним активом.

## Пределы доказательства

`pin_astra17_vm_image.py` имеет поля
`publisherSignatureVerified=false`, `nativeGuestVerified=false` и
`cveSourceApplicable=null` **даже при совпадении всех байтов**.

Нельзя писать в дипломе «подлинный сертифицированный образ», «все CVE
обнаружены» или «все версии Astra поддерживаются» только на основании
скачанного файла и контрольной суммы. Фактический эксперимент и
эксплуатационная приёмка остаются открытыми до реального нативного прогона
(issues #40 и #43).
