# Достоверность сканирования, возобновляемый откат и идентичность хоста

Дата: 28 октября 2026 года. Исходный срез — [`4c24948`](https://github.com/Danil-super/hardening-control-platform/commit/4c24948596984506bee3da2518dd8c97c95c9f37), после исправлений предыдущего аудита. Изменения и итоговые проверки объединяются в [PR №5](https://github.com/Danil-super/hardening-control-platform/pull/5). Рабочие серверы пользователя не использовались: испытания выполняются на временных файлах, отдельных процессах, контейнерных целях и одноразовых ВМ GitHub Actions.

Это продолжение [проверки жизненного цикла HCP](logic-validation-2026-10-28.md). Предыдущий документ сохраняет результаты своего среза; перечисленные там рекомендации по целевому журналу, реальной Astra, источникам Trivy, импорту Dependency-Track и идентичности машины реализуются этим набором изменений.

## Практический результат

Проверка подтверждает конкретную цепочку: реальные наблюдения сканера сохраняются в отчёте, известное нарушение обнаруживается, контрольное исправление различается, а ограничение источника остаётся видимым. Для firewall проверяется реальная фильтрация сетевых пакетов и восстановление после принудительной остановки процесса. Общий процент точности всех сканеров, полное покрытие всех CVE или автоматическое восстановление после любой аварии из этих испытаний не следует.

Обратимые автоматические действия платформы по-прежнему имеют явную область: `closePort` и `blockIp`. Обнаруженная CVE не означает, что HCP умеет безопасно обновить соответствующий пакет и откатить всё обновление ОС. Пакетное исправление требует отдельного проверяемого процесса.

## 1. Откат с журналом на самой цели

Ранее остановка между двумя `rename` оставляла сохранённое прежнее дерево и отсутствующий рабочий каталог firewall. Повтор не мог самостоятельно завершить файловое восстановление. Новый `rollback-state.json` сохраняет намерение **до** изменения дерева, промежуточный этап и завершение. Продолжение сверяет фактические файлы с журналом и архивом, включая ID транзакции, machine-id, backend, SHA-256, inode/device staging, UID/GID, mode и PDPL.

Проверены остановки процесса до и после файловых checkpoint, оба переименования, неизвестный reload и прерванная очистка. После сохранённого завершения повтор возвращает `replayed: true, changed: false` и не выполняет reload ещё раз. Неизвестный исход требует отдельной сверки; прошедшее время само по себе не снимает блокировку.

Постоянный целевой маркер и `flock` не позволяют другой транзакции, alias или контроллеру обойти незавершённую операцию. Backup оставляет `backed_up`; применение обязано предъявить проверенную копию своей транзакции. Неизвестный ответ backup также переводит контроллер в `interrupted`: архив и маркер могли успеть сохраниться. Независимый review воспроизвёл ещё более узкую границу — установка маркера с последующей ошибкой `fsync`; она теперь также сохраняет неизвестный исход.

Неподдерживаемые ACL/extended attributes отклоняются до изменения. Поддерживаемые метаданные и содержимое копии проверяются до и после резервирования, чтобы параллельное изменение исходных файлов не создавало ложную гарантию восстановления.

В нативных стендах helper действительно получает `SIGKILL` после первого `rename`. Проверяется отсутствие рабочего каталога, сохранность journal/previous, сохранение runtime deny и восстановление доступности штатным rollback. UFW проходит 12 контрольных проверок; firewalld — 21, включая новые SSH-соединения после применения, reload и восстановления. Это ограниченные сетевые измерения, а не доказательство равенства всех возможных правил ядра.

Порядок действий после сбоя и особенности ручной сверки: [восстановление операций](operations-recovery.md). Локальная отметка `restored_manually` не удаляет маркер на цели. Снимок ВМ и резервирование данных платформы остаются отдельными средствами; `SIGKILL` не моделирует отказ диска или потерю питания.

## 2. Реальная Astra вместо подмены идентичности ОС

Добавлен воспроизводимый [стенд QEMU/KVM](../deployment/astra-vm/README.md) с официальными **Astra Linux SE 1.8.1 и 1.8.6 base amd64**. Образы и полный vendor OVAL закреплены SHA-256 из публичных метаданных производителя. Гостевые машины имеют собственные ядра, исходные release-файлы и настоящую базу установленных пакетов. SSH доверяет заранее созданному и независимо закреплённому ключу гостя.

Первый прогон обнаружил ошибку настройки самого acceptance: глобальный `ansible.cfg` передавал путь к known_hosts раньше параметра inventory. Исправлен приоритет параметров; строгая проверка ключа сохранена. Повторный [нативный прогон](https://github.com/Danil-super/hardening-control-platform/actions/runs/40716626983) завершился успешно для обоих выпусков.

Условие выбранного vendor definition независимо проверяется по исходному XML и `dpkg --compare-versions`. Установка OpenSCAP не должна менять версии контрольных пакетов. Удалённые пакеты с остаточной конфигурацией не считаются установленными; установленные пакеты на hold учитываются.

Все 18 native ARF-результатов baseline сопоставляются со статусами и evidence HCP, а также с хешем фактически исполненного datastream. Четыре исходных несоответствия относятся к выбранным правилам HCP: глобальный SSH root login `without-password`, `MaxAuthTries=6`, `X11Forwarding=yes` и `kernel.kptr_restrict=0`. Это наблюдения закреплённых тестовых образов и авторской политики, не заключение о серверах пользователя или сертификационном соответствии Astra.

Число 45 у нового образа не означает «новая версия полностью исправлена». В таблице приведены результаты выбранной базы для установленных пакетов именно этого образа. Положительный vendor predicate не является демонстрацией эксплуатации, а отсутствие выбранной CVE не означает отсутствия остальных уязвимостей.

Полный JSON оказался существенно больше маленьких fixtures: около **75 МБ**. Это выявило несовместимость первоначального лимита нового механизма публикации в 32 МиБ. Лимит согласован с бюджетом OVAL; финальный native gate дополнительно пропускает весь реальный отчёт через публикацию с captured asset binding и веб-нормализацию, проверяя сохранность всех исходных полей. Усечение или потеря определений не допускаются.

Область испытаний — два выпуска base/x86-64. Astra 1.7, другие архитектуры, уровень max и обязательные механизмы доступа/целостности требуют отдельных стендов. Полный охват всех CVE и подлинность подписи vendor database не утверждаются; проверены закреплённые байты из указанного источника и их исполнение.

## 3. Проверяемые источники и происхождение пакетов Trivy

Коллектор сохраняет `Maintainer` и `Origin` DEB-пакетов вместе с binary/source version, epoch, архитектурой и dpkg status. Эти поля доходят до SBOM и результата. Метаданные установленного пакета служат ограниченной эвристикой происхождения и не выдаются за криптографическую проверку репозитория.

Совпадение CVE для стороннего или неизвестного поставщика сохраняется, но становится `manual` с неподтверждённой применимостью и неполным покрытием. Старый inventory без provenance не получает выдуманные сведения по текущему состоянию хоста.

Новый controller helper вычисляет SHA-256 базы, metadata, движка, SBOM и конфигурации до и после скана. Он также сравнивает идентичность файлов. Scan и refresh используют общий advisory lock, наследуемый реальным дочерним Trivy. Остановка helper не освобождает источник, пока дочерний сканер ещё работает. Неудачная загрузка сохраняет прежнюю пару DB/metadata; незавершённая публикация пары блокируется persistent marker. Изменение зарегистрированной пары между сканами обнаруживается отдельным манифестом.

Нативный Trivy 0.74.0 проверен со свежей загрузкой и повторным использованием того же cache:

| Эталон CVE-2023-0286 | Нативный результат | Результат HCP |
| --- | --- | --- |
| Ubuntu `libssl3 3.0.2-0ubuntu1.7`, amd64 | CVE найдена | failed с vendor evidence |
| Исправленный backport `3.0.2-0ubuntu1.8` | Эта CVE отсутствует | Эта находка отсутствует |
| Уязвимая версия i386 | CVE найдена | failed; архитектура сохранена |
| Искусственный source epoch `1:` | Эта CVE отсутствует согласно порядку версий | Совпадает с native; epoch сохранён |
| Искусственный неизвестный поставщик | Native совпадение присутствует | CVE сохранена как manual; coverage incomplete |

Последние два случая проверяют интерпретацию метаданных, а не наличие таких официальных пакетов. Каждый прогон использует синтетический inventory и реальный scanner/database; отдельный контейнерный acceptance проверяет настоящий SSH-сбор. Это небольшой размеченный набор, по которому нельзя честно вычислить общую precision/recall всего продукта.

Подробные гарантии, ограничения блокировки и процедура offline-import: [источники Trivy](scanner-source-evidence.md). Хеширование не изолирует файлы от администратора, игнорирующего advisory lock, и не архивирует все исторические гигабайтные базы автоматически.

## 4. Dependency-Track: импорт результатов анализа

Успешная передача SBOM теперь имеет продолжение: отдельный refresh получает анализ и сохраняет новый immutable report `dependency-track-analysis`. Delivery report остаётся исторической записью передачи. Проект, точный SBOM, исходный отчёт, component manifest, endpoint fingerprint и upload token связывают ответ с правильной операцией. Пагинация, число компонентов, принадлежность findings и timestamps проверяются до публикации.

Одного `processing=false` недостаточно: в Dependency-Track 4.14.3 так отвечает и неизвестный token. Новый адаптер требует дополнительного согласования импорта, анализа и точного component manifest. Повторный refresh не переписывает уже опубликованный результат. Источники защищены от удаления, пока на них ссылается производный отчёт.

Настоящий контейнерный сервис прошёл два сценария: ingest без advisory mirrors сохраняет неполноту; targeted NVD mirror и штатный internal analyzer обнаруживают CVE-2021-44228 у `log4j-core 2.14.1` и исключают исправленную `2.17.1`. Результат проходит через production refresh HCP.

`complete` обозначает согласованный импорт снимка. API не доказывает полноту всех mirrors или успешность каждого advisory source, поэтому результат остаётся `partial=true`, `sourceCoverageVerified=false`. Нулевой список не превращается в PASS, общую оценку безопасности или доказательство устранения. Подавленные и вручную классифицированные findings сохраняют явное решение источника. Требуемые разрешения и порядок работы: [интеграции](audit-integrations.md).

## 5. Привязка истории и операций к машине

Новая привязка использует app-specific отпечаток фактического machine-id и fingerprint ключа сервера из успешного SSH-подключения с уже установленным доверием. IP или alias сами по себе идентичностью актива не считаются. Поколения привязки и история изменений сохраняются; старые отчёты не получают текущий asset ID задним числом.

Подключение и inventory фиксируются до запуска. Результаты сначала попадают в закрытый каталог запуска, затем публикуются вместе с captured binding без перезаписи исторических файлов. Производные Trivy/Dependency-Track отчёты наследуют идентичность исходного inventory, а не текущий alias. Неаутентифицированные сетевые проверки явно остаются unknown и не получают выдуманное SSH-подтверждение.

Известные aliases одного актива разделяют блокировки в пределах контроллера. Более позднее завершённое изменение через другой alias блокирует устаревший rollback, в том числе после последующей перепривязки этого alias. Смена машины требует отдельной проверки и подтверждения. Клонированные machine-id и серверный ключ вместе остаются неразличимыми; общая история нескольких независимых контроллеров этим механизмом не вводится.

Операторская процедура и совместимость старых данных: [идентичность активов](asset-identity.md). В ходе независимого review специально проверяются гонки изменения inventory, смена поколения при незавершённой транзакции, восстановление read-only lease после падения и одновременный SSH closeout через другой alias.

Итоговый PDF показывает публичный ID актива и поколение каждого источника, а также явные причины исключения данных другой машины. Исторический план остаётся связан с исходными отчётами и не переносится на новый актив после смены alias. Внутренние хеши идентичности, SSH fingerprint и пути к ключам в PDF не выводятся. Двухстраничный пример с разными активами и длинными идентификаторами проверен визуально; проверка 4 000 находок подтверждает сохранение последней записи без усечения.

Удаление самостоятельного CVE-отчёта очищает его SBOM и отдельную конфигурацию Trivy только после удаления последней ссылки на эти файлы. Исторические имена SBOM поддерживаются; путь из импортированного `sourceEvidence` не используется для удаления, а неожиданная символическая ссылка останавливает операцию до удаления отчёта.

## Проверки и воспроизведение

После интеграции asset binding, PDF и очистки связанных файлов общий локальный набор прошёл **343 веб-теста**, проверку TypeScript, **202 Python-теста** и **17 deployment-тестов**. Ещё два Python-теста требуют локального native OpenSCAP и проверяются соответствующими CI-сценариями. Первый объединённый прогон обнаружил зависимость одного теста от рабочего inventory: тест получил отдельный настоящий INI-стенд, без подмены resolver и без ослабления проверки смены машины; полный повтор прошёл 343/343 без пропусков. Эти числа не являются процентом точности сканирования. Нативные PR gates выполняются на итоговом коммите.

Для слияния должны успешно завершиться проверка TypeScript, обычные тесты, production build, HTTP smoke, Docker build, Ansible syntax, контейнерный SSH/scanner lab, настоящий Python 3.5, UFW, firewalld, full-profile OpenSCAP, оба DTrack сценария и обе реальные Astra VM. Проверки с недоступной внешней зависимостью не заменяются фиктивным PASS.

Компактные фактические результаты, исходные SHA и ссылки на уже завершённые native runs сохранены в [машиночитаемом протоколе](evidence/reliability-2026-10-28.json). Он явно указывает проверенный срез до финальной asset-интеграции. Итоговый commit и его результаты доступны в [проверках PR №5](https://github.com/Danil-super/hardening-control-platform/pull/5/checks). Полные ARF/JSON и диагностические журналы публикуются как CI artifacts с ограниченным сроком хранения.

## После обновления установки

Обновление GitHub не заменяет обновление развёрнутого контейнера. Используйте [штатную инструкцию обновления](../README.md#если-платформа-уже-была-запущена) с сохранением постоянного тома. Выполните проверку подключения/идентичности хоста, соберите новый package inventory, повторите CVE-аудит и сформируйте новый итоговый отчёт. Старые PDF и исходные JSON остаются историческими данными.

Для Dependency-Track добавьте read permissions из инструкции интеграции. Для прерванного firewall сначала сверяйте состояние и сохраняйте backup/journal. Если необходима воспроизводимость старых CVE-результатов, отдельно сохраняйте использованные DB/metadata по их записанным SHA. Дальнейшее расширение доказательств — дополнительные выпуски Astra, подтверждённое происхождение пакетов из репозиториев и более широкий независимый размеченный набор уязвимостей.
