# Подключение и испытание семейства Astra Linux

Эта инструкция подготавливает **Astra любого выпуска как проверяемую ВМ**. HCP определяет семейство и возможности машины без списка разрешённых номеров версий; конкретный набор доступных проверок зависит от её Python, инструментов, служб и применимых баз. HCP установите на отдельном Ubuntu/Debian control node по [главному README](../README.md). Поддержка Astra не объявляется проверенной до реального прогона на вашем выпуске и уровне защищённости. Успешные испытания Ubuntu/Debian относятся к указанным в [протоколе](verification-report.md) системам.

## Принцип поддержки разных выпусков

Номер выпуска не выбирается вручную и не приравнивается к версии Debian. HCP сохраняет `/etc/os-release` и точный `/etc/astra_version`, включая номер обновления. Например, значение `1.6.7.15` остаётся именно таким; его нельзя автоматически исправлять на похожий номер `1.7.6.15`.

| Уровень | Как выбирается проверка | Что подтверждает результат |
| --- | --- | --- |
| Подключение | SSH, фактическая версия Python, совместимость Ansible, UID sudo | Машина доступна для выполнения поддерживаемых команд |
| Общие Linux-проверки | Наличие команд, systemd, пакетного менеджера и права | Состояние конкретной настройки; это не сертификация Astra |
| Firewall | Фактический активный UFW/firewalld и его возможности | Проверенный backend, предварительный просмотр, резервирование и откат |
| CVE пакетов Astra | Официальные данные для точного выпуска и пакетов | Отдельный OVAL-адаптер: результаты выбранных определений, свежесть, целостность и ограничения базы |
| OpenSCAP | Встроенный профиль HCP Astra или применимый внешний datastream, назначенный политикой | Только применимые правила этого профиля |

Такой подход рассчитан на ветки 1.6, 1.7, 1.8 и другие выпуски. **Поддержка семейства в коде не означает, что каждая редакция, архитектура и уровень защищённости уже испытаны.** Для каждого фактического стенда сохраняйте версию ОС/Python, уровень защищённости, используемые базы и результаты приёмки. Нельзя переносить успешный Ubuntu-профиль или CVE-базу Debian на Astra.

## 1. Подготовка ВМ

1. Установите Astra из своего дистрибутива. Запишите редакцию, выпуск, выбранный уровень защищённости и установленные обновления. Не отключайте средства защиты Astra для совместимости с проверками.
2. Создайте снимок ВМ и сохраните доступ к её консоли в гипервизоре. HCP и Greenbone должны видеть её адрес. Для VirtualBox можно использовать отдельную Host-only/Internal сеть для лаборатории; NAT-адаптер при необходимости служит для установки обновлений. Один NAT без маршрута или проброса не обеспечивает входящее подключение к гостевой ВМ.
3. Используйте репозитории именно своего выпуска Astra. Не добавляйте репозитории Debian/Ubuntu ради установки scanner или более нового Python. Перед установкой проверяйте наличие пакетов через `apt-cache policy openssh-server python3 openscap-scanner firewalld`.
4. Подготовьте SSH и технического пользователя по разделу «Подключение первого Linux-хоста» главного README. В текущем режиме автоматизации нужен Python `/usr/bin/python3` и неинтерактивный sudo для проверок с повышением прав. Правило `NOPASSWD: ALL` даёт полные административные права и предназначено в инструкции для отдельной лабораторной учётной записи.

До изменения firewall зафиксируйте через консоль:

```bash
cat /etc/os-release
cat /etc/astra_version
uname -r
python3 --version
hostname -I
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
```

Если ED25519 host key отсутствует, получите fingerprint существующего RSA/ECDSA публичного host key и выберите соответствующий ключ в мастере. Приватные ключи и пароли в протокол не включайте.

## 2. Подключение через сайт

В HCP откройте «Хосты», укажите отдельный alias, например `astra-lab`, адрес, порт и технического пользователя. Установите показанный **публичный** ключ HCP в `authorized_keys` этого пользователя. Сверьте fingerprint машины с результатом из её консоли, сохраните ключ и нажмите «Проверить подключение».

Мастер проверяет SSH, работу Ansible/Python и фактический UID при sudo. Дополнительно он читает выпуск Astra, ядро, инструменты и состояние средств управления firewall. Блок «Готовность к аудиту» показывает предпосылки отдельно от результата подключения. Подключённый хост можно сохранить даже при неподготовленном OpenSCAP или неподтверждённой CVE-базе.

Проверка готовности не устанавливает пакеты, не включает службы, не изменяет firewall и не обращается к интернету. Неизвестное состояние остаётся неизвестным. Ошибка запуска Ansible на Python цели требует проверки совместимости версий; факт наличия `python3` сам по себе недостаточен.

Целевым Python-скриптам HCP нужен Python **3.5 или новее**. Комплектный Dockerfile устанавливает Ansible из Debian 12: ветка `ansible-core` 2.14 поддерживает целевые Python 3.5–3.11. До загрузки модулей мастер читает фактическую версию Python через SSH/raw и сверяет её с установленным Ansible; несовместимость получает понятное объяснение. Неизвестная версия Ansible требует успешного реального запуска модуля. При собственной установке Ansible сверяйте [матрицу совместимости](https://docs.ansible.com/projects/ansible/latest/reference_appendices/release_and_maintenance.html#ansible-core-support-matrix): например, 2.18/2.19 требуют на цели Python 3.8+, а 2.20/2.21 — 3.9+. Поэтому установка самого нового Ansible отдельно от Docker-рецепта может нарушить подключение к старому Python Astra. Фактическую версию Python вашей ВМ нужно проверить; она здесь не предполагается.

### Диагностический JSON до подключения

Чтобы подготовить первый прогон даже без настроенного SSH, скопируйте на Astra единственный файл [hcp-host-readiness.py](../ansible/scripts/hcp-host-readiness.py) и выполните из папки с этим файлом:

```bash
sudo python3 hcp-host-readiness.py --include-oval-metadata > astra-readiness.json
```

Если репозиторий уже находится на Astra, из его корня используйте путь `ansible/scripts/hcp-host-readiness.py` вместо короткого имени. Нужен только системный Python 3.5+; интернет, Ansible и дополнительные Python-пакеты для этой команды не требуются. Сборщик не устанавливает пакеты и не меняет настройки.

Полученный `astra-readiness.json` можно приложить для разбора готовности вашей ВМ. В нём сохраняются:

- точное содержимое версии Astra, разрешённые поля `os-release`, ядро и Python;
- наличие инструментов и состояние поддерживаемых менеджеров firewall;
- состояние установки `oval-db`, версия и архитектура пакета;
- пути и SHA-256 доступных XML-файлов и сжатых XML, перечисленных в локальной базе пакетов.

Ключи, пароли, содержимое правил firewall и самих XML в JSON не включаются. Уровень защищённости PARSEC сборщик не определяет: запишите его отдельно из настроек Astra.

Раздел `localOval` содержит **метаданные, а не результат CVE-аудита**. `not_installed` означает отсутствие установленного пакета, `unknown` — ошибку или неоднозначный ответ; наличие пакета не подтверждает готовность базы. Файлы считаются только кандидатами: XML не проверяется на соответствие OVAL, подпись производителя и применимость к выпуску остаются `not_checked`, анализ уязвимостей — `not_run`. Контрольная сумма идентифицирует локальные байты и сама по себе не подтверждает их официальный источник или актуальность.

Для ограниченного чтения обрабатываются максимум 32 файла, до 64 МиБ каждый и до 256 МиБ суммарно. Пропуски, изменение файла во время чтения и обрезанный список отмечаются явно; они не превращаются в нулевое число CVE. Сжатые файлы хешируются без распаковки. Символические ссылки на файлы и специальные файлы не читаются. Без флага `--include-oval-metadata` остаётся обычная проверка готовности; именно её использует мастер подключения.

## 3. Порядок аудита

Назначение локальной/сетевой базы OVAL и встроенного профиля HCP: [пошаговая инструкция](astra-audit.md). Получение файла от пользователя не является условием установки платформы.

| Этап | Ожидаемое доказательство | Граница оценки |
| --- | --- | --- |
| Сбор фактов и базовый Ansible-аудит | Версия ОС, реальные параметры SSH, служб, учётных записей и сети | Это общие Linux-проверки; специальные механизмы Astra требуют отдельного профиля |
| ssh-audit и Nmap с control node | Реальная SSH-конфигурация протокола и видимые порты | Открытый порт сам по себе не означает CVE |
| Временный Lynis | Завершённый запуск и исходные предупреждения | Неприменимость отдельных проверок к Astra нужно разобрать |
| Пакетный инвентарь и SBOM | Имена, исходные/двоичные версии, архитектура, точный `/etc/astra_version` | Для CVE Astra запустите отдельный OVAL-аудит; пакетный Trivy не подтверждает полноту покрытия Astra |
| OpenSCAP | Применимый datastream, точный ID профиля, SHA-256 и результаты правил | Выберите встроенный профиль HCP Astra из 18 правил или подходящий внешний профиль; не назначайте профиль Ubuntu/Debian |
| Greenbone | Завершённая задача по точному адресу ВМ, актуальные feeds, XML и импорт в HCP | Поддержка сетевого сервиса не гарантирует поддержку всех пакетов Astra; HCP пока не запускает задачи Greenbone |
| Dependency-Track | Компоненты SBOM, готовые источники, законченный анализ и проверенные находки | Результаты доступны в DTrack; обратной загрузки находок в HCP пока нет |

Для каждой CVE сверяйте применимость к **точному пакету Astra**, выпуску и обновлению по данным её производителя. Общая запись NVD и похожая upstream-версия не подтверждают наличие уязвимости после дистрибутивного backport. Если подходящих данных нет, фиксируйте «применимость не подтверждена».

### Официальные данные Astra для следующего этапа

У производителя есть [бюллетени безопасности с разделом 1.7](https://astra.ru/support/security-bulletins/) и [каталог OVAL](https://dl.astralinux.ru/astra/oval/). На момент проверки каталог перенаправлял на интерфейс JFrog; конкретный XML, дата его обновления, подпись и применимость к конкретным выпускам Astra пока не подтверждены. Наличие этих источников не означает, что HCP уже использует их.

После установки ВМ проверьте пакет `oval-db` через её собственные репозитории:

```bash
apt-cache policy oval-db
dpkg-query -W -f='${Package}\t${Version}\t${Status}\n' oval-db
dpkg -L oval-db
```

Если пакет не установлен, последние команды сообщат об отсутствии — это диагностический результат. Не устанавливайте пакет из чужого выпуска. Факт применения `oval-db` в Astra 1.7.6/1.7.7 подтверждён [документацией собственных испытаний Kaspersky](https://support.kaspersky.com/ScanEngine/docker_2.1/ru-RU/301599.htm); эти результаты не переносятся на HCP и точную пользовательскую сборку.

Полученный официальный OVAL требует отдельной проверки происхождения, критериев дистрибутива/версий, совместимости с установленным OpenSCAP и нормализации результата в HCP. OVAL-описания пакетных уязвимостей **не заменяют XCCDF-профиль конфигурационного харденинга**. Для этого реализован отдельный [OVAL-аудит](astra-audit.md), который сохраняет семантику определений и ограничения покрытия; текущие Trivy/SSG не объявляются полной CVE-базой Astra.

## 4. Проверка управления харденингом

Сначала определите, кто управляет текущими правилами: UFW, firewalld, netfilter-persistent или средства Astra. HCP поддерживает операции UFW/firewalld и не мигрирует автоматически существующий firewall. Не включайте второй менеджер поверх действующего. Проверку другого backend проводите на отдельном снимке/клоне ВМ.

Для настроенного поддерживаемого backend выполните цикл из [инструкции стенда](../deployment/lab/README.md#3-контролируемые-отклонения-и-firewall): исходный аудит → резервная копия/preview → закрытие тестового HTTP-порта → внешний Nmap → новое SSH-подключение → rollback → повторные Nmap и SSH. Отдельно подтвердите, что HTTP-процесс продолжал работать во время запрета; это отличает сетевую фильтрацию от остановки сервиса.

Сохраните ID транзакции, отчёты до/после, результаты Nmap, версии инструментов, даты/источники баз и снимок исходной конфигурации. Проверенный сценарий требует наблюдаемого нарушения до изменения, ожидаемого эффекта после и восстановления после отката. Ошибки сканирования, неприменимые правила и отсутствие данных остаются отдельными результатами.
