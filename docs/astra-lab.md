# Испытание HCP на Astra Linux 1.7.6.15

Эта инструкция подготавливает **Astra как проверяемую ВМ**. HCP установите на отдельном Ubuntu/Debian control node по [главному README](../README.md). Поддержка Astra не объявляется проверенной до реального прогона на вашем выпуске и уровне защищённости. Успешные испытания Ubuntu/Debian относятся к указанным в [протоколе](verification-report.md) системам.

## 1. Подготовка ВМ

1. Установите Astra из своего дистрибутива. Запишите редакцию, выпуск, выбранный уровень защищённости и установленные обновления. Не отключайте средства защиты Astra для совместимости с проверками.
2. Создайте снимок ВМ и сохраните доступ к её консоли в гипервизоре. HCP и Greenbone должны видеть её адрес. Для VirtualBox можно использовать отдельную Host-only/Internal сеть для лаборатории; NAT-адаптер при необходимости служит для установки обновлений. Один NAT без маршрута или проброса не обеспечивает входящее подключение к гостевой ВМ.
3. Используйте репозитории именно своего выпуска Astra. Не добавляйте репозитории Debian/Ubuntu ради установки scanner или более нового Python. Перед установкой проверяйте наличие пакетов через `apt-cache policy openssh-server python3 openscap-scanner firewalld`.
4. Подготовьте SSH и технического пользователя по разделу «Подключение первого Linux-хоста» главного README. В текущем режиме автоматизации нужен Python `/usr/bin/python3` и неинтерактивный sudo для проверок с повышением прав. Правило `NOPASSWD: ALL` даёт полные административные права и предназначено в инструкции для отдельной лабораторной учётной записи.

До изменения firewall зафиксируйте через консоль:

```bash
cat /etc/os-release
cat /etc/astra_version
uname -r
python3 --version
hostname -I
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
```

Если ED25519 host key отсутствует, получите fingerprint существующего RSA/ECDSA публичного host key и выберите соответствующий ключ в мастере. Приватные ключи и пароли в протокол не включайте.

## 2. Подключение через сайт

В HCP откройте «Хосты», укажите отдельный alias, например `astra-lab`, адрес, порт и технического пользователя. Установите показанный **публичный** ключ HCP в `authorized_keys` этого пользователя. Сверьте fingerprint машины с результатом из её консоли, сохраните ключ и нажмите «Проверить подключение».

Мастер проверяет SSH, работу Ansible/Python и фактический UID при sudo. Дополнительно он читает выпуск Astra, ядро, инструменты и состояние средств управления firewall. Блок «Готовность к аудиту» показывает предпосылки отдельно от результата подключения. Подключённый хост можно сохранить даже при неподготовленном OpenSCAP или неподтверждённой CVE-базе.

Проверка готовности не устанавливает пакеты, не включает службы, не изменяет firewall и не обращается к интернету. Неизвестное состояние остаётся неизвестным. Ошибка запуска Ansible на Python цели требует проверки совместимости версий; факт наличия `python3` сам по себе недостаточен.

При диагностике через консоль можно скопировать на ВМ единственный файл `ansible/scripts/hcp-host-readiness.py` и выполнить:

```bash
sudo python3 hcp-host-readiness.py > astra-readiness.json
```

JSON содержит сведения ОС и состояния инструментов, без ключей, паролей и содержимого правил firewall. Он не определяет уровень защищённости PARSEC: этот параметр запишите отдельно из настроек Astra.

## 3. Порядок аудита

| Этап | Ожидаемое доказательство | Граница оценки |
| --- | --- | --- |
| Сбор фактов и базовый Ansible-аудит | Версия ОС, реальные параметры SSH, служб, учётных записей и сети | Это общие Linux-проверки; специальные механизмы Astra требуют отдельного профиля |
| ssh-audit и Nmap с control node | Реальная SSH-конфигурация протокола и видимые порты | Открытый порт сам по себе не означает CVE |
| Временный Lynis | Завершённый запуск и исходные предупреждения | Неприменимость отдельных проверок к Astra нужно разобрать |
| Пакетный инвентарь и SBOM | Имена, исходные/двоичные версии, архитектура, точный `/etc/astra_version` | CVE-покрытие пакетов Astra по данным производителя в HCP пока не реализовано; пустой Trivy не означает безопасность |
| OpenSCAP | Применимый datastream, точный ID профиля, SHA-256 и результаты правил | В использованном SSG 0.1.79 нет Astra. Не назначайте ей профиль Ubuntu или Debian |
| Greenbone | Завершённая задача по точному адресу ВМ, актуальные feeds, XML и импорт в HCP | Поддержка сетевого сервиса не гарантирует поддержку всех пакетов Astra; HCP пока не запускает задачи Greenbone |
| Dependency-Track | Компоненты SBOM, готовые источники, законченный анализ и проверенные находки | Результаты доступны в DTrack; обратной загрузки находок в HCP пока нет |

Для каждой CVE сверяйте применимость к **точному пакету Astra**, выпуску и обновлению по данным её производителя. Общая запись NVD и похожая upstream-версия не подтверждают наличие уязвимости после дистрибутивного backport. Если подходящих данных нет, фиксируйте «применимость не подтверждена».

### Официальные данные Astra для следующего этапа

У производителя есть [бюллетени безопасности с разделом 1.7](https://astra.ru/support/security-bulletins/) и [каталог OVAL](https://dl.astralinux.ru/astra/oval/). На момент проверки каталог перенаправлял на интерфейс JFrog; конкретный XML, дата его обновления, подпись и применимость к 1.7.6.15 пока не подтверждены. Наличие этих источников не означает, что HCP уже использует их.

После установки ВМ проверьте пакет `oval-db` через её собственные репозитории:

```bash
apt-cache policy oval-db
dpkg-query -W -f='${Package}\t${Version}\t${Status}\n' oval-db
dpkg -L oval-db
```

Если пакет не установлен, последние команды сообщат об отсутствии — это диагностический результат. Не устанавливайте пакет из чужого выпуска. Факт применения `oval-db` в Astra 1.7.6/1.7.7 подтверждён [документацией собственных испытаний Kaspersky](https://support.kaspersky.com/ScanEngine/docker_2.1/ru-RU/301599.htm); эти результаты не переносятся на HCP и точную пользовательскую сборку.

Полученный официальный OVAL требует отдельной проверки происхождения, критериев дистрибутива/версий, совместимости с установленным OpenSCAP и нормализации результата в HCP. OVAL-описания пакетных уязвимостей **не заменяют XCCDF-профиль конфигурационного харденинга**. Это отдельный следующий этап поддержки Astra, а не обещание автоматического покрытия текущими Trivy/SSG.

## 4. Проверка управления харденингом

Сначала определите, кто управляет текущими правилами: UFW, firewalld, netfilter-persistent или средства Astra. HCP поддерживает операции UFW/firewalld и не мигрирует автоматически существующий firewall. Не включайте второй менеджер поверх действующего. Проверку другого backend проводите на отдельном снимке/клоне ВМ.

Для настроенного поддерживаемого backend выполните цикл из [инструкции стенда](../deployment/lab/README.md#3-контролируемые-отклонения-и-firewall): исходный аудит → резервная копия/preview → закрытие тестового HTTP-порта → внешний Nmap → новое SSH-подключение → rollback → повторные Nmap и SSH. Отдельно подтвердите, что HTTP-процесс продолжал работать во время запрета; это отличает сетевую фильтрацию от остановки сервиса.

Сохраните ID транзакции, отчёты до/после, результаты Nmap, версии инструментов, даты/источники баз и снимок исходной конфигурации. Проверенный сценарий требует наблюдаемого нарушения до изменения, ожидаемого эффекта после и восстановления после отката. Ошибки сканирования, неприменимые правила и отсутствие данных остаются отдельными результатами.
