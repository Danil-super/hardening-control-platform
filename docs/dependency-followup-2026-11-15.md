## Удаление лишнего пакета коллекций Ansible

В Dockerfile `ansible` заменён на `ansible-core`. Полный пакет содержит
неиспользуемые коллекции, в том числе `ansible.posix.authorized_key`, к которому
относится исходная запись CVE-2026-11837. Штатные playbook HCP используют
`ansible.builtin`; собственная установка ключа HCP этот модуль не вызывает.
Контракт пользовательских сценариев уточнён в [инструкции](../deployment/README.md).
Совместимый старый core и отдельный современный runtime сохраняются;
EOL старого core этим не устраняется.

В container CI добавлена проверка отсутствия пакета коллекций и syntax-check
всех 14 штатных playbook. Проверка сначала отклонила прежний образ, затем
прошла в отдельной копии после удаления только `ansible`.
Для этой копии отдельно прошли:

- 373 Ansible/Python и 240 deployment-тестов, без пропусков;
- настоящий локальный модуль в старом и современном Ansible;
- четыре Python installer, vendor floors и `pip check`.
- Настоящий SSH к собственной цели во внутренней Docker-сети: старый и
  современный runtime выполнили `collect-facts` и `package-inventory`.
  Все 139 записей пакетов совпали между runtime; четыре отчёта сохранены.
  Цель, сеть и временные ключи удалены, порты хоста не публиковались.

Копия получена удалением пакета из прежнего образа, а не новой сборкой Dockerfile.
Это проверка совместимости. Рабочий HCP, Astra и их секреты не использовались.
Минимум MemAvailable при полном наборе — 7 859 355 648 байт; OOM/guard не сработали.
Целью SSH была одноразовая Debian-копия, не Astra; приёмку Astra это не заменяет.
Современный Ansible выдал прежнее предупреждение об изменении facts в 2.24;
текущие четыре запуска завершились без unreachable/failed.

При подготовке `0801773` доступ к npm и GitHub API останавливался на TLS/
connect timeout при работающем DNS. Context7 не ответил, сайт Ansible
также был недоступен. Состав пакетов проверен по установленным метаданным Debian
и настоящим CLI, без предположений о новых API. До восстановления доступа
полную пересборку и публикацию нового SHA подтвердить нельзя.

На момент коммита `0801773` новый whole-image Trivy ещё не выполнялся.
Исходные **773 строки, 185 HIGH / 12 CRITICAL** не удалены и не объявлены
устранёнными в установленной панели.

## Пять HIGH TIFF / HarfBuzz

В точном установленном образе `ac01def7` статически разобраны исходные строки
224 и 478–481: CVE-2023-25193, CVE-2023-52355, CVE-2026-12912,
CVE-2026-36849 и CVE-2026-52490. Все пять — **not_actionable для текущих
путей HCP**, с высокой уверенностью в этой ограниченной области.

Из остановленного контейнера извлечены 14 файлов и зависимости всех 1075 ELF;
процессы образа не запускались. TIFF вызывается через Pillow `_imaging`,
HarfBuzz — через `libraqm` и Pillow `_imagingft`. Штатный HCP формирует новый
векторный PDF: ReportLab TTFont сопоставляет Unicode с подмножествами глифов,
а текст выводится PDF-операторами. Pillow ImageFont/RAQM не используется.
Фиксированный шрифт сам по себе не защищает от текстового CVE HarfBuzz;
существенно отсутствие вызова уязвимого шейпера в проверенном пути.

Для TIFF повторно прослежена граница экранирования: `img` действительно
вызывает ImageReader, но переменный текст становится данными без повторного
разбора разметки. Декодирования управляемого отчётом TIFF нет. Для отдельного
tool-CVE отсутствуют и `tiffcrop`, и установленный `libtiff-tools`.
PDF-скрипт и оба вызывающих модуля не менялись между установленным кодом
`ff5597d` и проверенным `0801773`.

Исходный порядок, полные описания и каждое CVE сохранены отдельно, включая
смешанное описание SamplesPerPixel/PixarLog. Контракт:
`artifacts/triage/2026-11-15-tiff-harfbuzz-high.json`, SHA-256
`9fe1e2fdc5b0e35535222cbfb1986d9ac73cfd5e2413739332a1a869c8f41784`.
Файлы, helper и полный ELF-инвентарь —
`artifacts/tiff-harfbuzz-2026-11-15/`; привязка образа SHA-256
`cea0c55a7f7f8f90c6ce4479ffac9251c03dd851a692455f7184c938213b3a02`.

Это статическая оценка, не обновление библиотек и не эксплуатационный тест.
