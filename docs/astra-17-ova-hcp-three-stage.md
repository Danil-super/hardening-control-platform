# Astra Linux SE 1.7.6.15: настоящий HCP OpenSCAP-эксперимент на официальном OVA

**Статус:** сценарий реализован; его нативный PASS возможен только при
успешном выполнении отдельного exact-head CI и сверке исходного безопасного
протокола. Код/юнит-тесты сами по себе не являются результатом на Astra.

## Зачем

[PR #69](https://github.com/Danil-super/hardening-control-platform/pull/69)
доказал на **реальной** Astra SE 1.7.6.15 (base, x86_64) полный размер/SHA
официального VirtualBox OVA, работу QEMU/KVM, точные системные файлы
выпуска и сборки и два соединения по закреплённому SSH host key.
Это сняло блокер начального загрузочного эксперимента, но не показало
исполнения **реальных** HCP-плейбуков и правил безопасности.

Новый CI: `.github/workflows/astra17-ova-hcp.yml`,
новый валидатор: `deployment/tests/verify_astra17_ova_audit.py`.
Основной smoke runner запускает дополнительный этап только при
явном `--native-hcp-three-stage`. Без флага старый SSH smoke остаётся
неизменным и не выдаёт сканирование за выполненное.

## Реальный эксперимент

На **собственной одноразовой QEMU/KVM ВМ GitHub** (не на Astra пользователя):

1. Повторно сверить полный оригинальный OVA, размер, SHA-256 и фактический
   `ID=astra`, `/etc/astra_version=1.7.6`,
   `/etc/astra/build_version=1.7.6.15`, архитектуру, ядро и machine-id.
2. Для подключения Ansible требуется отдельное `ANSIBLE_SSH_ARGS`
   с уже закреплённым приватным `known_hosts`: стандартный
   `ansible.cfg` HCP объявляет другой `UserKnownHostsFile`, а SSH
   может выбрать первое встретившееся значение. Эксперимент не
   отключает `StrictHostKeyChecking`, он закрепляет правильный
   файл по умолчанию **раньше** других аргументов.
   При неуспехе в открытый протокол попадают только разрешённые
   категории `ssh/sudo/python/ansible`, без исходного журнала.
3. Только после этого через SSH по публично документированной фабричной
   паре **на своей временной ВМ** установить сгенерированный одноразовый
   публичный SSH-ключ `hcp-ci`. Проверить новый SSH **по ключу**
   и `sudo -n`; никакие правила sudoers не переписываются.
   Это **не** подтверждает выполнение мастера HCP в веб-панели.
3. **Экспериментальная совместимость:** оригинальная Astra 1.7.6.15
   действительно содержит Python 3.7, тогда как GitHub-hosted runner
   запускал ansible-core 2.21. Это не поддерживаемая пара: реальный
   [run #42039660473](https://github.com/Danil-super/hardening-control-platform/actions/runs/42039660473)
   завершился на `target_python_outside_upstream_ansible_support`.
   Только для одноразовой GitHub-VM контроллер получает **отдельное**
   Python 3.12 virtualenv с точно закреплённым
   `ansible-core==2.17.14`, поддерживающим целевой Python 3.7.
   Системный Ansible управляющей Ubuntu и Python на самой Astra не
   заменяются. Ansible 2.17 **снят с поддержки с ноября 2025 года**,
   поэтому эксперимент не является рекомендацией использовать эту
   связку в production. Для рабочих хостов необходим отдельный анализ
   поддерживаемой безопасной версии ОС/Python/контроллера.
4. Перед первым плейбуком выполнить три отдельные **read-only**
   транспортные проверки Ansible: SSH `raw`, Python-модуль
   `ping` без повышения прав и тот же модуль с `sudo`.
   Прочитать фактическую версию Python с гостя и версию
   `ansible-core` на контроллере; сверить их с официальной матрицей
   совместимости. Неизвестная или неподдерживаемая пара **блокирует**
   нативную приёмку без скрытой установки Python в Astra.
   При неуспехе сохранить в безопасном JSON только название этапа,
   числовой код и фиксированные категории, не строки логов.
4. Запустить **штатные** Ansible `collect-facts.yml` и
   `package-inventory.yml`; сверить настоящий дистрибутив, x86_64,
   ненулевой список реально установленных пакетов, SHA-256 исходных JSON.
4. Проверить установленный `oscap`; при его отсутствии попытаться
   установить настоящий OpenSCAP **только на тестовую ВМ** из действующих
   репозиториев производителя, без скрытия сетевых/пакетных ошибок.
5. Выполнить реальный штатный HCP `openscap-audit.yml` с
   `/__hcp_builtin__/astra-baseline.xml` и 18 оригинальными правилами.
   Сохранить RAW ARF, исполненный datastream, нормализованный JSON и их
   отдельные SHA внутри **закрытого каталога CI**.
6. Контролируемо добавить один бит `o+x` к `/etc/passwd`
   **только на одноразовом тестовом диске** и повторить тот же профиль;
   вернуть исходные права в `finally`, затем провести третий аудит.
   Оригинальный исходный образ не изменяется: используется QCOW2 overlay.
7. Требовать **ровно 18 различных оригинальных rule ID**, только
   реальные `pass`/`fail` без unknown/partial, один переход
   `pass → fail → pass` у `passwd_permissions`, отсутствие изменений
   остальных 17 правил и точное совпадение всех 18 исходных статусов
   после восстановления. Контрольные суммы source bundle и ARF сохраняются.
8. Проверить права `/etc/passwd` и выполнить **новый SSH** к прежнему
   host key/машине после восстановления. При любой ошибке/неопределённости
   результат **FAIL**, оригинальный VM overlay уничтожается в CI.

Ниже нет заранее приписанного результата `4→5→4`: это была
подлинная мера **Astra 1.8**, её нельзя переносить в 1.7 без наблюдения.

## Как сохраняются доказательства

CI публикует **только очищенный ограниченный JSON**:
количество подтверждённых пакетов, 18 статусов/счётчиков, единый
content bundle ID, SHA-256 оригинальных ARF/JSON/datastream и результаты
сохранности SSH/прав. Сырые файлы содержат потенциально чувствительную
информацию об ОС и хранятся только во временном закрытом каталоге GitHub
runner, **не** прикрепляются к публичным artifacts. Для финального диплома
понадобится отдельный защищённый операторский архив оригиналов со своим
контролем целостности и сроком хранения.

## Чего сценарий НЕ доказывает

- Полную оценку CVE из Astra OVAL 1.7 и корректность всех backports;
- Работающую штатную production-публикацию с проверенным
  `assetId/generation` в веб-панели;
- Выполнение полного HCP-мастера подключения вместо первоначального
  disposable SSH bootstrap;
- Общий откат всей ОС, безопасность любого firewall-изменения,
  эксплуатационную готовность Ubuntu control node;
- Применимость результатов base к `adv/max`;
- Цифровую подпись изготовителя исходного образа.

Поэтому даже успешный 18-rule прогон не закрывает полностью
[issue #40](https://github.com/Danil-super/hardening-control-platform/issues/40)
или [issue #38](https://github.com/Danil-super/hardening-control-platform/issues/38).
Далее нужны полный original vendor OVAL, production source/asset binding,
затем реальная приёмка control node по #43.

Отдельные отрицательные unit-тесты:
`deployment/tests/test_astra17_ova_audit.py`. Нативный CI должен
завершиться **на точном SHA** и предоставить проверяемый sanitized protocol,
иначе эксперимент остаётся непроверенным.


## 05.11.2026 — нативная граница после устранения Python/Ansible

В трёх настоящих CI-прогонах на официальном OVA успешно подтверждены Python 3.7,
точный контроллер Ansible 2.17.14 (только изолированная лаборатория), все три
проверки транспорта `raw/ping/sudo`, оригинальный Ansible `collect-facts` и
штатная инвентаризация **398 реально установленных пакетов**. На Astra также
присутствует `oscap`. Оригинальные ARF/datastream первой 18-rule проверки
однако отсутствовали. Это **не** является подтверждением 18 правил или OVAL.

Дополнена приватная диагностика нормализованного OpenSCAP-отчёта: если
сырой ARF или datastream не создан, в публичный JSON попадают **только**
булевы `rawArfPresent / executedDatastreamPresent / normalizedReportPresent`,
код запуска, безопасные значения `compose/dictionary/validation` и категории
ошибок вроде `sce_plugin_unavailable`. Сырые stderr, конфигурации, ARF,
пользовательские пути, значения и секреты наружу **не публикуются**.
Восстановление исходного режима `/etc/passwd` теперь проверяется даже при
ошибке сканера и отражается отдельным ограниченным флагом.

До успешной проверки настоящего профиля 18 правил результат и задача #40 остаются
непринятыми. При подтверждённой несовместимости OpenSCAP/SCE нужно отдельно
обосновать поддерживаемый способ оценки; **не отключать валидацию XML или SCE
ради зелёного CI**.


## Повторные нативные CI быстрее, без кэша секретов

`actions/cache@v4` хранит **только оригинальный публичный OVA** с ключом
его фиксированного SHA-256. При повторном запуске бинарный файл проверяется
полным хешированием до копирования в приватный каталог, а копия проверяется
второй раз. Повреждённый/подменённый кэш — блокировка, не успешная оценка.
При первом запуске оригинал скачивается по фиксированному HTTPS адресу и
помещается в кэш только после полной проверки всех байтов.
Гостевой диск, ключи, пароли, идентификаторы, ARF и журналы не кэшируются.
Сохранённый SHA от производителя не является независимой цифровой подписью.
