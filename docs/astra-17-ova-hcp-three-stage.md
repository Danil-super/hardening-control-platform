# Astra Linux SE 1.7.6.15: настоящий HCP OpenSCAP-эксперимент на официальном OVA

**Статус:** сценарий реализован; его нативный PASS возможен только при
успешном выполнении отдельного exact-head CI и сверке исходного безопасного
протокола. Код/юнит-тесты сами по себе не являются результатом на Astra.

## Проверенный нативный запуск 5 ноября 2026

На точном head `7b2713a` подтверждён [реальный CI 42082327179](https://github.com/Danil-super/hardening-control-platform/actions/runs/42082327179): 14/4 → 13/5 → 14/4 (pass/fail) по 18 исходным правилам. Исходный ограниченный JSON и его оригинальный ZIP сохранены с SHA-256:
[проверяемый протокол реального запуска](astra-17-ova-hcp-observed-2026-11-05.md).
Это доказательство только конкретного коммита, не автоматическая приёмка обновлённого PR и не полное OVAL/production-доказательство.

## Зачем

[PR #69](https://github.com/Danil-super/hardening-control-platform/pull/69)
доказал на **реальной** Astra SE 1.7.6.15 (base, x86_64) полный размер/SHA
официального VirtualBox OVA, работу QEMU/KVM, точные системные файлы
выпуска и сборки и два соединения по закреплённому SSH host key.
Это сняло блокер начального загрузочного эксперимента, но не показало
исполнения **реальных** HCP-плейбуков и правил безопасности.

Новый CI: `.github/workflows/astra17-ova-hcp.yml`,
новый валидатор: `deployment/tests/verify_astra17_ova_audit.py`.
Основной smoke runner запускает дополнительный этап только при
явном `--native-hcp-three-stage`. Без флага старый SSH smoke остаётся
неизменным и не выдаёт сканирование за выполненное.

## Реальный эксперимент

На **собственной одноразовой QEMU/KVM ВМ GitHub** (не на Astra пользователя):

1. Повторно сверить полный оригинальный OVA, размер, SHA-256 и фактический
   `ID=astra`, `/etc/astra_version=1.7.6`,
   `/etc/astra/build_version=1.7.6.15`, архитектуру, ядро и machine-id.
2. Для подключения Ansible требуется отдельное `ANSIBLE_SSH_ARGS`
   с уже закреплённым приватным `known_hosts`: стандартный
   `ansible.cfg` HCP объявляет другой `UserKnownHostsFile`, а SSH
   может выбрать первое встретившееся значение. Эксперимент не
   отключает `StrictHostKeyChecking`, он закрепляет правильный
   файл по умолчанию **раньше** других аргументов.
   При неуспехе в открытый протокол попадают только разрешённые
   категории `ssh/sudo/python/ansible`, без исходного журнала.
3. Только после этого через SSH по публично документированной фабричной
   паре **на своей временной ВМ** установить сгенерированный одноразовый
   публичный SSH-ключ `hcp-ci`. Проверить новый SSH **по ключу**
   и `sudo -n`; никакие правила sudoers не переписываются.
   Это **не** подтверждает выполнение мастера HCP в веб-панели.
3. **Экспериментальная совместимость:** оригинальная Astra 1.7.6.15
   действительно содержит Python 3.7, тогда как GitHub-hosted runner
   запускал ansible-core 2.21. Это не поддерживаемая пара: реальный
   [run #42039660473](https://github.com/Danil-super/hardening-control-platform/actions/runs/42039660473)
   завершился на `target_python_outside_upstream_ansible_support`.
   Только для одноразовой GitHub-VM контроллер получает **отдельное**
   Python 3.12 virtualenv с точно закреплённым
   `ansible-core==2.17.14`, поддерживающим целевой Python 3.7.
   Системный Ansible управляющей Ubuntu и Python на самой Astra не
   заменяются. Ansible 2.17 **снят с поддержки с ноября 2025 года**,
   поэтому эксперимент не является рекомендацией использовать эту
   связку в production. Для рабочих хостов необходим отдельный анализ
   поддерживаемой безопасной версии ОС/Python/контроллера.
4. Перед первым плейбуком выполнить три отдельные **read-only**
   транспортные проверки Ansible: SSH `raw`, Python-модуль
   `ping` без повышения прав и тот же модуль с `sudo`.
   Прочитать фактическую версию Python с гостя и версию
   `ansible-core` на контроллере; сверить их с официальной матрицей
   совместимости. Неизвестная или неподдерживаемая пара **блокирует**
   нативную приёмку без скрытой установки Python в Astra.
   При неуспехе сохранить в безопасном JSON только название этапа,
   числовой код и фиксированные категории, не строки логов.
4. Запустить **штатные** Ansible `collect-facts.yml` и
   `package-inventory.yml`; сверить настоящий дистрибутив, x86_64,
   ненулевой список реально установленных пакетов, SHA-256 исходных JSON.
4. Проверить установленный `oscap`; при его отсутствии попытаться
   установить настоящий OpenSCAP **только на тестовую ВМ** из действующих
   репозиториев производителя, без скрытия сетевых/пакетных ошибок.
5. Выполнить реальный штатный HCP `openscap-audit.yml` с
   `/__hcp_builtin__/astra-baseline.xml` и 18 оригинальными правилами.
   Сохранить RAW ARF, исполненный datastream, нормализованный JSON и их
   отдельные SHA внутри **закрытого каталога CI**.
6. Контролируемо добавить один бит `o+x` к `/etc/passwd`
   **только на одноразовом тестовом диске** и повторить тот же профиль;
   вернуть исходные права в `finally`, затем провести третий аудит.
   Оригинальный исходный образ не изменяется: используется QCOW2 overlay.
7. Требовать **ровно 18 различных оригинальных rule ID**, только
   реальные `pass`/`fail` без unknown/partial, один переход
   `pass → fail → pass` у `passwd_permissions`, отсутствие изменений
   остальных 17 правил и точное совпадение всех 18 исходных статусов
   после восстановления. Контрольные суммы source bundle и ARF сохраняются.
8. Проверить права `/etc/passwd` и выполнить **новый SSH** к прежнему
   host key/машине после восстановления. При любой ошибке/неопределённости
   результат **FAIL**, оригинальный VM overlay уничтожается в CI.

Ниже нет заранее приписанного результата `4→5→4`: это была
подлинная мера **Astra 1.8**, её нельзя переносить в 1.7 без наблюдения.

## Как сохраняются доказательства

CI публикует **только очищенный ограниченный JSON**:
количество подтверждённых пакетов, 18 статусов/счётчиков, единый
content bundle ID, SHA-256 оригинальных ARF/JSON/datastream и результаты
сохранности SSH/прав. Сырые файлы содержат потенциально чувствительную
информацию об ОС и хранятся только во временном закрытом каталоге GitHub
runner, **не** прикрепляются к публичным artifacts. Для финального диплома
понадобится отдельный защищённый операторский архив оригиналов со своим
контролем целостности и сроком хранения.

## Чего сценарий НЕ доказывает

- Полную оценку CVE из Astra OVAL 1.7 и корректность всех backports;
- Работающую штатную production-публикацию с проверенным
  `assetId/generation` в веб-панели;
- Выполнение полного HCP-мастера подключения вместо первоначального
  disposable SSH bootstrap;
- Общий откат всей ОС, безопасность любого firewall-изменения,
  эксплуатационную готовность Ubuntu control node;
- Применимость результатов base к `adv/max`;
- Цифровую подпись изготовителя исходного образа.

Поэтому даже успешный 18-rule прогон не закрывает полностью
[issue #40](https://github.com/Danil-super/hardening-control-platform/issues/40)
или [issue #38](https://github.com/Danil-super/hardening-control-platform/issues/38).
Далее нужны полный original vendor OVAL, production source/asset binding,
затем реальная приёмка control node по #43.

Отдельные отрицательные unit-тесты:
`deployment/tests/test_astra17_ova_audit.py`. Нативный CI должен
завершиться **на точном SHA** и предоставить проверяемый sanitized protocol,
иначе эксперимент остаётся непроверенным.


## 05.11.2026 — нативная граница после устранения Python/Ansible

В трёх настоящих CI-прогонах на официальном OVA успешно подтверждены Python 3.7,
точный контроллер Ansible 2.17.14 (только изолированная лаборатория), все три
проверки транспорта `raw/ping/sudo`, оригинальный Ansible `collect-facts` и
штатная инвентаризация **398 реально установленных пакетов**. На Astra также
присутствует `oscap`. Оригинальные ARF/datastream первой 18-rule проверки
однако отсутствовали. Это **не** является подтверждением 18 правил или OVAL.

Дополнена приватная диагностика нормализованного OpenSCAP-отчёта: если
сырой ARF или datastream не создан, в публичный JSON попадают **только**
булевы `rawArfPresent / executedDatastreamPresent / normalizedReportPresent`,
код запуска, безопасные значения `compose/dictionary/validation` и категории
ошибок вроде `sce_plugin_unavailable`. Сырые stderr, конфигурации, ARF,
пользовательские пути, значения и секреты наружу **не публикуются**.
Восстановление исходного режима `/etc/passwd` теперь проверяется даже при
ошибке сканера и отражается отдельным ограниченным флагом.

До успешной проверки настоящего профиля 18 правил результат и задача #40 остаются
непринятыми. При подтверждённой несовместимости OpenSCAP/SCE нужно отдельно
обосновать поддерживаемый способ оценки; **не отключать валидацию XML или SCE
ради зелёного CI**.


## Повторные нативные CI быстрее, без кэша секретов

`actions/cache@v4` хранит **только оригинальный публичный OVA** с ключом
его фиксированного SHA-256. При повторном запуске бинарный файл проверяется
полным хешированием до копирования в приватный каталог, а копия проверяется
второй раз. Повреждённый/подменённый кэш — блокировка, не успешная оценка.
При первом запуске оригинал скачивается по фиксированному HTTPS адресу и
помещается в кэш только после полной проверки всех байтов.
Гостевой диск, ключи, пароли, идентификаторы, ARF и журналы не кэшируются.
Сохранённый SHA от производителя не является независимой цифровой подписью.


## Исправление блокера oscap ds sds-compose=1 на Astra 1.7

Оригинальные CI [run #42053029615](https://github.com/Danil-super/hardening-control-platform/actions/runs/42053029615)
и [#42053029622](https://github.com/Danil-super/hardening-control-platform/actions/runs/42053029622)
подтвердили точный этап ошибки: на реальной Astra 1.7 подготовка
встроенного HCP XCCDF/OVAL/SCE посредством **`oscap ds sds-compose`**
возвращает `rc=1`; ARF ещё не создаётся. Причина на уровне конкретного
сообщения старого OpenSCAP пока не подтверждена. Гость штатно прошёл
Ansible facts, инвентаризацию 398 пакетов, sudo и SSH.

Для изолированного опыта добавлен явно выбранный флаг
`hcp_openscap_compose_on_controller=true`. При нём **не меняется**
набор 18 правил: оригинальные authored XCCDF/SCE, OVAL и CPE
складываются в закрытый временный каталог Ubuntu control node, собираются
в SDS с **обязательным** `oscap ds sds-validate` на контроллере.
Плейбук переносит этот проверенный XML на временный каталог Astra и
отказывается проводить оценку, если **SHA-256 полученного SDS не совпадает**
с исходным проверенным SDS. На целевой ОС остаётся неизменённый шаг
`oscap xccdf eval` с оригинальным ARF; ни правила, ни валидация
не отключаются, лишь **переносится место сборки**. Временные каталоги
обеих ОС очищаются через `always`, сырые ARF не публикуются.

Обычный встроенный аудит HCP на других системах остаётся прежним:
флаг по умолчанию выключен. Нативный успешный результат 18 правил ещё
требует конкретного повторного CI: перенос компоновки не гарантирует
поддержки схемы/движка оценки в установленном Astra OpenSCAP.


## Второй совместимый путь: оригинальные отдельные XCCDF/SCE/OVAL/CPE на Astra 1.7

В [нативном CI #42062289555](https://github.com/Danil-super/hardening-control-platform/actions/runs/42062289555)
после успешной сборки и валидации исходного SDS на Ubuntu OpenSCAP Astra
прочитал SDS (`oscap info rc=0`), но не смог валидировать его по схеме
(`oscap ds sds-validate rc=1`) и не сформировал ARF (`xccdf eval rc=1`).
Это **не** доказывает, какой конкретный компонент не поддерживается.

Новый явно включаемый режим
`hcp_openscap_standalone_on_target=true` при обязательном
`hcp_openscap_compose_on_controller=true` **не заменяет** оригинальный
профиль авторскими суррогатами. Все те же четыре исходных файла
(`astra-baseline.xml`, `check.py`, `astra-platform-oval.xml`,
`astra-cpe-dictionary.xml`) остаются неизменными. На контроллере всё так
же обязательно собирается и валидируется полный SDS; дополнительно
на целевой Astra запускаются `oscap xccdf validate`, `oval validate` и
`cpe validate` **над отдельными исходными XML**. Далее независимо
сравниваются SHA-256 **всех четырёх файлов** на управляющей Ubuntu и
целевой Astra. Любой отказ схемы, потеря компонента или несовпадение
хеша блокирует оценку.

Только после этих проверок на реальном госте запускается
`oscap xccdf eval --cpe <исходный CPE> --profile <исходный профиль>
--results-arf <приватный ARF> <исходный XCCDF>`.
Новая форма оценки в протоколе помечается
`evaluationForm=original-standalone-xccdf`; фактически оценённый
XCCDF сохраняется отдельно как `.evaluated-xccdf.xml` и проверяется по
SHA-256. **Нельзя** выдавать такой источник за SDS, успешно прошедший
валидацию **на самой Astra**. Исходный 18-rule ARF, все SCE evidence,
контролируемое нарушение и восстановление исходных прав, реальный SSH и
независимый OVAL-вендора по-прежнему обязательны. Если старая Astra
не принимает и этот режим, итог **FAIL / unsupported**.

Функция ограничена явным выбором; обычная оценка других Linux-хостов
не меняется. Данных для полной эксплуатационной приёмки пока нет.


### Протокол отдельной проверки схем 5 ноября 2026 года

Оригинальный [CI #42068358419](https://github.com/Danil-super/hardening-control-platform/actions/runs/42068358419)
не получил ARF и не выполнил ни одного подтверждённого 18-rule baseline:
проверки схем исходных отдельных XCCDF, OVAL, CPE на гостевой Astra не
прошли в совокупности. **Неизвестно, какой из трёх XML отвергнут.**

В ответ добавлена безопасная сводка `standaloneXmlSchemaExitCodes` с тремя
отдельными кодами `xccdf`, `oval`, `cpe` в зафиксированном порядке.
Исходный stdout/stderr, гостевые пути, machine-id и ключи не публикуются.
Если валидатор не был выполнен или не вернул полный набор кодов, сводка
остаётся пустой, а не выдаётся за три успешные проверки. Результат
18 правил будет принят только при реальном ARF с доказанным source bundle
и завершённым циклом нарушения/восстановления на настоящей Astra.

## 05.11.2026 — конкретные ошибки трёх отдельных XML-схем

Реальные подлинные KVM-прогоны [PR #72, run 42074282492](https://github.com/Danil-super/hardening-control-platform/actions/runs/42074282492)
и [PR #74, run 42074462969](https://github.com/Danil-super/hardening-control-platform/actions/runs/42074462969)
на Astra SE **1.7.6.15** завершились с одинаковым результатом:
на управляющем Ubuntu исходный SDS `compose=0, dictionary=0,
validation=0`, а проверки исходных отдельных XML на целевом
`oscap` дали **`xccdf=1, oval=1, cpe=1`**.
До оценки 18 правил дело не дошло, ARF отсутствует. Реальные
`collect-facts`, `sudo`, SSH, 398 пакетов и проверка восстановления
прав `/etc/passwd` успешно выполнены.

**Важно:** одинаковый числовой код может означать несовместимую CLI-команду,
отсутствующий набор локальных схем или ошибки исходной XML-схемы;
по одним кодам установить причину невозможно. Следующая проверка не
снимает требование к подлинным результатам. Новая приватная диагностика
в `0600` сохраняет до 2048 символов stdout/stderr для каждого из
трёх валидаторов **только внутри одноразового CI**. В публичный
протокол транслируются **только** допустимые числовые коды,
`validator_command_not_supported`, `required_schema_missing`,
`xml_schema_rejected`, `unsupported_xml_schema_version`,
`source_or_dependency_file_missing`, `permission_denied`,
`xml_parse_error`, `sce_engine_missing` и наблюдённая числовая
версия локального OpenSCAP (если строка версии однозначна).
Вне приватного стенда оригинальные диагностические строки,
пути, машины, SSH-ключи, диски и учётные данные не экспортируются.

Результат `available=true` у диагностического классификатора —
**не признак успешного OpenSCAP**. Все предыдущие strict gates
схем, SHA-256 четырёх исходных файлов, исходный ARF, точные 18 правил
и восстановление состояния остаются обязательными.

## 05.11.2026 — OpenSCAP 1.3.6: отсутствующие XSD как конкретный блокер

Подлинный [нативный run #42080478500](https://github.com/Danil-super/hardening-control-platform/actions/runs/42080478500)
на Astra 1.7.6.15 (оригинальный очищенный GitHub artifact
`13441325212`) подтвердил, что `oscap --version` сообщает **1.3.6**.
Приватная классификация настоящих `oscap xccdf validate` и
`oscap oval validate` вернула
`required_schema_missing`; для CPE код `1`, но категория
не определена. Все три проверки не прошли, ARF отсутствует,
исходные права `/etc/passwd` восстановлены. Это **не** означает, что
сами XML некорректны: ошибка в исходных XSD/CLI/зависимостях ещё
требует испытания.

В Debian XML-схемы OpenSCAP поставляются отдельным пакетом
`openscap-common`, но его наличие в конкретном выпуске Astra
проверяется **не предположением**, а запросом в репозитории самой
временной ОС. В штатной `main` HCP никаких автоматических установок
на пользовательские хосты нет.

В отдельном **только лабораторном** приёмочном runner добавлена
предварительная read-only проверка наличия трёх конкретных схем:
- `/usr/share/openscap/schemas/xccdf/1.2/xccdf_1.2.xsd`
- `/usr/share/openscap/schemas/oval/5.11.1/oval-definitions-schema.xsd`
- `/usr/share/openscap/schemas/cpe/2.0/cpe-dictionary_2.0.xsd`

Если схема отсутствует, runner вправе установить **только**
`openscap-common` из **уже настроенных репозиториев исходной
одноразовой Astra Linux**, после прямой проверки GitHub-hosted окружения
и доступности пакета. Репозитории не подменяются, компоненты PARSEC не
отключаются, системный Python не изменяется, чужие пакеты не
подгружаются. Если пакет уже установлен, но XSD отсутствуют,
результат блокируется и классифицируется отдельно — нельзя
произвольно «переустанавливать» безопасность настоящей ОС.
После установки runner обязан заново проверить **все три** источника
XSD и выполнить оригинальные штатные проверки схем и ARF на Astra.
Наличие пакета/XSD **само по себе не означает** `PASS` аудита.
Любая невозможность установки, неполный XSD или ошибка оценки
приводит к отрицательной приёмке.
