# Нативный трёхточечный эксперимент HCP на Astra Linux SE 1.8 — 4 ноября 2026 года

**Статус: реальные нативные измерения из GitHub Actions, а не синтетические фикстуры.**
Эта запись фиксирует наблюдения при CI-прогоне [Real Astra VM scanner acceptance](https://github.com/Danil-super/hardening-control-platform/actions/runs/41771982306)
для PR [#48](https://github.com/Danil-super/hardening-control-platform/pull/48).
Проверен head-коммит `99ba7dc8be54291b27dc5776461dee0b0066ee46`; принят в
основную ветку merge-коммитом `9b3e46133341174808eadca243daa2d7e897fd08`.

## Условия и источники

На одноразовом GitHub-hosted Ubuntu-контроллере в QEMU/KVM были запущены **две
самостоятельные реальные гостевые ОС Astra Linux Special Edition** с собственными
ядром и базой пакетов. Фактические системные файлы, kernel, machine-id и SSH host
key проверены в гостях; исходные официальные образы сверены по размеру и SHA-256
перед запуском. SSH использовал отдельные ключи и заранее закреплённые
отпечатки. OpenSCAP и инвентаризацию выполняли неизменённые production-playbook
HCP, а не подложные результаты. Оригинальные ARF, XCCDF, JSON и выполненные
datastream сохранены в публичных CI-артефактах.

Обе ВМ использовали один источник определения CVE производителя для ветки 1.8:
`oval-definitions-alse-1.8.xml`, SHA-256
`3ba7e4c8126be503fc95bb916f2d9b45306869bd0f58f200abc5b1e1effbbe3d`,

эти два результата **не измеряют общую полноту CVE-анализа**.

## Три реальные последовательные точки

Для экспериментального правила
`xccdf_org.hcp_rule_passwd_permissions` в одноразовой ВМ были выполнены:
исходная проверка, временное контролируемое расширение прав `/etc/passwd`,
повторная проверка, восстановление исходных разрешений и третий аудит.
Исходные разрешения восстанавливались в `finally`, даже при ошибке.
Это демонстрация обнаружения и фиксации изменений, **а не доказательство
того, что HCP сам выполнил безопасное автоматическое исправление**.

| Показатель | 1.8.1 | 1.8.6 |
| --- | ---: | ---: |
| Полностью сопоставимые правила | 18 | 18 |
| Исходное число `failed` | 4 | 4 |
| После контролируемого изменения `failed` | 5 | 5 |
| После восстановления `failed` | 4 | 4 |
| Переходы `passed → failed` после изменения | 1 | 1 |
| Переходы `failed → passed` после восстановления | 1 | 1 |
| Отличия состояний правил между исходным и восстановленным | 0 | 0 |
| `restorationMatchesBaseline18Rules` | `true` | `true` |
| Проверка полноты исходного профиля | 18/18 | 18/18 |

Все три оригинальных отчёта опубликованы посредством существующего
`publishCapturedAssetReports` с одной подтверждённой привязкой
`assetId` и `generation=1` для каждого гостя. Сравнение выполнялось
реальным `measure_astra_baseline.py --restored`; оно сверило одну и ту же
`bundle-sha256:d5dcd96987d288da7ca92bfcfced2b1cfc3b51f787821870ed14a49c9b0416b7`.
У исполненных OpenSCAP datastream разные хеши из-за времени компиляции:
скрипт сохраняет **каждый** SHA-256 отдельно и не объявляет это сменой
исходного набора правил.

## Проверяемое происхождение измерений

Публичный workflow содержит два самостоятельно завершённых job:

- [Артефакт Astra 1.8.1](https://github.com/Danil-super/hardening-control-platform/actions/runs/41771982306/artifacts/13296713861)
- [Артефакт Astra 1.8.6](https://github.com/Danil-super/hardening-control-platform/actions/runs/41771982306/artifacts/13297345967)

В каждом архиве исходные ARF находятся как `baseline.arf.xml`,
`violation.arf.xml`, `restored.arf.xml`, исходные отчёты —
`reports/hcp-real-astra-openscap-*.json`, опубликованные отчёты с
привязкой — `three-stage-bound-reports/*.json`, а числовой результат —
`three-stage-metrics.json`; статус и контрольные шаги — `protocol.json`.

| SHA-256 отдельного файла (внутри CI-артефакта) | 1.8.1 | 1.8.6 |
| --- | --- | --- |
| `three-stage-metrics.json` | `c41cd9f6fe4edfcc787c89e6f8307ab856c8b55ec7a2982349996525bd984a7e` | `1616b15e3822b5ef8be454b0d38df0142fe533e4080bbd14bd5ec32b28be64db` |
| `protocol.json` | `8cbc5d0aecd07c643fba45d7ff6f332e4aa6e4eab6c42e272e085918707646ea` | `e58c7cc0915c22a91fa3258f1b954e29091a491c3d73817dbb62cf68e83b62c9` |
| `baseline.arf.xml` | `99ac707996817b4d03dad9a6522aac82ec99f6f216c7af02560ae1f8527bce59` | `36386f7c450fba4438979ee474a2c9cd316eb8c4d160a2990f5a861aeaed6707` |

Оригинальные байты отдельных опубликованных `baseline/violation/restored`
включены в `three-stage-metrics.json` в полях
`source.baselineSha256`, `source.changedSha256` и
`source.restoredSha256`; там же есть SHA-256 каждого фактически выполненного
datastream. Это позволяет независимо сопоставить экспортированные материалы,
не копируя сырой `machine-id` или приватные SSH-ключи в диплом.

**Срок хранения артефактов GitHub Actions ограничен** (настроен
`retention-days: 14`): их надо сохранить в защищённый архив дипломного стенда
до истечения срока. Контрольные суммы в этом документе не заменяют оригинальные
файлы. Не размещайте частные идентификаторы гостя и приватные ключи в открытом
репозитории.

## Границы вывода

Точный результат: **в одинаковых 18 конфигурационных правилах наблюдался один
переход `passed → failed` при намеренном нарушении и обратный переход после
восстановления**, причём исходные и финальные результаты 18 правил совпали.
Это **не** доказывает возвращение каждого файла системы к исходному состоянию,
непрерывную доступность SSH, состояние firewall, все CVE, стойкость КСЗ, работу
режимов `adv/max` или высокую эффективность автоматического харденинга.
Нельзя переносить результаты на **Astra Linux SE 1.7.6.15**: для этого выпуска
нужна самостоятельная нативная проверка согласно `docs/astra-17-native-proof.md`
и задачам #40/#43.

См. также `docs/astra-experiment-acceptance.md` с формальными критериями
сравнимости, подтверждённой идентичности актива и безопасного отката.
