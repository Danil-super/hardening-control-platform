# Маршрут специалиста: подключение → аудит → разбор → изменение → повторная проверка

## Назначение

Маршрут в разделе «Хосты» показывает **одно следующее действие** на основе уже сохранённой информации HCP.
Это навигация, а не автоматический запуск сканирования и не экспертная система, самостоятельно разрешающая изменения.
Ни загрузка страницы, ни выбор хоста не запускают SSH, OpenSCAP, Trivy, обновление базы или исправление.

Вверху «Хостов» специалист может переключать только зарегистрированные хосты. Выбор открывает контекст
выбранного alias. Из таблицы сводной страницы на него можно перейти по ссылке
`/hosts?host=<имя>&#35;host-audit-flow`; разрешены только alias, фактически присутствующие в inventory
ответа авторизованного API, а не произвольный параметр URL.

## Основание подсказки

- Состояние управляющего узла: текущие сведения Ansible и inventory.
- Активная задача: серверный список заданий, получаемый через существующий поставщик состояния.
- Незавершённое исправление: сохранённый журнал транзакций и требование восстановления.
- Оценка аудит-доказательств: `riskSummary` из защищённого `/api/ansible/hosts`.
  Используются только последние применимые источники на инструмент и профиль, с проверкой свежести
  и привязки к идентичности актива. Диагностические факты и сырой инвентарь не считаются аудитом.
- При наличии результатов: категория найденных отклонений, включая **неоценённую** критичность.

Приоритеты маршрута: отсутствие хоста → обязательная сверка прерванного изменения →
неподготовленный контроллер → выполняемое задание → исключённая идентичность →
нет аудита → устаревший аудит → неполные доказательства → разбор находок →
изучение отчёта без зарегистрированных находок.

Если `riskSummary` отсутствует или содержит отрицательные, противоречивые либо некорректные счётчики,
маршрут сообщает, что статус аудита не подтверждён, и ведёт к истории. Он не выдаёт отсутствие данных API
за отсутствие выполненных проверок и не утверждает полноту. Переход к оценке находок не запускает исправления;
для последнего используется существующий процесс согласования/плана харденинга.

## Выполнение

1. **Подключение.** Добавить разрешённый сервер, сверить SSH fingerprint, подготовить ключ и
   выполнить preflight. Совместимость Python, sudo, OpenSCAP, OVAL и firewall
   подтверждается инструментальными проверками, а не галочкой в маршруте.
2. **Назначение политик и источников.** Под «Следующим действием» для
   выбранного хоста HCP показывает отдельную read-only сводку назначенных Astra OVAL
   и OpenSCAP. По кнопке «Источники и политики» открывается раздел
   `/data-sources?host=alias#host-audit-preparation` с тем же alias. Неверный
   или отсутствующий alias не используется для определения другого хоста.
   Для Astra выбрать применимый к выпуску источник OVAL и профиль OpenSCAP.
   Для поддерживаемых иных ОС использовать собственные проверенные источники;
   отсутствие Astra OVAL на них **не ошибка**. Состояние «Назначено» означает
   только наличие записи; исполнение, свежесть и применимость проверяются отдельно.
   Неполная или устаревшая база приводит к ограниченному результату, а не к PASS.
3. **Аудит.** Пользователь явно выбирает инструмент. Дождаться завершения задания,
   открыть исходный отчёт и сводку, проверить область оценки, идентичность и
   причину каждого `manual`/`partial`/`not_run`.
4. **Разбор.** Проверить применимость CVE и подтверждение результата; не складывать
   количество наблюдений из разных источников в число независимых CVE.
5. **План.** Отдельно согласовать изменение. Сейчас поддержан контролируемый
   firewall backend UFW/firewalld в подтверждённой области; произвольная CVE
   не превращается в разрешение на автоматическое обновление пакета.
6. **Повторная проверка.** Запустить тот же применимый профиль после изменения;
   сопоставить доказательства одной идентичности актива. Отсутствие находки
   не подтверждает, что все CVE обнаружены.

## Приёмка интерфейса

- Пустой inventory: показан маршрут подключения; никаких запросов сканирования.
- При выборе хоста read-only раздел источников читает только назначения; не запускает
  SSH, OpenSCAP, Trivy, обновление баз или изменение конфигурации.
- Если директория отчётов ещё отсутствует, API явно формирует нулевую сводку
  аудита для хоста, а не пропускает `riskSummary` и не выдаёт статус неизвестности.
- Есть хост с фактами, но без аудита: показан запуск первой проверки, не «проверено».
- Есть отчёты, но истёк срок или потеряна привязка: предложена повторная оценка
  либо сверка идентичности, а не исправление на основе старого отчёта.
- Есть свежие неполные или противоречивые доказательства: показано ограничение;
  маршрут ведёт к сводке, не к применению.
- Есть свежие находки, даже с неизвестной критичностью: сначала разбор источника.
- Есть свежие результаты без зарегистрированных находок: нет заявления о безопасности.
- Есть незавершённая транзакция: действие восстановления имеет приоритет над запуском
  нового аудита; журнал транзакций остаётся виден.
- Есть запущенное задание: интерфейс показывает, что оно ещё выполняется.
- Выбор хоста из сводной таблицы открывает тот же alias на странице «Хосты».
  Несуществующий alias из URL не создаёт хост и не попадает в операции.

Автоматические проверки: `web/tests/host-audit-workflow.test.mjs`,
`web/tests/dashboard-evidence-status.test.mjs`,
`web/tests/host-source-guidance.test.mjs` и
`web/tests/hosts-empty-reports-summary.test.mjs`. Ручная браузерная приёмка проверяет
навигацию и доступность элементов; unit-тесты не доказывают работу на настоящей Astra.

## Что ещё требуется

Маршрут не определяет автоматически применимость всех источников по одному имени ОС.
Полная готовность конкретного хоста требует живого preflight и завершённого сканирования.
Нативная приёмка Astra SE 1.7/1.6 и измерение «до → после → откат»
выполняются по `docs/astra-experiment-acceptance.md` на разрешённом стенде.
