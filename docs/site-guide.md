# Инструкция по работе с платформой

Панель подключает Linux-хосты с помощью одноразового SSH-пароля и устанавливает отдельный ключ для каждой машины. Установка, ключи, sudo и добавление машины описаны в **[единой инструкции Ubuntu → Astra](ubuntu-astra-setup.md#host-onboarding)**. Эта страница продолжает её после настройки подключения.

1. Просканируйте сеть или укажите адрес. Введите логин и пароль администратора Astra, нажмите «Подключить хост». Если форма запросит подтверждение сервера, вставьте отпечаток из доверенной консоли этой Astra или реестра и нажмите «Сверить и сохранить», затем снова «Подключить хост». HCP сравнивает ключ целевой Astra по сети, а не собственный ключ Ubuntu. Вход, создание отдельной пары, проверка прав root и сохранение выполняются автоматически. Пароль вводится через HTTPS/localhost и не сохраняется.
2. Для уже добавленного хоста используйте «Настроить». Укажите административную учётную запись и нажмите «Сохранить подключение». При смене пользователя или переходе со старого общего ключа введите пароль для установки индивидуального ключа. История сохраняется.
3. Выберите хост и профиль: «Базовый Linux», «SSH-сервер», «Веб-сервер» или «Docker-хост». В блоке «Основной аудит» нажмите «Проверить профиль» и откройте отчёт; проверьте полноту и ошибки сбора. «Проверить связь» — только быстрая проверка SSH/Ansible. Если такой же завершённый тест уже есть и после него HCP не зафиксировала операций изменения, платформа предложит открыть предыдущий отчёт и попросит подтвердить повтор. Это не запрет: подтвердите запуск после внешних изменений на сервере, обновления CVE-базы или профиля проверки, а также для контрольного аудита.
4. Для административного режима используйте root с разрешённым SSH-входом либо администратора, у которого работает `sudo su`. При первом подключении HCP проверяет sudo разовым паролем, не меняет `sudoers` и не хранит пароль. Для каждого ручного аудита, изменения и отката такого хоста введите пароль в поле «Пароль sudo для одного действия». [Требования к доступу](ubuntu-astra-setup.md#sudo-access).
5. В «Источниках» для Trivy выберите «Сетевая база» и нажмите «Сохранить и загрузить» (либо «Загрузить общую базу CVE», если режим уже активен). Дождитесь статуса «актуальна»; далее кнопка «Обновить общую базу CVE» загружает новый снимок перед аудитом. Это одна общая база для поддерживаемых ОС. Затем в «Дополнительных проверках» выберите «Пакеты и CVE — Trivy». Для CVE Astra назначьте группе базу нужного выпуска в «Источниках» → «CVE пакетов Astra» и там же выберите «CVE Astra — OVAL / OpenSCAP». Для конфигурационного OpenSCAP назначьте в «Политиках» профиль «Astra Linux — базовые проверки HCP», затем выберите «Профиль конфигурации — OpenSCAP». [Подготовка сканеров](astra-audit.md).
6. Для нескольких источников откройте «Сводка» в отчётах: она показывает совпадения CVE, портов и scanner-правил, не складывая оценки риска.
7. В «Истории» хоста можно удалить отдельный ненужный тестовый отчёт. Связанный SBOM удаляется только если больше нигде не используется. Отчёты, уже включённые в план устранения, операцию изменения, итоговый PDF или последующую цепочку проверки, защищены от удаления; журнал действий и итоговые PDF не очищаются этой кнопкой.
8. Для внешнего сетевого аудита Greenbone создайте Target с точным адресом выбранного хоста, запустите разрешённую Task, дождитесь `Done`, затем в **Scans → Reports** скачайте именно **Report → XML**. В HCP откройте «Сетевой сканер Greenbone / OpenVAS — импорт XML» у того же хоста и загрузите распакованный файл. Подробный порядок и запуск scanner: [интеграции аудита](audit-integrations.md#3-greenbone--openvas).
9. Перед изменением firewall изучите отчёт. В блоке «Обратимые изменения firewall» укажите параметры, причину и точное имя выбранного хоста в поле подтверждения. Для первого опыта используйте отдельный тестовый порт, например 8088.
10. Нажмите «1. Проверить» и изучите результат. Конфигурация firewall не изменяется; временный helper передаётся и удаляется даже для предварительной проверки.
11. Нажмите «2. Применить». Платформа подтвердит состояние firewall и открытые порты, сохранит backup UFW/firewalld на хосте, выполнит действие и запустит повторный аудит. Несвязанная неполнота профиля не блокирует изменение, но отсутствие сведений именно о firewall или портах — блокирует.
12. Для отмены найдите транзакцию со статусом `applied`, `failed` или `rollback_failed` с сохранённой резервной копией, нажмите «Откатить» и подтвердите имя хоста. После отката запустите аудит вручную. При нескольких изменениях одного хоста откатывайте их в обратном порядке.

Автоматический backup содержит только конфигурацию активного UFW/firewalld и остаётся в `/var/lib/hcp-backups` на целевой машине. HCP не делает снимок всей ОС и не создаёт автоматически резервную копию собственной SQLite. Команды для данных платформы: [бэкап и восстановление](backup-restore.md). При потере SSH для восстановления может потребоваться консоль ВМ; автоматического отката по таймеру нет.

## Регулярный аудит

### Выберите режим перед запуском

На странице **«Хосты»** доступны два разных режима, и они не подменяют друг друга:

| Режим | Что делает | Доступ к Astra |
| --- | --- | --- |
| **Внешний аудит** | Nmap проверяет TCP-порты, ssh-audit — параметры публичного SSH-рукопожатия | Не входит по SSH и не запускает команды на хосте |
| **Основной аудит профиля** | Сверяет локальные настройки выбранной роли, службы, пакеты и firewall | HCP автоматически выполняет read-only команды через уже настроенный SSH/sudo; оператору не нужен терминал Astra |

Внешний режим подходит для начального обследования или политики «без удалённого выполнения». Он не подтверждает состояние локального firewall, пользователей, пакетов и настроек ОС, поэтому его результат не является полным конфигурационным аудитом.

Не используйте API-планировщик веб-приложения: периодический аудит запускается systemd timer на control node. Установка описана в `deployment/README.md`. Timer вызывает отдельную команду в контейнере и использует `flock`, поэтому перезапуск панели не отменяет расписание и не создает параллельные проверки. Хост в режиме «sudo по паролю» намеренно не попадает в автоматический запуск: HCP не хранит его пароль. Для расписания используйте утверждённую техническую учётную запись или root по SSH.

Задача `packages` означает инвентарь и Trivy. Отдельный OVAL-аудит Astra в штатное расписание пока не включён; запускайте его вручную в «Хостах». OpenSCAP включается отдельно после назначения профиля.

## Допустимые действия

В текущей версии через панель разрешены только обратимые операции firewall:

- закрытие конкретного TCP/UDP-порта; TCP 22 и фактический SSH-порт управления защищены;
- блокировка IPv4-адреса с проверкой адреса управляемого хоста, фактического источника SSH и дополнительных адресов `HCP_CONTROL_IPS`.

## Если отчёт помечен «Проверка неполная»

Это не означает, что аудит «почти завершён» или что найденные проблемы автоматически недостоверны. Это означает, что хотя бы один контроль не вернул ответ, достаточный для вывода: например, не удалось получить эффективную конфигурацию SSH, список открытых портов или состояние firewall. Поэтому HCP не считает общую оценку и не трактует отсутствие находок как признак защищённости.

Откройте в отчёте блок **«Что не удалось проверить»**. Для каждого пункта там показаны причина и следующий шаг. После устранения именно этой причины вернитесь в «Хосты» и повторите основной аудит. Частый случай для SSH — сначала проверить конфигурацию на целевом сервере командой `sudo sshd -t`; не меняйте настройки только ради исчезновения предупреждения, если вы не понимаете последствия.

## Собственные сценарии

В «Сценариях» всегда доступны встроенные проверки для просмотра. Для создания собственных YAML-черновиков добавьте `HCP_ENABLE_CUSTOM_AUDITS=true` в `.env` и перезапустите HCP. Черновики сохраняются в постоянном runtime-хранилище HCP, поэтому не пропадают при пересборке контейнера. На рабочем control node можно сохранить черновик, но проверка и запуск произвольного Ansible YAML заблокированы: даже syntax-check способен загрузить локальные плагины и не должен выполняться для недоверенного текста. Тестируйте такой сценарий на отдельном тестовом control node с точной целью запуска; только там, после явного `HCP_PRODUCTION_MODE=false`, становятся доступны syntax-check и кнопка запуска. В production переносите лишь проверенный и рассмотренный вариант.
