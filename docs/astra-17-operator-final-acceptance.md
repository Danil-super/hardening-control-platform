# Astra Linux SE 1.7.6.15 — единая проверка реального эксперимента

**Статус: инструмент подготовки протокола, не опубликованные результаты опыта.**
Нативные 18 правил Astra 1.7.6.15 и отдельно полная выбранная XML OVAL уже
испытаны в scoped CI на конкретных SHA; ссылки и ограничения находятся в
[текущем паспорте релиза](release-status.md). Это не заменяет настоящий
операторский эксперимент через HCP на разрешённой ВМ, для которого предназначена
эта инструкция. Исторические испытания Astra 1.8.1 и 1.8.6 также не заменяют его.

## Результат этапа

Контроллерная программа `deployment/tests/accept_astra17_native_experiment.py`
связывает **разные доказательства одного опыта**:

1. Реально скачанный исходный OVA для выпуска **1.7.6.UU2** (base/adv/max),
   его полный SHA-256 и ранее сохранённый `*.json` от
   `pin_astra17_vm_image.py`. Имя файла и контрольная сумма **не** удостоверяют
   издателя криптографически.
2. Подлинные `facts.json` и три неизменённых JSON-отчёта HCP OpenSCAP:
   baseline, изменение, restored. Проверяются тот же подтверждённый актив,
   системная версия `1.7.6` **и полная сборка `1.7.6.15`** по разным файлам, поколение подключения, 18 одинаковых правил, неизменная
   исходная база правил, полнота сканирования и временная последовательность.
3. Приватный исходный `guest-identity.txt`, полученный через **уже
   независимо закреплённый SSH fingerprint** на управляющем узле. Входной
   `machine-id` остаётся только локально, в итоговом JSON его нет. Сценарий читает оба системных файла: `/etc/astra_version` (ожидаем 1.7.6) и `/etc/astra/build_version` (ожидаем 1.7.6.15). Оба значения должны совпадать, номер UU2 не выводится только из названия образа.
4. Реальный отдельный OVAL-отчёт **той же Astra 1.7.6.15** и заранее записанный
   SHA-256 именно этой XML-базы. Проверяются checksum, число определений,
   фактическое выполнение всех определений и `partial=false`.
   OVAL-отчёт обязан иметь тот же подтверждённый `assetBinding` (актив,
   поколение, fingerprint и ID подключения), что и три OpenSCAP-отчёта;
   одинакового alias недостаточно. Полный OVAL JSON может быть больше обычного
   лимита 32 МиБ, поэтому читается отдельным проверенным потоком до 256 МиБ
   с SHA-256 и защитой от замены inode. Это не означает, что база содержит
   все известные CVE или подписана изготовителем.
5. **Новый SSH-вызов после восстановления**: подтверждается возможность
   создать новое key-only соединение с той же машиной, тем же ядром,
   `machine-id` и SSH host key. Используется закрытый `known_hosts`
   и дополнительная сверка полного fingerprint ключа через
   `ssh-keygen -F`, в том числе для хешированного `known_hosts`.
   Для устранения гонки между просмотром и использованием записи снимок
   `known_hosts` копируется в приватный временный файл и используется
   **одновременно** для проверки fingerprint и самого SSH-вызова.
   Пароль, SSH agent и автоматическая смена доверенного SSH-ключа отключены.

Важная граница: новый SSH-вызов выполняет **только чтение** системных
идентификаторов, не запускает Ansible, сканеры, настройку ОС или firewall.
При отсутствии ключа, отчёта, достоверной версии, полномочий или после ошибки
он прекращает приёмку вместо самостоятельного изменения стенда.

## Что требуется до команды

На выделенной **Ubuntu control node**, а не на Astra, подготовьте:

- изолированную Astra SE 1.7.6.15 с подтверждённым режимом безопасности
  (base, adv либо max), снимком ВМ и доступной консолью гипервизора;
- оригинал OVA, локальный JSON хеш-проверки, отдельную запись происхождения;
- четыре исходных HCP JSON: `facts` и три OpenSCAP; отдельный OVAL JSON,
  относящийся к конкретному выпуску 1.7, и его SHA-256;
- первоначальное приватное наблюдение `guest-identity.txt` (права 0600);
- подтверждённые заранее host fingerprint, закрытые файлы private key и
  `known_hosts` (права 0600). Не пересылайте их в публичные отчёты;
- **фактически** выполненные контролируемое изменение и восстановление
  после сохранения исходной конфигурации. Наличие трёх файлов само по себе
  не доказывает причинности изменения.

## Запуск после выполнения трёх реальных проверок

На Ubuntu:

```bash
umask 077
python3 deployment/tests/accept_astra17_native_experiment.py \
  --image /private/original/alse-1.7.6.uu2-base-virtualbox-mg15.3.1-amd64.ova \
  --image-evidence /private/evidence/image-pin.json \
  --before /private/reports/baseline.json \
  --changed /private/reports/changed.json \
  --restored /private/reports/restored.json \
  --facts /private/reports/facts.json \
  --native-identity /private/evidence/guest-identity.txt \
  --oval /private/reports/astra-oval.json \
  --oval-sha256 ВАШ_ЗАРАНЕЕ_СОХРАНЁННЫЙ_64_HEX_SHA256 \
  --ssh-host ВАШ_РАЗРЕШЁННЫЙ_ХОСТ \
  --ssh-port 22 \
  --ssh-user ВАШ_РАЗРЕШЁННЫЙ_ПОЛЬЗОВАТЕЛЬ \
  --ssh-private-key /private/ssh/hcp-host-key \
  --ssh-known-hosts /private/ssh/known_hosts \
  --ssh-fingerprint SHA256:ВАШ_НЕЗАВИСИМО_СВЕРЕННЫЙ_ОТПЕЧАТОК \
  --output /private/results/new-astra17-acceptance.json
```

Все значения — **местозаполнители**, а не реальные данные пользователя.
Результат создаётся впервые с правами 0600, исходные файлы не перезаписываются.

Успех означает лишь
`astra-17-native-evidence-bounded-acceptance`: в одной идентифицированной
Astra 1.7.6.15 наблюдались 18 сопоставимых правил, исходная конфигурация
профиля, совпадающие состояния правил после восстановления, результаты
указанной OVAL-базы и новое закреплённое SSH-подключение.
Поля `independentVendorSignatureVerified=false`,
`fullSystemRollbackVerified=false`,
`generalCveCoverageVerified=false`, `operatorSignoffReceived=false`
явно не позволяют объявлять платформу полностью защищённой или принятой.

## Что ещё нужно для закрытия #40 и #43

Отдельно фиксируются нативный защитный уровень, оригинальные ARF, точные
изменения firewall, разрешения файлов и состояние других служб, снапшот
VM/проверенный обратный откат, размеры и подписи исходных OVAL, реальные
интервалы времени эксперимента, итоговый PDF и подпись оператора.

**Нативные 18 правил и выбранная полная OVAL-база прошли scoped CI;
актуальные SHA и runs приведены в [статусе релиза](release-status.md).**
Операторская приёмка сайта и восстановление целевого хоста остаются отдельными
условиями закрытия #40 и #43.
Синтетические проверки `test_accept_astra17_native_experiment.py`
проверяют только отсутствие ложного успешного исхода и защиту границ ввода.
