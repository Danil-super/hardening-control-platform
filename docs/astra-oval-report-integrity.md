# Проверка целостности результатов Astra OVAL при публикации отчёта HCP

Реальный [native CI 42089756207](https://github.com/Danil-super/hardening-control-platform/actions/runs/42089756207)
в лаборатории подтвердил полный выбранный набор оригинальной Astra 1.7 x86_64 OVAL:
**19 527** ID и столько же оценённых результатов. **337 true не являются
автоматически 337 уникальными CVE**. Это не эксперимент штатного production
HCP web-процесса `assetId/generation`.

Данный этап устраняет отдельную опасность на стороне читающего HCP:
до него `scanner.partial=false` без полного `definitionResults`,
исходных SHA или подтверждения выполненной оценки мог позволять показать
пустой OVAL-отчёт как завершённый. Теперь `web/lib/astra-oval-evidence.ts`
проверяет каждый ID и исходный native-state, количество и итоговый
`resultCounts`, источник с `checksumVerified`, SHA оригинального
результата OpenSCAP, `evaluationPerformed`, код завершения и отсутствие
ошибок; каждое истинное vulnerability-определение должно присутствовать
в исходных `findings`.

При неполных доказательствах `AnsibleReportSummary.partial=true`,
`needsReview=true`, причина указана безопасным машинным кодом
`ovalEvidence.reason`. **Сам исходный JSON не изменяется и не
подменяется**: специалист продолжает видеть оригинал, но ни dashboard,
ни агрегирующая сводка не должны считать его чистым. Отсутствующий
или некорректный digest отдельно снимает подтверждение scope.

Пространство ID ограничено 30 000 (соответствует пределу адаптера), а
сканирование OVAL выполняется прежде этой проверки. Классификация
`unknown`, `error`, `not evaluated`, отсутствующие результаты и
фальшивое совпадение подсчётов блокируют статус полной выбранной области.
Допустимый `not applicable` сохраняется как самостоятельный результат.
Синтетическая 19 527-ID проверка тестирует только сохранность
`definitionResults` через штатные `publishCapturedAssetReports` и
`readAnsibleReport`; **не** является новым нативным тестом Astra.

Остаются отдельно необходимые условия (#38, #40, #43): настоящий
производственный контрольный узел, авторизованный мастер SSH, неизменяемая
привязка `assetId/generation`, сверка JSON/PDF, независимая подпись
производителя, подтверждённые backport verdicts, восстановление
контроллера и проверка firewall rollback в изолированном стенде.


## Смена проверяемой базы OVAL в истории

Разные SHA-256 исходных Astra OVAL XML нельзя трактовать как одну и ту же
область оценки. Теперь ключ группировки отчётов содержит точный
`contentId`, для неизвестной области используется отдельный ключ
с идентификатором отчёта. Если после нового источника исчезли строки CVE
из прежнего источника, это **не** доказательство исправления: прежняя
область получает `lostCoverage: scope_changed` (либо `scope_unknown`)
и сохраняет ID исходных находок, новый источник отмечается текущим.

Повторный аудит с **тем же** SHA-256 не создаёт ложную потерю покрытия.
Сам список исходных результатов, данные прежней базы и привязка актива
не переписываются. Нативный CI-эксперимент не заменяет этот отдельный
продуктовый тест динамики источников.

## Нативные выгрузки Astra OVAL и происхождение критичности

На странице Astra OVAL основная выгрузка — **«Отчёт OpenSCAP (HTML)»**,
рядом — **«Исходный XML»** результатов. JSON HCP остаётся во вторичных
технических сведениях; там же доступна исходная база OVAL XML. HTML —
представление OpenSCAP, а не официальный или сертифицированный отчёт Astra.
Он не получает добавленную HCP классификацию критичности.

`GET /api/ansible/reports/<id>/native?format=html|xml|source-xml` требует
действующую административную сессию (проверка и в proxy, и в обработчике).
Исторические отчёты работают, если сохранились оригиналы и их манифест
`rawEvidence.version=1`: `.raw-evidence/<id>/oval-results.xml` и `source.xml`.
Для выгрузки достаточно соответствующего артефакта, необязательно полного
комплекта. Отсутствие оригинала возвращает явный `native_original_unavailable`,
а нарушение размера/SHA-256 — `native_integrity_failed`. JSON никогда не
подставляется вместо XML или HTML; повторный аудит хоста не запускается.

Перед выдачей сервер открывает только регулярные файлы без следования
символическим ссылкам; родительские каталоги закрепляются дескрипторами
Linux `/proc/self/fd`. Путь артефакта должен в точности соответствовать ID
отчёта и допустимому виду XML. JSON ограничен 64 MiB, каждый XML — 384 MiB;
копирование и SHA-256 идут блоками, проверяются также размер и изменение
файла во время чтения, а digest сверяется с записанным scanner digest,
если он имеется. Выдаётся проверенная приватная копия, не изменяемый
впоследствии опубликованный файл.

На управляющем узле проверена команда OpenSCAP 1.3.7:
`oscap oval generate report <oval-results.xml>` (HTML в stdout;
`--output <file>` также поддерживается). Хост-цель не участвует.
Нужны `/usr/bin/oscap`, `/usr/bin/prlimit` (util-linux), установленные
штатные XSL OpenSCAP и доступный для записи каталог отчётов. Запуск без
shell, с очищенным окружением и отключённым XML-каталогом; исходный UTF-8
XML перед HTML проверяется потоково: DTD, ENTITY, внешние processing
instructions и XInclude запрещены. Штатный OVAL report XSL не использует
`document()` или внешние imports. Выбор пользовательского stylesheet,
скачивание сущностей и сетевые параметры отсутствуют.

Бюджет: два активных экспорта на процесс, 120 секунд до завершения
выгрузки, 90 CPU-секунд и 1536 MiB адресного пространства генератора,
HTML не более 256 MiB, stderr не более 1 MiB. Рабочий каталог
`<reports>/.native-exports/export-*` и файлы имеют права 0700/0600;
они удаляются после завершения, ошибки или отмены клиентом. Обрыв процесса
контроллера/SIGKILL может оставить приватный рабочий каталог — его можно
удалить при остановленном контроллере. Ошибка/лимит генератора даёт 503;
XML остаётся самостоятельной выгрузкой. Файлы выдаются attachment с
`no-store`, `nosniff`, CSP sandbox/default-src none, запретом frame и
referrer: содержимое сканера недоверенное, внутри приложения не встраивается.
Сохранённый HTML вне браузерного ответа может не сохранять эти HTTP-ограничения.

Для реального запуска
`host-172.16.95.128-astra-oval-run-20261109T133850000Z-568ee538`
зафиксированы **4134** сработавших определения и **4068** уникальных CVE:
это разные величины. **2317** оценок получены из явной метки
`Chromium security severity` в описании (`chromium_description`),
**1817** не оценены **текущим адаптером HCP** (`not_provided`), а не
обязательно лишены оценки в источнике. Независимая потоковая проверка
сохранённых результатов и исходной базы (Expat, блоки 64 KiB, предел
384 MiB/файл и 90 секунд, запрет DTD/сущностей, сверка SHA/размера)
нашла все **4134** положительных ID в исходнике и **4068** уникальных
CVE-ссылок. В этих определениях **нет элемента/атрибута severity**, но
**4114** содержат элементы **CVSS2.0 и CVSS3.0**: все 2317 Chromium и
**1797 из 1817** неоценённых HCP. Только **20** неоценённых не содержат
этих полей. Текст `None` также является встречающимся значением, не оценкой.

Например, `oval:astra:def:1018334494808905445573835425666627`
(CVE-2022-37052) содержит CVSS2.0=`None` и
CVSS3.0=`NistCVSS3(cvss='AV:N/AC:L/PR:N/UI:R/S:U/C:N/I:N/A:H', score=6.5)`.
Адаптер `hcp-oval-audit.py` сейчас извлекает `severity` и явную метку
Chromium, но не эти расширения CVSS; JSON `cvss: null` поэтому **не
доказательство отсутствия CVSS в исходнике**. Правила нормализации этим
изменением не меняются. Это не низкий риск и не отсутствие уязвимости.
Страница явно указывает ограничение адаптера и происхождение
`oval_metadata`/`chromium_description`; исторический JSON не переписывается.
SHA-256 проверенного source.xml (134 668 815 байт):
`c9364c80d664907dc472475d2ef57689c314abecede7a58e7e9dae8250891d17`.

Для этого сохранённого результата (169 882 850 байт XML) дополнительно
выполнена проверка нового helper непосредственно с OpenSCAP 1.3.7 на
управляющем узле: HTTP Response 200, HTML **10 997 844 байта**, около
3 секунд, SHA-256 исходного результата
`0551c8e2e6c7efa94755e4c2380b549ec3e7f591083f09d3b142467bc4c0c7ba`.
Это проверка экспорта сохранённых доказательств, не повторное сканирование
и не новая сертификация. Отдельная синтетическая проверка реального
генератора подтвердила attachment и очистку рабочего каталога.
