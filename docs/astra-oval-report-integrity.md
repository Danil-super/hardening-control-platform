# Проверка целостности результатов Astra OVAL при публикации отчёта HCP

Реальный [native CI 42089756207](https://github.com/Danil-super/hardening-control-platform/actions/runs/42089756207)
в лаборатории подтвердил полный выбранный набор оригинальной Astra 1.7 x86_64 OVAL:
**19 527** ID и столько же оценённых результатов. **337 true не являются
автоматически 337 уникальными CVE**. Это не эксперимент штатного production
HCP web-процесса `assetId/generation`.

Данный этап устраняет отдельную опасность на стороне читающего HCP:
до него `scanner.partial=false` без полного `definitionResults`,
исходных SHA или подтверждения выполненной оценки мог позволять показать
пустой OVAL-отчёт как завершённый. Теперь `web/lib/astra-oval-evidence.ts`
проверяет каждый ID и исходный native-state, количество и итоговый
`resultCounts`, источник с `checksumVerified`, SHA оригинального
результата OpenSCAP, `evaluationPerformed`, код завершения и отсутствие
ошибок; каждое истинное vulnerability-определение должно присутствовать
в исходных `findings`.

При неполных доказательствах `AnsibleReportSummary.partial=true`,
`needsReview=true`, причина указана безопасным машинным кодом
`ovalEvidence.reason`. **Сам исходный JSON не изменяется и не
подменяется**: специалист продолжает видеть оригинал, но ни dashboard,
ни агрегирующая сводка не должны считать его чистым. Отсутствующий
или некорректный digest отдельно снимает подтверждение scope.

Пространство ID ограничено 30 000 (соответствует пределу адаптера), а
сканирование OVAL выполняется прежде этой проверки. Классификация
`unknown`, `error`, `not evaluated`, отсутствующие результаты и
фальшивое совпадение подсчётов блокируют статус полной выбранной области.
Допустимый `not applicable` сохраняется как самостоятельный результат.
Синтетическая 19 527-ID проверка тестирует только сохранность
`definitionResults` через штатные `publishCapturedAssetReports` и
`readAnsibleReport`; **не** является новым нативным тестом Astra.

Остаются отдельно необходимые условия (#38, #40, #43): настоящий
производственный контрольный узел, авторизованный мастер SSH, неизменяемая
привязка `assetId/generation`, сверка JSON/PDF, независимая подпись
производителя, подтверждённые backport verdicts, восстановление
контроллера и проверка firewall rollback в изолированном стенде.


## Смена проверяемой базы OVAL в истории

Разные SHA-256 исходных Astra OVAL XML нельзя трактовать как одну и ту же
область оценки. Теперь ключ группировки отчётов содержит точный
`contentId`, для неизвестной области используется отдельный ключ
с идентификатором отчёта. Если после нового источника исчезли строки CVE
из прежнего источника, это **не** доказательство исправления: прежняя
область получает `lostCoverage: scope_changed` (либо `scope_unknown`)
и сохраняет ID исходных находок, новый источник отмечается текущим.

Повторный аудит с **тем же** SHA-256 не создаёт ложную потерю покрытия.
Сам список исходных результатов, данные прежней базы и привязка актива
не переписываются. Нативный CI-эксперимент не заменяет этот отдельный
продуктовый тест динамики источников.
