# Приёмка Astra Linux и эксперимент для дипломной работы

Статус: методика и автоматическая проверка сравнимости данных. **Протокол фактического эксперимента заполняется только после запуска на настоящей ВМ и не должен быть заменён синтетическим примером.**

## Стенд и область

Приоритет — Astra Linux SE **1.7.6.15** на x86-64, затем отдельно 1.6.7.15 и другие поддерживаемые редакции/уровни защищённости. Для каждого опыта записываются точные `/etc/os-release`, `/etc/astra_version`, ядро, Python, OpenSCAP, пакетная БД, уровень защищённости, источник и версия OVAL, профиль XCCDF, механизм firewall, SSH-идентичность и время.

Контроллер HCP работает отдельно, подключает одобренный тестовый хост через SSH и выполняет проверки посредством интерфейса и штатных playbook. Постоянный агент не требуется. **Не изменять или отключать механизмы МРД, МКЦ, ЗПС, SELinux/PDPL ради успешного теста.** Перед исправлениями сделать снимок ВМ и проверить доступ к гипервизорной консоли.

Официальные сведения об обновлениях и бюллетенях для 1.7 публикуются изготовителем: https://astra.ru/support/security-bulletins/ . Описание репозиториев и публичных образов: https://registry.astralinux.ru/download/ . Ссылка на артефакт и его SHA-256 из одного HTTPS-хранилища без независимой подписи **не доказывают** издателя; локальный OVAL нельзя считать проверенным по происхождению только по совпадению хеша.

## Этапы одного испытания

1. Выполнить безопасное подключение через мастер HCP: уникальный ключ SSH, проверка fingerprint, целевой Python и sudo, без хранения разового пароля. Получить **сведения о хосте** и инвентарь.
2. Назначить встроенный профиль **«Astra Linux — базовые проверки HCP»** и отдельно применимый OVAL-источник производителя для точного выпуска. Если источник неизвестен, отразить `not_run`/неполноту, а не ноль CVE.
3. Выполнить исходную проверку OpenSCAP. Сохранить **оригинальный JSON HCP** и его привязку к активу. Для сравнения нужен полный применимый набор из 18 правил, без `manual`/неподтверждённых элементов.
4. На изолированной ВМ произвести **одно заранее описанное и разрешённое** изменение конфигурации (через контролируемые механизмы HCP, если выбранный backend поддерживается). Сохранить точный план и исходное состояние. Нельзя ради эксперимента выключать КСЗ Astra или устранять «найденные CVE» изменением фиктивных номеров пакетов.
5. Повторить тот же профиль и **исходный пакет правил** (поле `scanner.contentIdentity`, формат `bundle-sha256:…`), не меняя привязку к активу или область применимых правил. Получить новый, более поздний исходный JSON. OpenSCAP заново компилирует datastream и вносит временные метки; поэтому SHA-256 итогового XML может различаться при одинаковых исходных правилах. Оба SHA-256 выполненных datastream нужно сохранить отдельно.
6. На **управляющей машине**, не на Astra, выполнить:

   ```bash
   python3 deployment/tests/measure_astra_baseline.py \
     --before /path/to/real-before-report.json \
     --after /path/to/real-after-report.json \
     --output /path/to/new-experiment-metrics.json
   ```

   Входящие файлы читаются в ограниченном объёме и связываются по SHA-256; выход создаётся с правами `0600` без перезаписи. Если хост, поколение привязки, 18 правил, стабильный `bundle-sha256` исходного контента или полнота не совпадают, скрипт **прекращает** сравнение. SHA-256 исполненного XML сохраняется отдельно для каждого запуска, но его изменение из-за временных меток компилятора само по себе не является сменой политики.

7. При испытании харденинга с откатом провести третью проверку после восстановления и отдельно сопоставить её с исходным снимком. Отсутствие регрессии только выбранных правил не доказывает полной эквивалентности состояния ОС, firewall и сетевой доступности. Их проверять независимыми снимками.
8. Отдельно сохранить результаты OVAL, Trivy, Nmap, Lynis и Dependency-Track. Учитывать CVE-совпадения, предупреждения и причины `partial` по каждому инструменту. Не суммировать результаты разных средств как независимые CVE и не вычислять общую точность по одному тесту.

## Измеряемые показатели

| Показатель | Проверяемое определение |
| --- | --- |
| Число проверенных правил профиля | 18, одинаковые ID до/после, один `bundle-sha256` исходного профиля, один актив; разные SHA-256 двух исполненных datastream допускаются при идентичном исходном контенте |
| Нарушения до / после | Число `failed` в нормализованных результатах выбранного профиля |
| Подтверждённые устранения | Точные переходы `failed → passed` при одинаковом правиле |
| Регрессии | Точные переходы `passed → failed` |
| Чистое изменение нарушений | `failed_after − failed_before` (может быть отрицательным, нулевым или положительным) |
| Длительность | Только реальные start/end метки соответствующих прогонов; отсутствие временной метки — «не измерено» |
| Трудозатраты | Только отдельное наблюдение ручного процесса и автоматизированного при одинаковой области; без него экономия времени не рассчитана |
| CVE-покрытие | Только конкретная база, её область, полнота применимых OVAL-определений и документированные ограничения |

Данные эксперимента **не равны** общему показателю защищённости, вероятности эксплуатации или полноте обнаружения всех CVE. Если в исходном профиле нет нарушений, нельзя заявлять процент устранённых уязвимостей. Измерения должны сопровождаться идентификаторами и SHA-256 отчётов.

## Критерии завершения практической приёмки

- Реальная Astra подтверждена нативными identity-файлами, ядром и dpkg; версия и защитный уровень зафиксированы.
- Подключение и аудит выполняются через HCP; все подготавливающие действия на хосте документированы и не скрыты от оператора.
- Сохранены реальные JSON, их SHA-256 и фактический исход результатов OpenSCAP/OVAL.
- Восстановление конфигурации и доступность SSH проверены после контролируемых изменений; независимые проверки не заменяются одним статусом успешного задания.
- Итоговый PDF не скрывает `manual`, `not_run`, устаревшую базу и расхождение источников; исходные результаты и их SHA доступны для повторной оценки.
- Для каждого неподтверждённого выпуска и редакции сохраняется **ограничение**, а не утверждение об универсальной поддержке.

## Как интерпретировать CI

Модульные тесты скрипта используют **синтетические** входные JSON исключительно для проверки того, что он отклоняет неэквивалентные данные. Они не создают результатов испытания Astra 1.7. Реальная нативная приёмка Astra 1.8.1 и 1.8.6 описана отдельно в `deployment/astra-vm/README.md`, но не распространяется автоматически на 1.7.6.15 или редакции max/adv.
