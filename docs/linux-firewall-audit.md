# Как читать результат проверки firewall

Правило `firewall_active` входит в agentless-аудит. Оно читает действующие
правила локального INPUT и оценивает ограниченную модель обработки пакетов.
Результат относится к полученному снимку правил. Состояние службы UFW или
firewalld сохраняется как контекст, но само по себе не доказывает фильтрацию.

## Что проверяется

Модель рассматривает новые TCP/UDP-пакеты, поступающие через интерфейс,
отличный от loopback, без признака DNAT в conntrack. `NEW` и отсутствие DNAT —
два отдельных условия: новое соединение может подвергаться DNAT.

Для положительного результата анализатор ищет конкретный протокол и порт,
для которых обработка в наблюдаемых INPUT-цепочках доказуемо заканчивается
drop/reject. В evidence указывается область проверки и основание вывода.
Неизвестное условие рассматривается по обеим ветвям; возможный accept нельзя
терять из-за завершающего reject ниже по цепочке.

| Статус правила | Смысл |
| --- | --- |
| `passed` | Найден доказуемый ограничивающий путь для объявленной модели пакета в наблюдаемом семействе адресов |
| `failed` | В рамках модели доказан свободный проход TCP/UDP через наблюдаемые INPUT-цепочки либо INPUT-фильтрация отсутствует |
| `manual` | Данных или поддержанных конструкций недостаточно для такого вывода; `firewall_active` остаётся в `incompleteChecks` |

Положительная проверка ищет конкретный пример deny. Отрицательный результат
не выводится из отсутствия deny на нескольких пробных портах: отдельный
символический проход оставляет порт неизвестным и должен получить только
accept для всех возможных ветвей TCP и UDP.

Оценка не охватывает внешний сетевой путь, FORWARD, контейнерные сети, правила
гипервизора или облака, все адреса и интерфейсы, ICMP, существующие соединения
и DNAT-потоки. Доказательство для IPv4 не подтверждает IPv6 автоматически.
Даже `passed` не означает, что политика соответствует роли сервера или закрыт
конкретный нежелательный сервис. Для этого нужны политика доступных сервисов
и отдельная внешняя проверка, например Nmap.

## Разбор правил и неопределённость

Поддерживаются ограниченные формы проверок протокола, порта, состояния
соединения и интерфейса, стандартные verdict и переходы `jump`/`goto` nftables.
Типизированное условие ICMP/ICMPv6 не применяется к TCP/UDP-пакету. Для conntrack
status учитывается явно заданное отсутствие DNAT; остальные неизвестные flags
и сложные битовые выражения не подменяются нулём.

`jump` создаёт позицию возврата, `goto` её не создаёт. Если `return` не имеет
сохранённой позиции, применяется политика исходной base chain. Порядок правил
сохраняется: недостижимый deny после безусловного accept не является защитой.

Неизвестные действия, способные изменить пакет или обработку в другой
сопоставимой INPUT-цепочке, препятствуют положительному доказательству.
Анализатор не эмулирует все изменения пакетов и не пытается угадать их порядок
между разными механизмами firewall. Ошибка чтения или неполный разбор одного
packet-filter backend не скрываются успешным результатом другого. При
отсутствующей утилите остаётся ограниченный маршрут через доступный источник;
это не расширяет его область проверки.

Достижимое неразрешённое действие, цикл или исчерпание бюджета обхода сохраняют
неопределённость. Неизвестное условие всё ещё допускает доказанный вывод, если
обе его ветви дают нужный результат. Сложная работоспособная политика может требовать
ручной проверки. Причину следует разбирать по evidence и фактическому ruleset,
сохраняя действующую политику защиты.

Расширение iptables с названием `match` не обязательно является только условием.
Например, `hashlimit` может самостоятельно отбросить пакет через `hotdrop`, когда
достигнут настроенный предел таблицы. Неподдерживаемые модули и опции поэтому
сохраняют `manual`. Последующий ACCEPT, DROP или условие ESTABLISHED не должны
скрывать уже достижимое неизвестное действие. Заведомо ложное предшествующее
условие или предыдущее терминальное правило могут сделать его недостижимым.

Удаление причины `firewall_active` из `incompleteChecks` относится только к
этому правилу. Другие ограничения источников, результаты `failed` и проверки
`manual` в том же отчёте сохраняются.

Новые отчёты содержат `agentless.evaluatorVersion=1.3.0`. Поле
`agentless.version` по-прежнему задаётся версией профиля правил; эти значения
описывают разные части проверки. Исторические отчёты не переписываются.
Изменение результата после обновления может отражать исправленный разбор тех
же правил, поэтому сравнивайте версию evaluator, evidence и снимки ядра.

### Совместимые правила iptables в nftables

Некоторые системы показывают в JSON nftables выражение `xt conntrack` без
параметров. Из такого имени нельзя вывести, что правило разрешает только
ESTABLISHED или RELATED. Для ограниченного набора форм оценщик может получить
`--ctstate` из дополнительного вывода iptables с backend `nf_tables`.
Декодер этого пути ограничен проверенными форматами iptables **1.8.9 и 1.8.10**.
Другой выпуск с непрозрачными параметрами требует отдельного подтверждения.

Этот путь требует сопоставления семейств адресов, таблиц, цепочек, политик,
порядка и числа правил, а также поддержанной формы выражений конкретного
правила. Параметр восстанавливается внутри исходного графа nftables; другие
правила и неизвестные действия сохраняются. Предупреждение утилиты,
несоответствие представлений, неподдержанные объекты или отсутствие нужных
данных не разрешают подменить неопределённость успешным результатом UFW.

Повторные снимки обоих представлений и read-only запрос nftables generation
помогают обнаружить изменение конфигурации во время сбора. Это проверка
согласованности наблюдений, а не блокировка firewall или атомарный снимок
всего сетевого стека. Изменяемые счётчики пакетов не сравниваются как часть
конфигурации. Таблицы с отдельным владельцем не используются для такого
восстановления скрытых параметров.

## Настройка и диагностика

Сборщик выполняет read-only команды `ufw status`, `firewall-cmd --state`,
`nft -j list ruleset` и `iptables -S` на выбранном хосте с правами аудита.
Для поддержанных compatibility-правил дополнительно читаются версия backend,
таблицы `ip6tables -S` и поколение nftables через `NETLINK_NETFILTER`.
Во время проверки он не устанавливает пакеты, не меняет правила и не
перезапускает службы. Если команда присутствует, но не может прочитать
состояние ядра, ошибка должна оставаться видимой в отчёте.

При `manual` проверьте на доверенном административном сеансе доступность
команд, права чтения, исходный JSON nftables и указанное ограничение модели.
Не ослабляйте firewall ради получения `passed`. Общая подготовка SSH, Python
и sudo описана в [Linux setup](linux-setup.md).

Если в `filter_proofs.nftables.compatibility_bridge` указан недоступный источник,
проверьте названную причину: версию `iptables`/`ip6tables`, возможность чтения
обоих представлений, права `NETLINK_NETFILTER` в нужной network namespace и
отсутствие изменения правил во время аудита. Ошибка дополнительного чтения
сохраняет исходное непрозрачное выражение; его влияние зависит от достижимости
в анализируемом INPUT-пути.

Аудит и автоматическое исправление имеют разные границы. Транзакционное
применение и откат по-прежнему доступны только для поддерживаемых UFW/firewalld
на systemd. Наличие nftables в доказательствах аудита не включает отдельный
backend автоматического изменения nftables. См. [матрицу](linux-support.md)
и [резервное копирование](backup-restore.md).

## Проверки реализации

Регрессии выполняют настоящий embedded audit с контролируемыми ответами хоста:
переходы и возвраты, затенённый deny, неподдержанные условия, несколько цепочек,
изменение пакета перед последующей цепочкой, ошибки backend и пределы обхода.

Нативный RPM-стенд использует одноразовые AlmaLinux/Rocky VM. Проверяемый
контроль сохраняет firewalld запущенным: сначала считывает исходную политику,
затем временно добавляет собственное разрешающее runtime rich rule через
штатный API firewalld, удаляет его и сверяет восстановленное состояние.
Изменять чужую nft-таблицу с флагом `owner` напрямую или отключать этот флаг
для прохождения теста не требуется. Этот контроль предназначен исключительно
для принадлежащей стенду одноразовой VM.

Ожидаемые состояния правила: `passed` → `failed` → `passed` при работающем
firewalld во всех трёх фазах. Стенд сохраняет `firewall-audit-protocol.json`,
исходные nft/state snapshots, три отчёта и
`firewall-audit-normalized/protocol.json`. Нормализация должна сохранить
идентификаторы, статусы, риски, evidence и причины неполноты.

Результаты конкретных запусков, исправления по CI и проверяемые границы
собраны в [протоколе от 1 ноября 2026 года](linux-firewall-validation-2026-11-01.md).
