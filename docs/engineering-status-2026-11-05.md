# Hardening Control Platform — инженерный статус и следующий план

**Дата среза: 5 ноября 2026 г.** Это новый протокол, а не исправление
исторических показаний [4 ноября](engineering-status-2026-11-04.md).
Фактическое состояние PR и Actions может меняться после указанной даты.
«Работает код», «успешно прошёл CI», «нативно испытано», «оператор подтвердил
на собственном управляющем узле» — **разные уровни доказательства**.

## 1. Что является платформой

Один локальный Linux control node запускает веб-панель HCP, хранит SQLite,
SSH-ключи, доверенные fingerprints, историю, результаты анализа и
HMAC-контроль операций. По разрешённому SSH через Ansible проверяет
удалённые Linux-хосты **без постоянного агента**. Включает инвентаризацию,
источники пакетов/CVE, OpenSCAP, Trivy, отдельную Astra OVAL-проверку,
связанные отчёты JSON/PDF, управляемый firewall/rollback и резервирование.

HCP **не** является сертифицированным универсальным сканером всех Astra,
полным средством автоматического исправления всех CVE или SIEM.

## 2. Что подтверждено по коду и испытаниям

| Область | Подтверждённое состояние | Ограничения |
| --- | --- | --- |
| Веб-контроллер, SSH onboarding, inventory, источник/планы аудитов | Функции на main, HTTP/SSH Docker-lab в CI | Операторская установка на реальной Ubuntu не подтверждена |
| Trivy, Nmap, Lynis, ssh-audit, OpenSCAP, Astra OVAL | Реализованные пути, отдельные нативные/лабораторные тесты | Нет доказательства универсального CVE recall или совместимости всех выпуска/режимов |
| Правки UFW/firewalld и откат | Реальные изолированные SSH CI проверки | Не универсальный backend для любого firewall и не разрешение массового харденинга |
| Astra 1.8.1 / 1.8.6 OpenSCAP | Реальные KVM-ARF/JSON, 18 правил; 4 failed → 5 → 4 после нарушения и восстановления | Это не полное восстановление ОС и не Astra 1.7 |
| Резервная копия, SQLite/HMAC, перенос в новый Docker volume | Код, независимые хеш/голова журнала и lab-restore | Ещё нет подписанного DR-протокола на пользовательском control node |
| Подготовка Ubuntu одной командой | [PR #68](https://github.com/Danil-super/hardening-control-platform/pull/68) объединён с main 5.11; **4/4 обязательных CI — success** | Новый скрипт проверяет конфигурацию и Docker health, но не выполняет авторизованный SSH, backup/rollback и операторский sign-off |
| Графики и фильтры dashboard, итоговый PDF | Реализованы и протестированы на уровне данных/сборки | Независимая экспертная UI/UX-приёмка на desktop/mobile ещё не пройдена |

Новая команда read-only подготовки управляющей Ubuntu после собственного
заполнения секретов и создания inventory:

`python3 deployment/tests/preflight_control_node.py --project-dir . --env .env`

После самостоятельного запуска контейнера можно добавить `--check-running`.
Она не запускает Docker, не меняет адреса, не копирует ключи и не работает
на пользовательской Astra. Процедура: [control-node-preflight](control-node-preflight.md).

## 3. Что мы действительно узнали об Astra 1.7.6.15

**Обязательная нативная приёмка ещё НЕ пройдена.**

В [PR #62](https://github.com/Danil-super/hardening-control-platform/pull/62)
испытана настоящая официальная cloud-init qcow2
`alse-1.7.6.uu2-base-cloudinit-mg15.3.1-amd64.qcow2`
с проверкой точного размера/SHA и реально прочитанными
`ID=astra`, `/etc/astra_version=1.7.6`,
`/etc/astra/build_version=1.7.6.15`, ядром и SSH.

Проверены два независимых отрицательных A/B-варианта:

- [PR #66](https://github.com/Danil-super/hardening-control-platform/pull/66):
  другой официальный MG15.1.0 того же UU2, результат — неустранённый
  `cloud-init scripts_per_once` FAIL; PR закрыт **без merge**.
- [PR #67](https://github.com/Danil-super/hardening-control-platform/pull/67):
  временное исключение необязательного `parsec_user_max_ilev` только в
  user-data одноразовой ВМ; результат — тот же FAIL; ветка закрыта
  **без merge**, защита Astra не ослаблена в основном коде.

Текущий действительный отказ: один исполняемый shell-сценарий `per-once`,
проверка синтаксиса успешна, но реальное штатное выполнение завершается
с ошибкой (наблюдён ненулевой код 1). Наличие маршрута, resolver и
свободного места не доказывает внешнюю сетевую доступность.
Парсинг приватных логов разрешает лишь строго ограниченные категории;
**упоминание PARSEC само по себе не доказывает отказ MAC**. Корневая
причина выхода скрипта остаётся неустановленной. Выключать модуль
`scripts_per_once` для получения «зелёной» приёмки нельзя.

### Другой официальный путь: VirtualBox OVA → QEMU

Создан [PR #69](https://github.com/Danil-super/hardening-control-platform/pull/69)
с отдельным **исследовательским** нативным smoke-тестом официального
`alse-1.7.6.uu2-base-virtualbox-mg15.3.1-amd64.ova`:
**427995648 байт**, SHA-256
`72ccb335f4c46b5b6d1410cfe0c08f648f95a5e6fd1026f6e0b2d65d8b7ebf6e`
по фиксированным метаданным Astra Artifactory от 5 ноября.

Этот вариант не выключает защиту и не зависит от успешной инициализации
прошлого *cloud-init*-образа. Он пытается установить настоящую версию через
SSH, используя приватный overlay-диск. **На момент данного среза результат
нативного CI ещё не принят.** Даже успешный SSH-smoke не заменяет
проверку 18 правил, OVAL, HCP enrollment и rollback.
[Подробный контракт](astra-17-ova-native-kvm-experiment.md).

Нельзя называть исходный SHA цифровой подписью изготовителя:
он получен из того же Artifactory, что и образ.

## 5. Следующие крупные этапы

**А — закрыть доказательный разрыв Astra.** Проверить исходный результат
эксперимента OVA #69. Если SSH/точная версия PASS, переходить к нативной
инвентаризации через штатные Ansible playbooks, оригинальным 18-rule
OpenSCAP baseline/controlled change/rollback и полной OVAL 1.7 XML.
Не публиковать raw machine ID, ключи, конфигурации, скрытые учётные
данные. Не переносить модель bootstrap фабричного пароля в production.
Если эксперимент FAIL, документировать фактический этап и остановиться:
никаких синтетических успехов.

**Б — реально испытать управляющую Ubuntu.** После локального
`preflight_control_node.py` выполнить на принадлежащем оператору
изолированном стенде процедуру #43. Принимать результаты только при
независимом подтверждении восстановленного SHA/HMAC, отозванных сессий,
нового SSH и отката. CI-лаборатория не заменяет операторскую подпись.

**В — независимая CVE сверка.** Сохранять raw Trivy и OVAL отдельно от
вердикта производителя. Зафиксировать источник, возраст, целевой
выпуск/архитектуру, исходный пакет и сравнение версий с учётом backports;
unknown нельзя выводить как «уязвимости отсутствуют».

**Г — эксплуатационная наглядность и диплом.** Проверить dashboard и
итоговый PDF для набора реальных активов; сформировать воспроизводимый
эксперимент, фактические timestamps, результаты, исходные ARF/JSON и
границы применимости. CI artifacts имеют ограниченный срок хранения:
доказательства после проверки сохранить отдельно, не публикуя секреты.
