## Причина пауз и изменение HCP

Прежние максимальные задержки read-запросов совпали с окончанием OVAL.
Отдельный прогон настоящего пути публикации на копиях его JSON и двух
оригиналов (169 882 850 + 134 668 815 байт) воспроизвёл блокировку event loop.
CPU-профиль показал основное время в синхронном fsync. Это прямое измерение
того же пути сохранения, но не CPU-профиль первоначального рабочего запроса.

Копирование, запись и fsync оригиналов переведены на последовательные
асинхронные FileHandle-операции. JSON подготавливается и синхронизируется
до входа в короткую SQLite-блокировку; внутри неё остаются проверка конфликта
и публикация готовых файлов. Вызов Ansible ожидает публикацию до удаления
staging и освобождения привязки актива. Лимиты размера, запрет ссылок,
проверка изменения файла, SHA-256, неполные доказательства и отказ от
перезаписи исторических отчётов сохранены.

Три повтора до и после на тех же данных, с заранее открытой отдельной БД
и локальным Node 22.23.1. Рабочий контейнер использует Node 24.21.0;
его настоящий HTTP-прогон приведён отдельно ниже:

| Измерение | До | После |
| --- | --- | --- |
| Наибольшая пауза event loop в каждом повторе, мс | 10 653,74 / 6873,04 / 9859,80 | 73,89 / 165,82 / 67,47 |
| Медиана этих пауз, мс | 9859,80 | 73,89 |
| Полное время публикации, с | 10,65 / 6,87 / 9,85 | 11,71 / 11,62 / 12,84 |

Это улучшение доступности сервера во время дисковой записи, а не ускорение
самого накопителя. Ускорение полного времени публикации не заявляется.
Во всех шести повторах JSON совпал побайтно, SHA-256
`c6945c01c4f829dc7c3a9ea8d83d9149b172c565eccc4ba376b58b5dd80402a2`;
все сохранённые XML совпали по длине и SHA с манифестом.

Новая регрессия воспроизвела блокировку до изменения. После него проверены
доступность следующего оборота event loop до публикации JSON и конкурирующие
публикации: только один неизменный отчёт, без оставшихся staging/temporary.
Production build, **622 web-теста и 125 HTTP-проверок** прошли.
Graphify и Code Graph обновлены. Образ обновлён на принятом runtime;
это не чистая пересборка всех зависимостей и не новый GitHub CI.
При установке сохранены окружение, mounts, 13 проверяемых таблиц и 113
файлов отчётов; перед установкой сохранена отдельная копия SQLite.

## Четыре настройки Astra

Перед изменением создан и проверен новый snapshot VMware. Свежий SSH
подтвердил прежнюю закреплённую идентичность, пользователь test с sudo
работает на уровне целостности 63. Правила OpenSCAP и прежние observation
прочитаны до выбора значений; профиль и содержимое проверки не изменялись.

| Настройка | Было | Стало |
| --- | --- | --- |
| PermitRootLogin | without-password | no |
| MaxAuthTries | 6 | 4 |
| X11Forwarding | yes | no |
| kernel.kptr_restrict | 0 | 1 |

Вход root с ключом теперь запрещён, число попыток в одном SSH-подключении
ограничено четырьмя, X11 forwarding выключен. Значение kptr_restrict=1
соответствует выбранному правилу; более строгий режим 2 не навязывался.
Смысл директив проверен по [руководству OpenSSH](https://man.openbsd.org/sshd_config),
параметра ядра — по [документации Linux](https://www.kernel.org/doc/html/v6.1/admin-guide/sysctl/kernel.html).

Добавлены только два root-owned файла 0644:
`/etc/ssh/sshd_config.d/00-hcp-reviewed.conf` и
`/etc/sysctl.d/zz-hcp-reviewed.conf`. Исходный sshd_config не переписывался;
конфликтующих назначений kptr среди текущих sysctl-файлов не найдено.
Выполнены sshd -t и reload ssh, применён только один sysctl; массовый
sysctl --system, смена мандатных атрибутов, пакетов и firewall не выполнялись.
Пароль не передавался в argv, окружении или сохраняемых скриптах.

До применения вооружён трёхминутный systemd-таймер восстановления.
Он отменён только после нового закреплённого SSH, sudo, проверки синтаксиса,
эффективных контекстов test/root и текущего sysctl. Исходные данные и скрипт
возврата сохранены root-only на Astra. Само срабатывание этого таймера и
восстановление snapshot в этом этапе не испытывались. Это операторское
обслуживание через SSH, а не новая функция автоматического исправления SSH
в интерфейсе HCP.

исходного JSON. Тот же актив, поколение, подключение и contentId:
`bundle-sha256:d5dcd96987d288da7ca92bfcfced2b1cfc3b51f787821870ed14a49c9b0416b7`.
Отчёт:
`host-172.16.95.128-openscap-run-20261111T145913751Z-eae88f60`.

Локальные правила перепроверены отдельным запуском. Их SSH root/MaxAuthTries
