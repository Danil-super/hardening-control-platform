# Подключение и настройка Linux-серверов

Эта инструкция дополняет [запуск HCP](../README.md#короткая-инструкция-запустить-и-обновлять-hcp-локально)
и [матрицу возможностей Linux](linux-support.md). Управляющий узел и проверяемые
серверы могут иметь разные дистрибутивы. HCP не требуется устанавливать на
каждый сервер; на цели нужны SSH, поддерживаемый Python и необходимые права.

## 1. Подготовьте управляющий узел

Для штатного запуска используйте Docker Compose из корня репозитория. Сохраните
секреты и постоянный volume существующей установки по [backup/restore](backup-restore.md),
обновите `main`, затем выполните:

```bash
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 180
docker compose ps
```

Рабочий inventory хранится в постоянном состоянии HCP. Повторное копирование
`ansible/inventory.example.ini` поверх него не требуется. Проверьте доступ
контейнера к SSH-адресам серверов; для схем с ограничениями Docker bridge есть
описанный в README вариант host networking.

Образ содержит два отдельных runtime Ansible. Современный выбирается через
`HCP_ANSIBLE_MODERN_BIN_DIR=/opt/hcp-tools/ansible-modern/bin`; legacy остаётся
доступен для старого target Python. Если HCP установлен без Docker, создайте
отдельное окружение современного Ansible на Python 3.12–3.14, задайте абсолютный
путь к его `bin` в окружении сервиса HCP и сохраните совместимый legacy runtime
для старых целей. Команды проверяют реальную версию исполняемого Ansible.

```bash
python3.13 -m venv /opt/hcp-tools/ansible-modern
/opt/hcp-tools/ansible-modern/bin/pip install ansible-core==2.21.5
```

Владелец и доступ к `/opt/hcp-tools` должны быть настроены администратором.
Не устанавливайте пакет в системный Python проверяемого сервера ради смены
версии контроллера. Этот фрагмент готовит только Ansible; полный сценарий выше
использует Docker Compose. Для установки HCP без контейнера сверяйте состав и
версии остальных зависимостей с [Dockerfile](../Dockerfile). Отдельные требования
к SSH-сканеру и Paramiko описаны в [deployment README](../deployment/README.md).

## 2. Подготовьте целевой сервер

На цели нужен доступный OpenSSH, Python из репозиториев её выпуска и учётная
запись с проверяемым повышением прав через sudo. Для полного аудита используются
права root: без них нельзя подтвердить чтение shadow, эффективных настроек,
части журналов и firewall. `doas` не подменяет поддерживаемый sudo-путь.

Примеры установки базовых инструментов выполняются администратором именно
на целевой ОС, а не в контейнере HCP:

| Целевая ОС | Базовые пакеты |
| --- | --- |
| Debian/Ubuntu/Astra с соответствующим apt-репозиторием | `sudo apt-get update` затем `sudo apt-get install python3 openssh-server sudo iproute2` |
| AlmaLinux/Rocky/RHEL | `sudo dnf install python3 openssh-server sudo iproute` |
| SLES/openSUSE | `sudo zypper install python3 openssh sudo iproute2` |
| Alpine | От root: `apk add python3 openssh openssh-sftp-server sudo iproute2` |

Не включайте дополнительные репозитории другой ОС ради совпадения названий
пакетов. Наличие `rpm` на Debian или `dpkg` на RPM-сервере не определяет штатный
пакетный адаптер.

Для согласованного чтения **SQLite-базы RPM** выбранный Python должен иметь
модуль стандартной библиотеки `sqlite3`. Проверьте именно интерпретатор из
`ansible_python_interpreter`, например:

```sh
/usr/bin/python3 -c 'import sqlite3; print(sqlite3.sqlite_version)'
```

Подставьте настроенный путь, если он отличается. Пакет из PyPI для этого не
нужен: используйте штатную сборку Python своей ОС с поддержкой SQLite. Если
модуль недоступен, HCP не выполняет неподтверждённый RPM-запрос: возвращает
неполный результат с причиной ошибки и пустым списком пакетов. Доступ к самой
БД и возможность проверки её изменения оцениваются при сборе. Для dpkg, APK и
RPM с другим форматом БД этот модуль не требуется.

На systemd проверьте штатную службу `ssh` или `sshd`. На Alpine/OpenRC для
сервера, где SSH ещё не настроен:

```sh
rc-update add sshd default
rc-service sshd start
```

Создайте обычную административную учётную запись штатными средствами ОС,
настройте её существующие sudo-права и проверьте `sudo id -u`. HCP поддерживает
разовый пароль sudo, не сохраняет его и не создаёт автоматически универсальный
NOPASSWD. Для полностью автоматических плановых заданий заранее подготовьте
отдельную утверждённую схему прав; интерактивный пароль в планировщик не записывается.

### Стабильная идентичность

Для привязки актива и его отчётов HCP читает `/etc/machine-id`; если файла
нет, допускается `/var/lib/dbus/machine-id`. Нужна стабильная ненулевая строка
из 32 строчных hex-символов. Существующий неправильный/нечитаемый основной файл
не заменяется резервным. Данные передаются по аутентифицированному SSH и хранятся
в HCP в виде производного хеша вместе с fingerprint ключа сервера.

Транзакционный firewall helper дополнительно требует `/etc/machine-id` на
поддерживаемом systemd-хосте. Резервный D-Bus ID для аудита не расширяет список
поддерживаемых backend/платформ автоматического применения.

У минимального образа оба файла могут отсутствовать. Сначала подготовьте ID
штатным инструментом образа из доверенной консоли. Для systemd это
`sudo systemd-machine-id-setup`. Для ОС с D-Bus и без systemd можно использовать
`sudo dbus-uuidgen --ensure=/var/lib/dbus/machine-id` после установки штатного
пакета, содержащего эту утилиту. Не копируйте ID от другой ВМ и не меняйте его
у уже зарегистрированного сервера. При клонировании образа ID и SSH host keys
должны быть уникальны. Read-only аудит HCP сам эти файлы не создаёт.

## 3. Подключите хост в интерфейсе

В «Хостах» задайте alias, адрес, SSH-порт и пользователя. Отпечаток host key
получите из независимой доверенной консоли целевого сервера:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
```

Сверьте и сохраните его в форме HCP. После этого используйте парольный мастер
либо заранее настроенный ключ. Парольная форма доступна через HTTPS или
localhost/SSH-туннель. Мастер создаёт индивидуальную ключевую пару, проверяет
доступ и сохраняет подключение. Подробные шаги мастера одинаковы для Linux и
показаны в [разделе onboarding](ubuntu-astra-setup.md#host-onboarding).

Для нового, ещё не сохранённого alias мастер проверяет `/usr/bin/python3`;
этот путь должен быть доступен до первого подключения через мастер. Для уже
подготовленной записи рабочего inventory можно выбрать другой установленный
совместимый Python через host/group variables, например
`ansible_python_interpreter=/usr/libexec/platform-python`. Проверка сохранённого
подключения использует этот путь. Если `/usr/bin/python3` отсутствует и его
установка не предусмотрена ОС, сначала подготовьте запись inventory и ключевой
доступ штатным административным способом, затем выполните preflight в HCP.
Убедитесь, что это существующий интерпретатор, а не shell-обёртка или шаблон
автоопределения. После изменения повторите preflight; он должен использовать
тот же путь, что и аудит. Не изменяйте рабочий inventory параллельно с операцией.

## 4. Выполните проверку готовности

«Проверить подключение» показывает SSH, идентичность, Python, sudo, ОС и
отдельные предпосылки системного аудита, пакетов, CVE, OpenSCAP и firewall.
Состояние «Предпосылки выполнены» не означает «сервер безопасен».

При необходимости до подключения перенесите один read-only скрипт на сервер:

```sh
sudo python3 hcp-host-readiness.py > linux-readiness.json
```

Файл берётся из `ansible/scripts/hcp-host-readiness.py`. Для Astra можно добавить
`--include-oval-metadata`. При проверке не устанавливаются пакеты и не меняются
настройки. Убедитесь, что обнаружены правильные ID/версия, пакетный менеджер и
реальный менеджер служб. Неизвестный менеджер служб или отсутствие журнала
должны оставаться причиной неполного результата.

## 5. Настройте источники и запустите аудит

1. Сначала запустите системный аудит `basic_linux` и пакетную инвентаризацию.
   Посмотрите доказательства, причины `partial` и версию правил в JSON.
2. Для Trivy загрузите базу в «Источниках», проверьте её свежесть и только затем
   выполняйте CVE-аудит. Offline-режим требует заранее заполненного cache.
3. Для Astra назначьте собственный OVAL-источник и группу по
   [инструкции Astra audit](astra-audit.md).
4. Для OpenSCAP назначьте datastream и профиль точного выпуска. Не выбирайте
   профиль другой ОС только из-за похожего имени семейства.
5. Для неизвестного/неподдерживаемого источника сохраните инвентарь и причины
   неполноты. Нулевое число находок при неполной проверке не означает нулевой риск.

Разделяйте группы по политике, источнику и совместимости Python. Пример имён:
`debian_servers`, `rpm_servers`, `alpine_servers`, `astra_legacy`. Для повторных
проверок сравнивайте один актив, один профиль и одинаковую область проверки.

## 6. Проверьте исправление и откат на стенде

Сначала используйте копию сервера или специально выделенную ВМ. Для UFW/firewalld
проверьте активный backend, доступ SSH, результат backup, применение ограничения
к тестовому порту, фактическую доступность с клиента, повторный аудит и откат.
После отката должны совпасть настройки, права, владельцы и метки безопасности,
а runtime-правила должны восстановиться.

SELinux оставляйте enforcing. Если операция сообщает о неизвестном атрибуте,
несовместимом архиве или невозможности восстановить метку, устраните причину;
отключение SELinux не является шагом этой инструкции. При прерывании используйте
штатный путь восстановления существующей операции, описанный в
[operations recovery](operations-recovery.md), и повторно проверьте сеть.

На OpenRC/SysV и при самостоятельном nftables backend автоматические изменения
firewall в этой версии не обещаются. Отчёт и рекомендации доступны в пределах
подтверждённого аудита; включать неподдерживаемое применение вручную через
подмену идентификаторов или игнорирование preflight не следует.

## Диагностика

| Симптом | Что проверить |
| --- | --- |
| SSH работает, Python/preflight нет | Путь интерпретатора, фактическую версию, диапазон выбранного Ansible, sftp/scp |
| Группа не имеет общего runtime | Разделить старые и новые Python-цели; системный Python не заменять |
| Системный аудит частичный | `incompleteChecks`, команды `ss`/`sshd`, root-права, состояние менеджера служб и журналов |
| Пакеты собраны, CVE-покрытие частичное | Exact distro/release, исходный пакет, vendor/module/repository metadata, источник и возраст DB |
| Не проходит идентичность | Доверенный host key, постоянный machine-id, факт переустановки/клонирования; нужна явная перепривязка при смене машины |
| Откат отвергает старый backup | Совместимость format/metadata; архив без исходных SELinux labels не восстанавливать как подтверждённый |
