# End-to-end восстановление HCP на новом контейнере: изолированный CI-стенд

## Что проверяет этот сценарий

`deployment/lab/verify-restored-controller.py` — **реальная интеграционная**
проверка восстановления контроллера HCP на втором Docker-volume из исходного
постоянного volume после аудита двух разрешённых Linux SSH-целей. Он использует
**только** одноразовые, заранее определённые тестовые секреты из
`deployment/lab/docker-compose.yml`, запускается только на **GitHub-hosted**
runner и отказывает в работе с чужим Compose volume или контейнером.

Выполняется после `verify-ssh-enrollment.py`, `verify.py --online`,
проверки сохраняемости после обычного перезапуска HCP. Нужен
собственный тестовый стенд: эти инструкции **не предназначены** для запуска
против производственной установки или Astra Linux с пользовательскими данными.

## Последовательность автоматического эксперимента

1. Авторизованное соединение с реальной тестовой панелью по
   `http://127.0.0.1:3001`. Проверить ненулевую HMAC-цепочку, созданные
   сканерами исходные отчёты, отдельный SSH-ключ подключённого узла.
   Создать тестовый административный сеанс, который позднее должен быть
   отозван на восстановленной машине.
2. Независимо проверить, что исходный контейнер, его volume, сеть и
   учётные данные относятся именно к `hcp-lab`. Затем **остановить**
   лабораторный HCP, не останавливая два тестовых SSH-сервера.
3. На остановленном источнике сохранить настоящий TAR.GZ его
   `/var/lib/hcp` в приватном временном каталоге `.lab`. SHA-256
   вычислить по байтам архива; сам архив, database, ключи, `.env` и cookie
   **не включать в CI artifacts**.
4. Создать **совершенно новый** Docker volume, извлечь исходный TAR через
   `tar` из того же зафиксированного образа HCP. Сравнить SHA-256 и
   размер критических файлов между двумя **разными** volumes: SQLite,
   рабочий inventory, known_hosts, индивидуальные host keys, отчёты и SBOM.
   Требовать ненулевые свидетельства хостов и аудита.
5. **Только на восстановленной копии** выполнить штатный SQLite
   checkpoint (если нужен), затем вызвать принятый read-only инструмент
   `verify_restored_audit_chain.py` с оригинальным **синтетическим**
   ключом подписи из лаборатории. Сверить количество событий с
   исходной действующей панелью.
6. Выполнить `revoke_restored_admin_sessions.py`: прочитать count
   и SHA новой БД, затем явно разрешить `--apply` с её точным SHA и
   неизменяемой строкой подтверждения. В ходе этого эксперимента
   допускается изменение **только изолированного восстановленного**
   volume, не оригинала. После отзыва вторично подтвердить прежнюю
   HMAC-цепочку без переписывания её событий.
7. Запустить второй HCP из **той же версии образа** на
   `127.0.0.1:3002`, используя только новый volume и ту же закрытую
   тестовую сеть. Проверить настоящими HTTP-запросами:
   неавторизованный запрос к API получает **401**; cookie, выданная
   исходной панелью, получает **401**; новый login работает; чужой
   Origin на мутации получает **403**.
8. Проверить, что список хостов, их host-key fingerprints, сохранённые
   credential ID и количество исходных отчётов совпали. Убедиться, что
   настоящий API нового HCP считает сохранённую HMAC-цепочку валидной.
   Выполнить реальный `ansible ... -m ping` на заранее разрешённой
   SSH-цели из **восстановленного контейнера**.
9. Сохранить **только очищенный** протокол
   `.lab/restore-verification.json` с числом файлов, SHA TAR, числом
   HMAC-событий, количеством отозванных записей, результатами HTTP/SSH и
   фактической измеренной длительностью. Удалить второй контейнер и
   восстановленный volume. Оригинальный лабораторный HCP снова запустить
   даже при ошибке, не объявляя неуспешный прогон завершённым.

Полный код включён в GitHub Actions `.github/workflows/verify.yml`.
Тестовые SSH-цели **Debian**, это **не** проверка natively Astra SE 1.7,
не универсальная проверка CVE, не новая функция автоматического
восстановления на любом продакшен-сервере.

## Почему это важно для диплома

Проверяется технически наблюдаемая возможность переноса постоянного
состояния HCP и сохранность исходных доказательств после копирования, а не
только правильность формата TAR или зелёный unit-test SQLite. Можно
демонстрировать самостоятельное восстановление на одноразовом стенде,
логическую целостность аудита и невозможность использовать восстановленный
сеанс без повторного входа.

Но **реальная эксплуатационная приёмка #43 остаётся незавершённой**,
пока не пройден отдельно подписанный оператором цикл на его Ubuntu
с реальными данными, свежим разрешённым аудитом, независимым SSH/консольным
контролем, резервной копией firewall цели, rollback и проверкой состояния
после восстановления. CI не доказывает физическую доступность, резервные
копии внешних сервисов, независимую подлинность ключа HMAC или совместимость
со всеми выпусками Astra. Для целевой Astra 1.7.6.15 требуется #40.

## Безопасность и секреты

В лаборатории используются общедоступные фикстуры, запрещённые для реального
развёртывания. Никакой `docker cp` или `docker run` с актуальной
пользовательской .env не задействуется. В CI artifacts попадает только
санитизированный протокол; оригинальные TAR, старые browser cookies,
SQLite, индивидуальные host keys и тестовые файлы конфигурации
**в артефакты не загружаются**. При наличии неизвестного volume, чужого
префикса сети, другого образа или отличающегося набора тестовых
учётных данных скрипт отказывается останавливать контейнер.
