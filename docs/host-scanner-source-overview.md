# Проверка назначений источников по хосту — без запуска аудита

## Назначение

На странице «Источники» отдельная секция **«Назначенные источники и политики по хосту»**
позволяет выбрать зарегистрированный в inventory Linux-хост и увидеть, какой OVAL-источник
для Astra и какой профиль OpenSCAP назначены по текущим настройкам групп.

Секция делает только чтение двух существующих классов назначений:

- назначение Astra OVAL: тот же выбор более конкретной группы и проверка наличия
  реквизитов источника, что используются при запуске `astraOvalAudit`;
- назначение OpenSCAP: тот же приоритет группы и полный fallback на два параметра
  окружения, что применяются при запуске `openScapAudit`.

Сервисный метод: `GET /api/ansible/hosts/audit-preparation?alias=имя`.
Он работает в уже существующем защищённом контуре API администратора. Только точный
alias, известный в `linux_hosts`, допускается. Совпадение с именем inventory-группы
не допускается; объект group или CIDR нельзя использовать как точку оценки.

## Состояния

| Статус | Смысл |
| --- | --- |
| «Настройка назначена» | Указаны политика и необходимые поля; **не** гарантируется применимость, свежесть и успешное выполнение |
| «Не назначено» | Для данного хоста профиль/база не назначены; настройка может быть необязательной для конкретной ОС |
| «Конфликт групп» | Две конкретные группы назначают конкурирующие настройки; запуск не должен выбирать одну произвольно |
| «Нужна корректировка» | Политика есть, но не проходит проверку реквизитов или resolver не может безопасно разрешить её |

Для Astra запись сообщает заявленную область выпуска и архитектуры, тип местоположения
XML и наличие **отметки оператора о сверке**. Она никогда не сообщает, что установленные
пакеты этой ВМ уже проверены, XML скачан или аутентифицирован, OVAL применим ко
всем CVE или производитель криптографически подтверждён.

Для OpenSCAP показывается только тип выбранного профиля: встроенный авторский
HCP (18 правил), пользовательский или явно заданный через окружение. Никакие
скрипты на целевой машине из этой секции не выполняются.

## Порядок работы

1. Откройте «Источники», выберите зарегистрированный хост (из таблицы хостов можно
   передать `?host=alias`; UI примет его только при наличии в списке HCP).
2. Посмотрите состояние OVAL **только если это Astra Linux**. Для иных Linux-систем
   отсутствие Astra OVAL не является проблемой: у них свой маршрут CVE.
3. При отсутствии Astra OVAL перейдите к разделу «CVE Astra по данным производителя».
   Каталог 1.7/1.8 может предварительно заполнить форму; оператор проверяет
   применимость и реквизиты источника до сохранения. SHA-256 из того же URL
   не доказывает независимую подлинность.
4. При отсутствии OpenSCAP назначьте нужной группе профиль в «Политики».
5. Перейдите на «Хосты», выполните реальный preflight и требуемые проверки. Только
   завершённые исходные отчёты и доступные определения позволяют оценить результат.
6. Если группы пересекаются и источники конфликтуют, сначала приведите
   групповые назначения к одному источнику, не обходите проверку вручную.

## Безопасность и ограничения

- Секция не выполняет `oscap`, `ansible`, SSH, Trivy, скачивание базы или изменение хоста.
- Ответ не включает SHA-256 из настроек, абсолютные пути и URL-адреса OVAL.
- Неизвестный alias, group-as-host, хост вне `linux_hosts` отклоняются без подмены целью.
- API использует существующую авторизацию панели; за пределами сеанса
  администратора ответ недоступен.
- Сохранённое назначение не приравнивается к исполнению и не повышает оценку риска.
- Счётчики CVE, свежесть OVAL и актуальная ОС проверяются только в рамках
  существующих сценариев аудита.
- Автоматизированные регрессии: `web/tests/host-audit-preparation.test.mjs`.
  Они проверяют свойства read-only API и выбор назначения, а не результаты
  нативного сканирования Astra. Последнее требует отдельной приёмки.
