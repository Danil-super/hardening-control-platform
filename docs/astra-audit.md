# Аудит семейства Astra Linux: OVAL и профиль HCP

HCP разделяет две задачи: **CVE по определениям OVAL** и **проверку конфигурации по XCCDF-профилю**. Обе выполняет OpenSCAP на целевой машине. Номер выпуска не ограничен списком 1.6/1.7/1.8: учитываются фактическая идентичность ОС, область базы и возможности установленных инструментов.

Нужны подключённый через SSH хост, Python 3.5+, совместимый Ansible и OpenSCAP. Для встроенного конфигурационного профиля нужна поддержка SCE (`oscap --version`). Устанавливайте инструменты из репозиториев своего выпуска. HCP не заменяет системный Python, не устанавливает OpenSCAP автоматически и не отключает защитные механизмы Astra.

## Быстрый запуск после обновления HCP

При установке через Docker выполните на управляющей машине из каталога проекта:

```bash
git pull --ff-only
docker compose up -d --build hcp
```

1. В «Источниках» → «CVE пакетов Astra» назначьте группе локальный XML: при установленном `oval-db` сначала проверьте `/usr/share/oval/db.xml`. Сохраните область базы и её параметры.
2. В «Политиках» назначьте той же группе набор «Astra Linux — базовые проверки HCP».
3. В «Хостах» отдельно запустите «Проверить CVE Astra по OVAL» и «Проверить профиль OpenSCAP». Откройте оба отчёта и проверьте причины неполноты, если они есть.

Передавать XML разработчику для запуска не требуется: локальную базу читает адаптер на целевой машине. Разные выпуски Astra могут использовать разные источники через группы. Наличие файла и успешное выполнение движка сами по себе не подтверждают охват всех CVE.

## 1. CVE по локальной OVAL-базе

1. На Astra найдите предназначенный для неё файл OVAL. Для установленного `oval-db` пути показывает `dpkg -L oval-db`; `/usr/share/oval/db.xml` — распространённый путь, который можно изменить.
2. Проверьте происхождение, дату и область базы по данным поставщика. Для фиксации имеющихся байтов выполните `sha256sum /полный/путь/db.xml`. Самостоятельно вычисленный SHA не заменяет проверку происхождения.
3. В HCP откройте **«Источники» → «CVE пакетов Astra»**. Выберите группу и **«Локальный XML на проверяемом хосте»**. Укажите абсолютный путь, ожидаемый SHA-256 при наличии доверенной суммы и допустимый возраст базы.
4. Укажите область выпуска: точное значение `/etc/astra_version`, ветку с `.*` на конце либо `*`. Архитектуры при необходимости ограничиваются значениями `uname -m`. Это дополнительное ограничение администратора; `*` не подтверждает универсальность базы. Условия самих определений проверяет OpenSCAP.
5. Сохраните источник. В **«Хостах»** выберите точный alias и нажмите **«Проверить CVE Astra по OVAL»**.

Настройки применяются к группе. Более конкретная группа имеет приоритет над `linux_hosts`; две пересекающиеся конкретные политики останавливают запуск с объяснением. Для разных баз используйте отдельные группы. Настройка Trivy не переключает OVAL и наоборот.

Локальный режим не скачивает базу и не обращается к сети за обновлениями. XML копируется во временный каталог на том же хосте: проверка использует зафиксированные байты. Несовпадение SHA останавливает выполнение. Отсутствующая, неизвестная или устаревшая дата не превращается в актуальную дату скачивания.

## 2. Сетевая OVAL-база и изолированная сеть

В той же форме выберите **«Интернет или внутреннее HTTPS-зеркало»**. Нужен прямой адрес XML и ожидаемый SHA-256 из доверенного источника. Адрес страницы JFrog, HTML-каталога, архив или пакет `.deb` не заменяют XML. Произвольный актуальный URL производителя в HCP не зашит: источник задаётся явно.

XML скачивает **управляющая машина**, затем передаёт на хост по SSH. Целевой Astra интернет не нужен. Разрешены HTTPS и перенаправления внутри исходного HTTPS origin; адреса с логином, паролем, параметрами запроса и фрагментом отклоняются. Сертификат проверяется стандартным доверенным хранилищем Python; для внутреннего центра сертификации настройте доверие на управляющей машине. Ошибка загрузки не вызывает незаметного перехода к другой базе.

Для полностью изолированной сети перенесите проверенный XML на целевые машины и используйте локальный режим. Для сети с внутренним зеркалом можно оставить сетевой режим и указать внутренний HTTPS-адрес. При смене версии файла обновите ожидаемую сумму после проверки новой базы.

## 3. Как читать OVAL-отчёт

| Данные | Значение |
| --- | --- |
| `vulnerability`, результат `true` | Условия определения выполнены; связанные CVE учитываются, если метаданные не указывают исключительно на другую ОС |
| `vulnerability`, результат `false` | Условия этого определения не выполнены; это не утверждение об отсутствии всех CVE |
| `patch`, `compliance`, `inventory` | Сохраняются со своим смыслом; истинность не превращается автоматически в обнаруженную CVE |
| Ошибка, unknown, отсутствующий результат | Оценка неполная; причина сохраняется |
| Нет определений уязвимостей / все неприменимы | CVE-аудит не подтверждён; число найденных CVE не выдаётся как достоверный ноль |

Сохраняются все определения и результаты, ссылки на тесты, условия сравнения пакетов, найденные версии/архитектуры, точный SHA и дата базы, версия OpenSCAP и коды завершения. Число CVE считается по уникальным идентификаторам истинных определений класса `vulnerability`. Одной CVE могут соответствовать несколько определений и пакетов. CVSS не вычисляется из количества находок: отсутствие оценки поставщика остаётся отсутствием оценки.

Распознанные определения для чужих платформ сохраняются с исходным результатом, но исключаются из оценки CVE Astra; отчёт становится неполным. Неизвестная платформа не считается подтверждённо совместимой. Находки без известной критичности обозначаются в интерфейсе **«Риск не оценён»**, для них есть отдельный фильтр.

`scanner.partial=false` означает завершённую обработку выбранного набора при выполненных проверках целостности и свежести. **`fullCveCoverage=false` остаётся явным:** адаптер не доказывает охват всех CVE, подпись производителя или актуальность каждого определения. Область выпуска, указанная администратором, не выдаётся за проверку производителя. Веб-страница показывает первые 100 определений; полный набор доступен в JSON.

Защита обработки: обычные файлы, до 64 МиБ исходного XML и 128 МиБ результата, ограничение времени и числа элементов; DTD, сущности, XInclude, неподготовленные внешние переменные и сетевые OVAL-пробы не поддерживаются. Такие ограничения показываются как причина неполного аудита. XML должен быть UTF-8. Обычная проверка удаляет временные исходники и сырой результат после нормализации.

## 4. Встроенный профиль конфигурации Astra

1. Откройте **«Политики»**, выберите группу Astra.
2. В поле «Набор проверок» выберите **«Astra Linux — базовые проверки HCP»** и сохраните.
3. В «Хостах» запустите **«Проверить профиль OpenSCAP»**.

Встроенный профиль содержит **18 правил**:

- четыре проверки эффективной глобальной конфигурации SSH через `sshd -T`: вход root, пустые пароли, число попыток, X11;
- четыре проверки владельцев и прав `/etc/passwd`, `/etc/group`, `/etc/shadow`, `/etc/gshadow`;
- три проверки локальных учётных записей: root UID/GID, единственность UID 0, пустые пароли;
- шесть проверок текущих параметров ядра: ASLR, hardlinks, symlinks, ptrace, указатели ядра, доступ к dmesg;
- состояние службы auditd.

Невозможность прочитать параметр не даёт успешного результата. Неприменимые правила учитываются отдельно; полностью неприменимый профиль не считается успешной проверкой. Проверка SSH относится к глобальной конфигурации, а не ко всем возможным `Match`-контекстам; учётные записи — к локальным файлам, не ко всему внешнему каталогу; параметры ядра — к текущему состоянию. MAC/MIC/PARSEC, полный жизненный цикл аудита, настройка загрузки и все требования сертификации этим набором не охватываются.

Это **авторский профиль HCP**, не официальный профиль Astra, CIS или ФСТЭК. Исходники находятся в `ansible/scap/astra`. Из 18 правил 17 используют SCE, а проверка ASLR — нативный OVAL; CPE-словарь проверяет принадлежность ОС к семейству Astra без списка разрешённых выпусков. XCCDF, OVAL, словарь и SCE-код передаются во временный каталог, объединяются в datastream, проходят проверку схемы и выполняются без `--remediate`. В отчёте фиксируется SHA полученного datastream, включающего код проверок, результаты правил и наблюдения. Для сохранения сырого ARF и точного встроенного datastream через Ansible можно явно задать `hcp_openscap_keep_arf=true`; обычный запуск очищает временные файлы. Для внешнего SCAP-профиля остаётся выбор полного пути и идентификатора.

## 5. Испытания и границы подтверждения

Автоматические сценарии: `.github/workflows/astra-oval.yml` проверяет настоящие `oscap oval validate/eval` и сравнение установленного пакета на контрольном XML; `.github/workflows/astra-scap.yml` — XCCDF/SCE, 18 правил, обнаружение отклонения и восстановление; `target-python.yml` — фактическое выполнение на Python 3.5. Эти сценарии не подменяют испытание производителя базы или прогон на настоящей Astra: контрольная ОС и искусственные входные данные явно фиксируются в артефактах.

Результаты конкретных запусков см. в [протоколе проверки](verification-report.md). Для собственного стенда сохраните исходный JSON, версию Astra, выбранную базу/профиль и снимок ВМ; затем проведите аудит → контролируемое изменение → повторный аудит → откат. Диагностика `hcp-host-readiness.py` остаётся только проверкой готовности.

Первичные источники: [OpenSCAP: OVAL и XCCDF](https://static.open-scap.org/openscap-1.3/oscap_user_manual.html), [бюллетени Astra](https://astra.ru/support/security-bulletins/), [каталог OVAL производителя](https://dl.astralinux.ru/astra/oval/). Наличие публичного каталога само по себе не подтверждает доступность и пригодность конкретного XML.
