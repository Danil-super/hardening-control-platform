# Первый тестовый прогон HCP

Здесь приведена процедура испытаний с ожидаемыми результатами. Успешная сборка приложения и модульные тесты не заменяют её выполнение: фактические версии scanner, сетевые условия и состояние ВМ фиксируйте в протоколе своего стенда.

## 1. Быстрый прогон в Docker

Нужны Docker Engine/Compose v2 с поддержкой `up --wait`, Git, OpenSSH client и Python 3 для автоматической проверки. В Windows выполняйте команды в WSL2 с включённой интеграцией Docker Desktop; в macOS — в терминале с запущенным Docker Desktop. Команды выполняются из корня репозитория. Лаборатория использует отдельный Compose-проект `hcp-lab`, собственные ключи и volumes; рабочая установка HCP не затрагивается.

```bash
./deployment/lab/up.sh
docker compose -f deployment/lab/docker-compose.yml ps
```

Скрипт создаёт отдельный Ed25519-ключ, запускает Debian-контейнеры `lab-target`
и `lab-scheduled-target`, получает их SSH host keys через локальный Docker API,
ждёт готовности панели и проверяет Ansible `ping`. Ожидается `SUCCESS` и
`"ping": "pong"`. У каждой цели отдельный volume для host key и machine-id;
повторный запуск не меняет доверие молча. При изменении ключа сначала выясните,
был ли пересоздан volume соответствующего целевого контейнера.

Откройте `http://127.0.0.1:3001`, пароль `lab-only-password`. Этот пароль применяется только в отдельном стенде с loopback-привязкой. В списке должен быть хост `lab-insecure`, адрес `lab-target`, пользователь `lab`, порт `22`. Порт `2222` используется только при SSH с вашего компьютера; внутри Docker-сети HCP обращается к `lab-target:22`.

Для полного автоматического прогона сначала выполните описанную ниже проверку
парольного подключения `verify-ssh-enrollment.py`, затем [verify.py](verify.py).
Она нужна также для проверки отказа расписания на хосте с разовым sudo.
Список параметров выводит `python3 deployment/lab/verify.py --help`. Скрипт
проверяет реальные ответы стенда; результат фиксируется отдельно от unit-тестов.

Alias `lab-scheduled` относится к отдельному `lab-scheduled-target` с заранее
подготовленными ключевым доступом и NOPASSWD в одноразовом образе. HCP не выдаёт
эти полномочия при подключении. Запись входит в начальный inventory нового
лабораторного volume; существующий рабочий inventory не перезаписывается.
Полный новый сценарий запускайте на свежем изолированном стенде. Отсутствующий
alias в старом volume не исправляется удалением Trivy cache.

| Действие в панели | Ожидаемый результат |
| --- | --- |
| Базовый Linux-аудит | JSON-отчёт для `lab-insecure`; замечания к `PermitRootLogin yes`, `MaxAuthTries 8` и TCP-порту 23 |
| Аудит SSH | Результат переговоров с реальным SSH-сервером; перечень алгоритмов и их оценка |
| Nmap | TCP-порты 22 и 23 видимы из контейнера HCP |
| Проверка пакетов и CVE при пустом offline-cache | Инвентарь и SBOM созданы; CVE-результат неполный с объяснением отсутствия базы |
| Временный Lynis | Завершённый отчёт Lynis с собственным hardening index; после завершения нет каталога `/tmp/hcp-lynis-*`; ошибка сканера означает неуспешный прогон |
| OpenSCAP без подготовки | Явное сообщение об отсутствии scanner/content, а не успешный аудит с нулём проблем |
| Перезапуск HCP | Хост, сохранённые отчёты и выбор источника данных сохраняются |

Слушатель на порту 23 намеренно создан для проверки обнаружения порта и не реализует протокол Telnet. Название службы по известному номеру порта не доказывает наличие конкретного ПО. Число остальных замечаний зависит от версии образа и правил scanner.

Проверки из командной строки:

```bash
docker compose -f deployment/lab/docker-compose.yml exec --user node -T hcp ansible --version
docker compose -f deployment/lab/docker-compose.yml exec --user node -T hcp trivy --version
docker compose -f deployment/lab/docker-compose.yml exec --user node -T hcp nmap --version
docker compose -f deployment/lab/docker-compose.yml exec --user node -T hcp ssh-audit --help
docker compose -f deployment/lab/docker-compose.yml exec --user node -T hcp lynis show version
docker compose -f deployment/lab/docker-compose.yml exec -T lab-target sh -c 'ls -d /tmp/hcp-lynis-* 2>/dev/null || true'
```

Для проверки Trivy с базой из интернета откройте «Источники», выберите «Сетевая база» и нажмите «Сохранить и загрузить». При уже выбранном режиме используйте «Загрузить общую базу CVE», а для следующего снимка — «Обновить общую базу CVE». После статуса «актуальна» на странице «Хосты» в «Дополнительных проверках» выберите «Пакеты и CVE — Trivy». Затем переключитесь на «Локальная база» и повторите аудит: вторая проверка должна использовать сохранённую базу. У обновлённого образа может не быть известных CVE: не требуется искусственно добиваться ненулевого количества уязвимостей.

При недоступности registry сначала прочитайте ошибку. Наличие программы `trivy` само по себе не означает наличия её базы. Нужное внутреннее зеркало укажите отдельным Compose override; URL зеркала не используется в offline-режиме.

Остановка без потери данных:

```bash
docker compose -f deployment/lab/docker-compose.yml down
```

`down -v` удаляет все данные именно этого лабораторного Compose-проекта, включая ключ сервера. Применяйте его только при сознательном полном сбросе стенда; для нового доверия также потребуется удалить старые `.lab/known_hosts` после проверки причины смены ключа.

## Сквозное испытание восстановления на новом HCP (CI)

После завершённых лабораторных аудитов и проверки сохранности ключей
отдельный CI-шаг выполняет
`python3 deployment/lab/verify-restored-controller.py` из корня проекта.
Он работает **только на GitHub-hosted одноразовом раннере** и только с
контейнером `hcp-lab`. Скрипт не предназначен для запуска на производственном
контроллере: на время копирования он останавливает оригинальный **тестовый**
HCP и в блоке `finally` возвращает его в рабочее состояние.

Проверяется настоящий перенос volume через TAR в новый отдельный volume,
SHA-256 всех критичных исходных и восстановленных файлов, исходная и новая
HMAC-цепочка, намеренный отзыв тестового старого сеанса **только на
восстановленной копии**, HTTP 401 для прежней cookie, вход с новой cookie,
запрет мутаций при чужом Origin, сохранение хостов и настоящий Ansible SSH
ping с восстановленного контроллера. Никаких приватных архивов или
cookie в артефактах нет — только санитизированный
`.lab/restore-verification.json`.

Подробнее: [протокол сквозного восстановления второго HCP на отдельном Docker volume](../../docs/disposable-controller-restore-acceptance.md).
Это проверка управляемого Docker-стенда на Debian OpenSSH, а **не** нативной
Astra 1.7.6.15 или эксплуатационной среды пользователя.

## Проверка парольного подключения и отдельных ключей

На **одноразовом контейнерном стенде**, после `./deployment/lab/up.sh`, выполните:

```bash
python3 deployment/lab/verify-ssh-enrollment.py
```

Скрипт запускает второй Debian OpenSSH-контейнер, включает тестовый пароль у пользователя `lab` обоих контейнеров и проверяет: отказ до подтверждения сервера, неверный SSH- и sudo-пароль, отдельные пары, отсутствие взаимного доступа ключей, повторное подключение той же парой с отдельным sudo-паролем, `requiretty` без изменения `sudoers` и настоящий Ansible без общего ключа. Пароли в скрипте — публичные фикстуры только этого изолированного стенда. Протокол без паролей сохраняется в `.lab/ssh-enrollment.json`. Повторную проверку после перезапуска HCP запускайте с `--check-persistence`.

После испытаний удалите дополнительный тестовый контейнер командой `docker rm -f hcp-enrollment-target`, затем остановите обычный стенд. Эти испытания не подтверждают совместимость конкретного выпуска и политики Astra.

## Автоматический протокол

После `./deployment/lab/up.sh` выполните из корня репозитория:

```bash
python3 deployment/lab/verify-ssh-enrollment.py
python3 deployment/lab/verify.py --online
```

Проверяются реальные SSH, Ansible, Nmap, Lynis, заданные отклонения SSH, пакетный инвентарь и Trivy с сетевой и сохранённой локальной базой. Для OpenSCAP на неподготовленной цели проверяется отказ до запуска без назначенного профиля. Протокол сохраняется в `.lab/verification.json`; ошибка любого обязательного шага возвращает ненулевой exit code. Без `--online` загрузка CVE-базы не выполняется: существующая свежая база проверяется в offline-режиме, а отсутствующая, устаревшая или неподтверждённая база должна дать сохранённый неполный отчёт с ручной проверкой, нулём проверенных пакетов и без PASS.

На новом стенде CI запускает `python3 deployment/lab/verify.py --online --expect-cold-cache`: сначала подтверждает отсутствие базы и проверяет такой отчёт через API и повторное чтение с диска, затем загружает Trivy DB и сравнивает online/offline-результаты. Ключ `--expect-cold-cache` останавливает проверку, если база уже существует; скрипт не удаляет cache. Для повторного запуска на прежнем стенде используйте команду выше без этого ключа. Начальный offline-отчёт дополнительно сохраняется в `.lab/reports/vulnerabilities-offline-initial.json`.

Плановый путь проверяется запуском установленного `/usr/local/bin/hcp-scheduled-audit`
от пользователя `node`: CLI → внутренний API → production SSH/Ansible → публикация
отчётов. На хосте с разовым sudo обе задачи обязаны завершиться отказом без отчёта.
На отдельном `lab-scheduled` проверяются настоящий `sudo -n`, фактический Python,
выбор modern Ansible, системный аудит и инвентарь/CVE. Инвентарь сверяется с
независимым native dpkg-запросом; отчёты должны иметь подтверждённую привязку к
нужному активу. Объективно неполный результат требует ненулевого кода CLI и
сохранения причины. Это контейнерный тест; systemd и полный firewall проверяются
отдельно на VM. Снимки сохраняются в `.lab/reports/scheduled-*.json`, общий
протокол — в `.lab/verification.json`.

После загрузки базы можно отдельно проверить настоящее CVE-сопоставление и учёт исправления Ubuntu без установки уязвимого пакета:

```bash
bash deployment/lab/verify-trivy-matching.sh
```

Используются два явно обозначенных синтетических инвентаря Ubuntu 22.04 amd64: `libssl3` из исходного пакета `openssl`, версии `3.0.2-0ubuntu1.7` и `3.0.2-0ubuntu1.8`. Настоящий Trivy 0.74.0 со свежей базой должен найти `CVE-2023-0286` в первом и исключить именно эту CVE во втором согласно [USN-5844-1](https://ubuntu.com/security/notices/USN-5844-1). Другие CVE у исправленной контрольной версии допустимы. Проверяется полный программный путь HCP: формирование SBOM, `scanPackageInventory`, сохранение и нормализация отчёта. Состояние проверки изолировано от работающего приложения; используется уже загруженный cache лаборатории. Протокол, SHA-256 базы, её дата, SBOM, отчёты HCP и отдельный повторный native stdout сохраняются в `.lab/trivy-matching-acceptance/`. Повторный запуск требует нового каталога, переданного первым аргументом. Эта пара подтверждает конкретное vendor-сопоставление; она не измеряет общую полноту обнаружения CVE.

Без Docker, при установленных Node 24, зависимостях `web` и настоящем Trivy, тот же acceptance запускается из корня репозитория. `--refresh` загружает реальную базу через production-адаптер; без него требуется готовый cache с базой моложе 24 часов:

```bash
node deployment/tests/verify_trivy_matching.mjs --binary /path/to/trivy --cache-dir /path/to/trivy-cache --refresh --output .lab/trivy-matching-local
```

Проверка сохранности после перезапуска:

```bash
docker compose -f deployment/lab/docker-compose.yml restart hcp
docker compose -f deployment/lab/docker-compose.yml up -d --wait --wait-timeout 180 hcp
python3 deployment/lab/verify.py --check-persistence
```

Тот же сценарий добавлен в GitHub Actions как job `lab`. Он не заменяет испытания OpenSCAP с подходящим SSG, отдельного Greenbone, Dependency-Track и полного цикла firewall на ВМ.

Дополнительно есть отдельные CI-сценарии: полный исходный профиль OpenSCAP и шесть контрольных правил с нарушением/откатом; приём SBOM и анализ настоящей записи NVD в Dependency-Track; UFW и firewalld backup → preview → apply → rollback на Ubuntu-ВМ; [живой Greenbone](../greenbone/README.md) на отдельной HTTP-цели. Подтверждённые результаты, ссылки на артефакты и ограничения приведены в [отчёте проверки](../../docs/verification-report.md). Скрипты изменения firewall и прав файлов предназначены только для одноразового GitHub runner; на своей ВМ используйте процедуру ниже.

## 2. Полноценный стенд на виртуальных машинах

Для Astra Linux сначала выполните [единый порядок подключения Ubuntu → Astra](../../docs/ubuntu-astra-setup.md#host-onboarding), затем [испытания своего выпуска Astra](../../docs/astra-lab.md). Приведённые ниже команды установки UFW и примеры SCAP для Ubuntu/Debian не означают их применимость к исходной конфигурации Astra.

Контейнер разделяет ядро с Docker-хостом, обычно не запускает systemd и не имеет полного управления firewall. Поэтому результаты проверок ядра/служб могут быть неприменимы. В лабораторном контейнере специально нет `NET_ADMIN`: применение и откат firewall проверяйте на отдельной ВМ.

Для защиты диплома подготовьте:

- Linux control node с установкой HCP по [главному README](../../README.md).
- Две ВМ одного поддерживаемого выпуска Linux: контрольную с обычными настройками и тестовую с известными отклонениями. Для каждой достаточно начать с 2 CPU, 2–4 ГБ RAM и 15–20 ГБ диска; потребление зависит от выбранного SCAP-профиля.
- Приватную сеть между control node и ВМ. NAT-интерфейс нужен на этапе установки пакетов; проверяемые сервисы не публикуйте наружу. Сохраните снимок каждой ВМ перед изменениями.

Подключение каждой ВМ выполняйте по [единой инструкции](../../docs/ubuntu-astra-setup.md#host-onboarding): сканирование → адрес, пользователь и пароль → «Подключить хост». При первом входе форма запросит подтверждение сервера; установку индивидуального ключа, проверку и сохранение HCP выполнит автоматически. Для Debian/Ubuntu используется тот же порядок SSH и sudo; пакеты устанавливаются из репозиториев целевой ОС. Уже существующего пользователя и работающий доступ создавать повторно не нужно.

Для административного лабораторного прогона настройте [sudo по основной инструкции](../../docs/ubuntu-astra-setup.md#sudo-access) и подтвердите его проверкой HCP. Если хост уже добавлен без sudo, [измените существующую запись](../../docs/ubuntu-astra-setup.md#existing-host). Для первого аудита выберите «Базовый Linux».

Только для описанного ниже эксперимента UFW на Debian/Ubuntu установите его из консоли администратора, если он отсутствует:

```bash
sudo apt update
sudo apt install -y ufw
```

На Astra сначала определите действующий firewall и применимость сценария; установка UFW поверх другого менеджера не является частью подключения хоста.

## 3. Контролируемые отклонения и firewall

На тестовой ВМ через консоль создайте `/etc/ssh/sshd_config.d/00-hcp-lab.conf` с двумя строками `PermitRootLogin yes` и `MaxAuthTries 8`. После `sudo sshd -t` примените конфигурацию через `sudo systemctl restart ssh`. Парольный вход и root-пароль для этого эксперимента включать не требуется. Проверка должна обнаружить именно эти параметры; сама платформа пока не исправляет настройки SSH автоматически.

Запустите отдельный HTTP-сервис на тестовом порту 8088 и firewall (только на ВМ, из её консоли):

```bash
sudo systemd-run --unit=hcp-lab-http --property=User=nobody /usr/bin/python3 -m http.server 8088 --bind 0.0.0.0 --directory /tmp
sudo ufw allow 22/tcp
sudo ufw default allow incoming
sudo ufw --force enable
sudo ufw status verbose
```

Этот разрешающий baseline предназначен исключительно для изолированного эксперимента. Не создавайте отдельное `allow 8088`, которое могло бы иметь приоритет над более поздним запретом. Проверяйте доступ именно из control node:

```bash
docker compose exec --user node -T hcp nmap -Pn -sT -p 8088 АДРЕС_ТЕСТОВОЙ_ВМ
```

В «Обратимые изменения firewall» выберите закрытие `8088/tcp`:

1. Выполните предварительную проверку. Состояние UFW и доступность HTTP должны остаться исходными.
2. Укажите причину и точный alias хоста, подтвердите применение. Сохраните ID транзакции и backup.
3. Повторите Nmap с control node: порт больше не должен быть `open`. Сам процесс HTTP продолжает слушать сокет; локальный `ss` не доказывает обход firewall.
4. Выполните откат этой транзакции. Nmap снова должен показать `8088/tcp open`; SSH-доступ не должен прерываться.
5. Удалите экспериментальный сервис: `sudo systemctl stop hcp-lab-http` и верните снимок ВМ после окончания эксперимента.

Не используйте порт SSH как тестовую цель закрытия. Не меняйте firewall вручную между backup и rollback, иначе восстановление затронет и эти изменения.

Поддерживается один активный backend: UFW либо firewalld. Платформа сама его не устанавливает и не включает. Для firewalld перед backup временная и постоянная конфигурации должны совпадать; иначе запуск блокируется с объяснением. Для первого прогона проще использовать описанную UFW-ВМ. Архивы старого формата без метаданных backend/machine-id и контрольной суммы не пригодны для нового автоматического отката: их восстановление выполняется отдельно вручную.

## 4. OpenSCAP, Greenbone и Dependency-Track

**OpenSCAP.** На ВМ установите scanner и подходящий выпуск SSG по разделу OpenSCAP главного README. Запишите полный путь, `sha256sum` файла и точный профиль из `oscap info`. Назначьте профиль отдельной группе в «Политиках» и выполните аудит. Отчёт должен содержать не пустой список результатов правил и метаданные выбранного content. Проверка с неверным путём/profile должна явно сообщить об ошибке. Для одного реально нарушенного правила создайте исключение с причиной и будущей датой: находка должна оставаться видимой и не превращаться в «исправлено». После удаления исключения повторите аудит.

**Greenbone.** Это отдельный сервис, который не входит в Docker-лабораторию HCP. Обновите его feeds, выполните разрешённое сканирование тестовой ВМ, дождитесь завершения и экспортируйте report XML. При импорте в HCP должны совпасть адрес хоста, OID, CVE (если они есть), порт и severity. Нулевой результат на обновлённой ВМ допустим; не подменяйте реальный XML тестовой фикстурой при оценке работы scanner.

**Dependency-Track.** Разверните optional profile по главному README. Дождитесь готовности API и завершения загрузки настроенных источников. После пакетного аудита проверьте появление проекта с alias хоста, наличие компонентов и завершение BOM-processing в самом Dependency-Track. HCP подтверждает загрузку SBOM; получение всех результатов Dependency-Track обратно в платформу пока не реализовано.

## 5. Протокол, по которому принимается результат

Для каждого запуска сохраните: дату, commit HCP, версии ОС/scanner, источник и дату базы, профиль, ID отчёта, ожидаемое наблюдение и фактический результат. Для CVE вручную сверьте несколько записей с advisory поставщика с учётом дистрибутивной версии и backport; одинаковый upstream-номер не доказывает уязвимость установленного пакета.

Минимальные критерии успешного первого прогона:

- Все заданные конфигурационные отклонения обнаружены или явно объяснены как неприменимые.
- Отсутствующий scanner, недоступная/устаревшая база, неверный SCAP-профиль и ошибка соединения не превращаются в сообщение «проблем нет».
- Подтверждённый firewall-запрет меняет внешнюю доступность, rollback возвращает baseline, SSH сохраняется.
- Отчёты и доверенные ключи переживают пересоздание HCP; секреты не попадают в Git и Docker build context.
- Временные затраты ручного и автоматизированного сценария измерены на одинаковых ВМ и одинаковом наборе проверок. Время ожидания загрузки баз учитывается отдельно.

Успех этих проверок подтверждает работоспособность выбранного сценария, но не отсутствие всех возможных уязвимостей. Публикуйте в дипломе фактические результаты прогона и границы применимости каждого инструмента.
