# Живое испытание Greenbone

Этот сценарий разворачивает отдельный временный Greenbone Community, загружает
официальные feeds, запускает настоящий сетевой VT и проверяет обработку его XML
рабочим парсером HCP. Он не подключается к существующим инсталляциям Greenbone.

## Запуск

Нужен Linux-хост с Docker Engine/Compose, Python 3.10+ и интернетом для загрузки
образов. Минимум Greenbone — 4 ГБ RAM и 20 ГБ свободного диска, рекомендуется
8 ГБ и 60 ГБ. Первичная загрузка и обработка feeds может занять час и более.

Из корня репозитория:

```bash
python3 -m venv .venv-greenbone
.venv-greenbone/bin/python -m pip install PyYAML==6.0.3
.venv-greenbone/bin/python deployment/tests/verify_greenbone.py
```

Сценарий не принимает IP-адрес: он создаёт собственную контейнерную HTTP-цель,
включающую TRACE специально для проверки обнаружения. Единственная цель и порт
80 определяются из Docker. Все запущенные контейнеры находятся во внутренней
сети, порты на компьютере не публикуются. Никакие машины локальной сети не
сканируются. После испытания контейнеры и их временные данные удаляются.

По умолчанию загружаются официальные NASL/Notus VTs, конфигурации и форматы
отчётов. Полные справочники SCAP/CERT исключены из этого ограниченного сценария:
они не нужны для обнаружения включённого HTTP TRACE. Их первоначальное заполнение
создаёт отдельную большую нагрузку на БД. Это не подтверждает их готовность для
полного аудита; в постоянной установке Greenbone их нужно настроить отдельно.

Проверяется один официальный VT HTTP TRACE и его штатные зависимости при
включённом `safe_checks`. Это подтверждает реальный сетевой запуск и передачу
находки в HCP; полного аудита Astra, всех сетевых служб или покрытия CVE такая
проверка не подтверждает. HCP по-прежнему импортирует XML; запуск через GMP
здесь выполняет испытательный скрипт.

## Что является успешным результатом

- Образы загружены; точные digest сохранены и закреплены на время испытания.
- NVT-feed не старше семи дней; scanner и manager закончили загрузку VTs.
- В конфигурации выбран ровно один ожидаемый VT, включены безопасные проверки.
- Настоящая задача завершилась `Done`, известная проблема обнаружена, в журнале
  HTTP-цели присутствует реальный запрос TRACE.
- Нативный XML и отчёт HCP совпадают по адресу, числу результатов, OID, порту,
  severity и QoD; импорт не имеет статуса `partial`.

В `.lab/greenbone-acceptance/` остаются `protocol.json`, `native-report.xml`,
`hcp-report.json`, версии feeds, образы, конфигурация и журналы. Пароли не
сохраняются. Ошибка сети, нехватка места, незагруженные feeds или таймаут дают
ненулевой код завершения и явно не считаются пройденным испытанием.

Повторный запуск использует новую папку:

```bash
.venv-greenbone/bin/python deployment/tests/verify_greenbone.py \
  --output .lab/greenbone-second-run --timeout-minutes 120
```

Для отдельной проверки с полной первичной загрузкой SCAP/CERT:

```bash
.venv-greenbone/bin/python deployment/tests/verify_greenbone.py \
  --output .lab/greenbone-with-advisories --include-advisory-feeds --timeout-minutes 180
```

Это всё ещё одна тестовая HTTP-цель. Успешный короткий CI-прогон не означает,
что вариант с полной загрузкой advisory-баз тоже прошёл. Конфигурации сканирования
импортируются после готовности VTs и назначения Feed Import Owner; ожидание
сохраняет отдельную диагностику manager/scanner, а не только PostgreSQL.

В GitHub Actions используется workflow `Greenbone live scanner acceptance`;
артефакт с доказательствами называется `greenbone-live-scan`. Сам факт наличия
workflow не означает, что испытание прошло: проверяйте его реальное завершение
и поле `status` в протоколе.

## Происхождение конфигурации

Скрипт загружает [официальный Compose](https://github.com/greenbone/docs/blob/173b0a14e4c4032ee84b0c37f6a8fea84788f14f/src/_static/compose.yaml)
из фиксированного коммита и проверяет SHA-256. Временная адаптация убирает UI,
создаёт внутреннюю сеть и добавляет испытательную цель. Образы официального
stable-канала/feed обновляются при новом запуске; фактически использованные
digest сохраняются в протоколе и подставляются в временный Compose. Поэтому
обновление базы не маскируется обещанием одинакового результата разных дат.

Исходная конфигурация Greenbone распространяется по
[CC BY-SA 4.0](https://github.com/greenbone/docs/blob/173b0a14e4c4032ee84b0c37f6a8fea84788f14f/LICENSE).
Те же условия распространяются на её временную адаптацию.

Источники: [Community Containers](https://greenbone.github.io/docs/latest/22.4/container/index.html),
[загрузка feeds](https://greenbone.github.io/docs/latest/22.4/container/workflows.html),
[GMP API](https://docs.greenbone.net/API/GMP/gmp-22.7.html).
